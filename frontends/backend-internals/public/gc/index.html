G1과 ZGC는 왜 다르게 멈추는가

힙을 4GB에서 128GB로 키우면 G1의 정지 시간은 함께 자랍니다. ZGC는 거의 그대로예요. 왜 그런지, 그리고 그 대가로 무엇을 내는지 직접 확인합니다.

직접 조작하기

손잡이는 두 개뿐입니다. 재생 버튼은 정해진 순서를 훑을 뿐이니, 슬라이더를 직접 움직이는 쪽이 훨씬 많은 걸 보여줍니다.

손잡이무엇이 바뀌나
힙 크기G1의 정지 길이가 따라 자랍니다. ZGC는 거의 반응하지 않습니다
할당 속도G1은 정지 횟수가 늘고, ZGC는 일정 선을 넘으면 할당 지연이 생깁니다
로그 스케일선형에서는 ZGC 막대가 보이지 않습니다. 그게 요점이지만, 모양을 보려면 필요합니다

막대 색은 종류입니다. 회색은 young 수집, 황토색은 mixed 수집, 빨강은 Full GC, 파랑은 ZGC입니다.

이렇게 해보세요

1. 힙만 키워본다

할당 속도는 500 MB/s 고정 힙을 2GB → 128GB 로 천천히 끌어올린다 G1 young 정지 95ms → 538ms G1 mixed 정지 161ms → 915ms ZGC 최대 정지 0.28ms 그대로

G1은 살아 있는 객체를 복사하는 동안 멈춥니다. 힙이 크면 한 번에 훑는 young 영역도 커지고, 옮길 양이 늘어나니 정지도 길어집니다. ZGC는 옮기는 일 자체를 동시에 하므로 힙 크기가 정지에 영향을 주지 않습니다.

2. G1은 어디까지 목표를 지키나

힙 4GB → young 188ms (목표 안) 힙 16GB → young 208ms (거의 지킴) 힙 64GB → young 270ms (넘기 시작) 힙 128GB → young 538ms (완전히 벗어남)

G1은 MaxGCPauseMillis를 맞추려 young 영역을 줄입니다. 하지만 G1NewSizePercent(기본 5%) 아래로는 못 내려가요. 힙이 커지면 이 하한 자체가 커져서, 어느 시점부터는 목표를 지킬 방법이 없어집니다.

3. 짧은 정지가 항상 이기는 건 아니다

힙 16GB 고정 할당 속도를 500 → 3000 MB/s G1 young 정지 208ms 그대로 G1 GC 횟수 11회 → 67회 G1 처리량 96% → 73%

정지 길이와 정지 총량은 다른 문제입니다. 200ms짜리가 1분에 두 번이면 무해하지만 스무 번이면 처리량이 7% 깎입니다. p99 지연만 보고 판단하면 이 비용을 놓칩니다.

4. ZGC도 멈춘다

힙 16GB 할당 속도를 5000 MB/s 까지 올린다 ZGC 할당 지연 ms/s 수치가 나타난다 ZGC 처리량 떨어진다

동시 회수 속도보다 빨리 할당하면 스레드가 빈 페이지를 기다리며 멈춰 섭니다. GC 정지로 집계되지 않아 로그만 보면 "정지 0ms"인데 애플리케이션은 실제로 서 있어요. ZGC 튜닝에서 가장 놓치기 쉬운 지점입니다.

5. ZGC에는 힙을 넉넉히 준다

할당 속도 5000 MB/s 고정 힙 16GB → 지연 528ms/s 힙 128GB → 지연 312ms/s

여유 공간이 곧 시간입니다. 힙이 넓으면 동시 수집이 끝날 때까지 버틸 여유가 생겨요. G1에서는 힙을 키우면 정지가 길어지지만, ZGC에서는 힙을 키우는 게 대체로 이득입니다. 두 수집기의 튜닝 방향이 정반대인 이유입니다.

G1이 멈추는 지점

G1은 힙을 리전이라는 균일한 조각으로 나눕니다. 수집할 때는 리전 몇 개를 골라 collection set을 만들고, 그 안의 살아 있는 객체를 다른 리전으로 복사합니다. 복사가 끝나면 원래 리전은 통째로 비워요.

문제는 복사하는 동안 객체의 주소가 바뀐다는 겁니다. 애플리케이션 스레드가 옛 주소를 들고 있으면 안 되니, 복사하는 내내 세상을 멈춰야 합니다. 정지 시간이 곧 "옮긴 데이터의 양"이에요.

정지 시간 ≈ 고정 비용 + (옮길 살아있는 객체 양) / 복사 처리량

G1은 -XX:MaxGCPauseMillis(기본 200ms)를 맞추려고 young 영역 크기를 스스로 조절합니다. 예측이 빗나가면 다음 번에 young을 줄이는 식이죠. 실험대에서 힙 16GB까지 208ms로 목표 근처에서 버티는 게 이 덕분입니다. 정확히 200ms를 지키는 건 아니고, 목표는 어디까지나 목표입니다.

하지만 young 영역에는 하한이 있습니다. G1NewSizePercent 기본값이 5%인데, 힙이 128GB면 그 5%가 이미 6.4GB예요. 여기서 살아남는 15%만 복사해도 1GB에 가깝습니다. 목표를 지킬 방법이 사라지는 지점이 이렇게 생깁니다.

ZGC가 멈추지 않는 방법

ZGC의 핵심은 색깔 포인터(colored pointers)와 load barrier입니다.

64비트 포인터에서 실제 주소로 쓰이는 건 하위 44비트 정도입니다. ZGC는 남는 상위 비트에 이 객체가 마킹됐는지, 이미 이동했는지 같은 상태를 새겨 넣습니다. 그리고 애플리케이션이 참조를 읽을 때마다 그 비트를 검사하는 코드(load barrier)를 끼워 넣어요.

// 개념적으로 이런 검사가 참조 읽기마다 들어간다
Object o = obj.field;        // ← 여기서 barrier 실행
// 포인터 색이 낡았다면: 새 주소를 찾아 참조를 고쳐 끼운다

이 덕분에 객체를 옮기는 도중에도 애플리케이션이 계속 돌 수 있습니다. 옛 주소로 접근하는 스레드가 있으면 barrier가 즉석에서 새 주소로 안내하고 참조까지 갱신해주거든요.

그래서 ZGC의 STW는 사이클당 세 번, 각각 루트를 훑는 짧은 구간뿐입니다. JDK 16부터는 스레드 스택 스캔마저 동시에 수행해서, 정지 시간이 힙 크기와도 스레드 수와도 사실상 무관해졌습니다.

그럼 항상 ZGC를 쓰면 되나

아닙니다. 대가가 셋 있습니다.

  • 처리량 — load barrier가 모든 참조 읽기에 붙습니다. 워크로드에 따라 5~15% 정도 처리량이 깎입니다. 배치 잡처럼 지연보다 총 처리량이 중요한 경우엔 손해예요
  • 메모리 — 동시 수집 중에도 할당이 계속되므로 여유 공간이 필요합니다. 같은 작업에 G1보다 힙을 더 줘야 합니다
  • 할당 지연 — 위 실험대에서 본 그것입니다. 회수 속도를 앞지르면 결국 멈춥니다

JDK 버전별 상황

ZGC는 최근 몇 년 사이 크게 달라졌습니다. 예전 자료를 보고 판단하면 안 되는 영역이에요.

  • JDK 21 — 세대별 ZGC 도입 (JEP 439). 이전 ZGC는 세대 구분이 없어서 짧게 살다 죽는 객체도 매번 전체 힙을 훑어야 했습니다. 이게 ZGC의 처리량 약점이었어요
  • JDK 23 — 세대별 모드가 기본값 (JEP 474)
  • JDK 24 — 비세대 모드 제거 (JEP 490). 이제 -XX:+UseZGC는 곧 세대별 ZGC입니다
  • JDK 25 — 현재 LTS. G1은 여전히 기본 수집기입니다
"ZGC는 처리량이 많이 떨어진다"는 인상은 대부분 세대별 도입 이전 자료에서 온 것입니다. JDK 21 이후로는 격차가 상당히 줄었어요. 다만 여전히 0은 아니니 직접 측정하는 게 맞습니다.

현장에서 확인할 것

먼저 지금 뭘 쓰고 있고 얼마나 멈추는지 봅니다.

// 실행 중인 JVM
jcmd <pid> VM.flags | tr ' ' '\n' | grep -i gc

// GC 로그 켜기 (JDK 9+)
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20M

// 안전점(safepoint) 까지 보려면 — STW 는 GC 만의 것이 아니다
-Xlog:safepoint:file=safepoint.log

두 번째 로그가 중요합니다. 스레드 덤프, 힙 덤프, 클래스 재정의, 모니터 디플레이션, JIT 디옵티마이제이션도 STW를 만듭니다. GC 로그만 보고 "정지가 없다"고 결론 내리면 놓치는 게 생겨요.

ZGC를 쓰신다면 할당 지연을 따로 봐야 합니다.

-Xlog:gc+alloc=debug   // Allocation Stall 항목이 찍힌다

바꿀지 판단하는 기준은 대략 이렇습니다.

  • 힙이 32GB를 넘고 p99 지연이 문제라면 → ZGC를 재볼 가치가 있습니다
  • 힙이 8GB 이하라면 → G1으로 충분합니다. ZGC의 이점이 barrier 비용을 상쇄하기 어렵습니다
  • 배치·ETL처럼 총 처리 시간이 지표라면 → G1, 또는 Parallel GC까지 고려
  • Full GC가 찍히고 있다면 → 수집기를 바꾸기 전에 왜 따라가지 못하는지부터 봅니다. 대개 할당 속도나 누수가 원인이고, 수집기를 바꿔도 해결되지 않습니다
이 페이지의 수치는 개념을 보여주기 위한 단순 모델입니다. 실제 정지 시간은 객체 그래프 모양, 리전 크기, GC 스레드 수, 하드웨어에 따라 크게 달라집니다. 본인 워크로드로 측정하는 것을 대신할 수 있는 건 없습니다.
