필드를 다 더했는데 크기가 안 맞는다

헤더 파일을 보고 파서를 썼습니다. 필드 크기를 더하니 16바이트인데 실제 데이터는 24바이트예요. 오프셋을 하나 틀리게 잡으면 그 뒤 필드가 전부 밀립니다. 해상도가 엉뚱하게 나오고 프레임레이트가 말이 안 되는데, 어느 한 필드만 이상한 게 아니라 중간부터 전부 이상합니다.

손잡이무엇이 바뀌나
필드 배치선언 순서와 큰 것부터는 같은 다섯 필드를 순서만 바꾼 것입니다. sizeof 를 비교해보세요.
정렬 규칙pack(1) 은 패딩을 없애고, pack(4) 는 정렬을 4로 깎습니다. 같은 필드로 24 · 20 · 16 세 값이 나옵니다.
배열 원소연달아 읽을 원소 수. 1개면 오차가 0 입니다 — 그게 이 버그가 테스트를 통과하는 이유예요.

필드는 u8 type · u32 width · u16 shape · u8 flag · u64 ts 다섯 개입니다. 자에서 붉은 빗금이 필드 사이 패딩, 노란 빗금이 구조체 끝 패딩이고, 붉은 테두리가 붙은 칸은 합으로 계산했을 때 어긋나는 필드입니다.

이렇게 해보세요

1. 선언 순서 그대로 — 합은 16, sizeof 는 24

배치 선언 순서 · ABI 기본 정렬 필드 크기 합 16 · sizeof 24 · 내부 패딩 8 첫 어긋남 width — 실제 @4, 합으로는 @1

type 이 1바이트를 쓰고 나면 다음은 오프셋 1입니다. 그런데 u32 width 는 4의 배수에 놓여야 하니 3바이트를 버리고 4로 갑니다. ts 앞에서도 5바이트를 버려요. 합으로 계산한 파서는 width 를 오프셋 1에서 읽고, 그 뒤 네 필드가 전부 밀립니다. 자의 아래 줄을 보세요 — 두 줄이 한 번 어긋나면 다시 만나지 않습니다.

2. 큰 것부터 놓는다 — 같은 필드로 sizeof 16

배치 선언 순서 → 큰 것부터 (필드는 그대로) sizeof 24 → 16 · 내부 패딩 8 → 0 첫 어긋남 없음

필드를 하나도 안 바꿨습니다. 순서만 큰 것부터로 놓았어요. 패딩이 0 이 되고 8바이트가 사라집니다. 큰 정렬을 먼저 놓으면 뒤따르는 작은 필드들이 이미 맞은 자리에 들어가니까요. 이 배치에서는 합으로 계산해도 우연히 맞습니다 — 우연히요. 필드가 하나 추가되면 다시 깨집니다.

3. pack(1) — 패딩이 사라진다, 대가와 함께

배치 선언 순서로 되돌리고 · 정렬 pack(1) sizeof 24 → 16 · 내부 패딩 8 → 0 · 구조체 정렬 8 → 1

패딩을 강제로 없애니 합과 sizeof 가 같아집니다. 파서가 편해지죠. 대가는 정렬되지 않은 접근입니다 — 아키텍처에 따라 느려지거나(x86) 예외가 나거나(일부 ARM 설정) 컴파일러가 사용자 모르게 바이트 단위로 쪼개 읽습니다. 포인터를 넘기면 정의되지 않은 동작이 되는 경우도 있습니다. 프로토콜 구조체에는 흔한 선택이지만 공짜는 아닙니다.

4. pack(4) — 같은 필드로 세 번째 값

정렬 pack(1) → pack(4) sizeof 20 (ABI 기본 24 · pack(1) 16) 내부 패딩 4 · 첫 어긋남 width

정렬을 4로 깎으니 ts 앞 패딩이 5에서 1로 줄어듭니다. 같은 필드 목록이 정렬 규칙에 따라 24 · 20 · 16 세 크기를 갖습니다. 헤더 파일에는 이 규칙이 안 적혀 있어요 — 컴파일 옵션이나 #pragma pack 에 있고, 그마저 없으면 ABI 기본값입니다.

5. 꼬리 패딩이 생기는 배치 — 합 13, sizeof 24

배치 꼬리 패딩 (u32 width · u64 ts · u8 flag) · ABI 기본 합 13 · sizeof 24 · 내부 패딩 4 · 꼬리 패딩 7

마지막 필드가 오프셋 16에서 1바이트를 쓰고 끝나는데 sizeof 는 24 입니다. 구조체 정렬이 8 이라 끝을 8의 배수로 맞추기 때문이에요. 이 7바이트는 아무 필드도 아니고 아무 값도 없습니다. 그런데 배열에서는 이게 원소 간격이 됩니다.

6. 배열로 읽는다 — 첫 원소는 맞고 두 번째부터 틀린다

배열 원소 1 → 3개 (꼬리 패딩 배치) n=1 오차 0 · n=2 오차 11 · n=3 오차 22 · n=8 오차 77

여기가 가장 무섭습니다. 원소가 하나면 오차가 정확히 0 이에요 — 첫 원소는 오프셋 0에서 시작하고 마지막 필드까지 잘 읽힙니다. 그래서 샘플 하나로 만든 테스트가 통과합니다. 두 번째 원소부터 11바이트씩 밀리고, 8개면 77바이트가 밀립니다. 운영에서 데이터가 여러 개 오는 날 터지는 거죠.

7. 배치를 고치면 배열도 안전해진다

배치 꼬리 패딩 → 큰 것부터 (원소 3개 유지) sizeof 24 → 16 · 꼬리 패딩 7 → 0 · 배열 오차 22 → 0

큰 필드를 먼저 놓아 패딩이 0 이 되니 배열 오차도 사라집니다. 다만 이건 "지금 필드 목록에서" 우연히 맞은 것입니다 — 필드가 추가되거나 순서가 바뀌면 다시 깨집니다. 오프셋을 손으로 계산하는 파서는 언젠가 반드시 틀립니다.

한 필드가 밀리면 그 뒤가 전부 밀린다

이게 이 버그를 찾기 어렵게 만드는 성질입니다. 오류가 국소적이지 않아요.

필드 하나를 잘못 읽으면 그 필드부터 끝까지 전부 어긋납니다. 증상은 "해상도가 이상하다"가 아니라 "중간부터 전부 이상하다"이고, 그러면 어느 필드가 원인인지 증상에서 역추적할 수 없습니다.

그래서 실제로 이 문제를 푼 방법은 추측을 포기하고 수신 바이트를 파일로 덤프한 다음, 실측 데이터에서 오프셋을 역산하는 것이었습니다. 헤더 파일을 몇 번 더 읽어서 나오는 게 아닙니다.

레이아웃은 언어 표준이 아니라 ABI 가 정한다

여기가 헤더 파일을 봐도 답이 안 나오는 이유입니다. 근거의 성격을 구별해 적어두겠습니다.

주장근거의 성격
구조체 멤버 사이와 끝에 패딩이 들어갈 수 있다C 표준이 허용합니다. 다만 규칙은 정하지 않습니다
각 타입은 자기 크기에 정렬되고, 구조체 정렬은 멤버 정렬의 최대값이며, sizeof 는 그 배수다ABI 규칙입니다. x86-64 · AArch64 에서 그렇고, 다른 ABI 나 다른 컴파일러 설정에서는 다를 수 있습니다. 실험대는 이 규칙을 모델로 씁니다
비트필드의 배치훨씬 더 구현 정의적입니다. 비트 순서와 저장 단위 경계 처리가 컴파일러마다 달라, 이 실험대는 비트필드를 다루지 않습니다
즉 "헤더 파일만으로는 레이아웃을 확정할 수 없습니다." 같은 선언이 컴파일러 · 아키텍처 · pragma 조합에 따라 다른 바이트 배치를 만듭니다. 그래서 실측 데이터가 유일한 근거가 됩니다.

Java 는 패딩을 자동으로 넣어주지 않는다

C 구조체를 Java 로 옮겨 적을 때 함정이 하나 더 있습니다. java.lang.foreign 의 MemoryLayout 문서에 명시돼 있어요.

무엇문서가 말하는 것
자동 패딩넣지 않습니다. "This factory does not automatically align element layouts, by inserting additional padding layout elements" — 그래서 structLayout(JAVA_SHORT, JAVA_INT) 은 IllegalArgumentException 으로 실패합니다
고치는 방법structLayout(JAVA_SHORT, MemoryLayout.paddingLayout(2), JAVA_INT) 처럼 패딩을 손으로 써 넣거나, JAVA_INT.withByteAlignment(2) 로 정렬을 낮춥니다
구조체 크기멤버 크기의 단순 합입니다 — "S1 + S2 + ... + Sn". 즉 꼬리 패딩이 자동으로 안 붙습니다
자연 정렬"The natural alignment of a value layout whose size is N is N" — 크기가 곧 정렬입니다

정렬 위반은 예외로 잡히니 그나마 낫습니다. 정말 위험한 건 꼬리 패딩입니다 — 안 써도 예외가 안 나고, 크기가 조용히 작아집니다. 그 레이아웃으로 배열을 읽으면 6번 상황이 그대로 재현됩니다. 원소 하나로는 통과하고요.

버전마다 크기가 다르면

같은 구조체가 펌웨어 버전에 따라 크기가 다른 경우가 있습니다. 필드가 추가되면 그렇게 됩니다.

접근결과
버전 필드를 보고 분기한다버전 필드가 구조체 안에 있으면 그걸 읽으려고 이미 레이아웃을 알아야 합니다. 순환입니다
수신 길이로 레이아웃을 판별한다동작합니다. 버전별 전체 크기가 다르면 길이가 곧 식별자입니다. 최소 길이 검증도 가장 작은 버전 기준으로 맞춥니다
길이가 같은 두 버전이 있다면이 방법이 무너집니다. 그때는 프로토콜에 바깥쪽 버전 표시가 필요하고, 그건 협의 사항입니다

먼저 할 것수신 바이트를 파일로 덤프하고 헥스로 찍으세요. 헤더 파일을 다시 읽는 것보다 빠릅니다. 알려진 값(해상도 같은 것)을 찾아 오프셋을 역산합니다
골든 파일 테스트샘플 입력과 기대 결과를 고정해 두세요. 단, 원소를 두 개 이상 넣으세요 — 하나로는 꼬리 패딩 버그가 통과합니다
오프셋을 손으로 안 쓴다필드 목록에서 오프셋을 계산하게 만들고, 그 계산기에 정렬 규칙을 넣습니다. 상수로 박아둔 오프셋은 필드가 추가되는 날 전부 틀립니다
전체 크기를 단언한다파서에 assert sizeof == 예상 을 넣으세요. 레이아웃이 틀렸다는 사실을 가장 값싸게 알려주는 한 줄입니다
Java FFM패딩을 자동으로 안 넣습니다. 정렬 위반은 예외로 잡히지만 꼬리 패딩 누락은 조용합니다 — 구조체 크기를 C 쪽 sizeof 와 대조하는 테스트를 넣으세요
pack 을 쓸 때파서는 편해지지만 정렬되지 않은 접근이 생깁니다. 아키텍처에 따라 느려지거나 예외가 나고, packed 멤버의 주소를 넘기는 것은 위험합니다
바이트 순서이 페이지는 정렬만 다뤘습니다. 엔디언은 별개 문제이고 둘이 겹치면 증상이 더 헷갈립니다 — 오프셋이 맞는데 값이 이상하면 엔디언을 보세요

21번이 선로에 무엇이 나갔나였다면, 이 페이지는 도착한 바이트를 어떻게 읽나입니다. 둘 다 "문서를 봐도 안 나오고 실측해야 한다"로 끝나요 — 21번은 RFC 가 규정하지 않는 구현 동작이 있었고, 여기서는 레이아웃을 언어 표준이 아니라 ABI 가 정합니다.
