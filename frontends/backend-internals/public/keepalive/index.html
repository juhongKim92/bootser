서버는 두 시간 동안 살아있다고 믿는다

클라이언트의 전원이 나갔습니다. 서버의 소켓은 여전히 ESTABLISHED 입니다. 접속자 목록에도 그대로 있고요. 언제 알아차릴까요 — 그리고 그 사이에 보낸 메시지는 어디로 갔을까요.

직접 조작하기

이 실험대에는 시간이 흐르지 않습니다. 손잡이를 움직이면 그 조건의 사건 순서를 통째로 다시 계산해서 보여줘요. 2시간 11분을 실시간으로 기다릴 수는 없으니까요.

조작무엇이 일어나나
끊김 방식정상 종료(FIN 을 보냄) / 전원 차단(아무것도 안 보냄) / 앱 멈춤(커널은 응답, 앱은 무응답)
탐지 방식TCP 기본 / TCP 튜닝 / 애플리케이션 keep-alive
keep-alive 주기TCP 튜닝의 tcp_keepalive_time 이자, 앱 keep-alive 의 주기입니다. TCP 기본에서는 회색으로 죽습니다 — OS 설정이라 앱이 정하는 값이 아니니까요
Will 지연MQTT 5 의 Will Delay Interval. 탐지하고 나서 이만큼 기다렸다 Will 을 발행합니다
재접속까지같은 세션으로 다시 붙기까지 걸리는 시간. Will 발행 전에 돌아오면 Will 이 취소됩니다

이렇게 해보세요

1. 정상 종료와 전원 차단을 번갈아 눌러본다

탐지 방식은 TCP 기본으로 두고 정상 종료 탐지 즉시 Will 발행 안 함 전원 차단 탐지 2시간 11분 15초 Will 발행

버튼 하나 차이인데 결과가 완전히 다릅니다. 정상 종료는 클라이언트가 FIN 을 보내주기 때문에 서버가 즉시 압니다. 전원이 나가면 아무도 아무 말을 안 해요. 서버가 아는 방법은 직접 물어보는 것뿐입니다.

2. TCP 기본값의 실제 숫자를 본다

전원 차단 + TCP 기본 tcp_keepalive_time 7200초 (2시간) tcp_keepalive_intvl 75초 tcp_keepalive_probes 9회 7200 + 75 × 9 = 7875초 = 2시간 11분 15초

첫 프로브가 나가기까지가 두 시간입니다. 리눅스 기본값이고, 대부분의 서버가 그대로 씁니다. 이 두 시간 동안 서버의 접속자 목록에는 죽은 클라이언트가 멀쩡히 앉아 있어요.

더 나쁜 건, TCP keepalive 는 기본적으로 꺼져 있다는 것입니다. 소켓에 SO_KEEPALIVE 를 켜지 않으면 이 2시간짜리 타이머조차 돌지 않아요. 그러면 탐지는 영영 일어나지 않습니다.

3. 앱 멈춤으로 바꾼다 — 이 페이지의 핵심

앱 멈춤 + TCP 기본 또는 TCP 튜닝 탐지 영원히 안 됨 Will 영원히 안 나감 같은 조건에서 앱 keep-alive 로 바꾸면 → 1분 30초

여기가 가장 중요한 지점입니다. 프로세스가 데드락에 걸리거나, 긴 GC 정지에 들어가거나, 스레드풀이 고갈되어도 커널의 TCP 스택은 멀쩡합니다. keepalive 프로브가 오면 커널이 알아서 ACK 를 돌려줘요. TCP 는 "연결이 살아있다"고 정확하게 보고합니다.

문제는 우리가 알고 싶은 게 그게 아니라는 겁니다. TCP keepalive 는 회선이 살아있는지 확인하지, 애플리케이션이 일할 수 있는지는 확인하지 않습니다. 그걸 확인하려면 애플리케이션이 직접 대답해야 해요.

4. keep-alive 주기를 밀어 올린다

전원 차단 + 앱 keep-alive 주기 10초 → 탐지 15초 주기 60초 → 탐지 1분 30초 주기 120초 → 탐지 3분 (TCP 튜닝과 같아지는 지점) 주기 300초 → 탐지 7분 30초 (TCP 튜닝보다 느리다)

MQTT 는 주기의 1.5배 안에 아무 패킷도 안 오면 끊습니다. 주기를 길게 잡을수록 탐지도 그만큼 늦어져요. 주기를 2분보다 크게 잡으면 OS 튜닝(주기 + 60초)보다 오히려 느려집니다. 배터리를 아끼려고 주기를 늘리는 게 늘 이득은 아닙니다.

5. Will 지연으로 유령 알림을 막는다

전원 차단 + 앱 keep-alive(60초) Will 지연 60초, 재접속까지 100초 탐지 1분 30초 Will 발행 예정 2분 30초 재접속 1분 40초 ← 발행 전에 돌아왔다 Will 취소됨

지하철에 들어갔다 나온 클라이언트마다 "오프라인" 알림을 쏘면 아무도 그 알림을 안 믿게 됩니다. MQTT 5 의 Will Delay Interval 은 탐지하고 나서 잠깐 기다렸다가 발행해요. 그 사이에 같은 세션으로 돌아오면 Will 은 조용히 취소됩니다. 재접속 슬라이더를 발행 예정 시각 너머로 밀면 그대로 발행되는 것도 확인해보세요.

반쯤 열린 연결

TCP 연결이 끊기는 정상적인 방법은 FIN 을 주고받는 것입니다. 문제는 이게 양쪽이 협조할 때만 일어난다는 점이에요.

상황FIN서버가 보는 것
정상 종료온다즉시 닫힌 걸 안다
프로세스 강제 종료온다 (커널이 대신 보냄)즉시 안다 — 대개 RST
전원 차단안 온다아무것도 모른다
회선 단절안 온다아무것도 모른다
NAT·방화벽 세션 만료안 온다아무것도 모른다

아래 세 경우가 반쯤 열린(half-open) 연결입니다. 서버 쪽 소켓은 ESTABLISHED 로 남아 있고, ss -tn 에도 정상으로 찍히고, 접속자 수에도 포함됩니다. 실제로는 반대쪽에 아무도 없는데요.

눈여겨볼 것: 프로세스를 kill 하는 것과 전원을 내리는 것은 완전히 다릅니다. 프로세스가 죽으면 커널이 남아서 소켓을 정리하고 FIN 이나 RST 를 보내줍니다. 그래서 개발 중에 서버를 Ctrl+C 로 껐다 켜는 테스트로는 이 페이지의 문제가 하나도 재현되지 않습니다.

보내보면 알 수 있지 않나

맞습니다. 죽은 상대에게 데이터를 쓰면 TCP 가 재전송을 시작하고, 결국 포기하면서 오류를 올려줍니다. 다만 그것도 빠르지 않아요. 리눅스의 tcp_retries2 기본값 15 면 대략 15분이 걸립니다.

그리고 보낼 게 있어야 알 수 있다는 조건이 붙습니다. 채팅방이 조용하면 몇 시간이고 아무도 아무것도 안 보내죠. 그 사이 죽은 연결은 계속 살아있는 것으로 집계됩니다. keep-alive 가 필요한 이유가 정확히 이것입니다 — 보낼 게 없어도 주기적으로 물어보기 위해서.

세 층위의 keep-alive

이름이 비슷해서 자주 섞이는데, 서로 다른 층에서 다른 것을 확인합니다.

층확인하는 것앱 멈춤을 잡나
TCP keepalive회선과 상대 커널이 살아있는지못 잡는다
MQTT PINGREQ
WebSocket ping		프로토콜 계층이 응답하는지구현에 따라 다르다
애플리케이션 하트비트애플리케이션이 실제로 일할 수 있는지잡는다

가운데 줄에 주의하세요. 브라우저는 WebSocket ping 프레임에 자동으로 pong 을 돌려줍니다. 자바스크립트가 멈춰 있어도요. 그래서 서버가 ping/pong 으로 "클라이언트 정상"을 판정하면 탭이 얼어붙은 클라이언트를 정상으로 셉니다. 게다가 브라우저 자바스크립트에는 ping 프레임을 보내는 API 자체가 없어서, 클라이언트→서버 방향은 애초에 애플리케이션 메시지로 해야 합니다.

그래서 실무에서는 애플리케이션 레벨 하트비트로 수렴합니다. 그냥 {"type":"ping"} 같은 메시지를 주고받는 거예요. 촌스러워 보여도 이게 "애플리케이션이 살아서 메시지를 처리할 수 있다"를 확인하는 유일한 방법입니다. 응답을 만드는 경로가 실제 메시지 처리와 같은 스레드풀·같은 이벤트 루프를 지나야 의미가 있습니다.

Last Will and Testament

LWT 는 접속할 때 브로커에게 유언을 맡겨두는 것입니다. "내가 인사도 없이 사라지면 이 메시지를 대신 발행해줘."

MqttConnectOptions o = new MqttConnectOptions();
o.setWill("status/device-42", "offline".getBytes(), 1, true);
o.setKeepAliveInterval(60);
o.setCleanSession(false);

핵심은 언제 발행되고 언제 안 되는지입니다.

상황Will
정상 DISCONNECT 후 종료발행 안 함
keep-alive 시간 초과발행
네트워크 오류 · 전원 차단발행
프로토콜 오류로 브로커가 끊음발행
브로커가 다운됨발행 안 함 — 유언을 들고 있던 쪽이 죽었다

첫 줄이 LWT 의 설계 의도입니다. 정상 종료는 클라이언트가 스스로 상태를 정리할 수 있으니 유언이 필요 없어요. Will 이 발행됐다는 것 자체가 "비정상적으로 끊겼다"는 신호입니다.

마지막 줄은 놓치기 쉬운 함정입니다. 브로커가 죽으면 모든 클라이언트의 연결이 끊기지만 Will 은 하나도 안 나갑니다. 유언장을 보관하던 사람이 같이 사라졌으니까요. 그래서 LWT 만으로 "모든 단말의 온라인 상태"를 관리하면, 브로커 재시작 때 전부 온라인으로 남은 채 굳습니다.

MQTT 5 에는 예외가 하나 있습니다. DISCONNECT 를 보낼 때 이유 코드 0x04(Disconnect with Will Message)를 쓰면 정상 종료인데도 Will 을 발행하게 할 수 있습니다. "계획된 종료지만 상태 메시지는 필요한" 경우를 위한 장치예요.

온라인 상태를 제대로 만들려면

LWT 는 이벤트이지 상태가 아닙니다. 이벤트만 모아서 상태를 복원하려 하면 어긋납니다. 실무에서 쓸 만한 조합은 이렇습니다.

  • 접속 시 — online 을 retained 로 발행. 나중에 구독하는 쪽도 현재 상태를 바로 받습니다
  • Will — offline 을 retained 로 등록. 비정상 종료 시 브로커가 대신 덮어씁니다
  • 정상 종료 시 — offline 을 직접 발행하고 DISCONNECT. Will 이 안 나가므로 직접 해줘야 합니다
  • 타임스탬프를 같이 실으세요 — 순서가 뒤집혀 도착해도 오래된 값이 새 값을 덮어쓰지 않게
  • 브로커 재시작에 대비하세요 — 상태의 최종 근거는 마지막으로 뭔가를 받은 시각입니다. 주기적으로 그 값을 훑어 오래된 것을 오프라인으로 내리는 장치가 있어야 합니다

현장에서 확인할 것

연결 수가 실제 사용자보다 많은지 보세요. 반쯤 열린 연결이 쌓이면 여기서 먼저 드러납니다. 접속자 수가 서서히 우상향하고 재시작하면 뚝 떨어진다면 이 페이지의 문제입니다.

# 서버가 들고 있는 연결
ss -tn state established '( sport = :8080 )' | wc -l

# keepalive 가 실제로 켜져 있는지, 타이머가 얼마나 남았는지
ss -tno state established '( sport = :8080 )' | grep -o 'timer:([^)]*)' | sort | uniq -c

# 현재 커널 설정
sysctl net.ipv4.tcp_keepalive_time net.ipv4.tcp_keepalive_intvl net.ipv4.tcp_keepalive_probes

timer:(keepalive,...) 가 안 보이면 그 소켓은 SO_KEEPALIVE 가 꺼져 있는 것입니다. 커널 값을 아무리 튜닝해도 적용되지 않습니다.

중간 장비의 유휴 타임아웃을 확인하세요. 이게 가장 흔한 실전 함정입니다.

장비기본 유휴 타임아웃
AWS ALB60초 (조정 가능)
AWS NLB350초 — 조정 불가
nginx proxy_read_timeout60초
통신사 NAT보통 수 분, 예고 없음

keep-alive 주기가 이 값보다 길면 중간 장비가 먼저 연결을 끊습니다. 게다가 조용히 버리는 장비가 많아서 양쪽 다 끊긴 줄 모르는 반쯤 열린 연결이 됩니다. 규칙은 간단해요 — keep-alive 주기는 경로상 가장 짧은 유휴 타임아웃보다 확실히 짧아야 합니다. NLB 뒤라면 350초보다 한참 짧게, 보통 30~60초로 잡습니다.

탐지 시간을 SLA 에서 거꾸로 정하세요. "장애를 몇 초 안에 알아야 하는가"가 먼저입니다. 그 값을 1.5 × 주기 에 넣고 풀면 주기가 나옵니다. 30초 안에 알아야 하면 주기는 20초예요.

그리고 그 대가를 계산하세요. 단말 10만 대가 30초 주기로 핑을 보내면 초당 3,300 패킷이 됩니다. 배터리로 도는 단말이라면 주기를 줄이는 게 곧 배터리 소모입니다. 빠른 탐지와 유휴 비용은 정면으로 충돌하고, 이 실험대의 주기 슬라이더가 그 거래입니다.

이 페이지의 모델은 개념을 보여주기 위해 단순화한 것입니다. 실제 탐지 시각은 마지막 패킷이 언제였는지, 재전송 백오프가 어떻게 겹치는지, 중간 장비가 먼저 끊는지에 따라 달라집니다. 표시되는 값은 사망 직전까지 연결이 활발했다고 가정한 최악의 경우로 읽어주세요.
