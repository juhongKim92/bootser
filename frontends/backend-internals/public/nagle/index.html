작은 쓰기 두 번이 40밀리초가 된다

같은 400바이트를 write() 한 번으로 보내면 1ms, 두 번으로 나눠 보내면 42ms 입니다. 바이트 수도, 회선도, 코드의 나머지도 같아요. 보내는 쪽은 ACK 를 기다리고 받는 쪽은 타이머를 기다립니다 — 두 알고리즘이 각자 합리적인데 겹치면 서로를 기다립니다.

직접 조작하기

손잡이무엇이 바뀌나
쓰는 방식나눠 쓴다면 write() 를 여러 번 부릅니다(헤더 따로, 본문 따로). 합쳐 쓴다면 같은 바이트를 한 번에 넘겨요. 이 손잡이가 이 페이지 전체입니다.
쓰기 횟수응답을 읽기 전에 write() 를 몇 번 부르나. 2회부터 걸리고, 3회·4회로 늘려도 더 나빠지지 않습니다 — 왜인지는 아래에 있습니다.
한 번에 쓰는 크기1460(MSS)으로 올려 보세요 — 걸리던 것이 사라집니다. 꽉 찬 세그먼트는 Nagle 이 안 막고, 받는 쪽도 안 미룹니다.
NagleTCP_NODELAY 입니다. 끄면 지연이 사라지지만 패킷 수가 늘어납니다.
지연 ACK 타이머받는 쪽이 ACK 를 미루는 시간. 끔은 TCP_QUICKACK 이고, 500ms 는 RFC 1122 가 정한 상한입니다. 40ms 는 리눅스 값이에요.
왕복 시간같은 데이터센터면 1ms 안쪽, 대륙을 넘으면 100ms 대입니다. RTT 가 작을수록 40ms 가 상대적으로 더 크게 보입니다.

모든 시각이 결정됩니다 — 난수도 표본도 없어요. 세그먼트 하나는 1,460바이트(MSS)로 뒀습니다.

이렇게 해보세요

1. write 한 번 — 아무 일도 없다

쓰기 1회 × 200B · Nagle 켬 · 지연 ACK 40ms · RTT 1ms 총 1ms · 패킷 1개 · 추가 지연 없음

보낼 때 미확인 데이터가 없으니 Nagle 이 막을 게 없습니다. 요청이 반 왕복에 도착하고, 받는 쪽은 응답에 ACK 를 얹어 보냅니다 — 지연 ACK 타이머가 뜰 이유가 없어요. 여기까지는 두 알고리즘이 보이지 않습니다.

2. 두 번으로 나눈다 — 42ms

쓰기 1 → 2회 (200B 씩 · 합계 400B) 총 1 → 42ms · 추가 +41ms · 패킷 3개

첫 200바이트는 바로 나갑니다. 둘째 200바이트는 Nagle 이 붙잡습니다 — 앞의 것이 아직 ACK 를 못 받았고, 이건 꽉 찬 세그먼트가 아니니까요. 그런데 받는 쪽은 응답을 만들 수가 없습니다(요청이 덜 왔으니). 그래서 ACK 를 얹어 보낼 데이터가 없고, 지연 ACK 타이머 40ms 가 유일한 출구가 됩니다.

3. 같은 바이트를 합쳐 쓴다 — 다시 1ms

쓰는 방식 나눠 쓴다 → 합쳐 쓴다 (400B 한 번) 총 42 → 1ms · 패킷 3 → 1개

보낸 바이트는 정확히 같습니다. 바뀐 것은 write() 호출 횟수뿐이에요. 400바이트가 한 세그먼트에 들어가고, 미확인 데이터가 없으니 즉시 나갑니다. 이게 이 문제의 가장 싼 처방입니다 — 커널 설정도 아니고 소켓 옵션도 아니고 버퍼 하나입니다.

4. Nagle 을 끈다 — 지연은 사라지고 패킷은 늘어난다

Nagle 켬 → 끔 (TCP_NODELAY · 나눠 쓴 그대로) 총 42 → 1ms · 패킷 2개

붙잡는 규칙이 없어지니 둘째 세그먼트가 바로 나갑니다. 증상은 사라지는데 원인은 그대로예요 — 400바이트를 두 패킷으로 보내는 것은 여전합니다. 작은 쓰기를 초당 수만 번 하는 서비스라면 그 패킷 수가 그대로 비용입니다. Nagle 이 애초에 막으려던 게 그거였고요.

5. 받는 쪽에서 지연 ACK 를 끈다 — 2ms

지연 ACK 타이머 40ms → 끔 (TCP_QUICKACK) 총 42 → 2ms · 합쳐 쓰기(1ms)보다는 여전히 느리다

ACK 가 즉시 나가니 Nagle 이 곧바로 풀립니다. 그런데 완전히 공짜는 아니에요 — 왕복 하나가 더 듭니다(1ms → 2ms). 더 중요한 건 이 손잡이가 반대편에 있다는 겁니다. 우리 코드를 안 고쳤는데 상대 서버 설정을 바꾸니 나아지는 경우가 이래서 생깁니다.

6. 쓰기 크기를 1460으로 — 걸리지 않는다

크기 200 → 1,460B (= MSS · 나눠 쓰기 2회) 총 42 → 1ms · ACK 1개

둘 다 꽉 찬 세그먼트라 Nagle 이 막지 않습니다(Nagle 은 *작은* 세그먼트만 미룹니다). 그리고 받는 쪽도 미루지 않아요 — RFC 1122 가 꽉 찬 패킷 흐름에서는 적어도 두 개마다 하나는 ACK 하라고 정해뒀거든요. 세그먼트 두 개 = ACK 한 개, 타이머가 뜰 자리가 없습니다.

7. 합쳐 써도 걸리는 경우 — 꼬리가 작으면

크기 700B × 3회를 합쳐 쓴다 (합계 2,100B) 세그먼트 1,460 + 640 · 총 42ms

한 번에 썼는데도 걸립니다. 2,100바이트가 MSS 를 넘어 꽉 찬 세그먼트 하나 + 작은 꼬리 640바이트로 쪼개지고, 그 꼬리가 Nagle 에 붙잡히거든요. "합쳐 쓰면 된다" 는 MSS 안에 들어갈 때만 맞습니다. 요청이 MSS 를 넘는다면 다른 처방이 필요합니다.

두 알고리즘이 각자 무엇을 막으려 했나

둘 다 1980년대에 실재한 문제를 고친 것이고, 지금도 대체로 옳습니다.

알고리즘무엇을 아끼나
Nagle패킷 수. 1바이트를 보내려고 41바이트 패킷을 만드는 낭비를 막습니다. 규칙은 하나예요 — 미확인 데이터가 있으면 작은 세그먼트를 미룬다. RFC 1122 §4.2.3.4 는 이걸 MAY(선택)로 두고, 애플리케이션이 끌 수 있어야 한다고 적습니다
지연 ACKACK 패킷 수. 데이터 없이 ACK 만 든 패킷을 줄입니다. 응답에 얹어 보낼 수 있으면 그렇게 하고, 없으면 잠깐 기다립니다

문제는 "잠깐 기다린다" 와 "ACK 를 기다린다" 가 만날 때입니다. 보내는 쪽은 ACK 가 오면 보내겠다고 하고, 받는 쪽은 보낼 데이터가 생기면 ACK 를 얹겠다고 합니다. 그런데 받을 데이터가 다 안 왔으니 보낼 데이터도 안 생깁니다. 서로가 상대를 기다려요.

이건 교착이 아닙니다 — 타이머가 있어서 풀립니다. 다만 그 타이머가 40ms 고, 같은 데이터센터의 왕복이 1ms 인 세상에서는 40배입니다.

RFC 가 갈림길을 정해뒀다

왜 꽉 찬 세그먼트는 안 걸리는가. RFC 1122 §4.2.3.2 가 지연 ACK 를 허용하면서 단 조건을 이렇게 씁니다.

"An ACK SHOULD NOT be excessively delayed; the delay MUST be less than 0.5 seconds, and in a stream of full packets there SHOULD be an ACK for at least every other packet."

두 가지가 여기서 나옵니다. 첫째, 미룰 수 있는 상한이 0.5초입니다 — 40ms 는 명세가 아니라 리눅스가 고른 값이고, 손잡이를 500ms 까지 올려 보면 RFC 가 허용하는 최악을 볼 수 있습니다. 둘째, 꽉 찬 패킷이 흐르면 두 개마다 하나는 ACK 해야 합니다. 그래서 세그먼트가 꽉 차 있으면 타이머가 개입할 자리가 없어요.

Nagle 쪽 조건도 같은 자리를 가리킵니다 — 미루는 대상이 작은 세그먼트뿐입니다. 그래서 이 문제는 "작다"와 "미확인" 이 동시에 성립할 때만 생깁니다.

상황걸리나
write 한 번안 걸립니다 — 미확인 데이터가 없으니 Nagle 이 막을 게 없습니다
작은 write 두 번 이상걸립니다 — 이 페이지의 그림
꽉 찬 세그먼트들안 걸립니다 — Nagle 도 안 막고 RFC 규칙이 ACK 를 부릅니다
요청 하나 → 응답 하나안 걸립니다 — 받는 쪽에 얹어 보낼 데이터가 늘 있습니다

마지막 줄이 중요합니다. 이 문제는 write-write-read 패턴에서만 나옵니다. 요청-응답만 반복하는 코드에서는 평생 안 만나요. 그래서 라이브러리를 하나 바꾸다가 갑자기 나타납니다.

쓰기를 늘려도 더 나빠지지 않는다

쓰기 횟수를 3회, 4회로 올려 보세요. 42ms 에서 안 움직입니다. 처음 보면 이상한데, 이유가 있습니다.

애플리케이션이 write() 를 연달아 부르면 그 바이트들은 커널 송신 버퍼에 쌓입니다. Nagle 이 첫 세그먼트의 ACK 를 기다리는 동안 2·3·4번째 쓰기가 모두 버퍼에 들어와 있고, ACK 가 오는 순간 하나의 세그먼트로 합쳐져 나갑니다.

그래서 막히는 것은 한 번뿐입니다. 쓰기를 열 번 해도 40ms 는 한 번이에요. 반대로 말하면 — 쓰기를 줄이는 것으로는 안 없어집니다. 2회를 1회로 만들어야 없어집니다.

이 모델이 가정하는 것

가정깨지면 어떻게 되나
쓰기가 연달아 온다write() 들 사이에 애플리케이션이 일하지 않는다고 봤습니다. 사이에 계산이 오래 끼면 두 번째 쓰기가 버퍼에 늦게 들어와 합쳐지지 않고 따로 나갑니다 — 그러면 막히는 횟수가 늘 수 있습니다
받는 쪽이 다 받아야 답한다요청을 끝까지 읽어야 응답을 만든다고 봤습니다. 스트리밍 프로토콜처럼 앞부분만 보고 뭔가를 보내는 구현이면 ACK 가 얹혀서 이 문제가 사라집니다
손실이 없다재전송이 끼면 시각이 밀립니다. 그쪽은 26번·27번의 자리예요
40ms 는 리눅스 값명세는 0.5초 상한만 정합니다. 운영체제와 버전마다 다르고, 리눅스는 상황에 따라 이 값을 조절하기도 합니다 — 정확한 값을 코드가 가정하면 안 됩니다
