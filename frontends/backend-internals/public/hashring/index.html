링에서 굵은 띠는 소유 구간이고, 띠를 가로지르는 가는 눈금이 가상 노드 지점입니다. 바깥의 점 1500개가 키이고, 색은 어느 노드가 가져갔는지를 뜻합니다. 12시 방향이 해시 공간의 0입니다.

분포 막대의 세로선은 이상적인 값(1500 ÷ 노드 수)입니다. 막대가 이 선에 가까울수록 고르게 나뉜 겁니다.

이렇게 해보세요

1. 가상 노드 없이 시작한다

초기화 (노드 6, 가상 노드 1) 분포 막대를 본다 이상값 250 실제 424 … 101 편차(CV) 46.9% 최대/최소 4.20배

여섯 노드가 고르게 나눠야 할 몫이 네 배 넘게 벌어집니다. 해시가 고르게 퍼져도 링 위의 여섯 지점이 균등하게 놓이지는 않기 때문이에요. 구간 길이가 제각각이면 몫도 제각각입니다.

2. 노드를 하나 뺀다

가상 노드 1 상태에서 − 버튼 링 방식 7% 이동 나머지 연산 84% 이동 이웃 노드 345 → 446 으로 급증

여기가 컨시스턴트 해싱의 존재 이유입니다. 링에서는 사라진 노드가 맡던 구간만 다음 노드로 넘어갑니다. 나머지 연산은 제수가 바뀌므로 거의 모든 키의 목적지가 달라져요.

다만 7%라는 숫자를 그대로 믿으면 안 됩니다. 이 값은 죽은 노드가 갖고 있던 몫과 정확히 같습니다. 가상 노드가 1이면 그 몫이 제각각이라 어떤 노드가 죽느냐에 따라 크게 달라집니다 — 이 구성에서는 6.7%에서 28.3%까지 벌어져요. 그리고 그 부담을 시계방향 이웃 하나가 통째로 받습니다.

다만 − 버튼은 항상 마지막 노드를 뺍니다. 그래서 위 범위는 실험대에서 직접 확인할 수 없고, 화면에서는 늘 같은 7%만 보입니다.

3. 가상 노드를 늘린다

초기화 상태(노드 6)에서 가상 노드를 1 → 20 → 160 → 200 편차(CV) 46.9% → 20.4% → 8.3% → 5.5% 최대/최소 4.20배 → 1.85배 → 1.27배 → 1.16배 링 그림 색이 잘게 섞인다

노드 하나를 링 위 여러 지점에 흩어놓으면 큰 수의 법칙이 작동합니다. 지점이 많을수록 각 노드가 가져가는 구간 길이의 합이 평균에 수렴해요. 실무에서 150~160을 쓰는 관행이 여기서 나왔습니다.

4. 가상 노드가 많을 때 노드를 뺀다

가상 노드 160, 노드 5 상태에서 − 버튼 이동량 22% (이론 1/5 = 20%) 분포 387 / 371 / 379 / 363 — 고르게 흡수

이제 이동량이 1/N에 수렴합니다. 예측 가능해진 것이 진짜 소득이에요. 용량 계획을 세울 수 있게 됐다는 뜻이니까요.

분포도 보세요. 사라진 노드의 몫이 남은 넷에게 거의 균등하게 나뉘었습니다. 가상 노드가 1일 때 이웃 하나가 101개를 통째로 받던 것과 대조적이죠. 연쇄 장애를 막는 것이 가상 노드의 두 번째 역할입니다.

5. 노드를 다시 넣어본다

+ 버튼으로 노드를 추가 이동량 22% 나머지 연산 81%

추가할 때도 이동량은 1/N 수준입니다. 새 노드가 자기 구간만 가져올 뿐, 나머지 노드끼리는 아무 변화가 없어요. 스케일 아웃이 싸다는 것이 이 방식의 두 번째 이점입니다.

6. 가상 노드 개수는 나중에 못 바꾼다

가상 노드 슬라이더를 크게 움직인다 이동량 패널을 본다 이동량 70% 이상

지점의 좌표는 hash('node-A#' + i)라서 기존 지점 자체는 그대로 남습니다. 그런데도 이동량이 이렇게 큰 건, 지점이 대량으로 추가·제거되면서 구간 경계가 대부분 다시 그어지기 때문이에요. 노드 구성이 바뀐 게 아닌데도 그렇습니다. 반대로 160에서 200처럼 조금만 늘리면 기존 160개 지점이 유지되어 이동량은 16% 정도에 그칩니다 — 큰 폭으로 움직일 때가 문제예요. 운영 중인 캐시 클러스터에서 이걸 하면 전면 캐시 미스가 납니다. 처음에 정하고 모든 클라이언트가 같은 값을 써야 합니다.

나머지 연산의 문제

가장 단순한 샤딩은 이렇습니다.

int shard = Math.abs(key.hashCode()) % serverCount;

서버가 넷일 때는 잘 돕니다. 문제는 서버 수가 바뀌는 순간이에요.

key.hashCode() = 1234

servers = 4  →  1234 % 4 = 2   (3번 서버)
servers = 3  →  1234 % 3 = 1   (2번 서버)  ← 옮겨감

제수가 바뀌면 나머지가 통째로 재배치됩니다. 이론적으로 1 - 1/N, 즉 서버가 넷에서 셋이 되면 약 75%의 키가 다른 서버로 갑니다.

캐시라면 이 75%가 전부 미스가 됩니다. 서버 한 대가 죽었을 뿐인데 살아남은 서버들의 캐시도 대부분 무효가 되고, 그 트래픽이 한꺼번에 원본 저장소로 쏟아집니다. 장애 한 건이 전면 장애로 번지는 전형적인 경로예요.

링 위에 올리면

해결의 발상은 서버 수를 계산식에서 빼는 것입니다.

  1. 해시 공간(0 ~ 232−1)을 원으로 잇는다
  2. 서버를 hash(서버이름) 위치에 놓는다
  3. 키를 hash(키) 위치에 놓는다
  4. 키에서 시계 방향으로 처음 만나는 서버가 주인이다

키의 위치는 서버 수와 무관하게 고정입니다. 서버가 하나 사라지면 그 서버가 맡던 원호 구간만 다음 서버로 넘어가고, 나머지 구간은 아무 영향이 없습니다. 그래서 이동량이 1/N 수준으로 떨어집니다.

조회는 정렬된 지점 배열에서 이진 탐색이라 O(log(N × V))입니다.

// 실제 구현의 뼈대
TreeMap<Long, String> ring = new TreeMap<>();

void addNode(String node, int vnodes) {
    for (int i = 0; i < vnodes; i++)
        ring.put(hash(node + "#" + i), node);
}

String lookup(String key) {
    if (ring.isEmpty()) return null;
    Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));
    return e != null ? e.getValue()          // 시계 방향 첫 지점
                     : ring.firstEntry().getValue();  // 한 바퀴 돌아 처음으로
}

ceilingEntry가 없을 때 firstEntry로 감는 부분이 핵심입니다. 이 한 줄을 빠뜨리면 해시 공간 끝자락의 키들이 전부 실패해요.

가상 노드가 필요한 이유

링만으로는 부족합니다. 노드가 넷이면 링 위에 지점이 넷뿐이고, 그 넷이 균등하게 놓일 이유가 없거든요. 실험대에서 가상 노드를 1로 두면 편차가 47%에 이르고 최대/최소가 4배 넘게 벌어지는 걸 볼 수 있습니다.

해법은 노드 하나를 여러 이름으로 여러 번 등록하는 것입니다. node-A#0, node-A#1 … 이렇게요. 지점이 많아질수록 각 노드가 차지하는 구간 길이의 합이 평균에 수렴합니다.

가상 노드는 가중치에도 쓰입니다. 메모리가 두 배인 서버에 가상 노드를 두 배로 주면 그만큼 더 받아요. 이기종 서버로 클러스터를 꾸릴 때 유용합니다.

표의 절대값을 그대로 읽으면 안 됩니다. 실험대는 키가 1500개뿐이라, 링이 완벽하게 균등해도 표본 잡음만으로 CV가 5.8%쯤 나옵니다(√(1500 × 1/6 × 5/6) ÷ 250). 가상 노드 160 이상의 한 자릿수 값은 링의 불균형이 아니라 이 잡음 바닥을 재고 있는 셈이라, 노드 수에 따라 오르내리기도 합니다. 방향은 믿되 절대값은 믿지 마세요.
가상 노드를 무한정 늘리면 좋은 건 아닙니다. 링 크기가 노드 수 × 가상 노드 수라서 조회 비용과 메모리가 함께 늘고, 노드 변경 시 갱신해야 할 항목도 그만큼 많아집니다. 수천 개 노드 규모에서는 이 비용이 실제로 문제가 됩니다.

실제로 어디에 쓰이나

  • memcached 클라이언트 — libketama 계열. 노드당 가상 노드 160개가 사실상의 표준입니다. 실무의 "160"이라는 숫자가 여기서 왔어요
  • Cassandra — 토큰 링. 초기에는 노드당 토큰 256개가 기본이었지만, 4.0부터 새 할당 알고리즘과 함께 16으로 줄었습니다. 토큰이 많으면 복제본 배치가 흩어져 어느 한 노드가 죽어도 영향받는 조합이 많아지기 때문입니다
  • Dynamo (논문) — 2007년 Dynamo 논문이 이 방식을 대중화시켰습니다. 이름이 비슷한 DynamoDB 서비스와는 다른 시스템이에요
  • nginx — hash $request_uri consistent; 로 업스트림 선택에 사용
  • Envoy — ring hash, Maglev 로드밸런서
흔한 오해: Redis Cluster는 컨시스턴트 해싱을 쓰지 않습니다. 16384개의 고정 해시 슬롯을 노드에 나눠주는 방식이에요. CRC16(key) % 16384로 슬롯을 정하고, 슬롯–노드 대응은 별도로 관리합니다. 슬롯 단위로 옮기므로 재배치는 제어 가능하지만, 링 구조는 아닙니다.

현장에서 주의할 것

핫스팟은 여전히 생깁니다. 컨시스턴트 해싱은 키의 개수를 고르게 나눌 뿐, 트래픽을 고르게 나누지 않습니다. 인기 키 하나에 요청이 몰리면 그 노드만 터져요. 이 문제에는 bounded-load 변형이나 인기 키 복제 같은 별도 대응이 필요합니다.

노드가 죽으면 부담은 이웃 하나에게 갑니다. 가상 노드가 충분하면 여러 노드로 분산되지만, 적으면 시계방향 이웃 하나가 통째로 받습니다. 그 노드마저 넘어지면 연쇄 장애가 시작돼요. 실험대에서 가상 노드 1로 두고 노드를 빼보면 이 쏠림이 보입니다.

모든 클라이언트가 같은 링을 봐야 합니다. 해시 함수, 가상 노드 개수, 노드 이름 표기가 하나라도 다르면 클라이언트마다 다른 노드를 가리킵니다. 캐시 적중률이 설명 없이 떨어진다면 이걸 먼저 의심하세요. 특히 언어가 다른 클라이언트를 섞어 쓸 때 자주 발생합니다.

더 단순한 대안도 있습니다. 랑데부 해싱(HRW)은 링도 가상 노드도 필요 없습니다. 모든 노드에 대해 hash(키 + 노드)를 계산해 가장 큰 값을 고르면 끝이고, 분포도 균일합니다. 대신 조회가 O(N)이라 노드 수가 적을 때 유리해요.

이 페이지의 모델은 교육용으로 단순화했습니다. 해시는 FNV-1a 32비트에 murmur3 의 최종 믹싱을 덧붙여 썼습니다. FNV-1a 만으로는 상위 비트가 확산되지 않아 링 지점들이 한 자리에 뭉치더군요. 실제 구현은 대개 MD5나 MurmurHash 를 씁니다. 다만 이동량이 1/N로 떨어지는 것과 가상 노드가 분포를 고르게 만드는 것은 실제와 같습니다.
