How much bigger does a random key make the index

People say a UUID primary key doubles the index. Work it out from the documented rules and it is 1.30× at the same key width, 1.80× at worst. The number close to two — 1.83× — only appears once you multiply the key width in as well. This page is where those numbers get separated.

Work the dials

DialWhat it changes
Insertion orderSequential means every key is the new largest (a bigint sequence, UUIDv7, a time-ordered ULID). Random is UUIDv4 — landing anywhere.
Key width8 is bigint, 16 is uuid. This dial grows the index independently of occupancy — separating the two is the whole point of this page.
fillfactorHow full leaf pages are packed. The default is 90. Switch to random and turn this dial — nothing happens at all.
RowsRows in the index. The ratio does not depend on it — only the absolute size grows, linearly.

Block 8,192 bytes, page header 24, line pointer 4, index-tuple header 8, keys aligned to 8. Every number here is deduced from documented rules — no randomness and no samples.

Things to try

1. bigint, sequential — the baseline

8B key · sequential · fillfactor 90 · 10M rows 20B per entry · 367 of 408 slots used per page 27,248 pages · index 212.9MB

Every key is the new largest, so only the rightmost page grows. The documentation calls this case out specifically — "leaf pages are filled to this percentage during initial index builds, and also when extending the index at the right (adding new largest key values)." So occupancy is exactly the fillfactor.

2. Change only the key to uuid — 1.41×

Key 8 → 16B (still sequential) Per entry 20 → 28B · slots per page 408 → 291 Index 212.9 → 299.3MB (×1.41)

Insertion order was not touched. Eight extra bytes of key alone give 1.41×. One entry goes from 20 to 28 bytes (tuple header 8 + key + line pointer 4) and that many fewer fit on a page. None of this has anything to do with splits.

3. Switch to random — 1.30× at the same width

Order sequential → random (key still 16B) Occupancy 90% → 69.3% (average) · pages 38,315 → 49,752 Index 299.3 → 388.7MB (×1.30) · versus bigint sequential ×1.83

This is the heart of the page. The share caused by splitting is 1.30×, and the commonly quoted near-double, 1.83×, is that multiplied by the 1.41× of key width. Two causes had been folded into one number. Moving UUIDv4 → UUIDv7 recovers only the 1.30× — the key stays 16 bytes wide.

4. Push fillfactor to 100 — sequential shrinks

fillfactor 90 → 100 (uuid, sequential) Slots used 261 → 291 · index 299.3 → 268.5MB

Packing the right edge completely needs fewer pages. The documentation does not recommend it — "You should only consider this when you are completely sure that the table is static … A fillfactor setting of 100 otherwise risks harming performance: even a few updates or inserts will cause a sudden flood of page splits." You buy space and sell split risk.

5. Turn fillfactor with random insertions — nothing happens

fillfactor 100 · random Occupancy still 69.3% · index still 388.7MB

Drop fillfactor to 10 or raise it to 100 and the random case does not move. The documentation states its scope exactly: initial builds and extending at the right. Insertions landing mid-page never read that value. What sets occupancy there is the split rule, not the fillfactor.

6. bigint, random — the same 1.30×

Key 16 → 8B · random · fillfactor 90 Index 212.9 → 277.0MB (versus bigint sequential ×1.30)

Narrow the key and the ratio splitting creates is still 1.30×. The two causes only multiply; neither affects the other. Which is why the fixes are separate too — narrowing the key recovers 1.41×, ordering the key recovers 1.30×. Do both and the whole 1.83× is gone.

7. A hundred million rows — the ratio holds

Rows 10M → 100M (uuid, random) Index 388.7MB → 3.80GB · ratio still ×1.30

The size grows tenfold and the ratio does not move one digit, because occupancy has nothing to do with row count. So the "how many times" story holds at any scale, and only the point where the absolute size starts to hurt depends on scale — the moment the index stops fitting in the buffer cache.

The two rules the documentation gives

Everything this lab computes comes out of the two sentences below. There are no constants of my own.

SourceSentence
CREATE INDEX"B-trees use a default fillfactor of 90 … leaf pages are filled to this percentage during initial index builds, and also when extending the index at the right (adding new largest key values)."
nbtree/README"When we split a page, we try to equalize the number of bytes, not items, assigned to pages."

The first gives sequential occupancy = fillfactor. And it hides an important negative: by naming extending at the right, it says mid-page insertions do not read that value. That is recipe 5.

The second gives the occupancy range for random insertions. A full page splits its bytes in half, so both halves sit at 50% right after, and each fills to 100% before splitting again.

Invariant — with random insertions every leaf page is between 50% and 100% full. That is deduced from the documented split rule, and it is the basis for the lower and upper bounds this page computes. The index size is somewhere inside them.

Where 69.3% comes from — and what it is not

The "average" row in the lab sits at 69.3%. That number is not in any specification. It is the classic analytical result that the steady-state node occupancy of a B-tree under random insertions is ln 2 ≈ 69.3%.

So this lab displays it rather than computing it. What it computes is what the documentation implies: the lower bound (100% packed, 1.00×) and the upper bound (50% packed, 1.80×), with 69.3% marked as a reference line between them. Without that distinction, somebody else's analysis would look like my model's output.

Stated honestly: the index lands between 1.00× and 1.80×, and around 1.30× is common in a long-running system. "Double" is past even the upper bound of that range.

Separating the two causes

"UUIDs double your index" bundles two different things together.

CauseShareFix
The key is wide (8 → 16 bytes)×1.41Narrow it — bigint, or at least store UUIDs as uuid and not as text
The key has no order (mid-page inserts)×1.30Order it — UUIDv7, ULID, or a time prefix
Both×1.83This is the number that has been called "double"

Separated, the fixes differ. UUIDv4 → UUIDv7 recovers only the 1.30×, since the key stays as wide. Conversely, if you were storing UUIDs as text that is 36 bytes plus header, far worse — and switching to the uuid type recovers a large share on its own.

The real price is not size

This page only computes size. And 1.30× may be the smallest item on the bill. Sequential and random insertions differ in how many pages they touch, and that weighs far more.

WhatSequential vs random
Pages touchedSequential keeps returning to the same rightmost page. Random touches a different one per insert. Buffer-cache hit rate diverges right here
WALThe first touch of a page after a checkpoint writes a full page image to WAL. Sequential amortises that over one page; random pays it again per page
VACUUM and fragmentationFrequent splits break the match between logical and physical order — the documentation's phrase is "fragmentation of the on-disk index structure." Range scans pay for that
So do not decide on the size ratio. "It is only 1.3×, we are fine" and "it is 2×, absolutely not" both rest on the wrong calculation. Size is merely the easiest item here to measure.

What this model assumes

AssumptionWhat breaks if it fails
No duplicatesWith many equal keys the documentation describes a split that leaves "the left half of the page mostly full, and the right half mostly empty." That changes the occupancy range
No deletesMixed deletes and updates leave dead entries, pushing occupancy lower and running into no. 1's VACUUM story
Suffix truncation not countedPostgreSQL truncates key suffixes in internal pages to save space. Counting leaves only overstates internal pages — a small effect, since leaves dominate
Internal pages not countedOnly leaves are computed. With a fan-out in the hundreds, internal pages are under 1% of the total, so the absolute size is understated by about that much. The ratio is essentially unaffected
69.3% is a citationA classic analytical result, not a specification, and workload dependent. What this lab computes is the lower and upper bound

In the field

WhereWhat to check
Measuring the real thingThe pgstattuple extension's pgstatindex() reports actual avg_leaf_density. Read that instead of this page's arithmetic — near 90 means sequential, near 70 means random
UUIDs stored as textThe most common and the most wasteful. text/varchar(36) is 36 bytes plus header, more than double the uuid type's 16. Start here
Moving to UUIDv7What you recover is the ordering share (1.30×) only. It is still worth doing — but for pages touched, not for size. See the table above
Touching fillfactorIt only affects sequential-insert indexes. On a random-insert index nothing happens at all — confirm it in the lab above
REINDEXRebuilding takes the initial build path, so pages pack to fillfactor. It shrinks right afterwards and then drifts back into the range as random insertions resume. Temporary
How to measurepg_relation_size('idx') for size, read alongside write volume from pg_stat_user_tables. Do not read the ratio alone — watch whether it still fits in the buffer cache. Crossing that line is where it actually hurts

If no. 1 was about why deleting does not shrink anything, this page is about why inserting alone costs this much. And the answer not being "double" is this edition's conclusion — correcting an overstatement is also arithmetic.
