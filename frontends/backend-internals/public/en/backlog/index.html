Work the dials

DialWhat it changes
Connections arrivingNew connections per second. Above the accept rate the queue starts filling.
accept rateHow often the application calls accept(). Not how fast it serves requests — how fast it takes them in. A blocked event loop makes this zero.
backlogAccept-queue size: the smaller of the listen() argument and somaxconn. The default was 128 before Linux 5.4 and is 4096 after.
Burst lengthHow long the overload lasts. Read it next to the client-side latency — they are not the same number.
On overflowThis is tcp_abort_on_overflow. The default is drop silently. Turn it on and the client fails immediately with a RST.

Arrivals are evenly spaced, so every value comes out of a closed-form expression. No randomness, no samples.

Things to try

1. Without an overload, nothing happens at all

Arriving 400/s · accept 500/s · backlog 128 Queued 0 · dropped 0 · client latency none

If you take them in faster than they arrive, the queue is always empty. The backlog value makes no difference whatsoever — which is why nobody argues about it, and why nobody is looking at it on the day traffic piles up.

2. Raise arrivals to 2,000/s — the queue fills in 0.09s

Arriving 400 → 2,000/s (accept still 500 · for 5 seconds) Queue fills in 0.09s · dropped 7,372 Application metrics 0 · client latency 7s

1,500 per second have nowhere to go, so 128 slots fill in 0.09 seconds. Everything arriving in the next five seconds is thrown away. And the application never saw those 7,372 — the kernel dropped them. Latency graphs and error rates stay clean.

3. Two seconds of overload costs three — the wait outlasts it

Burst length 5 → 2s Overflow window 1.91s · client latency 3s — 1.57× the overflow window

Dropped connections retry at 1s, 3s, 7s. The wait needed is 1.91 seconds; the 1-second retry is still too early, and the next one is at 3. 1.09 seconds are spent sitting still while the server is already idle.

4. Four seconds costs seven — the gaps widen

Burst length 2 → 4s Overflow window 3.91s · client latency 7s — 1.79× the overflow window

The steps are 2ᵏ − 1, so the gaps keep widening. The first step past 3.91 is 7. The longer the overload, the larger the share of wasted time — 8 seconds costs 15, 16 costs 31. It approaches a factor of two.

5. Raise backlog to 4096 — drops turn into waiting

backlog 128 → 4,096 (arriving 2,000 · 5 seconds) Queue fills in 0.09 → 2.73s · dropped 7,372 → 3,404 Client latency 7 → 3s · back-of-queue wait 0.26 → 8.19s

It looks better, and it is — halfway. Fewer are dropped, but a connection at the back of that queue waits 8.19 seconds. And those 8 seconds never enter the latency the server measures, because the server's clock starts at accept(). This is where no. 11’s “rejection becomes waiting” meets no. 25’s “time that vanishes from the metrics”.

6. Send a RST instead — the wait disappears and an error arrives

On overflow: drop silently → send RST (tcp_abort_on_overflow=1) Client latency 7s → immediate · but immediate failure

Waiting seven seconds and succeeding, versus failing at zero — this is not a performance question, it is a policy decision. For a screen a user will wait on, the retry is better. For a client that can go to another instance, failing fast is far better. It is no. 11’s “rejection is a signal”, expressed as one kernel setting.

7. Seventy seconds of overload kills the connection

Burst length 5 → 70s Overflow window 69.9s · last retry at 63s Client ETIMEDOUT after 127s

Retries stop at 63 seconds (tcp_syn_retries defaults to 6). An overload longer than 64 seconds cannot be rescued by retrying. The client waits 127 seconds and then fails — and for all of it the user sees nothing, unless a shorter timeout was set.

There are two queues, and they misbehave differently

Linux keeps two connection queues. They are easy to confuse, but the symptoms differ, which makes the distinction worth having.

QueueWhat it holds · what overflow does
SYN queueConnections whose handshake is unfinished. Sized by tcp_max_syn_backlog — in the man page’s words, “If this number is exceeded, the kernel will begin dropping requests.” Enabling syncookies makes the limit moot
accept queueHandshake finished, application has not picked it up yet. Sized by listen()’s backlog, capped by somaxconn. On overflow, “the request may be ignored so that a later reattempt at connection succeeds”

Since Linux 2.2, listen()’s backlog refers to the second queue. It is often taken to mean the SYN queue, but the man page says the change explicitly — the backlog “specifies the queue length for completely established sockets waiting to be accepted, instead of the number of incomplete connection requests.”

The default changed, too. somaxconn is 4096 since Linux 5.4; before that it was 128. That is why the same code survives differently after a kernel upgrade.

Why the server knows nothing about it

The most uncomfortable table on this page. Here is what three parties saw during the same five seconds.

WhoWhat they see
ApplicationNothing. Zero requests, zero errors, normal latency. Those connections never came out of accept()
Kernel7,372 dropped, 128 queued. It shows up only in the listen queue overflow counter in netstat -s
ClientSeven seconds. With no way to learn why — no RST ever arrived

The key is that no RST is sent by default. The documentation for tcp_abort_on_overflow reads “Enable resetting connections if the listening service is too slow and unable to keep up and accept them” — something you enable is something that is off by default.

So the two sides disagree about the state. The client’s TCP considers the connection established the moment it sends its final ACK. The server application has not received it, and may never. Neither side tells the other.

This page deliberately does not narrate the packets. “Exactly which packet gets dropped” is widely repeated but is not something the man pages establish. What they do establish is three things — it is not delivered, no RST is sent, and a later reattempt may succeed — and those three are all this lab models.

Where the staircase comes from

The interval between retries is set by RFC 6298. Before any round-trip measurement exists, “the sender SHOULD set RTO <- 1 second”, and on each timeout “RTO <- RTO * 2”.

retransmission at 2ᵏ − 1 → 1 · 3 · 7 · 15 · 31 · 63 seconds
And since one more RTO has to expire after the last retransmission, giving up lands at 2⁷ − 1 = 127 seconds.

The RFC does not say how many times to retry. That is the OS’s call, and Linux defaults tcp_syn_retries to 6. The man page then describes that value: “The default value is 6, which corresponds to retrying for up to approximately 127 seconds.”

The spec gives the rule and the man page gives the total. That 2⁷ − 1 = 127 lines up was the check on this model — the staircase is not invented, two documents point at the same number.

So what a client experiences is not the length of the overload but the first step that covers it. The server has already recovered while the client sits waiting for its next retry.

What this model assumes

AssumptionWhat breaks if it fails
One burstArrivals are assumed to stop when the burst ends. In reality the retries themselves can arrive together and form a second burst, pushing the staircase out another step — that is no. 14
Evenly spaced arrivalsReal arrivals clump. Clumped arrivals fill the queue faster at the same average rate
The client follows the staircaseIt is assumed to use the OS TCP retries. An application-level connect timeout (say 3 seconds) means it gives up before the next step — which is often the better outcome
Queue time is pure waitingA connection that waited in the queue is assumed to be served normally afterwards. In practice the client’s own timeout may have passed, which turns it into no. 17’s work nobody is waiting for

In the field

WhereWhat to check
Is it overflowing nowIn ss -lnt, Send-Q is the backlog and Recv-Q is how many are waiting to be accepted right now. Equal means overflowing. For the running total, netstat -s | grep -i listen
Application settingFrameworks default the backlog differently (511, 1024, 100 are common). Setting it above somaxconn is silently capped — check both
Why accept is slowThe cause is not service speed but intake speed. A blocked event loop, a single accept thread, or a GC pause all leave the queue to fill
Deploy timeThe most common way to reproduce it. A fresh instance taking traffic immediately cannot keep up with accept while nothing is warmed up. Add it to the load balancer without a warm-up and you get exactly this picture
Getting it on a graphPut the kernel counters on the dashboard. Watch only application metrics and this event does not exist — the same blind spot as no. 25
Client timeoutsWithout a connect timeout the client hangs for up to 127 seconds. Three seconds and a move to another instance is almost always better — which is where no. 17’s budget story begins
Should the queue be biggerOnly when bursts are short and accept can catch up. Under sustained overload it just means waiting longer before failing — no. 11’s conclusion exactly

If no. 25 was the time the measurement missed, this page is the time before the measurement starts. The server's clock begins at accept(), and all of this happens in front of it.
