Everyone got a second and nobody gets to use one

One second at the gateway, one at the service, one at the DB client. Three layers, each picking a reasonable number on its own. And in that configuration the inner timeouts never fire at all. They expire at 1000ms, 1025ms and 1050ms — the outer layer always gives up first.

Working the dials

DialWhat changes
propagationOn, each layer spends the remaining budget it was handed, not its own default. With nothing left it fails immediately instead of calling at all.
three timeoutsThe value each layer picked on its own. Set them all equal — the ordering in the fire table inverts.
attempts per layerHow many times each layer tries, retries included. It applies to both hops, so calls to C go up to the square of this.
share of slow CC answers in either 65ms or 1.2s. This slider is the share of the latter.
C's slownessPersistent means this request is slow again if you retry it (overload, a slow query, a hot partition). Transient means the next attempt gets a different answer (a dropped packet, a brief pause).

The vertical blue line is the moment the client gives up. Everything in the hatched region to its right is work nobody is waiting for. The dashed red lines are where each layer's timeout fires. A dashed line to the right of the blue one means that timeout never gets a chance to fire.

The meters are not samples. Because C's latency is reduced to two points (65ms and 1.2s), every path is enumerated and probability-weighted, so the numbers are exact expectations. The same dial settings always produce the same figures.

Try this

1. One second each, no retries — the ordering is backwards

client→A 1.0s · A→B 1.0s · B→C 1.0s fires at 1000ms / 1025ms / 1050ms promises it cannot keep 1.00 per request (every call)

Each hop costs 25ms. An inner layer receives the request that much later, so its timer starts that much later and fires that much later. The outer layer always gives up first, so the inner timeouts never get a chance. The second B gave C is longer than B itself is willing to wait — a promise it cannot keep, and in this configuration every call is one.

2. Three attempts — the success rate does not move one decimal

attempts per layer 1 → 3 success 90.0% → 90.0% calls to C 1.00 → 1.80 · started after the deadline 0.00 → 0.80 one slow request: 9 calls to C · 5 at once · last one ends at 5.28s

All 0.80 of the added calls start after the client is gone. Only the first attempt can possibly contribute to the success rate. A request given one second works inside the system for 5.28 seconds, at one point calling C five times concurrently — no. 14 covers how that waste takes capacity down.

3. Raise the budget to three seconds — 100% with no retries at all

all three values 3.0s · 1 attempt success 90.0% → 100.0%

C's tail is 1.2s. A one-second window can never catch it and a three-second window always does. What moved the success rate was not the retry — it was where the timeout cuts the latency distribution.

4. Split the same three seconds into one second, three times — 100% down to 90%

B→C 3.0 → 1.0s · attempts 1 → 3 (budget still 3s) success 100.0% → 90.0% calls to C 1.00 → 1.80 · mean answer 329 → 1099ms

Turning retries on cost 10.0 points of success rate. A response that takes 1.2s is missed all three times through a one-second window. The same budget spent in one go would have caught it. Retries do not create time; they divide it.

5. If the slowness is transient — 99.9% from the same settings

C's slowness persistent → transient (rest as in 4) success 90.0% → 99.9% · calls to C 1.80 → 1.11

Whether a retry earns its keep depends on whether the failure carries into the next attempt. A dropped packet or a brief GC pause does not; overload, a slow query and a hot partition do. And you pay for narrowing the window either way — the difference between 4 and 5 is only whether there is any return on it.

6. Step them down by hand — the ordering comes right, and then

client→A 1.0s · A→B 0.9s · B→C 0.3s · 3 attempts fires at 1000 / 925 / 350ms — the ordering is right promises it cannot keep 1.80 → 0.30 but started after the deadline 0.50 · success still 90.0%

The values are now small enough that the inner layers give up first, and the retries actually fire. What is left is A's retry — A sends its second attempt at 925ms, and the client leaves at 1000ms. A has no way to know that. What you can choose by hand is a value, and a value cannot tell you how many milliseconds are left right now.

7. Turn on deadline propagation — same success rate, a fraction of the work

setting 1 (all 1s, 3 attempts) with propagation on success 90.0%, unchanged calls to C 1.80 → 1.00 · started after the deadline 0.80 → 0.00 promises it cannot keep 1.80 → 0.00 mean answer 499 → 294ms · a failing request answers at 3.05s → 1.00s

The budget C receives is not 1000ms but 900ms — the client deadline minus the hops the answer still has to cross. A's second attempt never leaves at all, because there is no budget for it. And the success rate did not move one decimal. That is not a coincidence.

Why the inner timeout cannot fire

A timeout is measured from the moment the caller sends. So an inner layer's timer always starts later. If all three values are t, they fire like this.

Who set itFires at
client → At
A → Bt + 1 hop — later than the client
B → Ct + 2 hops — later still
When the layer timeouts are equal, the inner ones structurally cannot fire. They are in the config file and the code does run, but the outer layer always gives up first, so the result is the same whatever the value is. It is dead configuration.

The time actually available is shorter still. C's answer has to cross six hops to reach the client, so out of a one-second budget C has 850ms to work in. The value C was told is one second. That gap is C building an answer nobody will receive.

Propagation does not raise the success rate

This is the sharpest turn on the page. Three timeouts, three retry depths and two kinds of slowness give 750 combinations, compared exhaustively.

Propagation raised the success rate in 0 combinations and lowered it in 0. All 750 matched to the decimal. What it did change: mean calls to C 1.16 → 1.08, started after the deadline 0.06 → 0.00, orphaned answers 0.044 → 0.000.

That is not luck, it is the arithmetic. Without propagation, getting C's answer at all requires the latency to land inside tC − 2 hops; for that answer to be useful it must also reach the caller before its deadline, so inside deadline − sent − 3 hops. The budget propagation hands down is exactly deadline − sent − 1 hop, which makes the success condition literally the same expression as the second one.

The only thing propagation cuts off is an answer that was going to be discarded. Which is why it cannot raise the success rate, and cannot lower it.

So propagation is not a success-rate mechanism but a cost and honesty mechanism. It buys the same success rate with a bit over half the work, and it reports failure at 1.00s instead of 3.05s. For the first time the downstream service can know that it is already late — and knowing that, it can decline to call, which hands that capacity to a request whose deadline has not passed. Same story as rejection being a signal in no. 11.

Three values that cannot all hold

The default configuration contains three numbers that contradict each other.

ValueWhat it demands
budget 1sTake out six hops (150ms) and the real working window is 850ms
tail 1.2sCatching a slow response needs a window of at least 1.25s
3 attemptsFor retries to fire at all, the layer timeout must be a third of the window ≈ 283ms

There is no way to catch a 1.2-second response through a 283ms window. The more retries you add the narrower the window gets, and the narrower it gets the more reliably the tail is cut off. One of the three has to change.

What you changeIn the lab
raise the budgetThe floor is tail 1.2s + six hops = 1.35s. All three set to 1.3s gives 90.0%; 1.4s gives 100.0% (one attempt). The cost is longer occupancy, so less capacity — Little's law, as in no. 8
cut the tailMake C faster, cache in front of it, or attach a fallback to the slow path. The only direction that genuinely raises the success rate
give up the retriesIf the slowness is persistent, retries only eat budget. In the lab: persistent 90.0% vs transient 99.9% — that gap is the entire case for turning retries on

Out in the field

WhereWhat to check
gRPCThe deadline propagates automatically in the grpc-timeout header, and the server can read what is left with Context.current().getDeadline(). Leaning on this is the cheapest path there is
HTTPThere is no standard header, so you carry it yourself. An absolute instant requires clock sync; a remaining-milliseconds value loses the hop latency spent carrying it. Neither is exact, so subtract a margin
connect vs readSetting connectTimeout and leaving readTimeout unset is common. Connecting fine and then not answering is what most outages look like, so this is the same as having no timeout
JDBCWithout socketTimeout (or the driver's equivalent) a query can hang indefinitely. @Transactional(timeout) cuts a query-cancel request, not the whole request — and if the socket is dead that cancel does not get out either
RestClient · WebClientSome combinations default to unlimited. If you did not set it, assume it is not there. Time spent waiting for a pooled connection is a separate item — it does not count against the read timeout
layer orderingIf you cannot get propagation in, then at minimum inner values must be smaller than outer ones. Equal values make the inner ones dead configuration. Values alone still leave A's retry blind, though (recipe 6)
measuringDo not just count timeouts. Count "calls that started after the caller had already left" — that is what makes this visible. A correlationId on the request plus its start time is enough to compute it

If no. 14 was how capacity collapses when work continues after everyone gave up, this page is why that work starts in the first place. Each layer's number was reasonable on its own, and the moment they multiplied they contradicted each other.
