The fields add up and the size does not

You wrote the parser from the header file. The field sizes add up to 16 bytes and the actual data is 24. Get one offset wrong and every field after it shifts. The resolution comes out nonsensical and so does the frame rate — not one field looking odd, but everything from the middle onward.

Working the dials

DialWhat changes
field orderAs declared and largest first are the same five fields in a different order. Compare the sizeof.
alignment rulepack(1) removes padding and pack(4) caps alignment at 4. The same fields give 24, 20 and 16.
array elementsHow many to read back to back. With one, the drift is zero — which is why this bug passes its test.

The fields are u8 type, u32 width, u16 shape, u8 flag, u64 ts. On the ruler, red hatching is padding between fields, yellow hatching is padding at the end of the struct, and a red outline marks the fields that land wrong if you compute offsets by adding sizes.

Try this

1. As declared — the sum is 16 and sizeof is 24

field order as declared · ABI default alignment sum of field sizes 16 · sizeof 24 · padding between fields 8 first misplaced field width — really at @4, naively @1

type takes one byte, so the next free offset is 1. But a u32 width has to sit on a multiple of 4, so three bytes are thrown away and it goes to 4. Five more are thrown away before ts. A parser that adds sizes reads width at offset 1, and the four fields after it are all shifted. Look at the lower row of the ruler — once the two rows diverge they never meet again.

2. Put the large ones first — the same fields in 16 bytes

field order as declared → largest first (fields unchanged) sizeof 24 → 16 · padding between fields 8 → 0 first misplaced field none

Not a single field changed — only the order, largest first. Padding goes to zero and eight bytes disappear. Put the big alignments first and the smaller fields that follow land on already-valid offsets. In this order adding sizes happens to give the right answer — happens to. Add one field and it breaks again.

3. pack(1) — the padding goes away, and so does something else

field order back to as declared · alignment pack(1) sizeof 24 → 16 · padding 8 → 0 · struct alignment 8 → 1

Force the padding out and the sum matches sizeof. The parser gets easy. The price is unaligned access — depending on the architecture that is slower (x86), or a fault (some ARM configurations), or the compiler quietly splitting it into byte-wise reads. Taking the address of a packed member can be undefined behaviour. It is a common choice for protocol structs, but it is not free.

4. pack(4) — a third size from the same fields

alignment pack(1) → pack(4) sizeof 20 (ABI default 24 · pack(1) 16) padding between fields 4 · first misplaced width

Capping alignment at 4 shrinks the padding before ts from five bytes to one. The same field list has three different sizes depending on the alignment rule. And that rule is not in the header file — it is in a compile flag or a #pragma pack, and failing that it is the ABI default.

5. A layout with trailing padding — sum 13, sizeof 24

field order trailing padding (u32 width · u64 ts · u8 flag) · ABI default sum 13 · sizeof 24 · between fields 4 · trailing 7

The last field writes one byte at offset 16 and sizeof is 24, because the struct's alignment is 8 and the end is rounded up to a multiple of it. Those seven bytes are not a field and hold no value. And in an array they become the element stride.

6. Read it as an array — the first element is fine and the second is not

array elements 1 → 3 (trailing-padding layout) n=1 drift 0 · n=2 drift 11 · n=3 drift 22 · n=8 drift 77

This is the frightening part. With one element the drift is exactly zero — the first element starts at offset 0 and every field reads correctly. So a test built from a single sample passes. From the second element it slips 11 bytes each time, and at eight elements it is 77 bytes out. It breaks in production, on the day more than one arrives.

7. Fix the layout and the array is safe too

field order trailing padding → largest first (3 elements) sizeof 24 → 16 · trailing padding 7 → 0 · array drift 22 → 0

Putting the large fields first drives the padding to zero and the array drift with it. But this only worked out for the current field list — add a field or change the order and it breaks again. A parser that computes offsets by hand will be wrong eventually.

Once one field shifts, every field after it shifts

This is the property that makes the bug hard to find. The error is not local.

Read one field at the wrong offset and everything from that field to the end is wrong. The symptom is not "the resolution looks off", it is "everything from the middle on looks off" — and then you cannot work backwards from the symptom to the field that caused it.

Which is why the way this actually got solved was to stop guessing, dump the received bytes to a file, and derive the offsets from real data. Rereading the header a few more times does not get you there.

Layout is decided by the ABI, not by the language standard

Here is why the header file cannot answer the question. Worth separating the kinds of evidence.

ClaimKind of evidence
Padding may appear between members and at the end of a structThe C standard permits it. It does not specify the rules
Each type aligns to its own size, a struct's alignment is the maximum of its members', and sizeof is a multiple of thatABI rules. True on x86-64 and AArch64; another ABI or another compiler configuration can differ. The lab models these rules
How bit-fields are laid outFar more implementation-defined. Bit order and storage-unit boundary handling vary by compiler, so this lab does not model bit-fields at all
In other words, a header file alone cannot pin down the layout. The same declaration produces different byte arrangements across compiler, architecture and pragma combinations. Which is what makes real data the only usable evidence.

Java will not insert the padding for you

Porting a C struct to Java has one more trap in it, and the java.lang.foreign MemoryLayout documentation is explicit about it.

WhatWhat the documentation says
automatic paddingThere is none. "This factory does not automatically align element layouts, by inserting additional padding layout elements" — so structLayout(JAVA_SHORT, JAVA_INT) fails with an IllegalArgumentException
how to fix itWrite the padding yourself, as in structLayout(JAVA_SHORT, MemoryLayout.paddingLayout(2), JAVA_INT), or lower the alignment with JAVA_INT.withByteAlignment(2)
struct sizeIt is the plain sum of member sizes — "S1 + S2 + ... + Sn". Meaning no trailing padding is added for you
natural alignment"The natural alignment of a value layout whose size is N is N" — the size is the alignment

An alignment violation at least throws, which is the good case. The dangerous one is trailing padding — leave it out and nothing throws, the size just quietly gets smaller. Read an array with that layout and recipe 6 replays exactly. And it passes with one element.

When the size differs by version

Sometimes the same struct has a different size depending on firmware version, because fields were added.

ApproachOutcome
Branch on a version fieldIf the version field is inside the struct, you need the layout to read it. That is circular
Identify the layout by the received lengthThis works. When each version has a different total size, the length is the identifier. Set the minimum-length check against the smallest version
If two versions share a lengthThe method collapses. Then the protocol needs a version marker outside the struct, and that is something to negotiate

Out in the field

WhereWhat to check
do this firstDump the received bytes to a file and print them as hex. It is faster than rereading the header. Find a value you already know — a resolution, say — and work the offsets back from it
golden-file testsPin a sample input and its expected output. With two or more elements — one element lets the trailing-padding bug through
never hand-write offsetsMake the offsets computed from a field list, with the alignment rule in the calculator. Offsets baked in as constants are all wrong the day a field is added
assert the total sizePut assert sizeof == expected in the parser. It is the cheapest single line that tells you the layout is wrong
Java FFMIt inserts no padding. Alignment violations throw, but missing trailing padding is silent — add a test that compares your struct size against the C-side sizeof
using packThe parser gets simpler and you get unaligned access. Depending on the architecture that is slower or a fault, and taking the address of a packed member is dangerous
byte orderThis page only covers alignment. Endianness is a separate problem and the two together are more confusing — if the offsets are right and the values are strange, look at endianness
