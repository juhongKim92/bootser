The load test never counted the 30 seconds it was frozen

During a five-minute load test the server stopped answering entirely for 30 seconds. The report that came out afterwards put p99 at 10ms. Its p99.99 was also 10ms. Measure the same event another way and it is 27.01 seconds. Both measured honestly. One of them simply never counted those 30 seconds.

Work the dials

DialWhat it changes
How it measuresClosed waits for a response before sending the next request — that is what most load tools do. Open keeps sending at the target rate regardless. Corrected measures closed-loop and then fills the missing samples back in.
Server frozen forRequests arriving in this window all get their answer after the freeze ends. Set it to 0 and every percentile in all three modes becomes identical — the difference exists only inside this window.
Test durationTotal length. This is the dial that sets the size of the distortion — not the load. The longer the run, the more optimistic the closed loop gets.
WorkersConcurrency in the generator. The target rate is workers ÷ normal response, so this dial is the load. Turn it — the distortion does not move one digit.
Normal responseWhat the server answers in when healthy. It is also the expected interval the correction uses, since that is how often one worker should be issuing.

Percentiles here use nearest rank: sort the n samples and take the ceil(q × n / 100)-th. No interpolation. Pinning one method and saying so matters because if values differ at the boundary, this page turns into an argument about percentile arithmetic instead of about sampling.

There is no randomness. Arrivals are evenly spaced and service time is constant, so every latency is determined and all three modes come out of closed-form expressions — no samples are generated and sorted.

Things to try

1. Set the freeze to 0 — all three are identical

Server frozen for 0s p50 · p99 · p99.9 · p99.99 · max all 10ms (in all three modes)

Start here, because it matters. In the healthy region the three modes cannot be told apart. The closed loop is not wrong in general — it diverges only while the server is frozen. Which is exactly why nobody discovers this on an ordinary day.

2. Freeze it for 30 seconds — even p99.99 misses it

Server frozen for 0 → 30s (closed loop) p99 10ms · p99.9 10ms · p99.99 10ms max 30.01s · samples 270,010

The server was completely dead for 10% of the test and not one percentile moved. Only as many requests were caught in the freeze as there are workers — 10 of them. Ten samples out of 270,000 do not reach p99.99. The “first visible at” meter is telling you it takes p99.996.

3. Switch to the open loop — the same event is 27.01s

How it measures: closed → open p99 10ms → 27.01s (2,701×) · p99.9 29.71s samples 270,010 → 300,000 · first visible at p99.996 → p90.0

The open loop keeps sending 1,000 per second whether or not the server answers. Thirty thousand requests pile into the freeze, and all thirty thousand become samples. Look at the closed-loop row on the timeline — that window is hatched. The closed loop did not mismeasure anything; it measured nothing there.

4. Turn on the correction — measure closed, then undo it

How it measures: open → corrected (measurement is still closed-loop) p99 27.01s — identical to the open loop samples 270,010 → 300,010 (30,000 records filled in)

If a stuck sample is 30.01s, then with an expected interval of 10ms it becomes 30.01s, 30.00s, 29.99s … — reconstructing what each request that never went out would have waited. This is not an approximation, it is an inversion: it lands on the value the open loop actually measured.

5. Five times the load — the distortion does not move

Workers 10 → 50 (1,000 → 5,000 rps · closed loop) Reported p99 still 10ms · first visible at still p99.996 Only the sample count moves: 270,010 → 1,350,050

This is backwards from intuition. Hit it harder and surely more requests land in the freeze — but the number caught grows with the workers and so does the total, and the two cancel. The bad-sample fraction is normal response ÷ (test duration − freeze), and load does not appear in it.

6. Shorten the test — now it shows up

Test duration 300 → 60s (closed loop · freeze still 30s) p99.99 10ms → 30.01s · first visible at p99.996 → p99.967 Stretch it to 600s and it becomes p99.998 — buried deeper

The exact opposite of “run it longer to be accurate”. The freeze happened once and the number of stuck samples is fixed at the worker count, so a longer run only piles up more healthy samples to dilute those ten. The same outage hides better the longer you test.

7. A 3-second freeze — even the open loop misses it at p99

Server frozen for 30 → 3s (open loop) p99 10ms — invisible · p99.9 2.71s · max 3.01s

The open loop is not magic. If the freeze is shorter than 1% of the test, it will not show at p99 there either. The difference is that with the open loop which percentile to look at is computable from the sample counts — here, anything past p99.0.

Why the closed loop cannot count that window

Most load tools have each worker send its next request only after a response arrives. Normally that is fine: the server answers in 10ms, so one worker issues 100 per second and ten workers give 1,000 per second.

Then the server freezes for 30 seconds and all ten workers freeze with it, in place. Ten requests went out during those 30 seconds, and after that, nothing. The 29,990 requests that should have existed never happened — and a request that never happened cannot be recorded as slow.

This is coordinated omission: the load generator keeps time with the server, taking its break precisely while the server is slow. In wrk2’s words — “each connection will only begin to send a request after receiving a response, high latency responses result in the load generator coordinating with the server to avoid measurement during high latency periods.”

So this is a sampling problem, not an accuracy problem. Nothing was measured incorrectly; nothing was measured at all. No amount of extra samples, and no amount of extra runtime, brings back a sample that was never taken.

The maximum is the same in all three

This is the most uncomfortable column on the page. Look at max.

Modep99max
closed10ms30.01s
open27.01s30.01s
corrected27.01s30.01s

All three maxima are exactly equal. So “we did look at the max — there was one 30-second outlier, probably noise” is available to you. It was not an outlier. It was 30,000 people, and the closed loop brought back ten of them.

The maximum tells you an event happened. Percentiles tell you how many people it happened to. Coordinated omission leaves the first intact and erases the second.

For the same reason, the closed loop’s tail has no shape. Below its threshold everything is 10ms; the instant it crosses, the value is the maximum — there is nothing in between. The open loop does have that in between (p99 27.01s, p99.9 29.71s, p99.99 29.98s). Read the table across and the closed row is a single step: 10ms · 10ms · 10ms · 30.01s.

So a closed loop can tell you “it was bad / it was not” and never “how bad”. The shape of a tail is made by the requests actually sent during the freeze, and the closed loop has only as many of those as it has workers.

What the correction does — straight from the source

HdrHistogram ships this correction as an API: recordValueWithExpectedInterval(value, expectedInterval). What it does is right there in the source.

recordSingleValue(value);
if (expectedIntervalBetweenValueSamples <= 0) return;
for (long missingValue = value - expectedIntervalBetweenValueSamples;
     missingValue >= expectedIntervalBetweenValueSamples;
     missingValue -= expectedIntervalBetweenValueSamples) {
    recordSingleValue(missingValue);
}

Record the value, then keep subtracting the expected interval, filling back the samples that should have been there. One 30.01-second sample with a 10ms interval becomes floor(30010 / 10) = 3,001 records. Ten stuck samples become 30,010 — near-exactly the 30,000 the open loop actually measured.

The correction is reconstruction, not estimation. Assume only that requests should have gone out at a fixed interval, and what each blocked request would have waited is computable — count backwards from the moment the freeze ends.

That said, a filled-in record is not a measurement. That is why this lab draws the corrected row in a different colour. Keeping “measured” and “reconstructed” visually apart is worth the ink.

A real measurement confirms the formula

wrk2’s documentation includes an actual measured run: 100 connections, 30 seconds, 2,000 rps, with Apache suspended by ^Z for 1.4 seconds.

Measurementp90p99p99.9max
corrected11.77ms1.27s1.42s1.42s
uncorrected4.87ms6.04ms1.41s1.41s

Three things are visible. The maxima are effectively the same (1.42 vs 1.41s), the p99s differ by 210×, and the uncorrected run does eventually show it at p99.9.

That last one is the interesting part. Feed those settings into this lab’s “first visible at” formula — 100 × healthy samples ÷ total samples — and it returns p95.3 for the corrected run and p99.83 for the uncorrected one. That matches the published output exactly: corrected is healthy at p90 (11.77ms) and frozen at p99 (1.27s); uncorrected is healthy at p99 (6.04ms) and frozen at p99.9 (1.41s).

The formula predicts which column flips, from the published numbers alone. That is the evidence this model is a checked mechanism rather than an inherited story. The 1.27s and 6.04ms above are wrk2’s measurements, not this lab’s output.

What this model assumes

AssumptionWhat breaks if it fails
Everything drains at onceBlocked requests are treated as all answered the instant the freeze ends. A real server drains its backlog at a finite rate, so the tail is longer — that is no. 11 and no. 14 territory. This model understates by that much
Two valuesThe server answers in 10ms or it is frozen, nothing between, which makes percentiles a staircase. Real distributions fill in that gap
Workers issue togetherThe workers’ send times inside the freeze differ by less than one normal response, and that difference is ignored (10ms inside a 30-second freeze)
One freezeWith several short freezes the closed loop catches one worker-count each time. The fraction is still freezes × workers ÷ total samples, which stays small

In the field

WhereWhat to check
Your toolFirst: does it support a fixed rate (open loop)? wrk2 takes a target rate with -R and measures latency from the intended send time. The original wrk, and most closed-loop tools, measure from the actual send
Reading the reportDo not stop at p99 — multiply the target rate by the duration and compare it to the sample count. Fewer samples than rps × seconds means the shortfall is exactly the window you failed to measure
Which percentileIt follows from the counts. If k samples were missed out of n, nothing below p(100 − 100k/n) is worth reading. That is what the “first visible at” meter is
Production metrics tooThis is not only a load-testing problem. Server-side latency is measured from when the request is picked up, so time spent waiting in the accept queue or the thread pool never enters it — no. 8’s hold time disappears right here
Queue wait especiallyCheck whether the timer starts at accept or at handler entry. The gap between them is the value that vanishes entirely when the queue grows in no. 11
HdrHistogramIf you already use it, switching to recordValueWithExpectedInterval is the whole change. The expected interval is how often one worker should issue — the target rate divided by the worker count

No. 22 was one event that two aggregation paths counted differently — and both were right. This page is not that. One side never saw the event at all. No amount of agreeing on the arithmetic brings back a sample that does not exist.
