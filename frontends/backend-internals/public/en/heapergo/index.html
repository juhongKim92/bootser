You doubled the container memory and the heap did not move

You got OOMKilled, so you took the container from 250MB to 500MB. And the maximum heap stays at 126MB — not one byte more. The plateau runs from 249MB to 504MB, and what creates it is a twenty-year-old 96MB default that has nothing to do with containers. Confirmed by asking the JVM 62 times.

The dials

DialWhat it changes
Container memoryThe cgroup limit. The JVM treats it as physical memory — -XX:MaxRAM is where that value stands in. Walk it through 249–504MB.
How the maximum is setErgonomics is the JVM deciding for you (the default); the others set -Xmx to a share of the container. Set it yourself and all the arithmetic below disappears.
MaxRAMPercentageThe share used on large memory. Default 25 — which means a 1GB container gets a 256MB heap.
MinRAMPercentageThe share used on small memory. Default 50, and this value sets the left edge of the plateau.
Off-heap actually usedWhat metaspace, code cache, thread stacks and direct buffers really consume. This number is not specified anywhere — it is an input we supplied, and one you have to measure in your own environment. Raise it until the spare goes negative and you land on OOMKilled.

Every value is determined — no randomness, no sampling. The maximum heap agrees with what the JVM actually printed at 62 points (Temurin 25.0.4.1+1).

Things to try

1. 128MB — half of it goes to the heap

container 128MB · ergonomics · Max 25% · Min 50% heap 64.0MB (50.0%) · initial heap 2.0MB · spare 4.0MB

On small memory it uses MinRAMPercentage, 50% — the branch whose source comment reads "Small physical memory, so use a minimum fraction of it for the heap". That the spare is only 4MB is already a warning, and step 7 comes back to it.

2. 249MB — the plateau begins here

container 128 → 249MB heap 126.0MB (50.6%) · double it (498MB) and the heap gains 0MB

The heap reached 126MB — and from here, doubling the container still gives you 126MB. Half of 249MB is 124.5MB, the ceiling sits at 124.8MB, so they have nearly met; the 2 MiB alignment rounds it up to 126MB. Everything above this hits that same ceiling. This one meter is the whole page.

3. 504MB — past double, and still 126MB

container 249 → 504MB (more than double) heap 126.0MB · ratio 50.6 → 25.0% · spare 318.0MB

More than twice the memory. The heap did not gain a byte; only the ratio halved. That is the dots sliding down the chart — the heap holds a horizontal line while the ratio keeps falling. And 318MB sits there with nobody using it.

4. 512MB — eight more megabytes and it finally moves

container 504 → 512MB (just 8MB more) heap 126.0 → 128.0MB · doubling now gains +128MB

25% of 512MB is 128MB, which finally clears the 124.8MB ceiling. Past the plateau the percentage does what it promised — from here, double the container and the heap doubles. The plateau's right edge is 126 ÷ 25% = 504MB.

5. 1024MB — what the default really looks like

container 512 → 1,024MB heap 256MB (25.0%) · spare 708MB

A 1GB container gets a 256MB heap. Metaspace, code cache and thread stacks will not use the remaining 768MB — with this lab's default of 60MB, 708MB is left over. 25% is a very conservative number, and it is why most containers waste memory.

6. MaxRAMPercentage to 75 — spend the idle memory

Max 25 → 75% (container still 1,024MB) heap 256 → 768MB · spare 708 → 196MB

The idle memory goes to the heap. And the plateau disappears — at 75% the ceiling is cleared by 167MB, so there is no room for a plateau at all. Raising the percentage is not only about a bigger heap; it removes the plateau. Whether 196MB covers your off-heap needs is something you have to measure.

7. Off-heap to 800MB — OOMKilled

Max back to 25% and off-heap 60 → 800MB heap 256MB + off-heap 800MB = 1,056MB · spare −32MB

The heap never exceeded its maximum. There is no OutOfMemoryError. The cgroup kills the process — no heap dump, no stack, not one trace on the Java side. The logs are clean and the pod restarts. And the usual response is to grow the container, which does nothing if you are sitting in the range from steps 2 and 3.

The formula is one line

All of it lives in Arguments::set_heap_size() in OpenJDK's arguments.cpp.

if (FLAG_IS_DEFAULT(MaxHeapSize)) {
  julong reasonable_max = phys_mem * MaxRAMPercentage / 100;
  const julong reasonable_min = phys_mem * MinRAMPercentage / 100;
  if (reasonable_min < MaxHeapSize) {
    // Small physical memory, so use a minimum fraction of it for the heap
    reasonable_max = reasonable_min;
  } else {
    // Not-small physical memory, so require a heap at least as large as MaxHeapSize
    reasonable_max = MAX2(reasonable_max, (julong)MaxHeapSize);
  }

Which comes to this.

heap = align_up( max(RAM × Max%, min(RAM × Min%, 124.8MB)), 2 MiB )

The min in the middle is what makes the plateau. And where that 124.8MB comes from is the strangest part of this page.

The plateau is a 96MB default

Four lines in gc_globals.hpp are all the constants this episode has.

FlagDefault
MaxRAMPercentage25.0
MinRAMPercentage50.0
InitialRAMPercentage1.5625
MaxHeapSizeScaleForWordSize(96*M) = 124.8 MiB

The last line is the ceiling. It is the default value of MaxHeapSize — not a percentage, nothing to do with containers, just 96MB scaled by 1.3. The intent behind the comment "require a heap at least as large as MaxHeapSize" was keep the heap from being too small on a big machine; in the container era it works in the other direction and keeps the heap from getting large.

So both edges of the plateau come out of that constant. The left is around 124.8 ÷ 50%, the right is 126 ÷ 25% = 504MB. Turn the two dials (Min and Max) and the plateau widens, narrows, and can vanish entirely — which is step 6.

Why 249MB yields 126MB

Half of 249MB is 124.5MB. That is below the 124.8MB ceiling, so it takes the "small physical memory" branch and comes out as 124.5MB. Yet the screen says 126MB.

Heap alignment — it rounds up in 2 MiB steps. Confirmed by measurement, and invisible if you only feed it even megabytes. You have to try odd ones.

Always upward. Which is why this lab finds the plateau's edges by scanning rather than solving — solving 124.8 ÷ percentage gave 250–499MB, while the measurement says 249–504MB. The alignment nudges both edges by a step.

The checkpoint is a generator, not a table

Other episodes on this site check against a table the documentation handed over — no. 26 used RFC 6928's round-trip counts, no. 27 the man page's "about 127 seconds". This one is different.

The JVM prints the answer for any input.
java -XX:MaxRAM=249m -XX:+PrintFlagsFinal -version | grep MaxHeapSize
So instead of matching a finite table you can compete with the generator — across the whole range of the dial.

That output is captured at 62 points and committed (tools/heap-fixture.mjs). The checks compare against that fixture, so they run without a JDK. It was captured on both Temurin 25.0.4.1+1 and Zulu 17, and every point agreed.

What this model assumes

AssumptionWhat breaks if it fails
the ceiling and the alignment are not specifiedScaleForWordSize(96*M) and the 2 MiB alignment are implementation, not specification — they appear in no document. A new JDK could change them, and then the fixture has to be re-captured; that procedure is kept as tools/gen-heap-fixture.mjs
MaxRAM equals the cgroup limitIn a real container os::physical_memory() returns the cgroup limit and it feeds the same formula. But setting MaxRAM explicitly enables a branch that skips the compressed-oops cap, so near 32GB it can diverge from a real container. Within this lab's range (64MB–8GB) it does not matter
off-heap usage is a number we suppliedMetaspace, code cache, thread stacks, direct buffers and the JVM's own footprint differ per application. This is the one number that could not be in any specification — it is a dial, and the page says to go measure it
the collector is not distinguishedAlignment can depend on the collector. The measurements were taken with the default (G1); ZGC may differ — no. 2 covers how those two differ

In the field

WhereWhat to check
First thing to look atWrite down the container limit and the maximum heap side by side. Run java -XX:+PrintFlagsFinal -version | grep MaxHeapSize inside that container and you are done — nothing to guess. If the ratio is not near 25%, you are on the plateau
When you get OOMKilledDo not go looking for a Java trace. There is none. Reason: OOMKilled in kubectl describe pod and exit code 137 are the only evidence. The absence of a heap dump is itself the signal that it was off-heap, not the heap, that overflowed
Order of fixes① set -XX:MaxRAMPercentage explicitly (somewhere near 75) — that removes the plateau and spends the idle memory ② measure off-heap and decide how much to leave ③ growing the container comes last, because inside the plateau it does nothing
-Xmx or the percentage?-Xmx makes all this arithmetic vanish (FLAG_IS_DEFAULT(MaxHeapSize) becomes false). But then you have to change it every time the container size changes. A percentage follows along — which is why the percentage wins in containers
Small containers are the dangerous onesA 256MB sidecar or batch job sits in the middle of the plateau. At that size doubling the container leaves the heap unchanged, which is where "we gave it more memory and it did not help" reports come from
Look at the initial heap tooInitialRAMPercentage is 1.5625% — a 1GB container starts at 16MB. Growing the heap all through warm-up means frequent GC. Setting -XX:InitialRAMPercentage equal to Max removes that stretch

Where no. 2 was about what happens inside the heap, this page is about how that heap's size gets decided — and that there is a range where the answer is not proportional to the container. That is the whole episode.
