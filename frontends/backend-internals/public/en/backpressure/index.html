Rejection is a signal, not a bug

RejectedExecutionException is flooding the logs. Remove the queue bound and it goes quiet. Then, minutes later, OutOfMemoryError — you did not remove the rejection, you traded it for an OOM.

Drive it yourself

One task takes 120ms. There are 8 cores. Those two numbers set your capacity.

controlwhat happens
producedHow many tasks per second enter the queue
consumer threadsHow many run concurrently. The effect depends entirely on the work type
work typeI/O wait (capacity = threads ÷ 0.12) / CPU · external process (capacity = min(threads, 8) ÷ 0.12)
queue policyWhat to do when it fills. The subject of this page
queue boundGreys out when unbounded

Things to try

1. Start inside capacity

50/s produced · 8 threads · I/O · bounded+Abort capacity 66.7/s queue around 0 rejected 0

Produce less than capacity and nothing queues up. The policy makes no difference at all. Cycle through all three and the screen is identical. Queue policy only starts to mean something once load exceeds capacity.

2. Raise production to 200/s

200/s produced · 66.7/s capacity queue stops at 500 rejected 133.3/s ← 133 tasks a second are dropped throughput 66.7/s

The queue fills in 3.8 seconds and rejection starts. The logs go red. But this is the system telling you the truth — that 200 are arriving where only 66.7 can be handled.

Look at completed tasks in the rejection panel. If that number is not climbing, consumption is not progressing at all, and that is not a queue problem — it means the consumer is blocked somewhere.

3. Make the queue unbounded — silence

unbounded queue rejected 133.3/s → 0 queue 500 → climbing heap 0 → 512MB OutOfMemoryError after 15.4s

The exception is gone. The logs are clean. And the queue grows by 133 a second, eating the heap. Fifteen seconds later the process dies.

All that changed is how the failure presents. Rejection tells you which task failed and when; an OOM kills the whole process and points its stack at whatever innocent code happened to ask for memory next.

4. Switch to CallerRuns

bounded + CallerRuns rejected 0 queue steady at 500 throughput 66.7 → 75.0/s (the producer pitches in) produced 200 → capped at 75.0/s

No rejection and no OOM. When the queue is full the producer thread runs the task itself, and while it does that it cannot produce anything new. That is backpressure — pushing back by slowing down.

Not free, though. Production dropped from 200 to 75. No work was lost, but uploads are now nearly three times slower. That is the honest outcome, and it is right that users see it.

5. Raise threads to 32 — works for I/O

I/O wait · threads 8 → 32 capacity 66.7 → 266.7/s queue 500 → 0

For work dominated by waiting, like an S3 upload, capacity grows with the thread count because those threads spend most of their time idle on a response. This is exactly where virtual threads earn their keep.

6. Change only the work type to CPU · process

still 32 threads, only the type changes capacity 266.7 → 66.7/s ← same as with 8 queue 0 → saturated at 500

Here is the second reversal. Four times the threads and capacity did not move. Spawning FFmpeg or encoding an image genuinely uses a core. With 8 cores only 8 things progress at once, and extra threads simply take CPU from each other.

Throwing virtual threads at this makes it worse. Threads being cheap means the number of concurrent processes explodes, and that is memory and context switching.

7. Drop production to 50/s

CPU work · 8 threads · 200 → 50 produced queue 0 rejected 0 policy does not matter

This is the real fix. Queue policy decides what happens when you overflow, not whether you overflow. Bring production under capacity and the three policies become indistinguishable again — you are back at recipe 1.

How to read a rejection

The exception looks like this, and everything you need is inside it.

Task rejected from ThreadPoolExecutor
  [Running, pool size = 8, active threads = 8,
   queued tasks = 500, completed tasks = 0]
fieldwhat it tells you
pool sizethreads created
active threadscurrently working. Equal to pool size means nothing is idle
queued taskswaiting. Equal to the bound means full
completed tasksthe number that matters most. Not climbing means consumption is not progressing at all

completed tasks = 0 is an especially bad sign. It means the queue is not overflowing because things are slow but because the consumer is blocked — a deadlock, an external call with no timeout, an exhausted connection pool. Enlarging the queue does nothing for that.

Turn rejection into a metric. Stop swallowing the exception, increment a counter and put it on a dashboard, and rejection stops being an incident signal and becomes a capacity signal. "How many are rejected per second" is the same question as "how much capacity are we short".

What each policy trades

policygives upprotects
bounded + Abortdiscards the excessmemory, latency
bounded + CallerRunsthe producer slows downmemory, completeness of work
unboundedthe process—

That third row is the point. An unbounded queue looks like it gives up nothing, but as long as load exceeds capacity it will fill the heap eventually. It defers; it does not prevent.

// bounded + default policy (Abort) — overflow throws RejectedExecutionException
new ThreadPoolExecutor(8, 8, 0L, MILLISECONDS,
        new ArrayBlockingQueue<>(500));

// bounded + CallerRuns — overflow is run by whoever submitted it
new ThreadPoolExecutor(8, 8, 0L, MILLISECONDS,
        new ArrayBlockingQueue<>(500),
        new ThreadPoolExecutor.CallerRunsPolicy());

// unbounded — rejection disappears and an OOM arrives
new ThreadPoolExecutor(8, 8, 0L, MILLISECONDS,
        new LinkedBlockingQueue<>());

The defaults are already unbounded

You can be in this state without ever having written LinkedBlockingQueue, because the standard factory methods are built that way.

factorywhat is unbounded
newFixedThreadPool(n)the queue. Threads are fixed at n; the backlog grows as far as the heap allows
newSingleThreadExecutor()the same. No queue bound
newCachedThreadPool()the opposite — threads are unbounded. There is effectively no queue; it makes a thread per task
newVirtualThreadPerTaskExecutor()a virtual thread per task, with no cap

"Fixed" sounds safe, but the only fixed thing is the thread count. Bounding the queue means constructing ThreadPoolExecutor yourself.

Can't we just add threads?

Recipes 5 and 6 are the answer. It depends on what the work is waiting for.

workadding threadswhy
S3 uploads, external APIs, database readsraises capacitymost of the time is spent waiting on a response; the CPU is idle
image encoding, compression, encryptionup to the core countit genuinely uses CPU. Beyond that they take it from each other
external processes like FFmpegmakes it worseprocess creation cost plus memory. Concurrency is bounded by physical resources

That last row is the classic misuse of virtual threads. Their benefit is releasing the carrier thread while blocked on I/O, and spawning a process through ProcessBuilder gets none of it. What you get instead is an explosion in concurrent processes, because threads became cheap.

Put external process execution behind a fixed-size pool with a bounded queue. Concurrency there is pinned to a physical resource — core count, GPU sessions — not something cheap threads can raise.

The real fix is on the production side

Recipe 7 shows it. Queue policy decides what happens on overflow; it does not stop the overflow. While load exceeds capacity, every policy pays something.

So the order is:

  1. Can production be reduced? Is there a way to get the same result from fewer tasks — this is usually where the answer is
  2. Can service time be reduced? Take a task from 120ms to 30ms and capacity quadruples
  3. Can consumer capacity grow? Subject to the ceiling in the table above, which depends on the work type
  4. Still overflowing? Then backpressure. It makes overflow safe; it does not remove it

Step one is the most overlooked and the most effective. Change spawning one external process per frame into spawning one and streaming the frames out, and the task count drops by a factor of N outright. Then the queue policy stops mattering — you are back at recipe 1.

Using CallerRuns carefully

It is a reasonable default, but know the side effects. They all come from one fact: it blocks the producer.

  • If the producer is an HTTP request thread, that request slows down. Propagating backpressure to the client is usually right, but the request thread pool can be exhausted
  • If the producer is a scheduler thread, every other scheduled job stops while it is busy. Especially dangerous with a scheduler pool size of one
  • Ordering is not preserved — a task the producer runs itself finishes ahead of what is already queued
  • If the producer holds a lock, it now runs a task while holding it. This is where deadlock risk comes from

When any of those bite, bounding in-flight work with a Semaphore is better. The producer waits in acquire(), so the effect is the same and what it is waiting on is explicit in the code.

private final Semaphore inFlight = new Semaphore(500);

void submit(Task task) throws InterruptedException {
    inFlight.acquire();                       // blocks here when there is no room
    executor.execute(() -> {
        try { task.run(); }
        finally { inFlight.release(); }
    });
}

What to check in production

Metrics first. Without them you find out the queue was filling when the OOM lands.

metricwhat it tells you
queue depthpinned to the bound means already saturated. Monotonic growth means an unbounded queue
rejection countthe size of your capacity shortfall. The goal is not zero, it is observed
completed-task rateflat means the consumer is blocked. Not a queue problem
active threads / pool sizeequal means saturated. Low active with a full queue means the block is elsewhere
heap trendrising without a sawtooth means something is accumulating

On Spring, ThreadPoolTaskExecutor exports executor.queued, executor.active and executor.completed through Micrometer already. You only have to name it.

A heap dump makes it obvious. If the OOM already happened, look at the dominators. LinkedBlockingQueue$Node near the top is this page's problem. Check what the queued tasks reference, too — the task object may be small, but holding an image buffer or a request context makes the real footprint far larger.

Load-test above capacity. Below it, all three policies look identical (recipe 1). Validating a policy means deliberately overflowing.

The order. When you find a queue overflowing:

  1. Is completed tasks climbing? If not, the consumer is blocked and this is not about the queue
  2. Compare production rate and capacity as numbers. Without knowing the shortfall you cannot decide anything
  3. Look for a way to produce less first
  4. Touch the queue policy last — and unbounded is not one of the options
This model is simplified for teaching. Service time is fixed at 120ms, cores at 8, and heap per queued task at 256KB; in reality service time has a distribution and the GC moves alongside it. In particular, the OOM timing depends heavily on what the tasks reference — what matters is not the number of seconds but that with an unbounded queue it always comes.
