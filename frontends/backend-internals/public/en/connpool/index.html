A 17-millisecond query drains the pool

A connection leak warning fires. You open the query at the top of the stack and it runs in 17 milliseconds, straight off an index. The pool keeps draining anyway — because that query is not the culprit.

Drive it yourself

Time does not run in this lab either. Move a control and the whole condition is recomputed. Query times are fixed — the queries were fast from the start.

fixedvalue
pre-processing5ms — validation and deserialisation. No database
query 117ms — the query the leak warning names
query 28ms
response render25ms — serialisation. No database

Actual database time is 25ms in every configuration. The only thing that changes on this page is how long the connection is held.

Things to try

1. Start with no external call

OSIV on · 50 req/s · external call 0 · pool 10 hold time 50ms (25ms of it database) connections needed 2.5 utilisation 25%

Nothing is wrong here. OSIV being on does not show when requests are short. Plenty of services live like this happily for years. The trouble starts the moment something slow moves into the request.

2. Add a 300ms external call — one S3 upload

external call 300ms hold time 350ms (25ms of it database — 7%) connections needed 17.5 ← the pool holds 10 capacity 28.6 req/s ← 50 req/s are arriving

Not one query got slower and the pool is dry. Of the 350ms hold, only 25ms — 7% — actually touches the database. The other 93% is spent holding a connection while waiting on S3. That is the hatched band above.

And what shows up in the logs at this point is a connection-acquisition timeout and the leak warning discussed below. Neither of them points at S3.

3. Turn OSIV off — it helps less than you expect

OSIV off (external call still inside the transaction) hold time 350ms → 325ms connections needed 17.5 → 16.25 ← still more than the pool of 10

Turning OSIV off removes the response rendering window — 25ms. And that is all it removes. While the external call sits inside the transaction the connection stays held. This is where it becomes clear that OSIV is only part of the problem.

4. Move the external call outside the transaction

OSIV off + I/O outside tx hold time 325ms → 25ms connections needed 16.25 → 1.25 capacity 30.8 → 400 req/s (13×)

This is the actual fix. Take a connection, run query 1, give it back, go to S3, take one again for query 2. Hold time becomes completely independent of the external call — push the slider to five seconds and it stays at 25ms. Try it.

5. Raise the external call to 3s and read the leak warning

OSIV on · external call 3000ms hold 3.05s → exceeds leak-detection-threshold top of the warning stack the 17ms query 1

Here is the heart of this page. The leak warning names where the connection was borrowed, not where it is being held. The first query borrowed it, so the first query's stack is what got captured. Tune that query all you like and 17ms becomes 16ms while the pool keeps draining.

6. Make the pool five times bigger

OSIV on · external call 300ms · pool 10 → 50 at 50 req/s needs 17.5 → a pool of 50 copes at 200 req/s needs 70 → exhausted again

A bigger pool holds for now. Then load quadruples and you are back in the same place. Without shortening hold time, pool size only buys time — and connections are a database-side resource you cannot grow indefinitely anyway.

Why the top of the stack is not the culprit

HikariCP's leak detection works like this: when a connection is handed out it starts a timer, and if the connection is not returned within leak-detection-threshold it logs a warning.

The important part is that the stack in that warning was captured when the connection was borrowed, not when the timer fired. It has to be — the leak-detection thread has no way of knowing where the holding thread currently is. All it has is the stack it recorded at hand-out time.

Connection leak detection triggered for conn0, stack trace follows
    at com.example.repository.OrderRepository.findByUser(...)   ← the 17ms query
    at com.example.service.OrderService.getOrders(...)
    ...

So whichever query ran first in the request is always the one named. Not because it is slow, but because it is the one that borrowed the connection.

Read the warning backwards. Instead of tuning the query it names, ask "what else did this thread do after it took the connection?" Finding the external call or heavy rendering later in the same request comes first.

OSIV — what the convenience costs

spring.jpa.open-in-view defaults to true. It keeps the persistence context open until the request finishes, so lazy loading still works after you leave the service layer. A genuinely convenient way never to see LazyInitializationException.

The price is connection hold time. While that context is open the connection stays attached, so serialisation and view rendering after the transaction has committed still occupy a slot in the pool.

Spring Boot knows this and warns you at startup.

spring.jpa.open-in-view is enabled by default. Therefore, database
queries may be performed during view rendering. Explicitly configure
spring.jpa.open-in-view to disable this warning

If you have seen that line, it is asking you to turn it off explicitly.

spring:
  jpa:
    open-in-view: false

With it off, lazy loading blows up outside the service layer. That is correct behaviour — it forces you to say what you need at query time. Move it to a DTO projection or a fetch join and your query count drops along the way.

Strictly speaking, exactly when a connection is acquired and released depends on Hibernate's connection.handling_mode. This lab draws the worst case: borrowed at the first query, held to the end of the request — which is also what tends to be observed in production. In your own environment, measure the real hold time rather than assuming.

Little's Law is all you need

Every number on this page comes from one line.

connections needed = requests per second × hold time (seconds)

At 50 req/s with a 350ms hold, 50 × 0.35 = 17.5 connections are needed at the same time. A pool of 10 is not enough. Invert it and you get capacity directly.

capacity = pool size ÷ hold time (seconds)
         = 10 ÷ 0.35 = 28.6 req/s

Note what is missing from that formula: query time. What appears is hold time. Making the query twice as fast removes 7% of the hold. Which is precisely why query tuning does not fix this.

Keep the network out of transaction boundaries

This is the half that remains after OSIV is off. While a transaction is open the connection is necessarily held, so the transaction boundary is the hold window.

@Transactional                       // ← starts here
public void upload(MultipartFile f) {
    Order o = repo.findById(id);      // 17ms
    s3.putObject(bucket, key, f);     // 3 seconds, connection still held
    o.markUploaded();                 // 8ms
}                                     // ← returned here

Put @Transactional at class level and methods like this appear quietly. Three ways out:

situationapproach
read-only external round trip@Transactional(NOT_SUPPORTED) — no connection held during the trip
publish or notify after commit@TransactionalEventListener(AFTER_COMMIT) — runs after commit and release
the external result must be persistedsplit the transaction in two. read → (release) → external call → write

If the publish must not be lost, step up to the Outbox pattern: write the event to a table in the same transaction and let a separate process read and publish it. The work inside the transaction shrinks to one local INSERT.

You will find advice to split transactions by injecting the bean into itself and calling through the proxy. Do not. It creates a circular reference and only reads correctly to someone who knows AOP. @TransactionalEventListener is the standard tool built for exactly this.

Can't we just grow the pool?

For now, yes. Then three things catch up with you.

  • More load puts you right back. With hold time unchanged, connections needed grow in direct proportion to load (recipe 6)
  • Connections are a database-side resource. PostgreSQL forks a process and allocates memory per connection. Once instances × pool size exceeds max_connections, the database starts refusing
  • A bigger pool is not a faster one. HikariCP's own documentation argues for small pools. Concurrency beyond your core count buys context switching and lock contention, not throughput

If you have so many instances that the raw connection count is the problem, a pooler like PgBouncer in front is an option. But that solves a connection count problem, not a hold time problem. Long holds stall behind the pooler just the same.

What to check in production

Two things to turn on first. Without them this page's problem is invisible.

spring:
  jpa:
    open-in-view: false
  datasource:
    hikari:
      leak-detection-threshold: 20000   # 20s. 0 means disabled (the default)
      # size it to your core count. Bigger is not the answer
      maximum-pool-size: 10

leak-detection-threshold is off by default. Leave it off and a connection can be held for minutes with nothing in the logs.

Metrics to watch. Hikari exports all of these through Micrometer.

metricwhat it tells you
hikaricp_connections_activeconnections in use right now. The left-hand side of Little's Law
hikaricp_connections_pendingthreads waiting for a connection. Anything but zero means already exhausted
hikaricp_connections_usagehold time distribution. The star of this page. A p99 far above query time is your answer
hikaricp_connections_acquiretime spent waiting to get a connection

Putting usage next to actual query time is the whole trick. The gap between them is the "held but idle" time, and this page is just a drawing of that gap.

From the database side.

-- sessions holding a transaction open and doing nothing
SELECT pid, state, now() - state_change AS idle_for,
       now() - xact_start AS xact_age, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start
LIMIT 20;

A long-standing idle in transaction means that session is holding a connection while the application does something else — and that something else is usually an external call. The query column holds the last statement executed, so that statement is not the culprit; go find what happened after it in the code.

The order. When you hit pool exhaustion, work through it like this.

  1. Find when pending stopped being zero — establish the start
  2. Compare usage p99 against query p99 — a gap means a hold problem
  3. Look in the code at what happens during that gap — external call, rendering, OSIV
  4. Touch pool size last
This model is simplified for teaching. Real requests vary in query count and external call duration, and bursty arrivals create waiting even in short windows. Little's Law is a statement about averages — it tells you how many connections are needed on average, not the instantaneous peak. Size a real pool with headroom on top of this.
