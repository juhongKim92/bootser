Both checked, and both passed

At least one person has to stay on call. Anyone stepping away checks first — "there's one other name here besides mine." When two people check at the same moment, both see one other name and both step away. Each touched only their own row, so no lock fired and no exception was raised.

This is everything each transaction does.

BEGIN; n = SELECT count(*) FROM oncall WHERE on_duty; -- read happens once if (n >= 2) UPDATE oncall SET on_duty = false WHERE id = :me; COMMIT;

The part that matters is WHERE id = :me. Each transaction writes only its own row. Different rows means row locks never collide, and as far as the database can tell the two transactions have nothing to do with each other.

Things to try

1. At a gap of zero, the four are indistinguishable

read → write gap 0s overlapping transactions ~0 · invariant-breaking commits 0 · minimum on call 1

Write the instant you have counted and nobody can slip in between. Press all four isolation buttons — not one number moves. With no conflict, isolation level means nothing. This is exactly why it never reproduces on a dev machine.

2. Open the gap to 0.6s — both count, both leave

Read Committed · 5 people · gap 0.6s over 1,200s: 367 commits · 6 invariant-breaking commits · minimum on call 0

Look at the in-flight transaction rows. Two people are each holding "saw 2" while the roster is already down to one. Both cleared the check and both write. No exception, no rollback. The log shows two ordinary commits.

3. Switch to Repeatable Read — not one number changes

Repeatable Read · everything else identical 367 commits · 6 invariant-breaking commits · minimum on call 0 identical to Read Committed

This is the point of the page. The isolation level went up and the result is the same down to the last digit. Two reasons. First, the app reads once — there is no repeated read, so a guarantee about repeated reads has nothing to apply to. Second, each transaction writes only its own row — had they updated the same row, PostgreSQL's Repeatable Read would have raised 40001, but on different rows there is no first-updater to win.

4. Take the roster to eight

Read Committed · 8 people · gap 0.6s overlapping transactions 57 → 171 · invariant-breaking commits 6 → 10

More people means more simultaneous pairs, and overlap triples. Load does not change the probability, it changes the frequency. This is the gap between staging and production — same code, different concurrency.

5. Serializable — it stops the bug and hands you an exception

Serializable · everything else identical invariant-breaking commits 0 · minimum on call 1 in exchange: 62 serialization failures (367 commits → 332)

PostgreSQL's Serializable is SSI, not locking. If someone changes a predicate you read before you commit, your commit raises 40001 could not serialize access. The invariant holds. What remains is who catches those 62 exceptions. Without retry code you have converted a correctness bug into a 500.

6. SELECT ... FOR UPDATE — materialise the conflict

Read Committed + FOR UPDATE invariant-breaking commits 0 · serialization failures 0 overlapping transactions 0 — they queue instead

Lock the rows you read in the counting query and the second person cannot even read until the first commits. Overlap drops to zero. You have forced a relationship onto two transactions that looked unrelated — this is called materialising the conflict. No exception means no retry code, but you have bought waiting, and opened the door to deadlock.

Why Repeatable Read does not stop it

All the name promises is that reading the same thing again returns the same value. This code never reads again. It reads once, decides on that value, and writes. The guarantee has nothing to attach to.

That is why the transaction rows in the lab carry a "count again" column. Under Read Committed that value is the currently committed count and has drifted from what was first read; under Repeatable Read the snapshot is frozen and it still shows the original. The two levels genuinely do behave differently. That difference just cannot stop this bug.

What stops it is not how high the isolation level is, but whether the database can see that the two transactions are related at all. Write only your own row and the relationship is invisible.

PostgreSQL's Repeatable Read is in fact stronger than the standard requires — snapshot isolation, so phantoms are gone too. It still does not stop write skew. "It worked on MySQL and not on PostgreSQL" stories start here, but for this particular bug neither of them stops it.

Contention over a single row — decrementing stock, say — has the shape covered in page 9 (claiming work). Write skew is harder because the contended thing is a condition, not a row. There is nothing visible to lock.

In practice

wherewhat to check
SpringIf you raised @Transactional(isolation = Isolation.SERIALIZABLE), check that the same commit added a retry. If it did not, you turned a correctness bug into a 500.
retry placement@Retryable belongs outside the transaction. Inside, it retries within a transaction that is already dead — the usual proxy-ordering trap.
what to catchSQLState 40001. Spring surfaces it as CannotAcquireLockException / ConcurrencyFailureException.
constraintsExpress it as a database constraint where you can. Count invariants usually materialise as a single aggregate row with a CHECK, updated alongside.
the costSerializable tracks read predicates and is not free. Heavy contention means more 40001s, more retries, and the amplification from page 14 starting up right here.
testingIt never reproduces at a gap of zero. Unless the test deliberately delays between the read and the write, this bug sails through CI.
