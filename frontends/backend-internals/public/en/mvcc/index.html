Driving it yourself

The play button only walks a fixed script. Press the session buttons directly and you can leave the script and build any situation you want. Touching any control during playback pauses it and hands you the state as-is.

What each button does

BEGINOpens a transaction. No snapshot yet. On its own this does not block VACUUM

Pressing SELECT or UPDATE with no open transaction issues BEGIN automatically, and the log says so.

Reading the display

  • Each slot is one tuple. Top number is xmin, bottom is xmax. Colour is the state
  • The ochre range on the axis is everything older than the horizon — safe to remove. Blue-outlined chips are pinned by an open transaction, labelled with the session letter
  • Table size is page count × 8KB. Empty slots do not shrink it if the page still exists
  • Bloat is dead tuples as a share of all tuples

Try these

1. BEGIN alone blocks nothing

Reset A BEGIN B UPDATE ×3 → COMMIT VACUUM → reclaimed A SELECT ← snapshot taken here B UPDATE ×3 → COMMIT VACUUM → reclaimed 0

The culprit is not BEGIN but the first statement. So in pg_stat_activity, do not read state alone — check whether backend_xmin is held.

2. The blocker keeps changing hands

Reset A SELECT B UPDATE ×3 → COMMIT VACUUM → 0. A is blocking B SELECT ← B opens one too A COMMIT VACUUM → 3 reclaimed. B's snapshot is newer A UPDATE ×3 → COMMIT VACUUM → 0. now B is blocking

The horizon is set by the oldest open transaction. Killing one long transaction does not end it — the next oldest immediately takes over the role. Watch the blue chip move from A to B on the axis.

3. UPDATE is what creates bloat

Reset B DELETE ×3 → COMMIT (repeat a few times) Watch the size → does not grow Reset B UPDATE ×3 → COMMIT (same number of times) Watch the size → pages appear

DELETE only marks death; it writes no new tuple. UPDATE keeps the old version and writes a new one, so it consumes space at twice the rate. This is why bulk update jobs are the usual suspect.

4. Only trailing pages get truncated

Reset B UPDATE ×3 → COMMIT (repeat until pages grow) VACUUM Check whether the last page is fully empty Empty → size drops, "truncated" appears in the log One survivor → size unchanged

VACUUM never moves data forward, so a hole in the middle of the file stays a hole. It can only cut from the end, and only when the end is completely empty.

5. Death is not settled until commit

Reset B UPDATE ×3 ← do not commit Look at slots → 3 dashed (uncommitted) appear Dead count 0 ← old versions still read as live VACUUM → nothing to do B COMMIT → 3 old versions finally die VACUUM → reclaimed

Old versions cannot be removed before commit: a rollback would make them the correct answer again. The dashed slots are the opposite case — new versions nobody can see yet. Meanwhile that transaction pins the horizon with its own xid; check the axis.

PostgreSQL does not modify rows

This trips up almost everyone arriving from another database. An UPDATE in PostgreSQL does not change the existing row. It stamps a death marker on the old version and writes a new version somewhere else. A DELETE likewise removes nothing — it only marks.

Every tuple carries two system columns you can select directly:

SELECT xmin, xmax, * FROM orders LIMIT 5;
  • xmin — the transaction that created this version
  • xmax — the transaction that killed it (0 while still live)

This is why readers never block writers: a reader simply picks the version matching its snapshot. The cost is garbage, and VACUUM is what collects it.

Why VACUUM cannot just delete

A dead tuple is not automatically removable. Some transaction may still be entitled to see that version.

So PostgreSQL computes a boundary: the oldest snapshot held by any currently open transaction. That is the xmin horizon. Anything that died after that line is untouchable.

One long-lived open transaction pins cleanup for the entire database at that moment — even if it does nothing at all. It is not limited to the tables it touched: the whole database is affected. Not the whole instance, though — ordinary tables in other databases keep getting cleaned (shared catalogs are a separate matter).

In the lab above, session A runs a single SELECT and then idles. Yet every dead tuple session B produces stays stuck. This is the most common bloat scenario in production.

Reclaiming does not shrink the file

When VACUUM removes dead tuples, the space becomes reusable — but the file does not get smaller. VACUUM never relocates data forward, so a hole in the middle stays a hole.

There is one exception: trailing pages that end up completely empty can be truncated and returned to the OS. Watch the lab for when page count drops and when it refuses to.

To actually get disk back you need one of:

  • VACUUM FULL — rewrites the whole table under an ACCESS EXCLUSIVE lock, blocking even reads, and needs free space roughly equal to the table
  • pg_repack — the same result with essentially no downtime. Usually the production answer
  • For partitioned tables, DROP the partition

What to check in production

If a table keeps growing and you cannot see why, look for old transactions first:

SELECT pid, state,
       age(backend_xid)  AS xid_age,
       age(backend_xmin) AS xmin_age,   -- long read-only transactions show up here
       now() - xact_start AS duration, query
FROM pg_stat_activity
WHERE state != 'idle' OR backend_xid IS NOT NULL
ORDER BY xact_start
LIMIT 10;

Selecting xmin_age alongside matters. The long read-only transaction this page is about never writes, so its backend_xid is NULL — read xid_age alone and the culprit shows up blank.

An idle in transaction session sitting for hours is very likely your culprit — a connection that opened a transaction and never committed.

For the scale of the bloat:

SELECT relname,
       n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;

Prevention comes down to a short list:

  • Set idle_in_transaction_session_timeout. Highest impact by far
  • Move long analytical queries to a read replica — but note hot_standby_feedback can push the replica's horizon back onto the primary
  • Keep transaction boundaries explicit in your connection pool, especially code that returns a connection with autocommit disabled
  • Batch large UPDATE statements so autovacuum can keep pace between chunks
This model is simplified for teaching. Real PostgreSQL also deals with HOT updates, hint bits, freezing and multixacts. The mechanism that matters here — the xmin horizon blocking reclamation — works exactly as shown.
