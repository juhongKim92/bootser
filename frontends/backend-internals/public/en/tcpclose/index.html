One close() call, and a RST goes out on the wire

The device finished sending and closed the socket. The tail of the body never reached the server. It is tempting to say the FIN overtook the data, but that is impossible. What actually happened is something else — and the client code is one close() call in every case.

Working the dials

Receive buffers are 64KB on both sides. A TLS record holds at most 16,384 bytes of plaintext (RFC 8446 §5.1).

The lab shows an upper bound on loss, not an amount. What a RST destroys is "bytes sitting in the peer's kernel buffer that the application has not read yet", and that depends on how fast it reads — we cannot know it. So the lab computes only the bound, min(body, receive buffer). Showing an invented number would defeat the point.

Try this

1. Read the response, then close — FIN, zero loss

read then close · body 16KB · response 1KB · no TLS signal on the wire FIN · loss bound 0 clean-shutdown verdicts 3 / 3

The baseline. When a FIN goes out, loss is structurally zero. A FIN occupies a position in the sequence number space, at the very end of the byte stream, and a receiving TCP cannot hand anything past a gap to the application. "A clean EOF with a hole in it" does not exist. That is what the close signal sitting at the tail of the stream diagram means.

2. Close without reading — same code, now a RST

only the close mode changes (response still 1KB) signal on the wire FIN → RST loss bound 0 → 16 KB · verdicts 3/3 → 2 / 3

Call close() with 1KB unread in the receive buffer and the kernel sends a RST instead of a FIN. RFC 9293 §3.6.1 says so — "if such a host issues a CLOSE call while received data is still pending … its TCP implementation SHOULD send a RST to show that data was lost". And the peer that receives the RST discards its receive buffer. The application verdict is still "clean" — you did call close().

3. Set the server response to 0 — the same code becomes safe

response 1KB → 0 (close mode stays "close unread") signal on the wire RST → FIN · loss bound 0

Not one character of the client changed, and it is safe now. With no response to leave unread there is no pending data. This is why the bug is so hard to reproduce: it appears the day the server starts sending a 100 Continue or an error body, or the day one header is added to the response. Nothing changed on the client.

4. Set SO_LINGER to 0 — a RST even with no response

close mode SO_LINGER 0 (response still 0) signal on the wire FIN → RST

Unconditional, regardless of pending data. People turn on setSoLinger(true, 0) or ChannelOption.SO_LINGER to reclaim connections faster, but it is not a "get rid of TIME_WAIT" option, it is a "throw the data away" option.

5. Terminate TLS at the backend and skip close_notify

TLS at the backend · close_notify not sent clean-shutdown verdicts 2 / 3 (TLS says no) unit of truncation: bytes → 16 KB (a record)

RFC 8446 §6.1: "Each party MUST send a close_notify alert before closing its write side." Without it the receiver cannot distinguish "the sender finished" from "an attacker cut the connection" — a truncation attack. Implementations either error out or quietly accept. And because TLS encrypts in records, a connection that dies mid-record loses the whole record, not a few bytes.

6. Move TLS termination to the load balancer — one more place to lose data

TLS at the backend → at the load balancer connection segments 1 → 2 · loss points 2 loss bound 16KB → 32 KB

Terminating TLS splits the connection in two. The AWS NLB documentation says exactly this about a TLS listener: "uses a server certificate to terminate the front-end connection". TCP's ordering guarantee is per hop and does not carry across — the same structure as QoS being per hop in no. 5.

7. shutdown(WR) → read the response → close — all clean

close mode shutdown(WR) · close_notify sent signal on the wire FIN · loss bound 0 · verdicts 3 / 3

Close the write side first to say "nothing more is coming", read the server's response to the end, then close. With nothing left unread there is no reason for a RST. This is the only case where all three layers agree that the shutdown was clean.

A FIN cannot overtake data

Let us clear the wrong explanation out of the way first. The observed symptom is exactly that shape, which is why this story writes itself — but it does not hold.

Why it is impossible
A FIN occupies a position in the sequence number space. In the words of RFC 9293 §3.4, "the FIN is considered to occur after the last actual data octet" — one position, at the very end of the byte stream
A receiving TCP hands bytes up in order only. With a gap in the middle it holds whatever arrived after it
So EOF always appears after every byte has been delivered. The state "a clean EOF with a hole in it" does not exist
A FIN segment can physically arrive before an earlier data segment — reordering happens. But it does not surface as EOF. If the data never arrives you get a timeout error, not an EOF.

This is not a single sentence in an RFC; it is a consequence of the ordered-delivery service model. So the page argues it rather than quoting it.

"Clean shutdown" means three different things

The three verdicts in the lab are the point of this page. Three layers look at the same moment and disagree.

LayerWhat it judges onIn recipe 2
applicationDid you call close()Clean — the code has nothing but close()
TLSDid you send close_notify (RFC 8446 §6.1)Clean (no TLS here)
TCPFIN or RSTNot clean — it was a RST
Which is why "it shut down cleanly and lost data" is not a contradiction. The two halves of that sentence are talking about different layers. It is also where an application developer and a network engineer reach opposite conclusions about the same incident.

What the RFC requires versus what implementations do

Building this page meant checking the sources, and only one of three claims was actually in a specification. The others are implementation behaviour or argument. Worth separating.

ClaimKind of evidence
close() with unread data sends a RSTIn the spec. RFC 9293 §3.6.1 (SHLD-3). But it is a SHOULD, not a MUST — implementations have latitude
A peer receiving a RST discards its receive bufferImplementation behaviour. §3.5.3 only goes as far as "aborts the connection and advises the user" and says nothing about buffer disposition. Every implementation does it; the spec does not demand it
There is no EOF with a holeAn argument. It follows from the ordered-delivery model, and no single clause states it
What a proxy does with its buffer on a front-side RSTUnknown. Not documented. What is confirmed is that nginx's proxy_half_close defaults to off (one direction closing closes both) — and nothing beyond that is asserted here

The fix that worked and the fix that did nothing

The most instructive part of a real incident with this shape was the difference between two attempted fixes.

FixOutcome
Have the server wait a few seconds after noticing the disconnect, then finaliseCompletely ineffective. The server was not the one discarding anything, so waiting changed nothing. It was added and then deleted
Have the server echo the close signal, and the client close only after receiving itWorks. The client has to read the response, so nothing is left unread and the RST disappears; the server's completion is confirmed; and the close_notify timing falls into place
The second fix works whichever of this page's mechanisms was the culprit. So in hindsight you could say the cause did not need to be known. Except the same team shipped the ineffective fix first — because without the cause there is no basis for choosing the right fix.

No. 14 and no. 20 both dealt with raising a timeout as a fix, and the same test applies here: raising it knowing the distribution of the normal case is a fix; raising it without knowing is a deferral.

Out in the field

WhereWhat to check
count this firstThe connections reset counters in netstat -s. In tcpdump, isolate resets with tcp[tcpflags] & tcp-rst != 0. If that number jumps alongside a deploy or a firmware change, this is your page
client sideDoes it read the response to the end before closing? Code that sends and discards the response is where this starts. If there is nothing more to send, say so with shutdown(WR), read the response, then close
SO_LINGERGo find where it is set to 0. It is an option that throws data away
where TLS terminatesTerminating at the load balancer splits the connection. On AWS, a TLS listener terminates and a TCP listener passes through — the test is whether it terminates, not whether it is L4 or L7
proxy settingsFor nginx stream, proxy_half_close defaults to off. Turn it on if your protocol closes one direction first
server shutdownSpring Boot's server.shutdown currently defaults to graceful, which protects in-flight requests. The risk is setting it to immediate, or having spring.lifecycle.timeout-per-shutdown-phase longer than the platform's termination grace period so you get killed first
idle timeoutsWrite to a connection the load balancer already reaped as idle and you get a RST (AWS NLB defaults to 350s). No. 7 is the other side of this — believing a dead connection is alive
application framingSend without Content-Length, or drop the terminating chunk, and the server has no basis for deciding whether what it got is everything. The worst implementations parse the truncated body and pass it on — no error, just corrupt data

If no. 7 was believing a connection is alive after it died, this page is closing one properly and losing data anyway. Both come from "the connection ended" meaning different things at different layers.
