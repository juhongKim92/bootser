How a cache falls apart when one node leaves

One of your four cache servers just died. If you split the keys with a modulo, the caches on the three survivors are mostly worthless too. Here is why — and how the ring prevents it.

This is the whole reason consistent hashing exists. On the ring only the range the departed node owned passes to the next node. Modulo changes its divisor, so nearly every key gets a new destination.

Do not take that 7% at face value, though. It is exactly the share the dead node happened to hold. With one virtual node those shares vary wildly, so it depends entirely on which node dies — in this configuration the range runs from 6.7% to 28.3%. Adding costs about 1/N as well. The new node takes only its own range; nothing changes between the existing nodes. Cheap scale-out is the second benefit of this scheme.

6. You cannot change the virtual node count later

Each point sits at hash('node-A#' + i), so the existing points stay exactly where they were. The reason so many keys still move is that points are added and removed in bulk, and almost every arc boundary gets redrawn — even though the node set never changed. Go the other way and nudge 160 up to 200: the original 160 points survive and only about 16% of keys move. It is the large jumps that hurt. Do this on a live cache cluster and you get a total cache miss. Pick it up front and make every client use the same value.

What is wrong with modulo

The simplest sharding looks like this.

int shard = Math.abs(key.hashCode()) % serverCount;

With four servers it works fine. The problem is the moment the server count changes.

key.hashCode() = 1234

servers = 4  →  1234 % 4 = 2   (server 3)
servers = 3  →  1234 % 3 = 1   (server 2)  ← moved

Change the divisor and the remainders are reshuffled wholesale. In theory 1 - 1/N of the keys move, so going from four servers to three sends roughly 75% of your keys elsewhere.

For a cache, that 75% is 75% misses. One server died, yet the caches on the survivors are mostly invalidated too, and all of that traffic lands on the origin store at once. It is the classic path from a single failure to a total outage.

Putting it on a ring

The idea behind the fix is to take the server count out of the equation.

  1. Join the hash space (0 … 232−1) into a circle
  2. Place each server at hash(server name)
  3. Place each key at hash(key)
  4. The key belongs to the first server clockwise from it

A key's position is fixed regardless of how many servers exist. When a server disappears, only the arc it owned passes to the next server and the rest of the ring is untouched. That is what drops the movement to around 1/N.

Lookup is a binary search over a sorted array of points, so O(log(N × V)).

// the skeleton of a real implementation
TreeMap<Long, String> ring = new TreeMap<>();

void addNode(String node, int vnodes) {
    for (int i = 0; i < vnodes; i++)
        ring.put(hash(node + "#" + i), node);
}

String lookup(String key) {
    if (ring.isEmpty()) return null;
    Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));
    return e != null ? e.getValue()          // first point clockwise
                     : ring.firstEntry().getValue();  // wrap around to the start
}

The wrap to firstEntry when ceilingEntry returns nothing is the part that matters. Drop that one line and every key at the top end of the hash space fails.

Why virtual nodes are necessary

The ring alone is not enough. Four nodes means four points on the ring, and there is no reason those four land evenly. Set virtual nodes to 1 in the lab and you can watch the spread reach 47% with a max/min gap over four times.

The fix is to register one node many times under different names — node-A#0, node-A#1, and so on. The more points, the closer each node's total arc length converges to the mean.

Virtual nodes also give you weighting. Give a server with twice the memory twice the virtual nodes and it takes twice the share — useful for clusters built from heterogeneous machines.

Do not read those absolute numbers too literally. The lab hashes only 1500 keys, so even a perfectly even ring lands around CV 5.8% from sampling noise alone (√(1500 × 1/6 × 5/6) ÷ 250). At 160 virtual nodes and above, the single-digit figures are measuring that noise floor rather than any imbalance in the ring — which is why they can even move the wrong way as you change the node count. Trust the direction, not the digits.
More is not always better. The ring holds nodes × virtual nodes entries, so lookup cost and memory grow together, and every node change touches proportionally more entries. At a scale of thousands of nodes this cost is a real constraint.

Where this is actually used

  • memcached clients — the libketama lineage, where 160 virtual nodes per node is the de facto standard. That "160" you see everywhere came from here
  • Cassandra — the token ring. It defaulted to 256 tokens per node early on, but dropped to 16 in 4.0 along with a new allocation algorithm: more tokens scatter replica placement, which increases the number of combinations affected when any single node dies
  • Dynamo (the paper) — the 2007 Dynamo paper is what popularised the approach. Not the same system as the similarly named DynamoDB service
  • nginx — hash $request_uri consistent; for upstream selection
  • Envoy — ring hash and Maglev load balancers
A common misconception: Redis Cluster does not use consistent hashing. It divides 16384 fixed hash slots among the nodes — CRC16(key) % 16384 picks the slot, and the slot-to-node mapping is maintained separately. Moving whole slots keeps resharding controllable, but it is not a ring.

What to watch for in production

Hotspots still happen. Consistent hashing distributes the number of keys evenly, not the traffic. Pile requests onto one popular key and that node alone falls over. That problem needs its own answer — a bounded-load variant, or replicating hot keys.

When a node dies, one neighbour takes the load. With enough virtual nodes it spreads across many, but with few, the single clockwise neighbour absorbs all of it. If that node goes down too, the cascade begins. Set virtual nodes to 1 in the lab, remove a node, and the skew is right there.

Every client must see the same ring. One difference in hash function, virtual node count, or node naming and clients disagree about which node owns what. If cache hit rate drops for no visible reason, suspect this first — it is especially common when clients in different languages share a cluster.

There is a simpler alternative. Rendezvous hashing (HRW) needs neither a ring nor virtual nodes: compute hash(key + node) for every node and take the highest, and the distribution is uniform by construction. Lookup is O(N), so it wins when the node count is small.

This model is simplified for teaching. The hash is 32-bit FNV-1a with murmur3's final mixing bolted on — FNV-1a alone does not diffuse the high bits, so the ring points clumped together in one place. Real implementations usually use MD5 or MurmurHash. What is faithful is the part that matters: movement falling to 1/N, and virtual nodes evening out the distribution.
