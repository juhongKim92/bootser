The load is gone and it still will not recover

Fixed throughout: capacity 100/s, server queue cap 500, client timeout 1.0s. The hatched part of the queue bar is work whose client has already given up but which is still sitting in the queue.

Things to try

1. Nothing happens on a normal day

λ 60/s · capacity 100/s · no retries goodput 60/s · queue 0 · wasted 0

Arrivals are below capacity, so nothing queues; nothing queues, so nothing times out; nothing times out, so nothing retries. Move the retry sliders anywhere you like — the screen does not change. Retries are free on a normal day, which is why nobody knows what they cost.

2. Spike it and put it back — with no retries

160/s for twenty seconds, then 60/s again during: queue 500 · goodput 0 after: goodput back to 60/s within seconds

While arrivals exceed capacity the queue fills and goodput drops to zero. Nothing surprising there. Then the load lifts, the queue drains at forty a second, and everything returns. This is the behaviour we expect — the cause goes away and so does the effect.

3. Do exactly that again with 3 tiers × 3 attempts — it does not come back

L 3 · r 3 → amplification A = 27× twenty seconds later λ is back at 60/s and goodput is still 0/s · queue 495/500 · wasted 100/s

This one panel is the whole page. Every condition matches recipe 2 except the retry settings. The inbound graph has already come down to 60/s and goodput does not follow it up. On the chart the pale bars (arrivals) drop while the solid bars (goodput) stay pinned to the floor.

4. Now push the load down further

after the spike, drop λ to 10/s — a tenth of capacity goodput still 0/s recovery threshold = capacity ÷ amplification = 100 ÷ 27 = 3.7/s

Cutting the load six-fold does not help. Ten new requests a second, each attempted up to twenty-seven times, is 270/s as far as the server is concerned, and 100/s of capacity still cannot cover it. You have to get below 3.7/s before it lets go. Drag the slider yourself — at 4/s it stays stuck and at 3/s it comes back.

5. Turn on jitter — the waves go away, and

jitter on, everything else unchanged attempts meter swings 1,480–2,300 → pinned at 1,620/s goodput still 0/s · still stuck

Exponential backoff without jitter makes clients that failed at the same instant come back at the same instant, so the attempt rate arrives in waves. Turn jitter on and the clump scatters — the attempts meter settles on 1,620/s, which is 60 × 27, the amplification factor exactly. What it will not do is get you out. Jitter reduces concurrency, not volume, and volume is set by r^L alone.

6. Turn on the circuit breaker — only this gets you out

breaker on · opens for 5s below 50% success while open it rejects immediately and queues no retries queue 0 · goodput back to 60/s

What a breaker does is not fail requests faster. It cuts the retries. For the five seconds it stays open, amplification falls from 27× to 1×, effective arrivals of 60/s drop below the 100/s capacity, and the queue empties. An empty queue restores the success rate and the breaker closes. Turning the load down will not bring it back; cutting the retries will.

Why it will not come back

A request sitting in the queue is abandoned by its client after one second. The server does not know that. The socket is still open, the request is still queued, and when its turn comes the server processes it to completion. That is the hatched part of the queue bar. The server is a hundred percent busy — and nobody is left to receive the result.

CPU at 100%, throughput 100/s, goodput 0/s. On a dashboard this system looks like it is working hard.

Meanwhile every client that gave up retries. Three tiers at three attempts each means one original request reaching the server up to twenty-seven times. A baseline load of 60/s looks like 1,620/s to the server — 60 × 27, sixteen times capacity. The attempts meter in the lab reads exactly that (with jitter off it waves between 1,480 and 2,300; with jitter on it sits at 1,620). So the queue never empties. Because it never empties the next request times out too, and because it times out it retries again — the retries feed the state the spike created.

Two thresholds

This system has two stable states: the normal one where everything succeeds on the first try, and the stuck one where everything fails and everything retries. The threshold for crossing between them is not the same in both directions.

directionconditionat the defaults
it breaksλ > C + C·T / d105/s for a twenty-second spike
it recoversλ < C / A3.7/s (100 ÷ 27)
the gapA = r^L×28×

Breaking happens near capacity. The longer the spike, the closer that threshold sits to the 100/s capacity — a five-second spike needs 121/s, a twenty-second one 105/s, a sixty-second one 102/s. The moment the queue passes C·T = 100 items is where timeouts begin, and the excess needed to push it that far is inversely proportional to how long you push.

Recovery happens at capacity divided by amplification. With no retries the two thresholds coincide and there is no hysteresis at all. Add one more attempt per tier and the gap widens multiplicatively. The grey band on the scale under the lab is that gap, and the orange marker is the current load. While the orange marker sits inside the grey band, that load can neither break the system nor revive it.

When we set a retry policy we think we are deciding how many failures to forgive. What we are actually deciding is how far the load must fall before a collapsed system can come back.

In practice

Spring Retry@Retryable(maxAttempts=3) on three tiers is 27×. Each tier decides independently, so nobody ever sees the product.
Feign / RestClientClient-level default retries stack on top of application retries, making one tier behave like two.
retry budgetsBound retries by ratio rather than count — "retries may be at most 10% of all requests". That pins amplification near 1.1× and the hysteresis nearly disappears.
Resilience4jPut CircuitBreaker outside Retry so an open breaker actually cuts retries. The other order lets retries keep hammering the breaker.
server-side discardOn dequeue, drop anything that has waited longer than the timeout instead of processing it. That is the one line that turns 100/s of waste into zero.
jitterAdd it. Removing the waves is worth it on its own. Just do not mistake it for having dealt with amplification.
