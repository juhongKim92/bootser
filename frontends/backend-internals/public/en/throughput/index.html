The bandwidth is there and the throughput is not

Working the dials

DialWhat changes
bandwidthThe most the link can carry. Watch the throughput not move — outside the region where bandwidth is the ceiling, nothing happens at all.
RTTRound-trip time. Throughput is inversely proportional to it: halve the RTT and you double the throughput.
window · connectionsTheir product is how much you can have in flight. Raising either one moves throughput by the same amount.
lossSwitches on the third ceiling. It is proportional to the connection count, which is where the protocol table flips.

The three bars are the three ceilings. The blue one is the current bottleneck, and the green (or red) bar at the bottom is the actual throughput. However long the bandwidth bar is, throughput follows the shortest bar.

The curve sweeps bandwidth only, from 1 Mbps to 20 Gbps. On the left it climbs on the diagonal (bandwidth is the ceiling) and at some point it goes completely flat (something else is). That knee is the whole page.

There is no randomness. It is the min of three expressions, so the same dial settings always produce the same numbers.

Try this

1. 5.24 Mbps out of a 1Gbps link

bandwidth 1Gbps · RTT 100ms · window 64KB · 1 connection · no loss throughput 5.24 Mbps · link utilisation 0.524% bottleneck window ÷ RTT

You put 64KB in flight and wait 100ms. That is all of it — 65,536 B ÷ 0.1 s = 5.24 Mbps. You are using 0.5% of the link. The other 99.5% is idle and there is no way to fill it: once the window is full, there is nothing you are allowed to send until an ACK comes back.

2. Ten times the link — 1.0× the throughput

bandwidth 1Gbps → 10Gbps throughput 5.24 → 5.24 Mbps (1.0×) link utilisation 0.524% → 0.052%

You bought ten times as much and throughput did not move one decimal. Bandwidth is not in the formula. Look at the curve — you are already out on the flat part. The only thing that changed is utilisation, and it got worse. This is the answer to “we upgraded the link, why is it not faster”.

3. A tenth of the RTT — ten times the throughput

RTT 100 → 10ms throughput 5.24 → 52.43 Mbps (10×)

Exactly ten times, because throughput is inversely proportional to RTT. This is why moving the server closer to the user (a CDN, another region) beats buying link capacity. Bandwidth you can buy; RTT is set by the speed of light — so the only lever is distance.

4. Leave the RTT, use six connections — six times the throughput

RTT back to 100ms · connections 1 → 6 throughput 5.24 → 31.46 Mbps (6×)

If you cannot cut the RTT, raise the concurrency. Window × connections is “how much is in flight”, and six times in flight is six times out. This is why browsers open six connections per origin. Raising the window sixfold gives exactly the same result — only the product appears in the formula.

5. A 1MB window — 83.89 Mbps on a single connection

connections 6 → 1 · window 64KB → 1MB throughput 83.89 Mbps

One connection is fine as long as the window is big. This is what window scaling is for — the window field in the TCP header is 16 bits, so 64KB is its maximum, and the scale option pushes that ceiling out. With the option off you are stuck in recipe 1 forever. And this is still 8.4% of a 1Gbps link.

6. Add 0.1% loss — from 83.89 down to 4.52

loss 0 → 0.1% throughput 83.89 → 4.52 Mbps (a factor of 18.5) bottleneck window÷RTT → loss

The third ceiling switched on: MSS·√(3/2) ÷ (RTT·√p) — inversely proportional to the square root of the loss rate. Growing the window to 1MB became completely pointless. The window bar still reads 83.89 Mbps, the loss bar reads 4.52, and throughput follows the shortest bar. One packet in a thousand costs you a factor of 18.5.

7. Keep the loss, use six connections — six times back

connections 1 → 6 (loss still 0.1%) throughput 4.52 → 27.14 Mbps (6×)

The loss ceiling is proportional to the connection count, because each connection carries its own congestion window and a loss only halves that one. Which is why, on the same path, HTTP/1.1 over six connections is six times faster than HTTP/2 over one. Look at the protocol table.

Throughput = concurrency ÷ RTT

The second of the three ceilings has already appeared twice on this site. Same formula, different unit.

WhereUnit of concurrencyFormula
this pagebytes in flight (window × connections)throughput = bytes ÷ RTT
no. 8connection pool sizethroughput = pool size ÷ hold time
no. 5Receive Maximumthroughput = unacked messages ÷ RTT
All of it is Little's law — concurrency = throughput × latency. To fill 1Gbps at the default settings you need 125 MB/s × 0.1s = 12.5 MB in flight, and you have 64KB. A factor of 191.

So “should I add bandwidth or connections” is the wrong question. The right one is “how many bytes do I have in flight, and how many would fill the link”. The in flight and to fill meters in the lab are those two numbers.

At 0.002% loss, HTTP/1.1 overtakes HTTP/2

The third ceiling is proportional to the connection count. Which makes HTTP/2, having collapsed to one connection, six times more fragile under loss.

The crossover is at 0.00207% loss (about 21 ppm). Real internet paths usually run 0.01–1% — well above the crossover. It is equally true that HTTP/2 dominates on a lossless path, and that any loss at all flips it.

None of which makes HTTP/2 a bad choice. This table only looks at bulk transfer throughput. Where HTTP/2 actually wins is many small requests — no per-connection handshake, compressed headers, and no request queue at the HTTP layer. That value does not show up in this formula.

HTTP/3 does not fix this law

A common misconception worth naming. QUIC still does congestion control per connection. Many streams, one window. Which is why the lab's throughput for it is exactly the same as HTTP/2.

What was wrongDoes HTTP/3 fix it?
transport-level HOL blocking — a loss on one stream holds up data that has already arrived for anotherYes. This is what QUIC actually fixes
throughput inversely proportional to the square root of lossNo. The window is still per connection
the window ÷ RTT ceilingNo. Same formula
round trips to establish the connectionYes. Down to 0-RTT / 1-RTT

HOL blocking shows up in when individual streams complete, not in throughput. The total is the same and the first paint is earlier. So the lab's meters cannot show it, and it appears only as the HOL column in the comparison table.

Out in the field

WhereWhat to check
window scalingThe window field in the TCP header is 16 bits, so 64KB is the hard limit. If the scale option (net.ipv4.tcp_window_scaling) is off, or middleboxes strip it, you are locked in recipe 1. If you measure something near 5.24 Mbps, check this first
buffer limitsThe maximum in tcp_rmem / tcp_wmem is the real ceiling on the window. Below the BDP the kernel cannot grow the window past it — and the defaults are not chosen with long paths in mind
BBREscapes this page's third ceiling. BBR does not treat loss as a congestion signal; it estimates bandwidth and RTT instead, and does far better than CUBIC on lossy long paths. The square-root law is a property of loss-based control
measuringA bandwidth graph will never show you this. Watch bytes in flight together with RTT. In ss -i those are cwnd, rtt and bytes_in_flight
bulk transferMultipart parallel upload to S3 or any object store is recipe 4. Splitting into parts shrinks the retry unit, yes — but mostly it raises concurrency
replication lagWhen cross-region replication cannot keep up, look at the concurrency of the replication stream before the bandwidth. One stream is recipe 1
short transfersA small file finishes before the window has grown (slow start). In that regime neither bandwidth nor window sets the time — the number of round trips does. This lab models steady state only

If no. 8 was how many connections should I hold, this page is why that number comes out the way it does. The same formula met twice in different units — and only the third ceiling, loss, is new here.
