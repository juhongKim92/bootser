A rollback does not give the sequence back

One day the ingest batch stops. nextval: reached maximum value of sequence. But the table only holds about thirty million rows. Where did the other two billion go?

Drive it yourself

An ingest batch running every minute. Twelve files arrive per cycle and each is COPYed as 3,000 rows. Some of them are bad files whose companion table is missing.

Things to try

1. Turn nothing on and just watch

validate after COPY · no cap · no terminal state · 10% bad sequence 0 → 2,147,483,647 rows 0 → about 35 million runs out in roughly 18 hours

Just watch the two bars separate. The top one sprints for the ceiling while the bottom stays flat on the floor. Sixty times more value burned than rows stored. Ingest stops entirely in under a day.

2. Add an attempt cap only

attempt cap 5 runs out in 18 hours → about 30 days retry pool grew forever → settles at five cycles' worth

A big improvement, because the retry pool stops growing without bound and settles at five cycles' worth. Consumption changes from quadratic to linear. But the leak itself is untouched — each bad file just burns sequence five times on its way out instead of forever.

3. Switch to a terminal state

terminal state on (instead of the cap) runs out in 30 days → about 41 days retry pool 0 — it leaves after the first attempt

A bad file burns once and moves to a terminal state. The retry loop is now completely severed and the pool sits at zero. Yet over two hundred million values have still been burned — each file does one COPY and rollback before it leaves.

4. Move validation before the COPY — the heart of the page

validate before COPY burned 200M → 0 runs out in 41 days → 46 days

The leak disappears completely. A bad file never reaches the COPY, so it never touches the sequence. One control moved, and burned value goes to zero.

The lesson shrinks to one line: validate before you do anything you cannot undo. A transaction gives you rows back. It does not give sequences back.

5. Fix everything and it still fills in 46 days

every safeguard on, just left running burned 0 runs out in 46 days ← from healthy ingest alone

This is the second conclusion. Plug every leak and int4 still fills in 46 days. Two billion is simply not a large number for a table taking 46 million rows a day. Fixing the code and widening the column to bigint are two separate jobs, and you need both.

Why sequences do not roll back

This is where the page starts. A PostgreSQL sequence operates outside the transaction.

BEGIN;
  INSERT INTO gps_history ...;   -- nextval() hands out 1,000 values
  -- validation fails
ROLLBACK;

-- rows: none.  sequence: still advanced by 1,000

That is deliberate. If sequences rolled back, concurrent transactions would have to wait on one another — queueing up just to get a number. A sequence promises uniqueness, not continuity.

So all of these are correct behaviour:

  • Values written by a rolled-back transaction are gone forever
  • With cache configured, a session discards its whole cached block on exit
  • Values held by a session that crashed never come back either
Which means id values must never be used as a count. "The last id is two billion, so there are two billion rows" is exactly the assumption that delays discovery of this incident. Count rows with count(*).

When validation sits after the side effect

The offending code usually looks like this.

@Transactional
public void migrate(File file) {
    copyGpsRows(file);                        // ① COPY 3,000 rows — 3,000 sequence values
    copyDriveRows(file);

    if (!hasAdasTable(file)) {                // ② validate here
        throw new IllegalStateException(...); // ③ rollback — rows go, sequence stays
    }
    markMigrated(file);                       // ④ never reached
}

Swapping ① and ② is the whole fix. Validate first and a bad file never gets near the COPY.

public void migrate(File file) {
    if (!hasAdasTable(file)) {                // ① validate first
        markPermanentlyFailed(file);          //    move to terminal state and return
        return;
    }
    copyGpsRows(file);                        // ② only what passed gets copied
    ...
}

Generalised: finish every reversible check before you do the irreversible thing. Sequences are not the only thing that does not roll back.

The three requirements of a retry loop

Stopping the leak leaves the retry loop itself. A structure where a failed job is retried forever is dangerous on its own. It needs at least three things.

1. A terminal state

There has to be a state that exits the retry set. Without one, failed records stay in the queue forever.

-- one more state value is the entire fix
migrate_flag: 'N'  pending          → retried
              'Y'  done
              'E'  permanent failure → excluded from retries

In the lab this single toggle drops the retry pool to zero. The cheapest safeguard there is, and the one most often missing.

2. An attempt cap

For failures you cannot classify as permanent — transient network errors and the like — a cap is the answer. One attempt_count column does it.

What happens with a cap but no terminal state? Recipe 2 in the lab: much better, still leaking. They do not substitute for one another.

3. Retry on a whitelist

The most commonly inverted of the three. The usual shape is this:

try { work(); }
catch (IOException | TimeoutException e) { fail(job); }   // only these are failures
catch (Exception e) { requeue(job); }                     // everything else retries ← danger

The default is retry. Any new exception automatically takes the infinite-retry path. Disk full, expired credentials, malformed data — everything that will fail forever no matter how often you try lands right here.

if (isRetryable(e)) requeue(job);   // retry only what you know is transient
else                fail(job);      // default to failure

Inverting that default alone keeps unknown failures out of the loop.

Put exponential backoff on top. Retrying every minute hammers a struggling peer while it is struggling. If the peer is an external API you extend their outage; if it is your own database you extend your own.

Two billion is smaller than it sounds

The second conclusion from recipe 5. The integer ceiling of 2,147,483,647 is not a large number at modern data volumes.

inserts per secondtime to hit the int4 ceiling

500about 50 days
1,000about 25 days
5,000about 5 days

Add whatever rollbacks and caching throw away and it arrives sooner. And arriving is a total outage, not a slowdown — inserts simply stop.

Worse is what you then have to do. Converting integer to bigint on a large table takes an ACCESS EXCLUSIVE lock and rewrites the whole thing. On tens of gigabytes that table is unusable for the duration. You are already in an outage and the recovery costs more of it.

-- the column and the sequence both have to change
ALTER TABLE gps_history ALTER COLUMN id TYPE bigint;   -- full rewrite
ALTER SEQUENCE gps_history_id_seq AS bigint MAXVALUE 9223372036854775807;
SELECT setval('gps_history_id_seq', (SELECT max(id) FROM gps_history));

Which is why new tables should be bigint from the start. There is rarely a good reason to save four bytes here.

What to check in production

Alert on sequence usage. It is the only way to know before you arrive.

-- usage across every sequence
SELECT schemaname, sequencename,
       last_value,
       max_value,
       round(last_value::numeric / max_value * 100, 2) AS pct_used
FROM pg_sequences
WHERE last_value IS NOT NULL
ORDER BY pct_used DESC
LIMIT 20;

Set the warning line at 70% and the bigint conversion becomes planned work rather than an incident. That difference is large.

Put the sequence and the row count side by side. That is what the two bars on this page are.

SELECT (SELECT last_value FROM gps_history_id_seq)          AS seq,
       (SELECT count(*) FROM gps_history)                   AS rows,
       (SELECT last_value FROM gps_history_id_seq)
         - (SELECT count(*) FROM gps_history)                AS gap;

Ordinary deletes create a gap too. But a gap several times the row count means something is inserting and discarding on repeat. That contradiction is the fastest route to the cause.

Turn the retry queue into metrics.

metricwhat it tells you
records pending retrymonotonic growth means there is no exit condition
max attempt_countwhether anything is reaching the cap
retries for a single idwhether one record is stuck in the loop
records in the terminal stateit should grow. Zero means nothing is using that state

That last row matters. Defining a terminal state and having nothing ever reach it is common. The count is the only way to know your classification logic actually runs.

Log per-record outcomes in the batch. Isolate each record in a try/catch so one failure cannot halt the whole run, and record which file failed and why. That is what makes the 'E' pile reviewable by a human later.

This model is simplified for teaching. The batch cycle is fixed at one minute with twelve files of 3,000 rows each, and the retry pool accumulates as a real number. Real exhaustion dates depend on ingest volume, how the failure rate varies, and the sequence cache setting. What matters is not the number of days but the fact that the two bars separate.
