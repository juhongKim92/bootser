Scaling out broke the messages

Chat worked perfectly on one server. Add a second and half the messages stop arriving — without changing a line of code. This is the bill for WebSocket keeping its state on the server.

Things to try

1. Go from one server to four

local only, room of 12, 0% reconnecting 1 server delivery 100% 2 servers delivery 50% 4 servers delivery 25% 8 servers delivery 12.5%

The code did not change; only the server count did. Delivery falls to exactly 1/N. The server that received the event knows only the sockets attached to itself and has no idea the others exist. A rare case of scaling out breaking a feature outright.

2. Switch to broadcast

4 servers, room of 12 local only delivery 25% Redis fan-out 0 broadcast delivery 100% Redis fan-out 4.00

One Redis channel, every server subscribed. Whichever server receives the event, it travels through Redis to all of them. Delivery is back to 100% — at the cost of copying every message once per server.

3. Shrink the room to see what fan-out costs

broadcast, 8 servers, room of 3 Redis fan-out 8.00 wasted 67.0% several red dashed cards — received, nobody to deliver to

Here is the real cost of broadcasting. Three people in the room, and all eight servers receive the message, deserialise it, look through their room table, find nobody, and drop it. In a product full of one-to-one conversations, adding servers turns directly into wasted CPU.

4. Switch to per-room channels

8 servers, room of 3 broadcast fan-out 8.00 wasted 67.0% per-room channel fan-out 2.64 wasted 0%

Give every room its own channel, and have each server subscribe only to the rooms it actually holds. Servers with no member never receive it at all, and fan-out drops from 8 to 2.64. Not free, though — the channel count grows with the number of rooms, and every join and leave means a subscribe or unsubscribe.

5. Put some people mid-reconnect

per-room channel, 4 servers, room of 12, 20% reconnecting delivery 80% missed total keeps climbing

Pub/Sub does not fix this one. Redis Pub/Sub does not store anything. If you are not subscribed at the moment of publication, the message is simply gone. A three-second reconnect means three seconds of messages lost permanently. That 100% delivery figure only ever meant while the connection was up.

Why more servers break it

HTTP is easy to scale because it is stateless — any server produces the same result. WebSocket is the opposite. The connection itself is state, and that state lives in one specific server's memory.

// the usual first implementation
Map<String, Set<WebSocketSession>> roomSessions;   // ← this server's memory

void broadcast(String room, String payload) {
    for (WebSocketSession s : roomSessions.get(room)) {   // ← only sockets on this server
        s.sendMessage(new TextMessage(payload));
    }
}

This code is perfectly correct on one server. The moment there are two, half the room stops receiving. It is not a bug so much as code written on the assumption of a single instance.

This failure comes from instance count, not load. So it never reproduces in dev or staging on one instance, and only appears in production on N. And because it gets reported as "messages sometimes don't arrive", it is easy to misdiagnose as a network problem.

Sticky sessions are not the answer

The first idea that comes to mind is pinning everyone in a room to the same server at the load balancer. It does work. The costs are steep.

  • Load skews. One large room can occupy an entire server
  • Every deploy disconnects everyone. Take that server down and the whole room drops
  • Cross-room messages become impossible. Notifications, mentions and presence all cross room boundaries
  • A room can outgrow one server. And then you are back to the same problem

Sticky sessions remain useful for keeping a connection on one server — landing a reconnect back where it was. They are just not a message propagation strategy.

What Pub/Sub does

The point is that servers no longer need to know about each other. Each one only needs to know Redis.

// the server that received the event — it does NOT write to its own sockets
redis.convertAndSend("room:" + roomId, payload);

// every server runs the same subscriber code
void onMessage(String channel, String payload) {
    String room = channel.substring("room:".length());
    for (WebSocketSession s : roomSessions.get(room)) {   // ← only its own share
        s.sendMessage(new TextMessage(payload));
    }
}

The important detail is that the publishing server does not write to its own sockets directly. It writes when the message comes back through Redis. That keeps the path singular, so ordering and duplication only have to be reasoned about in one place. Mixing a direct write with Pub/Sub gives you a bug where only people on your own server receive everything twice.

How to slice the channels

That is the choice between the lab's two Pub/Sub modes.

approachfan-outcost
one channelserver count Nservers with no member still receive, deserialise and discard
per-room channelservers holding a memberchannel count grows with rooms; subscribe/unsubscribe on every join and leave

Expected fan-out is N(1 − (1 − s)^k), where s is the chance a given member sits on a given server and k is the room size. (1 − s)^k is the probability that a server holds nobody from this room — which is exactly the broadcast waste ratio.

The rule is simple. If rooms are larger than your server count, broadcast is fine; if they are smaller, waste dominates. Products built on one-to-one chats or personal notifications — rooms of one or two — pay more waste with every server you add.

Careful on Redis Cluster. A plain PUBLISH propagates to every node in the cluster, no matter how you slice channels. To confine a channel to a node you need Redis 7's sharded Pub/Sub (SPUBLISH / SSUBSCRIBE). If you moved to per-room channels and Redis load did not drop, look here.

Pub/Sub stores nothing

This is the property people discover last. Redis Pub/Sub delivers only to whoever is subscribed at the moment of publication. No queue, no replay, no acknowledgement.

So the gaps open up at these moments:

  • Client reconnecting — subway, elevator, switching networks. That is the lab's "reconnecting" slider
  • Server restart or deploy — anything published while that server had no subscription is simply not there
  • Redis restart — the subscription state itself disappears

Even when the delivery readout says 100%, that only ever covered the time the connection was up. What the user experiences is "part of the conversation is missing".

Filling the gap

The standard shape is to let Pub/Sub handle live delivery only, and keep the record somewhere else.

1. store the message first        → get a monotonically increasing seq
2. publish through Pub/Sub carrying that seq
3. the client remembers the last seq it received
4. on reconnect it asks for everything after that
   GET /rooms/{id}/messages?after={lastSeq}

In this shape Pub/Sub is only a "something new happened" signal, and correctness belongs to the store. Missing a signal is harmless because the next reconnect fills it in, so Pub/Sub's lack of guarantees stops mattering.

Ordering works the same way. Pub/Sub preserves order within a channel but guarantees nothing across channels, and a reconnect breaks the stream anyway. Having the client sort by seq and detect gaps to re-request is the reliable route.

If you need stronger guarantees, Redis Streams (persistence, consumer groups, replay) or Kafka are the step up. But most chat and notification systems are well served by Pub/Sub + a store + seq resync. Asking the broker for delivery guarantees moves your operational complexity up a level.

What to check in production

Run two instances when you test. None of the problems on this page reproduce on one. Starting two locally on different ports and connecting to each catches most of it.

Look for code that still writes to its own sockets. Adopt Pub/Sub but leave a direct session.sendMessage() on the publish path, and people on that one server receive everything twice — an awkward symptom to trace.

Confirm you unsubscribe. With per-room channels, failing to unsubscribe when the last member leaves means subscriptions pile up, and the longer a server runs the closer its fan-out creeps back to broadcast.

Plan for the reconnect storm during deploys. Take one server down and every connection on it reconnects at once, then all of them call the resync endpoint. Without exponential backoff and jitter on the client, every deploy becomes a self-inflicted DDoS.
