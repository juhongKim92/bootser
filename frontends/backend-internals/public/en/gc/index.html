Try these

1. Move only the heap

Hold allocation at 500 MB/s Walk the heap from 2GB to 128GB G1 young pause 95ms → 538ms G1 mixed pause 161ms → 915ms ZGC max pause 0.28ms, unchanged

G1 stops the world while copying live objects. A bigger heap means a bigger young generation per collection, more to copy, longer pauses. ZGC relocates concurrently, so heap size does not enter the pause equation.

2. How far can G1 hold its target

4GB → young 188ms (inside target) 16GB → young 208ms (about on target) 64GB → young 270ms (overshooting) 128GB → young 538ms (long gone)

G1 shrinks the young generation to honour MaxGCPauseMillis. But it cannot go below G1NewSizePercent (5% by default). As the heap grows that floor grows with it, and past some point the target becomes unreachable.

3. Shorter pauses do not always win

Hold heap at 16GB Raise allocation 500 → 3000 MB/s G1 young pause 208ms, unchanged G1 GC count 11 → 67 G1 throughput 96% → 73%

Pause length and total stopped time are different problems. A 200ms pause twice a minute is harmless; twenty times a minute costs 7% of your throughput. Looking only at p99 latency hides this.

4. ZGC stops too

Heap 16GB Raise allocation to 5000 MB/s ZGC alloc stall a ms/s figure appears ZGC throughput drops

Allocate faster than ZGC can reclaim concurrently and threads block waiting for free pages. This is not counted as a GC pause, so the log says "0ms" while the application is genuinely stopped. It is the easiest thing to miss when tuning ZGC.

5. Give ZGC room

Hold allocation at 5000 MB/s Heap 16GB → stall 528ms/s Heap 128GB → stall 312ms/s

Headroom is time. A wider heap gives the concurrent cycle room to finish before you run out of pages. Growing the heap lengthens G1's pauses, but for ZGC a bigger heap is usually a straight win — which is why the two collectors are tuned in opposite directions.

Where G1 stops

G1 divides the heap into uniform regions. To collect, it picks a set of regions and copies the live objects out into fresh ones, then frees the originals wholesale.

The catch is that copying changes addresses. Application threads must not be holding stale ones, so the world stays stopped for the entire copy. Pause time is simply "how much live data got moved".

pause ≈ fixed cost + (live bytes to copy) / copy throughput

G1 resizes the young generation to hit -XX:MaxGCPauseMillis (200ms by default), shrinking it when it overshoots. That adaptation is why the lab above stays near the target up to a 16GB heap, at 208ms. Not exactly 200ms — it is a target, not a guarantee.

But the young generation has a floor. G1NewSizePercent defaults to 5%, and 5% of a 128GB heap is already 6.4GB. Copying even the 15% that survives is close to a gigabyte. That is how the target becomes unreachable.

How ZGC avoids stopping

ZGC rests on colored pointers and a load barrier.

A 64-bit pointer only needs about 44 bits for the real address. ZGC stores state in the spare high bits — whether this object has been marked, whether it has already been relocated. Every reference read in the application carries a small check of those bits.

// conceptually, this check rides along with every reference load
Object o = obj.field;        // ← barrier runs here
// if the pointer colour is stale: find the new address and fix the reference in place

This is what lets the application keep running while objects are being moved. A thread reaching a stale address gets forwarded on the spot, and its reference is healed.

So ZGC's STW work is three short root-scanning windows per cycle. Since JDK 16 even thread stack scanning is concurrent, which makes the pause essentially independent of both heap size and thread count.

So should everything use ZGC

No. There are three costs.

  • Throughput — the load barrier rides on every reference read, costing roughly 5–15% depending on the workload. For batch jobs measured in total time, that is a straight loss
  • Memory — allocation continues during collection, so ZGC needs headroom. Expect to give it more heap than G1 for the same job
  • Allocation stalls — the ones in the lab above. Outrun the collector and you stop anyway

What changed by JDK version

ZGC has moved a great deal recently, so old benchmarks mislead.

  • JDK 21 — Generational ZGC arrives (JEP 439). Before this, ZGC had no generations at all, so short-lived garbage forced a full-heap traversal every time. That was its throughput weakness
  • JDK 23 — generational mode becomes the default (JEP 474)
  • JDK 24 — non-generational mode removed (JEP 490). -XX:+UseZGC now means generational ZGC
  • JDK 25 — current LTS. G1 remains the default collector
The reputation that "ZGC costs a lot of throughput" mostly comes from pre-generational measurements. The gap narrowed considerably after JDK 21 — though it is not zero, so measure rather than assume.

What to check in production

Start with what you are actually running and how much it stops.

// live JVM
jcmd <pid> VM.flags | tr ' ' '\n' | grep -i gc

// GC logging (JDK 9+)
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20M

// safepoints too — STW is not only GC
-Xlog:safepoint:file=safepoint.log

That second one matters. Thread dumps, heap dumps, class redefinition, monitor deflation and JIT deoptimisation all stop the world. Concluding "no pauses" from the GC log alone leaves things out.

On ZGC, watch stalls separately:

-Xlog:gc+alloc=debug   // Allocation Stall entries

Rules of thumb for switching:

  • Heap over 32GB and p99 latency hurting → ZGC is worth measuring
  • Heap at or under 8GB → G1 is fine; ZGC's benefit rarely covers the barrier cost
  • Batch or ETL where total time is the metric → G1, or even Parallel GC
  • Seeing Full GCs → find out why it cannot keep up before changing collectors. Usually it is allocation rate or a leak, and a new collector will not fix either
The numbers here come from a simplified teaching model. Real pauses depend on object graph shape, region size, GC thread count and hardware. Nothing substitutes for measuring your own workload.
