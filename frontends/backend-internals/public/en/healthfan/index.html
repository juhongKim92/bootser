The database blinked and every instance dropped out at once

Your health endpoint pokes the database — you were told that was good practice. So when the database is unwell for 90 seconds, all four instances drop out simultaneously. They share the dependency, so they reach the same answer at the same moment. Sixty seconds to go out, a hundred and fifty to come back — the same interval, but the thresholds are 2 and 5, so the two directions differ by 2.5×. And the instant they are all out, the load balancer sends to all of them.

The dials

DialWhat it changes
What the check looks atShallow only asks whether the process is alive. Deep pokes the database — which turns an outage in a shared dependency into simultaneous eviction of several instances. Why half differs from all is the picture on this page.
InstancesHow many are registered in the target group. It only matters during partial eviction — the load multiplier on the survivors is N ÷ survivors.
Outage lengthHow long the shared dependency is unwell. Short outages are never detected — the consecutive-failure count cannot be reached. That there is no middle ground is the point.
Check intervalHealthCheckIntervalSeconds. 30 seconds by default, and the documented range is 5–300. This one value fixes eviction, return and new-instance entry all three at once.
Unhealthy thresholdUnhealthyThresholdCount. Default 2, range 2–10. That many consecutive failures takes a target out.
Healthy thresholdHealthyThresholdCount. Default 5, range 2–10. That the default differs from the unhealthy threshold is where this page starts.

All times are relative to the start of the outage and fully determined — no randomness, no sampling. Load balancer nodes are fixed at two (two AZs), and the figures shown are the worst phase (why that is computed as two ends rather than sampled is below).

Things to try

1. A ten-second blip — nothing happens

deep·all · 4 instances · 30s interval · unhealthy 2 · healthy 5 · outage 10s eviction none · healthy 4 / 4 · failed checks 0–1

On a 30-second interval, at most one check lands inside a 10-second window. Two consecutive failures cannot happen. The health check never sees this outage. Some requests failed, but the routing did not move a hair — and that is usually the right behaviour.

2. Stretch it to ninety — all out, so all get traffic

outage 10 → 90s evicted at 60s · back at 240s · routing abnormal for 180s healthy 0 / 4 · fail-open · load on survivors ×1

At 60 seconds all four go out simultaneously — same database, same answer, same moment. And when healthy reaches zero the documented behaviour fires: "the load balancer fails open" — all of them are unhealthy, so all of them get traffic. In routing terms nothing changed. The database was unwell for 90 seconds and routing is not normal until 240.

3. Only half affected — this is worse

deep·all → deep·half (same 90-second outage) healthy 2 / 4 · load on survivors ×2 · times unchanged

Only two went out, so fail-open does not trigger. The remaining two carry four instances' worth of traffic. If they cannot, the next check takes them out too — and then you are in fail-open anyway. A partial failure is worse than a total one, because when everything is out the load is at least spread across four again. The opposite of the intuition.

4. Switch to a shallow check — no eviction

deep·half → shallow (does not touch the DB) eviction none · healthy 4 / 4 · routing abnormal for 0s

Same database outage. Requests still fail. The only difference is that routing does not wobble. The moment the database returns, so does the service — no extra 150 seconds. One setting decides whether the same outage is "a few failed requests" or "everyone evicted plus 150 seconds of recovery".

5. Healthy threshold to 2 — half the abnormal window

deep·all · healthy threshold 5 → 2 back 240 → 150s · routing abnormal 180 → 90s · asymmetry ×2.5 → ×1

Eviction is unchanged at 60 seconds. The only thing that moved is how long coming back takes, and that alone halves the abnormal window. The default of 5 is a conservative choice — don't readmit a flapping instance — but during a shared-dependency outage that conservatism only ever delays recovery. This is the cheapest dial on the page.

6. Interval down to five — everything speeds up, but

interval 30 → 5s (healthy threshold back to 5) evicted 60 → 10s · back 240 → 115s · new instance 30 → 5s

The documented minimum. Eviction, return and new-instance entry all get faster. But eviction at 10 seconds means a single 10-second pause takes an instance out. The timeout default is 5 seconds, so one GC pause or stop-the-world becomes two consecutive failures. The price of a shorter interval is false positives, not database load.

7. Interval up to three hundred — everything gets worse

interval 5 → 300s (the documented maximum) eviction none (the 90-second outage is invisible) · new instance 300s

Nothing is detected, which looks like a win — except the same interval also governs new-instance entry. A scaled-out instance waits 300 seconds before it takes traffic. And a genuinely dead instance survives for 600. This dial does not improve in one direction, because it fixes three things at once.

The documentation fixes the arithmetic

The checkpoint for this episode is ALB's target-group health check page. Defaults and rule live in the same table.

SettingDefaultRange
HealthCheckIntervalSeconds30s5–300
UnhealthyThresholdCount22–10
HealthyThresholdCount52–10
HealthCheckTimeoutSeconds5s2–120
"If the health checks exceed UnhealthyThresholdCount consecutive failures, the load balancer takes the target out of service. When the health checks exceed HealthyThresholdCount consecutive successes, the load balancer puts the target back in service."

Put the defaults into the rule and two times fall out — eviction at 2 × 30 = 60 seconds, return at 5 × 30 = 150 seconds. The same interval, and yet the two directions differ by 2.5×. That is the starting point of this whole page, and no document warns you about the asymmetry.

The documentation also guarantees why those times come out as clean multiples.

"Each health check request is independent and the result lasts for the entire interval. The time that it takes for the target to respond does not affect the interval for the next health check request."

So response time never mixes into the detection time. It is always a whole multiple of the interval — which is precisely why this model needs no randomness.

Fail-open — all dead means all get traffic

The instant healthy reaches zero, routing inverts. The documentation even names the behaviour.

"If a target group contains only unhealthy registered targets, the load balancer routes requests to all those targets, regardless of their health status. This means that if all targets fail health checks at the same time in all enabled Availability Zones, the load balancer fails open."

It is a reasonable choice — better than sending nowhere. But the premise that health checks protect you disappears here. And it has one side effect.

How many are outfail-openLoad on survivorsWhat happens

The load multiplier is not monotonic. It worsens with every instance lost, and then the moment the last one goes it drops from ×4 back to ×1. Which means there really is a band where somewhat broken is worse than entirely broken.

One interval fixes three things

This is what steps 6 and 7 show. A single HealthCheckIntervalSeconds sets three different times simultaneously.

Why new instances are quick is spelled out separately in the documentation.

"After your target is registered, it must pass one health check to be considered healthy."

A new instance only has to pass once. An instance that dropped out needs five. So scaling out is five times faster than bringing an existing instance back. During a deploy that asymmetry inverts the intuition — the new pod takes traffic almost at once, while the pod that merely stumbled stays out for a long while.

The phase is not sampled

There is no telling where in the interval an outage begins. But compute both ends and no randomness is needed.

best — outage starts just before a checkimmediately(2−1) × 30 = 30s

The difference is exactly one interval. What the screen shows is the worst case, because that is the one you can plan capacity against. The same approach no. 28 took when it split segment counts into odd and even.

What this model assumes

AssumptionWhat breaks if it fails
instances fail togetherThey share a database, so they are treated as reaching the same answer at the same moment. In reality connection pool states differ slightly and evictions scatter by a few seconds — and that scatter creates the partial-eviction band that step 3 warns about. The model does not draw that intermediate state
one clean outageRepeated blips reset the consecutive-failure count, so eviction comes later or not at all. It moves non-monotonically
evicted instances stay healthyThe path where survivors actually die under the extra load is outside the model. That belongs to no. 11 and no. 14 — this page only walks you to that door
two nodes (two AZs)The documentation says "Each load balancer node checks the health of each target", so the check count multiplies by AZ. The eviction time does not change, though — each node decides on its own
the defaults are specified, the outage is not30 · 2 · 5 are fixed by the documentation and do not move. The outage length is an input we supplied — no specification could contain it

In the field

WhereWhat to check
First thing to look atOverlay HealthyHostCount on the same time axis as your database metrics. If it steps down 60 seconds after a database wobble and only climbs back 150 seconds later, this is your page. Viewed on separate charts, the causality is invisible
The cheapest fixTake the shared dependency out of the health check. Evicting instances because the database died fixes nothing — every destination fails anyway. Expose dependency status on a different endpoint and use it for alerting only
ThenHealthyThresholdCount to 2. Step 5 prices it — the abnormal window halves. The unhealthy threshold cannot go below 2; that is the documented floor
Before shortening the intervalIt means eviction at interval × 2. Five seconds gives you ten, which is the length of one GC pause. The timeout default is 5 seconds, so checks during a pause count as plain failures
KubernetesDifferent names and different defaults — periodSeconds 10, failureThreshold 3, successThreshold 1. With a healthy threshold of 1, ALB's asymmetry is absent. But putting the same deep check on both readiness and liveness makes a database outage into pod restarts — considerably worse
Do not rely on fail-openIt does not trigger when a single AZ is wiped out — the documentation says "in all enabled Availability Zones". If one AZ's instances all drop, they stay dropped and the other AZ absorbs their load
How to measure itLeave the database alone and make only the health path return 500. Do it on one instance and time when HealthyHostCount falls and rises — 60 and 150 seconds will confirm whether the arithmetic above holds in your account
