You took the lock and two of you got in

You acquired the Redis lock correctly. No contention, a clean acquisition. And then the work ran longer than the TTL, so the lock expired while you were still holding it. The next instance starts the same job, and the first worker keeps going with no idea that its lock is gone.

Working the dials

DialWhat changes
fencing tokenThe resource rejects any write whose token is lower than the highest it has seen. Turn it on while watching the duplicate-execution meter.
auto-renewA watchdog pushes the expiry out on every renewal interval. During a pause the renewal cannot go out.
lock TTL · work timeIf the work is longer than the TTL, the lock expires mid-flight. Push the TTL above the work time — and then look at the dead-worker wait meter.
pause length · chanceGC pauses, swap, scheduling delay. The moment the pause exceeds the TTL is the boundary this page is about.
renew everyRenewing more often extends the pause you can survive — up to TTL − renewal interval. Never past that.
instancesHow many instances want the same job. When the lock expires the next one takes it.

On the timeline a green outline is the span where the lock is genuinely held, and red hatching is the span where the worker has lost the lock and keeps working anyway. The grey bar is the process being frozen. The squares on the resource row at the bottom are writes, and the number in each is that write's token.

The meters are not samples. A pause either happens or it does not, so every path is enumerated and probability-weighted — these are exact expectations.

Try this

1. Nothing froze, nothing failed — and two of them got in

lock TTL 3.0s · work 5.0s · pause chance 0% · 2 instances same job executed 2.00× · duplicate execution 100.0% time spent working without the lock 4000ms

Nothing broke. No pause, the network is fine. The work is simply longer than the TTL. The lock expires at 3s and the second instance legitimately takes it at that moment. Now two of them are inside the critical section. The first worker has no way to find out that it lost the lock — expiry is something the lock server does quietly.

2. Turn on fencing tokens — duplicate execution does not move one decimal

fencing token off → on same job executed 2.00 → 2.00× · duplicate execution 100.0% → 100.0% writes rejected 0.00 → 0.00

A fencing token does not stop two of them getting in. It cannot — it is something the resource does after the work has already started. In this configuration not even a write gets rejected: token 1 writes at 5s and token 2 at 8s, so the order is already right. Fencing starts to matter when the order inverts.

3. Add a pause — the result is now wrong

pause chance 0% → 20% · pause length 8.0s (fencing off) stale write becomes final 0.0% → 16.0% token 2 writes at 8s, and token 1 overwrites it at 13s

The first worker freezes for 8s and wakes up. Meanwhile the second worker finished and wrote. But the first worker wakes up, completes its work, and writes anyway. The stale value overwrites the fresh one. No exception, no log — the same species of accident as no. 15. Only the result is wrong.

4. Now turn on fencing tokens — this time it works

fencing token on stale write becomes final 16.0% → 0.0% · writes rejected 0.16 duplicate execution still 100.0% · same job still 2.00×

The resource has already seen token 2, so it rejects token 1's write. The result is correct again. And duplicate execution did not drop one decimal. The same job still ran twice, and two of them were still inside the critical section. What fencing bought is correctness; what it never bought is mutual exclusion.

5. Turn on auto-renew — duplicates go away, as long as the pause is short

auto-renew on · renew every 1000ms · pause length 4.0s duplicate execution 100.0% → 20.0% · same job 2.00 → 1.20× the remaining 20.0% is exactly the cases where a pause happened

The watchdog pushes the expiry out every second, so the lock survives even though the work is longer than the TTL. Recipe 1's problem is gone. What remains is 20.0% — exactly the pause chance, because during a pause the renewal thread is frozen too. Renewal is something a thread does, and a GC pause stops that thread as well.

6. Renew ten times as often — still helpless against a 4-second pause

renew every 1000 → 100ms (10× as often) 2.5s pause: 20.0% → 0.0% (survived) 4.0s pause: 20.0% → 20.0% (did not)

Renewing more often stretches the survivable pause to TTL − renewal interval. A 2.5s pause is covered now. But the ceiling is the TTL itself. Drive the interval to zero and you get TTL − 0 = TTL, and a 4-second pause is longer than a 3-second TTL. No. 2 measured G1 stopping for 538ms on a 128GB heap; swap or a full GC goes into whole seconds.

7. Push the TTL above work + pause — 0% duplicates, and nine seconds

lock TTL 3.0 → 9.0s (work 5s + pause 4s) duplicate execution 0.0% · same job executed 1.00× waiting on a dead worker's lock up to 9.0s

Duplicates are finally zero. The price shows up when an instance dies — a dead process cannot release its lock, so the next instance simply waits nine seconds for the expiry. A TTL sets two numbers at once: it is your safety margin and it is your failure-recovery delay.

What a fencing token does and does not prevent

The comparison table in the lab is the point of this page. Change only the defence, on the same configuration, and a fencing token moves exactly one column.

DefenceDuplicate executionStale write becomes final
none100.0%16.0%
fencing token100.0% — unchanged0.0%
auto-renew20.0%0.0%
A lock does not guarantee mutual exclusion. What a lock with an expiry gives you is the optimisation that usually only one runs, and correctness comes from the resource. If the resource does not participate, there is nothing you can do.

So the real question is not "which lock should I use" but "can my resource check a token". Usually it cannot. A conditional update (WHERE version = ?), a conditional write (S3 If-Match) and a unique constraint are the tools you have; a plain UPDATE ... SET or an outbound API call has nowhere to put the check.

With nowhere to put the check, what is left is idempotence — making the same job produce the same result when it runs twice. Instead of straining to prevent duplicate execution, you move to making duplicate execution safe. No. 5 reached exactly the same conclusion about QoS 1: exactly-once delivery is expensive, and allowing duplicates and being idempotent is usually cheaper.

The moment a pause exceeds the TTL

There is exactly one condition under which a stale write becomes the final state.

pause > TTL. In the lab a 3000ms pause gives 0.0% and a 3100ms pause gives 16.0%. It is a cliff. If the frozen worker wakes up later than its replacement finished, its stale write arrives last.

With auto-renew on, the boundary moves to TTL − renewal interval. Where in the renewal cycle the pause begins decides whether the real margin is closer to TTL − interval or to TTL, and since safety is decided by the worst case, the lab draws the pause as starting just before a renewal.

What matters is that either way the ceiling is the TTL. And raising the TTL above the worst-case pause makes that same number your failure-recovery delay. There is no good value — there is only a choice about which price to pay.

Redlock does not touch this problem

Running the lock across several servers (Redlock) solves the availability of the lock store. Nothing on this page went wrong in the store.

Where it went wrongDoes Redlock change it?
the client froze (GC, swap)No. However many nodes you add, a frozen client cannot send a renewal
the work outlasted the TTLNo. The TTL is unchanged
the resource does not look at tokensNo. That is the resource's side
one lock server diedYes. This is the problem Redlock actually solves

Which is why there is no dial in the lab for the number of lock servers. Adding one would not move a single meter.
