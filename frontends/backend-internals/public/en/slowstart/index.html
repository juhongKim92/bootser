One byte bigger and it costs another round trip

A 14,600-byte response goes out in one round trip. 14,601 bytes takes two. One byte is worth an entire round trip. TCP does not use the whole line from the start — it feels its way up. So transfer time does not scale with size; it is a staircase of round trips.

Work the dials

DialWhat it changes
Response sizeBytes sent in one go. Flip between 14,600 and 14,601 — this whole page is about that one byte.
Initial windowSegments allowed in the first round trip. 3 is the RFC 3390 era, 10 is what RFC 6928 made standard, 30 is what some CDNs raise it to by hand.
Round-trip timeHow long one round trip takes. The number of round trips does not depend on it — only the height of each step changes, never where the steps fall.
ConnectionNew adds a handshake round trip and starts the window at its initial value. Reused means the window is already large, so the staircase disappears.
Delayed ACKWhether the receiver sends one ACK per two segments. On, the window grows 1.5× per round trip; off, 2×. Saving ACKs costs growth.

One segment is 1,460 bytes (MSS). The round-trip count is a function of size and initial window only, so it comes out of a closed-form expression — no randomness and no samples.

Things to try

1. 14,600 bytes — one round trip

Response size 14,600B · initial window 10 · RTT 100ms Round trips 1 · total 200ms (100 handshake + 100 transfer) Segments per round 10

10 segments × 1,460 bytes is exactly 14,600. It lands precisely on the initial window. Below this point shrinking the response buys nothing — a 1,000-byte response also takes 200ms.

2. Add one byte — one more round trip

Response size 14,600 → 14,601B Round trips 1 → 2 · total 200 → 300ms Segments per round 10 / 1

The second round trip exists to carry a single segment — it spends a whole 100ms delivering 1 byte out of a possible 1,460. This is where the intuition that transfer time scales with size breaks: it is a staircase.

3. 100KB on the old setting — seven round trips

Response size 100,000B (69 segments) · initial window 3 Round trips 7 · total 800ms Segments per round 3 / 4 / 6 / 9 / 13 / 19 / 15

The RFC 3390-era initial window. The window grows 1.5× per round, so starting at 3 it takes five round trips to become useful. The first three rounds carry 13 segments — 19% of the response.

4. Raise the initial window to 10 — no application change

Initial window 3 → 10 (size and RTT unchanged) Round trips 7 → 4 · total 800 → 500ms Segments per round 10 / 15 / 22 / 22

Same application, same response, same line. 300ms from one kernel setting. This is why RFC 6928 changed the standard, and Google measured it before proposing the change — those numbers are quoted below.

5. Turn delayed ACK off — the window doubles instead

Delayed ACK on → off (100KB · initial window 10) Round trips 4 → 3 · total 500 → 400ms Segments per round 10 / 15 / 22 / 22 → 10 / 20 / 39

Delayed ACK halves the number of ACK packets — and halves how fast the window grows, because each ACK opens the window by one segment. What it saves is ACK traffic; what it pays is early throughput. Usually a good trade, but not where the first response matters.

6. Reuse the connection — the staircase disappears

Connection new → reused (100KB · initial window 10) Total 500 → 100ms (no handshake, window already large)

The handshake round trip is gone and there is no slow start left to do. This is what keep-alive and connection pools actually buy you — not bandwidth, but skipping the staircase. If no. 8 was about pool size, this is why the pool exists.

7. Send 1MB — the smaller the response, the more the window matters

Response size 1,000,000B (685 segments) · initial window 10 Round trips 9 · total 1.00s · with window 3 it is 13 At 100KB it was 4 vs 7 (1.75×) · at 1MB it is 9 vs 13 (1.44×)

The window grows exponentially, so on big transfers the starting value gets washed out. Put the other way round: the smaller the response, the more the initial window is everything — and most backend responses live down there.

Why it is a staircase

TCP starts without knowing how fat the pipe is. So it sends one initial window and stops to wait for ACKs. An ACK means that much got through, so it opens the window and sends again.

How much it opens is the arithmetic of this page. In slow start, one ACK opens the window by one segment. But with delayed ACK the receiver only sends one ACK per two segments — so per round trip the window becomes 1.5×.

window → window + window/2
10 → 15 → 22 → 33 → 49 → 73 … With delayed ACK off it is window → window × 2, so 10 → 20 → 40.

Which means there is a fixed amount you can send in the first r round trips. Fit inside it and you pay r; exceed it by one byte and you pay r+1. With an initial window of 10 the boundaries are these.

The RFC hands you a table to check against

One thing had to be settled before writing this model: does the window grow 1.5× or 2× per round trip? The first draft assumed 2× — that is how slow start usually gets described.

But RFC 6928 prints a round-trip table comparing initial windows of 10 and 3.

Segments to sendInitial window 10Initial window 3

Compute with 1.5× and all six cells match. Compute with 2× and 21 segments at window 3 comes out at 3 (the RFC says 4) and 78 segments at window 3 comes out at 5 (the RFC says 7) — two cells wrong. The spec gave the algorithm, and the same document gave a point to check it against.

The lab reproduces that table directly — set the size to 30,660 bytes (21 segments) with an initial window of 3 and it returns 4 round trips. Being able to check the model against reality before building it is entirely thanks to that table.

RFC 6928 defines the initial window as min(10 × MSS, max(2 × MSS, 14600)). The cap is in bytes, which has an odd consequence: on a jumbo-frame path with an MSS of 8,960 the formula returns 17,920 bytes — two segments. Make your segments bigger and the count you may send in the first round trip drops from 10 to 2.

Bandwidth is not in this formula

What sets the round-trip count is the response size and the initial window, and nothing else. Line speed does not appear anywhere. Move to 1Gbps and 14,601 bytes still takes two round trips.

No. 19 arrives at the same conclusion for the steady state — ten times the bandwidth, 1.0× the throughput. This page is why the start behaves that way. It is the gap no. 19 marked when it said it does not cover the slow-start phase.

So the fix is not on the bandwidth side either. You can remove round trips (initial window, connection reuse), make a round trip cheaper (RTT — what a CDN sells), or keep the response under the step. That is the whole list.

What Google actually measured

RFC 6928 carries the evidence that changed the standard. Raising the initial window from 3 to 10 gave:

WhereAverage latency reduction
Average datacenter11.7% (68ms)
Low-bandwidth datacenter8.7% (72ms)
High-RTT, high-BDP pathsover 20%
Low-RTT pathsabout 5%
The cost — retransmission rate1.98% → 2.29% · 3.54% → 4.21%
Those are Google’s measurements, not this lab’s output. All the lab computes is the round-trip count and what those round trips cost in time.

Note the retransmission rate went up too. It is not free — pushing more into the first round trip means dropping more on narrow paths. It was still worth changing because the latency gain was larger, and that table is the argument.

What this model assumes

AssumptionWhat breaks if it fails
No lossLose a single packet and you leave slow start for congestion avoidance, where the window grows linearly instead of exponentially — many more round trips. That regime is no. 19’s square-root law
The receive window is not the limitIf the peer’s receive buffer is small, the congestion window does not matter — the smaller of the two wins. That is no. 19’s BDP
The bytes are readyThe application is assumed to already hold what it will send in the first round trip. If the server is still waiting on the database, an open window sends nothing
Reused means warm“Reused” assumes earlier transfers already grew the window. After a long idle the kernel shrinks it back (slow start after idle), so in practice part of the staircase returns
TLS is not countedThe handshake here is one TCP round trip only. TLS 1.3 adds one more and TLS 1.2 adds two — a staircase in front of the staircase

In the field

WhereWhat to check
Reading the current valueOn Linux, no initcwnd in ip route show means the default (10). Change it with ip route change … initcwnd 30 initrwnd 30 — note it is per route, not a global sysctl, which is the part people get wrong
First response size14,600 bytes is the magic number. Fit what the first screen needs inside it and you pay one round trip. Compression earns double here — not by saving bytes but by staying under the step
Connection reuseThe biggest win available. Check that keep-alive is genuinely alive and that the pool is not opening a fresh connection per request. This is where no. 8’s pool pays for itself
Reset after idleLinux shrinks the window after an idle period; net.ipv4.tcp_slow_start_after_idle=0 turns that off. A live connection with a cold window is a common state
Behind a proxyThe initial window is per hop. A TLS-terminating proxy splits the connection in two and each half slow-starts on its own — the same shape as ordering being per hop in no. 21
MeasuringCount round trips, not bandwidth. tcpdump shows how many bursts the first response leaves in. If your latency graph has visible steps, this is it
QUIC tooHTTP/3 also slow-starts. What it fixes is handshake round trips (0-RTT, 1-RTT), not how the window grows

If no. 19 was about why the steady state never fills the line, this page is about the start not even trying to. And most backend responses finish before the steady state arrives.
