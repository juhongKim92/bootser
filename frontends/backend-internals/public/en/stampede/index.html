The moment the TTL ends

Drive it yourself

dialwhat it changes
approachRe-runs all four from the same random seed. Requests arrive in the same order, so any difference is down to the approach alone.
request rate λRequests per second for this one key. Duplicate recomputes per expiry scale directly with it.
recompute time THow long it takes to refill the cache — the width of the window the stampede runs through.
TTLHow often it expires. It sets the frequency of the stampede, not its size.

The dotted line on the chart is the height of one recomputation. In a healthy system the bars sit on that line. A red column is a stampede.

Things to try

1. A 99.4% hit rate — nothing wrong on any dashboard

unprotected · λ 500/s · recompute 200ms · TTL 30s hit rate 99.4% · average recomputes 3.01/s and at the expiry instant, 101 at once

The hit rate is TTL / (TTL + T) = 30 / 30.2 = 99.34%. Recomputes average three a second. No average metric shows a problem. But those three do not arrive evenly — once every thirty seconds, 101 arrive together. Watch the column on the chart.

2. Drop the TTL to 3s — the column is exactly as tall

TTL 30s → 3s hit rate 99.4% → 94.1% · average recomputes 3.01 → 29.4/s duplicates per expiry still 100 · peak concurrent still 101

Shortening the TTL makes the column arrive more often, not lower. Its height is set by λ · T, and TTL does not appear in that. This is why "tune the TTL" never fixes it. Lengthening it only makes the incident rarer — and therefore more surprising when it lands.

3. Double the request rate — double the column

λ 500/s → 1000/s duplicates per expiry 100 → 201 · peak concurrent 101 → 202 hit rate unchanged at 94.1%

The hit rate does not move a single digit while the instantaneous load exactly doubles. The more popular the key, the more dangerous it is — the key getting the most value out of your cache is the key that blows up hardest. That is what λ · T means in practice.

4. Mutex / singleflight — the duplicates go, the waiting arrives

recomputes per expiry 100 → 1 · peak concurrent 1 in exchange, the other 99 wait up to 200ms hit rate 93.8% (essentially unchanged)

Only the first request through recomputes; the rest wait for its result. The column is gone. It was not free. λ·T − 1 = 99 requests are stopped for as long as the recomputation takes. The backend is protected, and those 99 still spend 200ms — the same trade as CallerRuns in page 11.

5. Probabilistic early expiry — the expiry never arrives

hit rate 100% · recomputes per expiry 1 · peak concurrent 1 waiting 0 · stale responses 0

Each request evaluates now − T·β·ln(rand()) ≥ expiry, so as expiry approaches it becomes increasingly likely that someone refreshes early. One volunteer steps up before the deadline and a hard miss never happens. The hit rate reaches 100%. The T in that formula is the point — the more expensive a key is to recompute, the earlier it volunteers.

6. stale-while-revalidate — serve the old value and buy time

recomputes per expiry 1 · peak concurrent 1 · waiting 0 in exchange, 100 stale responses per expiry

Hand back the expired value and refresh once in the background. No column and no waiting. The charge is accuracy — the 100 requests arriving in the 200ms after expiry get a stale value. Some data cannot take that (stock levels, balances) and some does not care (a trending list). You only ever get to pick one of the three.

Why the hit rate cannot show you this

There are two numbers. The average recompute rate is λ·T / (TTL+T) — 3.01 per second at the defaults. The instantaneous peak is λ·T — 101. A factor of thirty-three.

Size the worker pool from the average and three a second is plenty. What you actually need is 101 at once. The average is fine and the instant collapses.

This is Jensen's inequality from page 13 (plan cache) wearing different clothes. There the optimizer picked a plan from the average selectivity; here we size capacity from the average recompute rate. Both judge by the mean and both fail in the tail.

When expiries line up

That is one key. The real outages happen when many keys expire at the same instant — and that is remarkably easy to arrange.

whenwhy they line up
right after a deployThe cache starts empty and traffic fills it all at once. Filled together means the TTLs end together.
cache server restartSame reason. The second incident arrives exactly one TTL after recovery.
bulk refresh jobsPush everything in at 3am and it all expires at the same time the next day.
absolute TTLsexpireAt(midnight) is synchronised by design.

The fix is jitter on the TTL — something like TTL × (1 + rand()·0.2) scatters the expiries. It is exactly the prescription from page 14, where jitter on the backoff removed the retry waves, and it has exactly the same limit. Jitter spreads a clump; it does not reduce a total. It will not remove the stampede on a single key — for that you need one of the four approaches above.

In practice

wherewhat to check
Spring Cache@Cacheable is unprotected by default. With Caffeine, refreshAfterWrite is close to SWR, and a LoadingCache loader gives you per-key singleflight.
Redis + local cacheRedis does not stop stampedes. A mutex means taking a Redis lock yourself, which introduces the separate problem of a lock TTL shorter than the recomputation.
singleflight scopeWith ten instances, an in-process mutex only gets you down to ten. 100 → 10 is a real win but it is not 1. Getting to 1 costs a distributed lock.
early expiryStore how long the recomputation took alongside the value so you know T. That one extra field is the whole implementation.
TTL jitterAdd it. Just do not think it dealt with the stampede — it addresses synchronisation, not duplication.
measurementTrack peak concurrent recomputations, not the hit rate. Watch only averages and this problem stays invisible forever.
