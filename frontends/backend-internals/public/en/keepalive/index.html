Drive it yourself

Time does not run in this lab. Move a control and it recomputes the whole sequence of events for those conditions — there is no waiting out two hours and eleven minutes in real time.

Things to try

1. Toggle between clean close and power cut

leave detection on TCP default clean close detected immediately Will not published power cut detected 2h 11m 15s Will published

One button apart, and completely different outcomes. A clean close works because the client sends a FIN, so the server knows at once. Cut the power and nobody says anything. The only way the server can find out is to go and ask.

2. Look at what the TCP defaults actually are

power cut + TCP default tcp_keepalive_time 7200s (2 hours) tcp_keepalive_intvl 75s tcp_keepalive_probes 9 7200 + 75 × 9 = 7875s = 2h 11m 15s

Two hours before the first probe even goes out. That is the Linux default, and most servers run it untouched. For those two hours a dead client sits happily in the connected list.

Worse: TCP keepalive is off by default. Without SO_KEEPALIVE on the socket, even that two-hour timer never starts, and detection never happens at all.

3. Switch to app hang — the heart of this page

app hang + TCP default or TCP tuned detected never Will never published switch the same case to app keep-alive → 1m 30s

This is the important one. A process can deadlock, sit in a long GC pause, or exhaust its thread pool, and the kernel's TCP stack is entirely fine. A keepalive probe arrives and the kernel ACKs it on its own. TCP reports, quite correctly, that the connection is alive.

The trouble is that this is not what we wanted to know. TCP keepalive checks whether the wire is alive, not whether the application can do any work. For that, the application itself has to answer.

4. Push the keep-alive interval up

power cut + app keep-alive interval 10s → detected in 15s interval 60s → detected in 1m 30s interval 120s → detected in 3m (ties with TCP tuned) interval 300s → detected in 7m 30s (slower than TCP tuned)

MQTT disconnects when nothing arrives within one and a half times the interval. A longer interval means proportionally later detection. Past two minutes it becomes slower than a tuned OS setting (interval + 60s). Stretching the interval to save battery is not always the win it looks like.

5. Use Will Delay to stop phantom alerts

power cut + app keep-alive (60s) will delay 60s, reconnects after 100s detected 1m 30s Will scheduled for 2m 30s reconnected at 1m 40s ← back before it fired Will cancelled

Fire an "offline" alert every time a client goes through a tunnel and nobody trusts the alerts any more. MQTT 5's Will Delay Interval makes the broker wait a moment after detecting before publishing. Return on the same session in that window and the Will is quietly cancelled. Push the reconnect slider past the scheduled time and watch it fire after all.

Half-open connections

The normal way a TCP connection ends is an exchange of FINs. The catch is that this only happens when both sides cooperate.

situationFINwhat the server sees
clean closearrivesknows immediately
process killedarrives (the kernel sends it)knows immediately — usually an RST
power cutnevernothing at all
link goes downnevernothing at all
NAT or firewall entry expiresnevernothing at all

The bottom three are half-open connections. The server-side socket stays ESTABLISHED, shows up perfectly healthy in ss -tn, and counts toward your connection total. There is simply nobody on the other end.

Worth noticing: killing a process and cutting power are not the same thing at all. When a process dies the kernel survives it, cleans up the socket and sends a FIN or RST. Which means testing by hitting Ctrl+C on your dev server reproduces none of the problems on this page.

Wouldn't writing to it tell us?

It would. Write to a dead peer and TCP starts retransmitting, eventually gives up and surfaces an error. Just not quickly: with Linux's default tcp_retries2 of 15, that takes roughly fifteen minutes.

And it comes with a condition — you have to have something to send. A quiet chat room goes hours with nobody sending anything, and dead connections keep counting as live the whole time. That is exactly why keep-alive exists: to ask periodically even when there is nothing to say.

Three layers of keep-alive

The names are similar enough to blur together, but they sit at different layers and check different things.

layerwhat it verifiescatches an app hang?
TCP keepalivethe wire and the peer's kernel are aliveno
MQTT PINGREQ
WebSocket ping		the protocol layer respondsdepends on the implementation
application heartbeatthe application can actually do workyes

Watch that middle row. Browsers answer WebSocket ping frames with a pong automatically, even when the JavaScript is completely frozen. So a server that judges "client healthy" from ping/pong counts frozen tabs as healthy. On top of that, browser JavaScript has no API for sending ping frames at all, so the client-to-server direction has to be an application message anyway.

Which is why production converges on an application-level heartbeat — literally exchanging something like {"type":"ping"}. It looks crude, but it is the only way to verify that the application is alive and processing messages. For it to mean anything, the reply has to travel the same thread pool and the same event loop as real message handling.

Last Will and Testament

A Will is a note you leave with the broker when you connect: "if I disappear without saying goodbye, publish this for me."

MqttConnectOptions o = new MqttConnectOptions();
o.setWill("status/device-42", "offline".getBytes(), 1, true);
o.setKeepAliveInterval(60);
o.setCleanSession(false);

What matters is when it fires and when it does not.

situationWill
disconnects with a proper DISCONNECTnot published
keep-alive timeoutpublished
network error or power cutpublished
broker closes it on a protocol errorpublished
the broker itself goes downnot published — the one holding the note died

That first row is the design intent. A client shutting down cleanly can tidy up its own state, so it needs no will. The fact that a Will was published is itself the signal that something ended abnormally.

The last row is the trap people miss. When a broker dies every client disconnects, and not a single Will goes out — the executor of the will went down with them. Manage device presence purely through LWT and every device stays frozen as "online" through a broker restart.

MQTT 5 adds one exception. Send a DISCONNECT with reason code 0x04 (Disconnect with Will Message) and the Will is published despite the clean close — for the case where the shutdown is planned but the status message is still wanted.

Building presence that actually works

A Will is an event, not a state. Try to reconstruct state from events alone and it drifts. A combination that holds up in production looks like this.

  • On connect — publish online retained, so anyone subscribing later immediately gets the current state
  • Will — register offline retained, so the broker overwrites it for you on an abnormal end
  • On clean shutdown — publish offline yourself, then DISCONNECT. No Will fires, so this is on you
  • Carry a timestamp so an out-of-order delivery cannot let a stale value overwrite a fresh one
  • Plan for broker restarts — the real source of truth is when something was last heard from. You need a sweeper that periodically ages stale entries out to offline

What to check in production

See whether connection counts exceed real users. Accumulating half-open connections show up here first. If your connected count creeps upward and drops sharply on restart, this page is your problem.

# connections the server is holding
ss -tn state established '( sport = :8080 )' | wc -l

# whether keepalive is actually on, and how much timer is left
ss -tno state established '( sport = :8080 )' | grep -o 'timer:([^)]*)' | sort | uniq -c

# current kernel settings
sysctl net.ipv4.tcp_keepalive_time net.ipv4.tcp_keepalive_intvl net.ipv4.tcp_keepalive_probes

No timer:(keepalive,...) on a socket means SO_KEEPALIVE is off for it, and no amount of kernel tuning will apply.

Check the idle timeouts of everything in the path. This is the most common real-world trap.

devicedefault idle timeout
AWS ALB60s (configurable)
AWS NLB350s — not configurable
nginx proxy_read_timeout60s
carrier NATusually minutes, never announced

If your keep-alive interval is longer than any of these, the middlebox closes the connection first. And plenty of them drop it silently, leaving a half-open connection neither side knows about. The rule is simple: your keep-alive interval must be comfortably shorter than the tightest idle timeout on the path. Behind an NLB that means well under 350s — 30 to 60 seconds is the usual choice.

Derive detection time backwards from your SLA. Start from "how fast do we need to know", put that into 1.5 × interval and solve. Need to know within 30 seconds? The interval is 20.

Then price it. A hundred thousand devices pinging every 30 seconds is 3,300 packets per second. On battery-powered devices, a shorter interval is battery burn. Fast detection and idle cost pull directly against each other, and the interval slider in this lab is that trade.

This model is simplified for teaching. Real detection times depend on when the last packet actually went out, how retransmission backoff overlaps, and whether a middlebox closes things first. Read the numbers here as the worst case, assuming the connection was active right up until the moment of death.
