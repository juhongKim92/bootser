Going from 31 threads to 256 drops throughput from 9.04 to 3.24 — a factor of 2.79. But response time is far worse than that: 23 times. On a throughput graph this reads as "slightly worse". What users experience is the other number.

Three symbols

SymbolMeaning
nConcurrency. Thread-pool size, worker count, in-flight requests — however many of the thing you are increasing
σ (sigma)Serial fraction. The share that only ever passes one at a time no matter how many threads there are: locks, a single connection, an ordered queue
κ (kappa)Coherency cost. What threads spend coordinating with each other — cache-line invalidation, lock contention, coherency traffic. It grows with the number of thread pairs, so it enters as n(n−1)

σ and κ are dials, not constants I picked. Your system's values have to be fitted from load tests — what this page does is show you what shape follows once those two are known.

Things to try

1. One thread — the starting point

n=1 · σ=5% · κ=none (0) Throughput 1.00 · response time ×1.00

The baseline. With κ at zero the USL becomes exactly Amdahl — the two curves overlap. Zero κ means no retrograde region. Adding threads is always a gain, or at worst not a loss.

2. Push to 256 (κ=0) — you hit the ceiling

n 1 → 256 (κ still 0) Throughput 1.00 → 18.62 · Amdahl ceiling ×20.0 Response time ×13.75

256 times the threads for 18.62 times the throughput. With σ=5% the ceiling is 1/0.05 = 20× and no amount of threads passes it. That is Amdahl's law — diminishing returns, never negative ones. Response time is already 13.75× though.

3. Switch on the coherency cost — throughput falls to 3.24

κ 0 → 0.001 (n still 256) Throughput 18.62 → 3.24 · Amdahl still says 18.62 Peak n*=31 · response time ×79.03

Same thread count, 5.7× less throughput. κ is paid per pair of threads, so it enters as n(n−1) and dominates the denominator as n grows. The Amdahl curve (blue) keeps climbing while the USL (green) has already bent and come back down. Watch where the two diverge.

4. Come down to the peak — 8× fewer threads, 2.8× the throughput

n 256 → 31 (= the peak n*) Throughput 3.24 → 9.04 (2.79×) Response time 79.03 → ×3.43 (23× better)

Removing threads multiplied throughput by 2.79. And response time improved 23-fold. This is the heart of the page — the peak is n* = √((1−σ)/κ). With σ=5% and κ=0.001 that is √(0.95/0.001) = 30.82.

5. Overshoot slightly — throughput barely moves

n 31 → 64 Throughput 9.04 → 7.82 (−13%) Response time 3.43 → ×8.18 (2.4× worse)

Throughput fell only 13%. A throughput dashboard will not flag that. Response time, meanwhile, went up 2.4×. Near the peak the two metrics come apart — throughput bends gently while latency climbs steeply. Little's law is why (below).

6. Halve the serial fraction — the ceiling moves, the peak does not

σ 5% → 2% (n=31 · κ=0.001) Amdahl ceiling ×20.0 → ×50.0 Peak n* 30.82 → 31.30 (barely moves)

Halving the serial section is major work, and the ceiling went up two and a half times. But the peak moved from 30.82 to 31.30 — half a thread. σ only appears inside (1−σ) in the peak formula. What sets how far you can scale is not σ but κ.

7. Five times the coherency cost — the peak halves and more

κ 0.001 → 0.005 (σ=5%) Peak n* 30.82 → 13.78 · best throughput 9.04 → 5.47

Five times κ shrinks the peak by √5. So 14 threads is the best you get and anything beyond is a loss. Reducing κ comes before adding threads — removing shared state, sharding, splitting locks is that work.

The two formulas

Amdahl — S(n) = n / (1 + σ(n−1))
With a serial fraction σ you never pass 1/σ. Returns diminish; they do not go negative.
USL — C(n) = n / (1 + σ(n−1) + κn(n−1))
Add κn(n−1): a cost per pair of threads, growing as n². Past some point the denominator outruns the numerator.

That point is the peak. Differentiate, set to zero, and n* = √((1−σ)/κ). Turn the dials and the "peak" meter always agrees with that formula.

Response time breaks first

Throughput and response time are tied by Little's law: with n in flight and throughput C(n), one request takes n / C(n).

That is where the asymmetry comes from. Past the peak the numerator keeps growing while the denominator shrinks, so latency degrades from both ends at once.

This edition's checkpoint is mathematics

Other editions on this site had a checkpoint from outside — a second example in a paper, a table printed in an RFC, a total stated in a man page. This one is different.

The USL is not a specification but a fitted model. σ and κ are values you fit from measurements, not values I get to choose. So the coefficients are exposed as dials, and what gets verified is not the coefficients but the two points the formulas produce.
What is checkedHow
The Amdahl ceiling1/σ. That no n ever passes it — checked across every combination
The USL peak√((1−σ)/κ). That the rounded integer really is the maximum — checked exhaustively from 1 to 256
With κ=0The USL must equal Amdahl exactly

So read this page as "if σ and κ look like this, the shape looks like that" — not as "my throughput is 9.04". You take away a shape, not a number.

What this model assumes

AssumptionWhat breaks if it fails
Steady stateLoad is assumed constant. Bursts are no. 27; not recovering afterwards is no. 14
σ and κ are constantsIn reality they shift with load — lock contention changes character as threads grow, caches fall off a cliff once the working set grows. Do not extrapolate outside the fitted range
Threads are homogeneousEvery thread is assumed to do the same work. Mixed workloads have no single σ
The measurement is honestThroughput and latency are assumed measured correctly. On a closed-loop load generator, no. 25 stacks on top of this — you may not be able to see the past-the-peak state at all

In the field

WhereWhat to check
Measure firstVary the thread count across several values and record throughput. Three points are enough to fit σ and κ. Measuring one point and then scaling up is how this starts
Am I past the peak?Try removing threads. If throughput goes up, you were past it. The test takes five minutes and almost nobody runs it
Which metricResponse time, not throughput. Near the peak throughput bends gently and latency climbs steeply — watch the one that breaks first
Reducing κRemove shared state, shard, split locks, go thread-local. Halve κ and the peak rises by √2 — do this before adding threads
Virtual threadsCreation cost goes to nearly zero but σ and κ are unchanged. If anything concurrency now grows so easily that overshooting the peak is easier — which is why putting a limit back with a semaphore or a connection pool becomes the answer (no. 8)
Pool sizeThe same curve. Growing the pool raises κ on the database side and lowers the peak. No. 8's "a smaller pool is faster" is this formula in other words
No extrapolatingDo not measure 16, 32, 64 and predict 1024. κ is not constant across that range. Use the fit to decide where to measure next, not to predict

If no. 8 was about why a smaller pool is faster, this page is about whether that optimum can be computed. The answer — yes, but only after you measure.
