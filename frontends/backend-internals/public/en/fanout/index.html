The servers did not get slower. The users did

One server usually answers in 10ms, and once every hundred requests it takes a second. That is a perfectly decent server. But the moment one screen asks a hundred such servers in parallel, 63.4% of users wait a second. Nothing about the server changed. The only thing that grew is the count.

Work the dials

DialWhat it changes
Fan-out widthHow many servers one round calls in parallel — the number of pieces a single screen needs: shards, partitions, microservices, cache nodes.
Chance one server is slowHow often one server answers on the 1000ms side instead of 10ms. Turning this dial is the only way to change the server at all — and most of this page leaves it alone.
Rounds per screenHow many times that fan-out happens in sequence — fetch the list, then the details, then the permissions. Servers touched is width × rounds.
Second copyIf the first answer has not arrived, send the same request to another replica and take whichever returns first (a hedged request). This is not a retry — the first request is not cancelled, the second one overlaps it.
When to send itHow long to wait before sending the copy. 10ms is a cliff — fire earlier than the fast answer and every single request goes out twice.

The meters are not samples. One server’s response is reduced to two points (10ms and 1000ms), so everything is a closed-form calculation. There is no randomness: the same dials always give the same numbers.

Each cell in the grid is one user. The number of filled cells is the expected value, rounded — not the result of drawing a hundred users and counting.

Things to try

1. One server → a hundred. The server never changes

Fan-out width 1 → 100 (chance one server is slow stays 1%) Requests that get the tail 1.00% → 63.4% Versus one server ×1.00 → ×63.4 · mean response 20 → 638ms

Not one dial that touches the server was moved. 1% is still 1%. Only the count grew, and the share of users who feel it grew 63 times. A screen is slow if at least one of the hundred is slow, and that probability is 1 − 0.99100.

2. The width where half is crossed — 69

Fan-out width 68 → 69 Requests that get the tail 49.5% → 50.0% The “width that crosses half” meter had been reading 69 all along

From here on the median user gets the tail. This is not a p99 story any more, it is a p50 story. A 1% event on a server becomes the ordinary experience once the width passes 69. The point is the solution of 0.99N < 0.5, so the meter shows it whatever the current width is.

3. Make every server ten times better — still one user in ten

Chance one server is slow 1% → 0.10% (width stays 100) Requests that get the tail 63.4% → 9.52% Versus one server ×63.4 → ×95.2 · mean 638 → 104ms

Cutting a tail by a factor of ten is usually a quarter of work. The result is still one user in ten. And notice the amplification went up (×63.4 → ×95.2) — the better each server gets, the more of that gain fan-out eats. The improvement is linear; the thing multiplying it is exponential.

4. Turn the copy on — 63.4% → 0.995% for 1% extra load

Second copy on (sent at 30ms · server still 1%) Requests that get the tail 63.4% → 0.995% Versus one server ×63.4 → ×0.995 · mean 638 → 39ms Extra requests 1.00%

Six times better than the ten-fold server improvement in recipe 3 — without touching the server. A leaf is now slow only if both copies are slow, so its tail probability is squared, p → p². The amplification meter reading ×1.00 is the point: the tail a user feels is now the same as the tail one server has. The fan-out looks like it disappeared.

5. Send the copy at 5ms — same tail, a hundred times the load

When to send it 30ms → 5ms Requests that get the tail 0.995% → 0.995% (not one digit moves) Mean response 39 → 23ms Extra requests 1.00% → 100.0%

The fast answer arrives at 10ms, so firing at 5ms means every request goes out twice. The mean does improve (39 → 23ms) — that was not free, it was bought: double the traffic for 16ms. And the tail did not move at all. Everything the copy could cut was already cut at 30ms.

6. Two rounds — same tail as width 200, different mean

Rounds per screen 1 → 2 (width 100) tail 63.4% → 86.6% · mean 1275ms Width 200 · 1 round tail 86.6% · mean 867ms

The two tail probabilities are identical to the last digit, because the formula only sees servers touched (100×2 = 200×1). Tail probability cannot tell “split up” from “widened”. The means differ, though — 1275ms against 867ms — because sequential rounds add slow stretches while parallel width overlaps them. That is why splitting a service into lighter pieces leaves the screen exactly where it was.

How 1% becomes 63%

A screen is slow when at least one server is slow — not when all of them are. So it is easier to count the other side: everything is fast with probability (1−p)N, and all the rest is tail.

P(user gets the tail) = 1 − (1 − p)N
Hold the server’s own property p still and grow only N, and this climbs exponentially toward 1.

What makes this uncomfortable is that every dashboard stays green while it happens. The server mean did not move, nor its p50, nor its p99. The only thing that moved is how many servers one screen calls — and that is usually not a number anyone tracks as a performance metric.

The paper confirms this formula twice

The axis of this page is not a model I invented — it comes from Dean and Barroso, The Tail at Scale (CACM 2013). The paper says: “consider a system where each server typically responds in 10ms but with a 99th-percentile latency of one second … If a user request must collect responses from 100 such servers in parallel, then 63% of user requests will take more than one second.”

More valuable, though, is that the paper gives a second point on the same curve: “Even for services with only one in 10,000 requests experiencing more than one-second latencies at the single-server level, a service with 2,000 such servers will see almost one in five user requests taking more than one second.” Put p = 0.01% and N = 2000 into this model and it returns 18.1%. That is “almost one in five”.

One point can match by luck; two points mean the formula is right. That is the evidence this page did not simply implement an inherited explanation — checking it in the source before building the model is exactly what this step was for.

Why a copy beats improving the server

Send a second copy (a hedged request) and the condition for a leaf being slow changes from “it is slow” to “it is slow twice”. The probability goes from p to p². Improving a server divides p — that is linear. The copy squares it.

What you doResult at width 100
Nothing63.4% · mean 638ms
Make servers 10× better9.52% · mean 104ms — a quarter of engineering work
Send one more copy0.995% · mean 39ms — 1% extra load

The extra load is 1% because the copy only goes out on slow requests. The fast answer arrives at 10ms and we wait 30ms, so the only calls that get a copy are the slow 1%. The paper reports that in real systems the threshold is set at the 95th percentile, which limits the additional load to approximately 5%; and in a BigTable benchmark reading 1,000 keys spread over 100 servers, a hedging request after a 10ms delay cut the 99.9th-percentile latency from 1,800ms to 74ms while sending just 2% more requests.

Those figures — 5%, 1,800ms, 74ms, 2% — are Google’s measurements, not this lab’s output. All the lab computes is a probability and a weighted mean of two points.

What the lab does show is the cliff on the other side of the threshold. Drop the send time below 10ms and the copy goes out on every request: extra load 100%. The tail is unchanged. The same technique, the same result, a hundred times the cost — and the two settings sit right next to each other.

What this model assumes

AssumptionWhat breaks if it fails
Independence1 − (1−p)N holds when slowness on the servers is unrelated. A shared switch, a GC pause on a shared host, a hot shard — any shared cause correlates the leaves and the formula overestimates. The copy stops helping for the same reason: it inherits the shared cause
Two pointsA server answers at 10ms or 1000ms and nothing in between, which makes percentiles a staircase. That is why this page talks in probabilities rather than percentiles. Real tails are spread out, not a single value
Cancellation is freeWith the copy on, the losing request must be cancelled. If cancellation does not propagate, the loser keeps working and the extra load is larger than the number here — that is no. 17 territory
There is spare capacityA copy trades spare capacity for latency. If you are already saturated, no. 14 happens instead — the copies become the load

In the field

WhereWhat to check
The number to count firstNot server p99 — how many servers one screen calls. Very few teams track it. Count the downstream calls hanging off one correlationId and you have it
Copies vs retriesThey are different. A retry goes out after a failure is confirmed; a copy goes out alongside something still running. Cutting tails with retries means short timeouts, which starts the budget-splitting of no. 17
The thresholdSet it from a recent percentile of that call, not a fixed millisecond value. A fixed value sends every request twice on the day the service slows down — precisely the worst day for it
CancellationIf copies are on, the loser must be stopped. gRPC propagates ClientCall.cancel() into the server Context; plain HTTP clients often just drop the connection while the server keeps working
IdempotencyThe same request now executes twice. Use copies for reads, or make the write carry an idempotency key — the same condition as no. 9
Shrinking the widthThe most reliable fix there is: batch the lookups, defer the pieces that are off-screen, cache a leaf out of existence. Halve the width and the tail comes down near half — and no. 16 is what happens when that cache expires all at once
Partial answersDraw with whatever arrived instead of waiting for the slow leaf. If a few missing results are acceptable, this is the cheapest option of all — the paper calls them “good enough” responses
MeasurementPut server p99 and screen p99 side by side on one dashboard. The gap between them is the fan-out amplification — the “versus one server” meter on this page is exactly that number

If no. 17 was about how layers divide a budget they were given, this page is about how distributions combine inside it. There, three sensible values multiplied into a contradiction; here, one perfectly sensible probability is multiplied by a count and becomes a different number.
