Add a second instance and the same job runs twice

The batch ran fine for months. Traffic grew, you started one more instance, and from that day the same file gets processed twice. Nothing in the code changed. This defect never reproduces on a single instance.

Things to try

1. On one instance, press all four

1 instance in-memory excess runs 0% read-then-write excess runs 0% conditional UPDATE excess runs 0% SKIP LOCKED excess runs 0%

All four are flawless. No amount of testing separates them. This is why the defect survives into production — with one instance in dev and one in staging, the tests cannot tell these apart.

2. Go to two — in-memory collapses

2 instances · in-memory excess runs 0% → 100% every job runs twice

synchronized is only meaningful inside one JVM. The other instance does not know that collection exists. And because this strategy never changes the database state, the row keeps looking PENDING, so every polling instance claims it. Push to six instances and it becomes 500%.

3. Write the state — it looks fixed

2 instances · read-then-write excess runs 100% → 0.5% push to 6 instances → 2.5%

This is the most dangerous position on the page. Going from 100% to 0.5% looks like a fix. Tests pass, and watching it for a few days shows nothing. But 0.5% is not 0. At a hundred thousand jobs a day, five hundred of them run twice.

The window between the SELECT and the UPDATE is still open — narrower, not closed. A low-probability bug is not a fixed bug; it is a bug that is hard to reproduce.

4. Switch to a conditional UPDATE

6 instances · conditional UPDATE excess runs 2.5% → 0% wasted claims 0 → 5.00 / job

Duplicates are gone. Put WHERE state='PENDING' in the statement and the database lets exactly one instance through. But a new number appeared — the five losers' wasted attempts. Correctness is bought, and six instances now fight over the same row every time.

5. Switch to SKIP LOCKED

6 instances · SKIP LOCKED excess runs 0% wasted claims 5.00 → 0

The contention disappears too. Each instance skips rows already locked and takes a different batch, so there is nothing to fight over. This is why it is the standard way to build a job queue on PostgreSQL.

6. Turn on mid-job death — zombie rows

SKIP LOCKED · dies mid-job 15% · no reclaim zombie rows keep piling up claimed, and never finished turn the reclaim timeout on → zombies 0

Claiming is now exact, but what happens when you claim and then die is still unanswered. That row sets to RESERVED and nobody ever picks it up again. Jobs quietly disappear. Create a claimed state and you must create the path back out of it.

Why one instance hides it

The nature of this defect is right here: it comes from instance count, not load.

Load-driven problems reproduce when you apply load. This one never appears on a single instance no matter how hard you push, because inside one JVM synchronized genuinely works and there is no second instance to slip into the read-then-write window.

Which is why it gets reported as "sometimes a file is processed twice". It will not reproduce, so it is filed as a transient error — and the same report comes back a few weeks later. Starting two instances locally is enough to break that cycle.

The four strategies

1. In-memory collection with synchronized

synchronized (waitList) {
    if (!waitList.contains(id) && !runningList.contains(id)) {
        waitList.add(id);          // ← this JVM's memory
    }
}

Putting the check and the add in one critical section is correct. It does close the check-then-act race inside a JVM. The scope of that protection is simply that one JVM.

2. Read, then write the state

Job job = repo.findFirstByStateOrderById(PENDING);   // ← read
if (job != null) {
    job.setState(RESERVED);                          // ← write
    // another instance reading in between passes too
}

Moving from memory to the database is the right direction. What remains is that reading and writing are two round trips, and however short the gap, a window is a window.

3. Conditional UPDATE — atomic claiming

UPDATE job
   SET state = 'RESERVED', reserved_by = :me, reserved_at = now()
 WHERE id = :id
   AND state = 'PENDING';        -- ← this condition is the whole trick

-- proceed only when rowCount == 1. Zero means someone else took it

Collapsing read and write into one statement removes the window. The database serialises on the row lock, so however many instances fire at once, exactly one gets rowCount = 1. No in-memory lock and no separate distributed lock required.

4. SELECT … FOR UPDATE SKIP LOCKED

SELECT id FROM job
 WHERE state = 'PENDING'
 ORDER BY id
 LIMIT 10
 FOR UPDATE SKIP LOCKED;         -- step over rows already locked

The conditional UPDATE is correct, but everyone aims at the same row, so wasted attempts grow linearly with instance count. SKIP LOCKED steps over locked rows entirely, so each instance takes a different batch and contention goes to zero.

Available from PostgreSQL 9.5 and MySQL 8.0. Raise the LIMIT to claim several at a time and cut your polling frequency as well.

Claiming, then dying

Once claiming is exact, the next question arrives: who undoes a job that was claimed and then abandoned?

Nobody. That row stays RESERVED forever. It does not show up in queries, it never counts as a failure, and it behaves exactly like a job that was never there.

-- return rows that have been held too long
UPDATE job
   SET state = 'PENDING', reserved_by = NULL, reserved_at = NULL,
       attempt_count = attempt_count + 1
 WHERE state = 'RESERVED'
   AND reserved_at < now() - interval '10 minutes'
   AND attempt_count < 5;        -- do not retry forever

There is a trap here. The timeout must be comfortably longer than your maximum processing time. Reclaim a job from an instance that is still alive and working, and the claiming you just made exact turns straight back into duplicate execution.

When processing times vary wildly, use a heartbeat instead of a fixed timeout: refresh reserved_at periodically while processing, and reclaim on "last refresh is old". Live jobs keep refreshing and never get reclaimed.

Do not forget attempt_count alongside it. A reclaim path on its own gives you jobs that are reclaimed forever and fail forever, burning resources on every pass. Past the limit they have to move to a terminal state.

It is still not exactly-once

Make claiming atomic, add reclaiming, and you have at-least-once. Finish a job and die just before writing DONE, and it gets reclaimed and run again.

So the last line of defence is always the same: make the job itself idempotent. Put a unique constraint on the job id where results are written, use an upsert, or check for already-processed and skip.

Claiming is the mechanism that reduces duplicates; idempotency is the mechanism that makes duplicates safe. They are layers, not alternatives.

What about a distributed lock?

A Redis-based distributed lock (Redisson and friends) solves the same problem. For a job queue, though, a conditional UPDATE or SKIP LOCKED is usually the better fit.

  • It adds a dependency. The job table is already in the database; pulling in Redis purely for the lock is a strange trade
  • If lock expiry and processing time disagree, you get an instance still working after its lock has been released. Same shape as the zombie-reclaim trap, except this one happens silently
  • Job state and lock live in different stores, so now you have consistency to maintain between them. They cannot share a transaction

Making sure a scheduler fires on only one instance (ShedLock and similar) is a different matter. That is choosing who runs, not claiming work, and sits at a different layer from this page.

What to check in production

Run two instances locally. Start two on different ports against the same database and most of what this page describes surfaces within minutes. A single-instance test proves nothing in this area.

Put these queries on a dashboard.

-- zombie rows: claimed long ago, still unfinished
SELECT state, count(*), min(reserved_at), max(now() - reserved_at) AS oldest
FROM job
WHERE state = 'RESERVED'
GROUP BY state;

-- jobs accumulating retries — stuck in a reclaim loop
SELECT id, attempt_count, reserved_by, reserved_at
FROM job
WHERE attempt_count >= 3
ORDER BY attempt_count DESC
LIMIT 20;

A steadily growing oldest in the first query means there is no reclaim path. A growing count in the second means reclaiming works but the jobs keep failing for the same reason.

Count duplicate executions directly. If your result table has a unique constraint on the job id, constraint violations are your duplicate count. If it does not, now is a good time to add one — it both prevents and counts.

Log which instance claimed what. Write your instance identifier into reserved_by and put it in the log MDC, and you can trace after the fact which instance took a job. Without it, the logs cannot tell you when a duplicate happens.

The order. When you hit duplicate execution, work through it like this.

  1. Check how many instances are running — one means this is not your problem
  2. Check whether the claim is one statement. Two round trips is your cause
  3. Check whether the claimed state has a path back out
  4. Check that the reclaim timeout exceeds your maximum processing time
  5. Then check whether the job is idempotent — that layer remains after all four
This model is simplified for teaching. The duplicate probability for read-then-write assumes a 1-second poll interval and a 5-millisecond gap between read and write. Real probabilities depend heavily on poll interval, query latency, and how much the instances' polling schedules overlap. The point is not that the number is small — it is that the number is not zero.
