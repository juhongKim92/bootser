The same number, different on two screens

The detail screen says 48.32. The statistics screen says 60.42. Same metric, same period, same database. You put the two queries side by side to find the bug and they are both correct. One is the overall weighted mean and the other is the mean of daily means. What is wrong is not a value — it is that there are two definitions.

Working the dials

DialWhat changes
sample skewSkews the per-day row counts (the total stays at 300). Only the weighted mean moves; the mean of daily means does not.
stored precisionHow many decimals the daily mean is stored with. Cut it and there is no way back to agreeing with the source.
roundingtrunc · numeric · double. Same decimal place, three different stored values.
day grouping · boundary rowsWhich day the rows near midnight land in. The weighted mean does not budge; only the mean of daily means moves.

The data is three days. Every row within a day has the same value (40.25, 60.75, 80.25) and each day starts with 100 rows. Bar width is the row count and height is that day's mean.

The values 0.25 and 0.75 were chosen deliberately. They are exactly representable in binary floating point, so rounding to one decimal produces a genuine tie and the tie-breaking rule actually applies. A value like 0.35 does not exist exactly in binary at all, so there is no tie to break — which is worse, and covered below.

Try this

1. Even counts and exact storage — the two paths agree

skew 0% · exact storage · 100 rows per day path A 60.4167 · path B 60.4167 · difference 0 decimals in agreement 6

The baseline. With equal row counts a weighted mean and an unweighted one coincide, because all the weights are the same. This is the only place the two screens show the same number — and row counts are rarely equal day to day in practice.

2. Skew the samples — a gap of 12.1

skew 0% → 60% (row counts 100/100/100 → 220/40/40) path A 60.4167 → 48.3167 path B unchanged at 60.4167 · difference 12.1000

The rows piled up on day one, whose value is the lowest (40.25), so the overall weighted mean falls. And the mean of daily means does not move a digit — each day's mean is unchanged and you are adding three of them and dividing by three. Ignoring row counts is that path's definition. Push the skew to 90% and the gap reaches 18.15.

3. Store one decimal — 0.05 remains

skew back to 0% · stored precision exact → 1 decimal (trunc) stored values 40.2 · 60.7 · 80.2 path B 60.4167 → 60.3667 · difference 0.0500

The skew is gone and they still differ. Precision discarded at write time does not come back. The source still knows 40.25 and the stored value only knows 40.2. The only way to make them agree is to cut the source down to the same decimal place too — agreeing by throwing accuracy away.

4. Swap trunc for round — 0.05 the other way

rounding trunc → round · numeric stored 40.2·60.7·80.2 → 40.3 · 60.8 · 80.3 path B 60.3667 → 60.4667

trunc(v, s), in the words of the PostgreSQL documentation, "Truncates v to s decimal places" — it discards. round rounds. Same one decimal, completely different stored values. If one screen uses trunc and the other uses round, matching the decimal places will never make them agree.

5. Same round, only the type changes — different again

rounding round · numeric → round · double stored 40.3·60.8·80.3 → 40.2 · 60.8 · 80.2 path B 60.4667 → 60.4000

Same value, same function, same decimal place — and it differs because of the type. The PostgreSQL docs spell it out: for numeric, "ties are broken by rounding away from zero"; for double precision, "platform dependent, but round to nearest even is the most common rule". 40.25 becomes 40.3 under numeric and 40.2 under double (2 being even). And the double side is platform dependent — the same code can answer differently on another server.

6. Move the day boundary — only one side moves

exact storage · grouping UTC → local (+9) · boundary rows 40 row counts 100/100/100 → 60/140/100 · day 2 mean 60.75 → 54.89 path A unchanged at 60.4167 · path B 60.4167 → 58.4643

This is the heart of the page. Forty rows near the boundary moved from day one to day two. They carry their values, so day two's mean is now a blend. And path A does not budge — averaging the same set of rows in one pass does not care where the day boundaries are. Change the timezone and only one screen's number changes.

7. Stack all three — 8.65

skew 60% + 1-decimal double storage + local grouping + 40 boundary rows path A 48.3167 · path B 56.9667 · difference 8.6500 decimals in agreement 0

The three causes push in different directions, so fixing any one of them leaves the values apart. This is why the investigation ends at "I matched the decimals and it still does not line up". There was never one cause.

Both are right — there are two definitions

The longest part of debugging this is looking for which side is the bug. The answer is neither.

The two numbers are answers to different questions. "What was the average speed over this period?" and "What was the average of the daily average speeds?" are not the same question. Which one is correct is a product decision, and if you leave it to the code, each screen decides for itself.

No. 13 and no. 16 covered Jensen's inequality — judge by the average and break in the tail. Here the problem is averaging an average: the place where the weights get lost.

Making them agree means giving up accuracy

The common fix is "let us match the decimal places". It does work in the lab. The way it works is the problem.

FixOutcome
Cut both sides to one decimalThey agree. But you got there by discarding precision the source already had. The two screens match and both are now less accurate
Unify the rounding functionNecessary and insufficient. Even with trunc and round reconciled, differing types still split on ties
Unify the type as wellEven here, the weighting problem and the day-boundary problem remain — recipes 2 and 6 have nothing to do with rounding
Collapse to one pathThis is the only real fix. Compute in one place and have everything else read that result. It is not about matching values; it is about having one definition

In floating point a tie is not a tie

The lab's values are 0.25 and 0.75 on purpose. They are binary fractions, exactly representable, so rounding to one decimal creates a genuine tie and the rule really does decide the outcome.

A value like 60.35 does not exist exactly in binary floating point. What is stored is slightly above or slightly below it. So it is not "exactly halfway", no tie rule is invoked, and which way it rounds depends on the direction of that approximation. Unifying the rule does not make it predictable.

The PostgreSQL documentation warns about this directly — "Comparing two floating-point values for equality might not always work as expected" — and recommends numeric when you need exact storage. real carries at least 6 decimal digits and double precision at least 15.

Out in the field

WhereWhat to check
ask this first"What is the definition of this number?" — before comparing queries. Until it is settled whether the metric is a weighted mean or a mean of daily means, neither query can be fixed
count the pathsGrep for how many code paths compute the same metric. More than one and they will diverge eventually. Collapse to one and have the rest read its result
stored precisionCut decimals when persisting an aggregate and there is no way back to agreeing with the source. If you are going to cut, the source-side display has to cut the same way — and that is a decision to be less accurate
roundingtrunc discards (trunc(42.4382, 2) → 42.43). round rounds, but numeric breaks ties away from zero while double precision usually rounds half to even and is platform dependent. The same value can round differently on different servers
typesUse numeric when you need exact storage. An aggregate stored in real (6 digits) has already lost precision at larger magnitudes
timezonesPin the storage, transport and display convention in one document. Pick UTC storage with conversion at display time, or the other way, and make sure two APIs never group the same metric by different bases. Metrics with a lot of data near the boundary — overnight trips, late-night orders — diverge the most
regression testsOnce the paths are unified, add a test that compares the two API responses. Catching a re-divergence in code review is not realistic

If no. 15 was results going wrong because of concurrency, this page is results being two things because the definition split. Both are silent — no exception, no log, just different numbers. Except here what is missing is not code to fix but a definition to decide.
