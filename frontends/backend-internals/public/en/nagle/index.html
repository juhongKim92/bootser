Two small writes cost forty milliseconds

The same 400 bytes takes 1ms as one write() and 42ms as two. Same byte count, same link, same everything else in the code. The sender waits for an ACK while the receiver waits for a timer — two algorithms, each sensible on its own, waiting for each other.

Work the dials

DialWhat it changes
How it writesSplit calls write() several times (header, then body). Joined hands over the same bytes in one call. This dial is the whole page.
write() callsHow many writes happen before the response is read. It stalls from 2 onward, and 3 or 4 are no worse — the reason is below.

Every instant here is determined — no randomness, no samples. One segment is 1,460 bytes (the MSS).

Things to try

1. One write — nothing happens

1 write × 200B · Nagle on · delayed ACK 40ms · RTT 1ms Total 1ms · packets 1 · added delay none

There is no unacknowledged data, so Nagle has nothing to hold. The request lands half a round trip later and the receiver puts its ACK on the response — the delayed-ACK timer has no reason to run. Up to here, neither algorithm is visible.

2. Split it in two — 42ms

write() 1 → 2 (200B each · 400B total) Total 1 → 42ms · added +41ms · packets 3

The first 200 bytes go out immediately. Nagle holds the second 200 — the first is still unacknowledged and this is not a full-sized segment. But the receiver cannot produce a response (the request is incomplete), so it has no data to carry an ACK, and the 40ms delayed-ACK timer becomes the only way out.

3. Join the same bytes — back to 1ms

How it writes: split → joined (400B in one call) Total 42 → 1ms · packets 3 → 1

The bytes sent are exactly the same. The only thing that changed is the number of write() calls. 400 bytes fit in one segment and nothing is unacknowledged, so it leaves at once. This is the cheapest fix available — not a kernel setting, not a socket option, a buffer.

4. Turn Nagle off — delay gone, packets up

Nagle on → off (TCP_NODELAY · still split) Total 42 → 1ms · packets 2

With nothing holding it, the second segment leaves immediately. The symptom is gone and the cause is not — 400 bytes still travel as two packets. For a service doing tens of thousands of small writes per second, that packet count is the bill. Which is what Nagle existed to prevent.

5. Turn off delayed ACK on the receiver — 2ms

Delayed-ACK timer 40ms → off (TCP_QUICKACK) Total 42 → 2ms · still slower than joining the write (1ms)

The ACK leaves at once, so Nagle releases immediately. But it is not free — one extra round trip (1ms → 2ms). More importantly, this dial is on the other side. That is how "we changed nothing and it got better after they touched their server" happens.

6. Write 1460 bytes at a time — no stall

Bytes per write 200 → 1,460B (= MSS · still 2 split writes) Total 42 → 1ms · ACKs 1

Both are full-sized segments, so Nagle does not hold them (it only defers *small* ones). And the receiver does not defer either, because RFC 1122 says in a stream of full packets there should be an ACK for at least every other packet. Two segments, one ACK — no room for the timer.

7. Joining is not always enough — a small tail stalls too

700B × 3 written joined (2,100B total) Segments 1,460 + 640 · total 42ms

One write, and it still stalls. 2,100 bytes exceeds the MSS, so it splits into one full segment plus a 640-byte tail, and Nagle holds that tail. "Just join the writes" only holds while the request fits in one MSS. Beyond that you need a different fix.

What each algorithm was protecting

Both fixed a real problem in the 1980s, and both are still mostly right.

AlgorithmWhat it saves
NaglePacket count. It stops you spending a 41-byte packet to carry one byte. One rule: while unacknowledged data is outstanding, defer small segments. RFC 1122 §4.2.3.4 makes it a MAY and says an application must be able to turn it off
Delayed ACKACK packet count. It avoids packets that carry an ACK and nothing else. If there is a response to ride along on, it rides; otherwise it waits a moment

The trouble is where "waits a moment" meets "waits for an ACK". The sender says it will send once an ACK arrives; the receiver says it will ACK once it has data to send. But the data has not fully arrived, so there is nothing to send. Each is waiting on the other.

This is not a deadlock — a timer breaks it. But that timer is 40ms, and in a world where a datacenter round trip is 1ms, that is forty times the cost.

The RFC marks the fork

Why do full-sized segments escape? RFC 1122 §4.2.3.2 permits delayed ACK with this condition attached:

"An ACK SHOULD NOT be excessively delayed; the delay MUST be less than 0.5 seconds, and in a stream of full packets there SHOULD be an ACK for at least every other packet."

Two things follow. First, the ceiling on deferral is half a second — 40ms is not the spec but a value Linux chose; push the dial to 500ms to see the worst the RFC allows. Second, a stream of full packets must be ACKed at least every other packet. So when segments are full there is no room for the timer to intervene.

Nagle's side points at the same place — it only defers small segments. Which means this problem needs "small" and "unacknowledged" to hold at the same time.

SituationDoes it stall?
One writeNo — nothing unacknowledged, so Nagle has nothing to hold
Two or more small writesYes — the picture on this page
Full-sized segmentsNo — Nagle lets them through and the RFC rule forces the ACK
One request → one responseNo — the receiver always has data to ride an ACK on

That last row matters. This only appears in a write-write-read pattern. Code that strictly alternates request and response never meets it — which is why it shows up out of nowhere after a library swap.

More writes do not make it worse

Push the write count to 3 and 4. It stays at 42ms. Surprising at first, but there is a reason.

When the application calls write() repeatedly, those bytes accumulate in the kernel send buffer. While Nagle waits for the first segment's ACK, writes 2, 3 and 4 are all sitting in that buffer — and the moment the ACK lands they leave as a single segment.

So it stalls exactly once. Ten writes still cost one 40ms wait. Put the other way round — reducing the number of writes does not help; getting to one does.

What this model assumes

AssumptionWhat breaks if it fails
The writes come back to backThe application is assumed to do no work between write() calls. With a long computation in between, the second write reaches the buffer late and goes out separately — which can mean more than one stall
The receiver answers only when completeIt is assumed to need the whole request first. A streaming protocol that emits something after the first chunk gets an ACK for free and never sees this
No lossA retransmission shifts every instant. That regime is no. 26 and no. 27
40ms is a Linux valueThe spec only sets the 0.5-second ceiling. It differs by OS and version, and Linux adapts it in some cases — never let code assume the exact number

In the field

WhereWhat to check
First thing to look atWhether the latency distribution has a bump near 40ms. It only shows in a histogram, never in the mean — only the stalled requests pay the 40
Order of fixes① buffer and write once (cheapest, and it lowers packet count) ② if that is impossible, TCP_NODELAY ③ if the other end is yours, TCP_QUICKACK. ① is rarely actually impossible
JavaWriting straight to an OutputStream without BufferedOutputStream turns each write() into a segment. Writing headers and body separately is especially common. Socket.setTcpNoDelay(true) exists, but the order above still holds
HTTP clientsMost already set TCP_NODELAY. But hand-rolled binary protocols and older RPC stacks often do not — check the socket options for real
Worse when you are closeAt 100ms RTT, 40ms is 40%. At 0.5ms RTT it is eighty times. The nearer you are, the more it hurts — the opposite of intuition
How to confirmtcpdump shows it plainly: one small segment leaves, then 40ms of nothing, then an ACK, then the next segment. That empty 40ms is the evidence
Before disabling NaglePrice the extra packets. A service sending very many small messages may find Nagle was earning its keep — there, batching in the application is the right answer

If no. 26 was about not sending when you could, this page is about both sides waiting while there is something to send. Neither is caused by bandwidth, and both hurt more inside the same datacenter.
