You added AsyncAppender and the logs went missing

You heard that synchronous logging holds up requests, so you wrapped the appender in AsyncAppender. But the default queue is 256 events, and the moment 51 slots remain it starts dropping INFO. Thirty thousand events a second disappear with no exception and no warning. What comes next is worse — when the errors start pouring in there is nothing left to drop, so your application threads block instead.

The dials

DialWhat it changes
queueSizeHow many events the queue holds. 256 is the documented default. Raising it delays the dropping — and lengthens the wait by exactly as much. That is Little's law.
discardingThresholdOnce remaining capacity falls to this share, TRACE·DEBUG·INFO are dropped. 20% is the default, and Keep all is the documented 0 — which turns out to invite blocking.
neverBlockWhen the queue is full, block or drop. The default is to block (false). Turn it on — the ERRORs start vanishing.
Arrival rateEvents the application wants to log. A service that writes 20 lines per request at 2,000 requests a second offers 40k.
Time per writeHow long the worker takes to dispatch one event. Its reciprocal is the pipe's throughput — 100μs means 10k events a second. The real cause is always this dial.
WARN·ERROR shareThe share of arrivals that cannot be dropped. A few percent in normal operation, and it spikes during an incident — which is this page's reversal.

Every value is determined — no randomness, no sampling. The excess always splits into exactly three parts that sum to (arrival − drain).

Things to try

1. The pipe keeps up — nothing happens

8k/s arriving · 10k/s draining · queue 256 · dropping at 20% queue 0 / 256 · dropped none · wait 0.1ms

Arrivals are below the drain rate, so the queue never grows. One event clears the pipe in 0.1ms — exactly the time to write it. Here AsyncAppender does precisely what it advertises. The trouble is that this is the normal state, not the interesting one.

2. Four times the arrivals — gone from 6.83ms on

arrivals 8k → 40k/s (drain unchanged at 10k/s) dropping from 6.83ms · INFO 30k/s lost · blocking none queue 205 / 256 · wait 20.6ms

The queue fills at 30k a second, and at 205 events (that is 256 − 51) dropping begins. From there the queue stops growing — the entire excess leaves as discarded INFO. The application notices nothing. No exception, no warning line, no metric. And the wait went from 0.1ms to 20.6ms, a factor of 206 — because 205 events are queued ahead of each new one.

3. The errors arrive — now it blocks

WARN·ERROR share 5% → 50% (an incident has started) blocking from 11.93ms · INFO 20k/s lost · ERROR calls block at 10k/s

Dropping only sheds INFO. But half of what arrives now is WARN or ERROR — 20k a second against a pipe that passes 10k. Dropping cannot close the gap. The queue takes on its last 51 events, fills, and put() starts blocking: every logging call now waits 100μs. Dropping was the valve that protected the application, and it is empty exactly when you need it.

4. Turn on neverBlock — the ERRORs vanish

neverBlock off → on (same incident) blocking none · but ERROR lost at 10k/s · INFO 20k/s

The blocking is gone. In its place, anything arriving at a full queue is dropped regardless of level. put() became offer(), and a failed offer simply disappears. The very ERRORs you would investigate the incident with are vanishing at 10k a second. This dial does not remove the cost — it converts blocking into loss.

5. Set "keep all" — and it blocks sooner

discardingThreshold 20% → keep all (0) · error share back to 5% blocking from 8.53ms · dropped none · absorbed 30k/s

This is the setting the documentation describes as "To keep all events, set discardingThreshold to 0". Not one line is lost. Instead the dropping threshold is gone, so the queue runs straight to 256 and blocks at 8.53ms rather than merely dropping at 6.83ms. Step 2 survived this load; this configuration does not. Turning off dropping is turning off the safety valve.

6. Queue of 4,096 — later dropping, sixteen times the wait

queueSize 256 → 4,096 (20% dropping · 5% errors) dropping from 6.83 → 109.23ms · wait 20.6 → 327.8ms

Dropping now starts close to sixteen times later. The amount lost is exactly the same — 30k a second — it merely starts later. And there is a bill: the queue settles at 3,277 events, drained at 10k a second, so one event takes 327.8ms to clear the pipe. That is Little's law — queue length over drain rate. During an incident you would be reading logs from a third of a second ago.

7. A faster sink — everything disappears

time per write 100 → 5μs (drain 10k → 200k/s) dropped none · blocking none · queue 0 / 256

Arrivals are still 40k. The only thing that changed is the drain rate. The queue, the thresholds and the dials are all symptoms; the cause is a drain rate below the arrival rate. A local file sits around 5μs, but an appender that ships over the network — Logstash, Kafka, CloudWatch — makes 100μs optimistic. This page begins on the day you start shipping logs over the wire.

The specification fixes two thresholds

The checkpoint for this episode is the AsyncAppender property table in the logback documentation. Two rows hand us numbers.

"queueSize — The maximum capacity of the blocking queue. By default, queueSize is set to 256."
"discardingThreshold — By default, when the blocking queue has 20% capacity remaining, it will drop events of level TRACE, DEBUG and INFO, keeping only events of level WARN and ERROR. To keep all events, set discardingThreshold to 0."

Multiply the two and one threshold falls out exactly — 256 × 0.2 = 51.2 → 51 events. Once 51 or fewer slots remain, which is to say once the queue length reaches 205, INFO starts disappearing. That is the first threshold.

The second comes from the neverBlock row of the same table.

"If the queue is filled up, then application threads are blocked from logging new events until the worker thread has had a chance to dispatch one or more events."

This is where asynchronous logging turns back into synchronous logging. And the reason the sentence is so quiet is that "blocked" comes with no exception and no log line — things simply get slower.

The excess splits three ways and only three

The model rests on one sentence. There is a rate the application wants to log at, λ, and a rate the pipe passes, μ, and the difference is handled in one of three ways.

HandlingWhenWhat it costs
drop INFOremaining capacity ≤ thresholdthe context you debug with is gone. Silently
drop regardless of levelfull and neverBlockthe ERRORs go too. Also silently
threads absorb itfull, default settingsrequests slow down. The log pipe becomes the throughput ceiling
The three are exclusive and sum to exactly λ − μ. Which is to say: remove one and another grows. The dials only choose the form in which you pay — whether you pay at all is decided by the drain rate alone.

Step 3 shows that multiplication. It drops and blocks. Above the dropping line an INFO event never enters the queue at all, so that call is not blocked, it is simply lost, while the WARN and ERROR events competing for slots are the ones that block. Not one or the other — both at once.

The valve is empty exactly when you need it

This is the most valuable reversal on the page. discardingThreshold is the mechanism that protects the application by losing logs. But the only thing it can lose is INFO.

In normal operation 95% of arrivals are INFO, so it works well. Then an incident starts —

SituationWARN·ERROR shareCan dropping close the gap?
normal5%yes — the whole excess leaves as INFO
error storm50%no — 20k a second remains after dropping everything
all errors100%there is nothing to drop at all
The capacity of the safety valve is inversely proportional to the size of the accident. Generous while everything is quiet, and zero at the moment you actually need it.

A bigger queue is not a fix

Raising queueSize is the first fix anyone reaches for, and step 6 prices it.

queueSizeDropping startsAmount lostWait per event
2566.83ms30k/s20.6ms
4,096109.23ms30k/s (identical)327.8ms

Not one event fewer is lost. The steady-state loss rate is λ − μ and the queue size does not appear in it. What a queue does is absorb a burst, and that does nothing for a sustained excess.

What it does add is waiting. This is Little's law, showing up in the same role for the fifth time on this site — no. 8 (connection pools), no. 19 (window × connections), no. 5 (Receive Maximum), no. 30 (threads), and here.

327.8ms is an operational problem in its own right. You are making incident decisions on logs from a third of a second ago. And if the process dies in that window, the 3,277 events in the queue never reach the disk — which is where the documented maxFlushTime lives: "Events that cannot be processed within this window are discarded."

What this model assumes

AssumptionWhat breaks if it fails
a constant drain rateTime per write is treated as a constant. Real sinks stall for tens of milliseconds on fsync or log rotation — μ goes to zero for that window and the queue takes on that time × λ. A 20ms stall on a 100μs pipe is 2,000 events on its own, which overruns a 256-event queue eightfold
a constant arrival rateThis is a steady-state view. Real logs arrive in bursts — which is why the queue exists. If the burst is smaller than the queue, nothing on this page happens at all
a constant level mixThe interesting thing is the mix changing during an incident, and the model only ever shows one instant of it. You compare two points with a dial; the transition itself is not drawn
one worker threadAsyncAppender has a single worker — that is the implementation, not an assumption. Which is why the only way to raise μ is to make one write faster, never to parallelise
256 and 20% are specifiedThose the documentation fixes, so they do not move. The time per write, however, is an input we chose — it is not in any specification, and it is the number you have to measure in your own environment

In the field

WhereWhat to check
First thing to look atYou cannot find missing logs in the logs. Look at counts instead — if you know how many lines a request ought to write, the number of lines absent is the only evidence you get. Grouping by correlation ID makes it visible (no. 12)
Getting a metric out of itlogback does not expose a dropped-event counter. Exporting the queue depth is effectively your only gauge — if it is pinned at queueSize − discardingThreshold, you were dropping for that entire period
Order of fixes① raise the drain rate (write to a local file and let a separate process ship it — get the remote appender off the request path) ② log less ③ and only then the queue size. Starting at ③ is the most common ordering mistake
Before turning on neverBlockIt makes ERRORs disappear. "Better than stalling the service during an incident" may well be the right call — but then route ERROR to its own appender, synchronous and unqueued. The point is to choose what you lose
includeCallerDataThe property the documentation calls "rather expensive". Turning it on captures a stack per event, so μ falls — it turns this page's causal dial the wrong way
On shutdownWhatever the queue could not flush within maxFlushTime is discarded. The moment a deploy takes the pod down, your last log lines leave by this path — and they may be exactly the ones before the failure
Other frameworksLog4j2's async logger uses the LMAX Disruptor and makes the same choice through AsyncQueueFullPolicy (the default has the calling thread write directly — which is to say, block). Different names, the same two thresholds
