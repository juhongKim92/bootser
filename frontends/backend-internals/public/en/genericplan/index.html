Slow from the sixth execution

Long after the deploy, one query starts running slowly. You pull its plan and it looks fine. From the application it is still slow — because the parameter the optimizer is looking at is not the value you passed.

Drive it yourself

The same prepared statement runs over and over. Parameters come in two kinds — a common value covering 60% of the table, and a rare value covering 0.1%.

controlwhat happens
common value shareHow often the common value is queried. The rest use the rare value
n_distinctDistinct values recorded in statistics. The generic plan's estimated selectivity is 1/n_distinct
plan_cache_modeA setting available from PostgreSQL 12. auto is the default

The costs used here:

table            1,000,000 rows
index scan       0.004ms per matched row   → scales with selectivity
sequential scan  150ms flat                → independent of selectivity
planning         0.4ms                     → a custom plan pays it every time

crossover  s* = 150 / (0.004 × 1,000,000) = 3.75%
           below it the index wins, above it the sequential scan does

Things to try

1. Set the common value share to zero — the generic plan wins

common value 0% · auto custom 4.4ms (index 4.0 + planning 0.4) generic 4.0ms (no replanning)

When parameters are always similar the generic plan is faster, because it plans once. On short queries planning can exceed 10% of total time — this is exactly why prepared statements and a plan cache exist.

Starting here matters. "Generic plans are bad" is not the lesson. What is bad is a skewed distribution.

2. Raise it to 25% — a step appears at the sixth

common value 25% · auto runs 1-5 custom — the value is visible, so the plan fits it run 6 locks to generic run 7+ the bars rise as a block average 40.9ms → 603ms (15×) no step? hit reset and try again — it is a coin toss

Watch the step form in the graph. For the first five executions PostgreSQL plans with the value in hand. On the sixth it builds a generic plan, compares costs, and if the generic looks cheaper it keeps using it.

The red bars are the price. The generic plan estimated 1/n_distinct = 0.5% and chose an index scan; when a value covering 60% arrives, that means walking 600,000 of a million rows through the index. 2.4 seconds — for work a custom plan would have finished sequentially in 150ms.

Sometimes it does not switch. If all five warm-up executions happen to be rare values, the custom average is recorded cheaply and the generic looks expensive — about one time in four at a 25% share. Hit reset to draw again. That this is not a bug but the nature of the problem is what recipe 6 is about.

3. Switch to force_custom_plan

plan_cache_mode = force_custom_plan average 603ms → 40.9ms worst 2.4s → 150ms cost 0.4ms of planning on every execution

The problem disappears. Planning with the value in hand puts a sequential scan on the common value and an index scan on the rare one. You pay 0.4ms and buy back a factor of fifteen.

4. Use force_generic_plan to see the worst case immediately

plan_cache_mode = force_generic_plan only red bars remain every common-value execution takes 2.4 seconds

A way to see it without waiting for the switch — and the same trick works in production. Turn on SET plan_cache_mode = force_generic_plan; and run EXPLAIN, and you get the plan your application actually uses. Substituting a literal and running EXPLAIN never shows you that plan.

5. Drop n_distinct to 20 — no switch happens

n_distinct 200 → 20 (estimated selectivity 5%) generic estimate 20ms → 150ms (it picks a sequential scan) custom average 40.9ms 150 > 40.9 → it does not switch

Once the estimated selectivity passes the 3.75% crossover, the generic plan also chooses a sequential scan. Its estimated cost of 150ms then looks more expensive than the custom average, and PostgreSQL keeps the custom plan. That is correct behaviour — the optimizer is judging correctly with the information it has.

Inverted, this says something useful. A generic plan is dangerous when its estimate is smaller than reality — that is when it chooses an index, and that is when large values blow up.

6. Drop the common value share to 5% — again no switch

common value 5% · n_distinct 200 custom average 11.7ms (mostly rare values, so it is cheap) generic estimate 20ms 20 > 11.7 → it does not switch

This is the subtle one. When the common value arrives rarely, the first five executions are almost certainly rare values, the custom average is recorded as very cheap, and the generic plan looks expensive by comparison.

But that is luck. Let a couple of common values land in the first five and the custom average rises and the generic wins. Same code, same data, different behaviour per connection. Whatever traffic warmed a connection decides how it behaves for the rest of its life.

Why the sixth

PostgreSQL's plan cache works like this.

runs 1-5   custom plans — replanned each time with the parameter value
           the estimated cost of each is recorded

run 6      build a generic plan once and estimate its cost
           generic estimate <= custom average  →  generic from now on
           otherwise                           →  stay custom

Five is a constant. It is not tunable. Which is why the symptom appears exactly on the sixth execution — run your load test five times and nothing is wrong.

Once it locks to generic it never goes back. That prepared statement stays generic for its whole life; only closing the connection or DEALLOCATE restarts the count.

The optimizer decides from an average

The axis of this page is one line.

cost(E[s])  ≠  E[cost(s)]

the cost computed from the average selectivity
  ≠  the average of the actual costs

When it builds a generic plan the optimizer cannot see the parameter. So it estimates the selectivity of WHERE col = $1 as 1/n_distinct — an assumption that every value occurs equally often.

On a skewed column that assumption matches no execution at all. With 200 distinct values where one covers 60% of the table, the "average" 0.5% value does not exist. The optimizer plans for a value that never arrives, and every execution runs that plan.

Which means the better the average looks, the more dangerous it is. The further the estimate falls below the crossover, the more confidently the generic plan reaches for an index, and the harder the tail breaks. Recipe 5 shows the opposite direction — a larger estimate is safer.

Seeing the plan that is really used

This is where the most common misdiagnosis happens. You chase a slow query with EXPLAIN ANALYZE, but substituting a literal gives you a custom plan. That is not what the application runs.

-- this is a custom plan. It may not be what the application uses
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'PENDING';

-- this is what the application actually runs
SET plan_cache_mode = force_generic_plan;
PREPARE p(text) AS SELECT * FROM orders WHERE status = $1;
EXPLAIN ANALYZE EXECUTE p('PENDING');
RESET plan_cache_mode;

If the two plans differ, this page is your problem. force_generic_plan exists from PostgreSQL 12; on older versions you have to PREPARE and EXECUTE six times to see it.

When Java actually gets a prepared statement

There is one more layer here. A JDBC PreparedStatement is not automatically a server-side prepared statement.

conditionwhat changes
PgJDBC prepareThresholdDefaults to 5. The same SQL on the same connection five times before it becomes server-prepared; until then it is parsed every time
connection turnoverWhen HikariCP's maxLifetime or similar replaces a connection, the counter restarts from zero
PgBouncer transaction modeConnections change per transaction, so server-side prepared statements never take hold. The problem cannot occur — and neither can the benefit
HibernateReuse requires an identical SQL string. IN (?, ?, ?) with a different parameter count is a different statement

Put together: five in PgJDBC × five in PostgreSQL. Roughly ten executions of the same query on one connection before a generic plan appears. Which is why it never shows under light traffic and arrives suddenly as traffic grows.

What to check in production

Start with this question. "Is this query's parameter distribution even?" Status values, types, tenant ids, country codes — these are usually not even. If it is not, you have a candidate.

-- look at the skew directly. What share does the top value hold?
SELECT status, count(*),
       round(count(*) * 100.0 / sum(count(*)) OVER (), 2) AS pct
FROM orders GROUP BY status ORDER BY 2 DESC LIMIT 10;

-- what do the statistics know?
SELECT attname, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';

Read n_distinct alongside most_common_freqs. When the top frequency is far above 1/n_distinct, that is exactly how far the generic estimate is off.

Capture the slow executions. Averages hide this.

# postgresql.conf — log the real plan of slow executions
auto_explain.log_min_duration = '500ms'
auto_explain.log_analyze = on
auto_explain.log_parameter_max_length = 0   # do not log values (sensitive data)

pg_stat_statements and its mean_exec_time respond poorly to this problem: one statement mixing 4ms and 2,400ms still has a plausible-looking mean. Read max_exec_time and stddev_exec_time next to it.

The order to fix it.

  1. Look at statistics first. A stale ANALYZE or a low default_statistics_target leaving too few MCVs is common
  2. Confirm the plans really differ by running EXPLAIN under force_generic_plan
  3. See whether the query can be fixed. If an unnecessary sort or derived table is what blocks index use, removing it beats any setting
  4. Then plan_cache_mode. force_custom_plan can be set per session. You are paying planning cost again, which can lose on short queries
  5. Route the heavily skewed value separately. Sometimes the common value deserves its own query entirely

Step 4 sits after step 3 deliberately. force_custom_plan removes the symptom, not the cause. If the reason the plans diverge lives in the query's shape, that is what to fix.

This model is simplified for teaching. Real PostgreSQL costs account for page counts, correlation, cache hit rates and parallelism, and the generic plan's selectivity estimate uses null fraction and the MCV sum alongside 1/n_distinct. The switch decision here compares execution times, where PostgreSQL compares estimated costs. What matters is the structure, not the numbers — a plan built without seeing the value is used for every execution.
