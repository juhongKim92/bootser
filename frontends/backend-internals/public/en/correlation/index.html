When does matching responses by order go wrong

You ask a device for its config and wait for the answer. With one request in flight nothing can go wrong. But the moment one response arrives late, every request after it receives someone else's answer as its own — and nobody notices.

Drive it yourself

The same command goes to the same device continuously. Requests keep flowing and responses come back a moment later.

Things to try

1. Start with one request

1 concurrent · single slot · no disturbance correct 100% mismatched 0

Flawless. Even pendingMap.put(serial, future) is fine here. Most code starts in this state, and passes review in this state.

2. Raise concurrency to 4 — the single slot collapses

4 concurrent · single slot · no disturbance correct 100% → 0% mismatched 0 → 100% log: "the future for #12 was overwritten by #13"

The network is perfectly healthy and everything mismatches, because put overwrites the previous future outright. The slot always holds the newest request while the arriving response belongs to the oldest. Look at the waiting row — it only ever holds one.

3. Switch to a FIFO queue — it looks fixed

FIFO queue · no disturbance correct 0% → 100% mismatched 100% → 0%

Give each key a queue and complete the longest-waiting request first, and the overwriting is gone. The screen is completely clean. The real project stopped here, understandably — the symptom that had been reproducing was gone.

4. Reorder the responses

FIFO queue · reordering 40% mismatched 0% → around 50%

FIFO rests on the assumption that the first request's response arrives first. Nothing guarantees that. The device processes out of order, a retransmission slips in, the network rearranges — and it drifts.

Worse, it never corrects itself. Slip by one and everything after stays one behind. There is no reason for the alignment to come back.

5. Serialise — reordering is handled

serialised · reordering 40% mismatched 50% → 0% throughput drops to a third

Send one at a time and there is no order to reverse. It is correct again — at the price of far fewer requests completed in the same time. You bought correctness with throughput.

6. Keep it serialised and turn on late responses — it breaks again

serialised · late responses 40% mismatched 0% → around 60%

This is the most important position on the page. Mismatches happen with only one request in flight.

Request A times out and leaves the queue. Request B takes its place. Then A's response arrives late and completes B. B's caller receives A's configuration as its own. This is not a concurrency problem — it is a missing-identifier problem, and that is what this step shows.

7. Turn on duplicates — FIFO fails completely

FIFO queue · duplicates 40% mismatched near 100%

When retransmission delivers the same response twice, the second copy completes the next request's future. One response finishes two requests. And since misalignment never recovers, everything after stays shifted.

On MQTT QoS 1, duplicates are not an exception — they are promised behaviour. Positional matching and QoS 1 must not be combined.

8. Switch to correlationId

correlationId · duplicates 40% mismatched 0% switch the disturbance to reordering or late — still 0%

When the response carries which request it answers, arrival order stops mattering. A late response finds its partner already gone and is quietly discarded; a duplicate finds an id already completed and is discarded too. All three disturbances become harmless.

Loss still happens under late responses, and that is correct — a request that timed out did fail. What matters is that its failure no longer contaminates a different request.

Why a mismatch is worse than a loss

This is why the readouts split into three. The three outcomes differ enormously in severity.

outcomewhat the caller seesseverity
losta timeout exceptionloud. Retry and move on
mismatcheda normal responsesilent. A wrong value believed to be right
correcta normal response—

A loss reports itself. It lands in the logs, shows up in metrics, becomes a retry. A mismatch leaves nothing behind. Device A's config screen can be showing device B's values while, as far as the system is concerned, every request succeeded.

Which is why this class of bug gets reported as "the values are sometimes wrong". It will not reproduce, the logs show only successes, and it usually gets blamed on frontend caching — while the place that attached the wrong value sits several layers below.

Three causes stacked under one symptom

In the real incident, "the response never arrives" had three separate causes underneath it.

  1. The response topic was never subscribed to — so every request timed out
  2. The timeout was raised from 3 to 10 seconds — which deferred the symptom and left the cause
  3. Futures were being overwritten — found eight days later

Fixing the third brought in the FIFO queue, and the overwriting genuinely stopped. But a fourth layer was still there — recipes 4 through 7 on this page.

The timeout increase is the painful one. It hid the symptom for eight days. Mitigation is a deferral, not a diagnosis, and when you defer you must leave a ticket for the cause behind.

Adding a correlationId

MQTT 5 put this in the protocol, so the payload does not have to change.

// request — carried as a standard property
MqttProperties props = new MqttProperties();
props.setCorrelationData(correlationId.getBytes());
props.setResponseTopic("device/" + serial + "/config/resp");

// response — look the waiting request up by that value
byte[] cd = message.getProperties().getCorrelationData();
CompletableFuture<Config> f = pending.remove(new String(cd));
if (f != null) f.complete(parse(message));      // no partner? discard quietly

On MQTT 3.1.1, or when the device firmware cannot change, put it in the payload. The device only has to echo the value back, which is usually the smallest possible change.

{ "reqId": "9f2c...", "cmd": "getConfig" }      →
                                                ← { "reqId": "9f2c...", "config": {...} }

The last line is the crux. A response with no partner is discarded. That is the whole difference from positional matching — positional matching attaches an orphan response to whoever is next in line; id matching throws it away.

If the firmware cannot change

Agreeing a protocol change with the device side often takes time. These help meanwhile, but none of them is complete and you should use them knowing that.

stopgaphandlesdoes not handle
serialising (one in flight)reorderinglate responses · duplicates (recipe 6)
tombstones — keep a timed-out key brieflylate responsesreordering
bothmost of all threethroughput, and the window that remains

A tombstone holds the slot of a timed-out request open for a while. A response arriving into that slot is discarded rather than attached to the next request. It is a cheap way to target late responses specifically — though how long to hold it becomes another guess.

Even with a stopgap in place, start the correlationId conversation now. Firmware changes have long lead times, and if the stopgap gets recorded as "already fixed" in the meantime, it never changes.

This is not an MQTT problem

Every structure where requests and responses travel on separate channels has the same shape.

  • Kafka request-reply — request and reply topics are separate, which is why a correlation id in the headers is the convention
  • WebSocket RPC — many requests share one socket. Without an id in the frame you end up relying on order
  • Serial links to devices and equipment — this is what sequence numbers in those protocols are for
  • Asynchronous callback APIs — if the callback does not say which call it belongs to, same problem

HTTP mostly escapes this because the connection holds the request-response pairing for you: a response on that socket is that request's. The moment you lose that guarantee — by multiplexing, or by receiving the reply on a different channel — you have to hold the pairing yourself.

What to check in production

Start by answering this. "What happens when the same command reaches the same target twice at once?" If the answer does not come immediately, you are probably in this page's state.

Look at the pending data structure. The key is everything.

Map<String, CompletableFuture<T>> pending;         // keyed by serial → single slot
Map<String, Queue<CompletableFuture<T>>> pending;  // keyed by serial → FIFO
Map<String, CompletableFuture<T>> pending;         // keyed by correlationId → safe

The third and the first have identical types. That is exactly why code review misses this. What to look at is not the data structure but what goes into the key.

Worth measuring.

metricwhat it tells you
orphan responsesresponses discarded. Not zero means late and duplicate responses are real
pending map sizemonotonic growth means futures are accumulating uncompleted
timeout ratethe first sign of a missing subscription or overwriting
request-response latency distributionthe only basis for choosing a timeout

The first row is cheap and effective. Once correlationId is in place, orphan responses become a plain counter. Under positional matching those same responses were silently attached to somebody else's request — impossible even to count.

Test by sending two at once. One test that fires the same command at the same target concurrently and asserts each response carries its own value will reproduce recipe 2. Add a test that deliberately returns the responses in reverse and you catch recipe 4 as well.

This model is simplified for teaching. Round-trip time, timeout and disturbance rates are fixed values; in reality all of them have distributions. In particular, the absolute mismatch percentages depend heavily on how the disturbance is distributed — what matters is not the percentage but that positional matching, once misaligned, never recovers on its own.
