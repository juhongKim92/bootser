손잡이무엇이 바뀌나
팬아웃 폭한 라운드가 병렬로 부르는 서버 수입니다. 화면 하나를 그리는 데 필요한 조각의 개수라고 보면 됩니다 — 샤드, 파티션, 마이크로서비스, 캐시 노드.
서버 하나가 느릴 확률서버 하나가 1000ms 쪽으로 답하는 비율. 나머지는 10ms 입니다. 이 값은 손잡이를 돌려도 서버 자체는 전혀 안 변한다는 뜻이에요.
화면당 라운드그 팬아웃을 순차로 몇 번 하는가. 목록을 받고 상세를 받고 권한을 확인하는 식입니다. 닿는 서버 수는 폭 × 라운드입니다.
사본 한 번 더첫 응답이 안 오면 같은 요청을 다른 복제본에 한 번 더 보내고 먼저 온 것을 씁니다(hedged request). 재시도가 아닙니다 — 첫 요청을 취소하지 않고 겹쳐서 보냅니다.
사본을 쏘는 시점첫 응답을 몇 ms 기다린 뒤 사본을 보내는가. 10ms 를 경계로 추가 부하가 절벽처럼 바뀝니다 — 빠른 응답보다 이르게 쏘면 모든 요청이 두 번 나갑니다.

미터의 수치는 표본이 아닙니다. 서버 하나의 응답을 두 점(10ms · 1000ms)으로 줄였기 때문에 전부 닫힌 식으로 계산됩니다. 난수가 없고, 같은 손잡이 조합이면 언제나 같은 숫자가 나옵니다.

격자의 칸 하나가 사용자 한 명입니다. 채워진 칸 수는 기대값을 반올림한 것이지 어떤 100명을 뽑아 세어본 결과가 아닙니다.

이렇게 해보세요

1. 서버 하나 → 100대. 서버는 그대로다

팬아웃 폭 1 → 100 (서버 하나가 느릴 확률 1% 그대로) 꼬리를 맞는 요청 1.00% → 63.4% 개별 서버 대비 ×1.00 → ×63.4 · 평균 응답 20 → 638ms

손잡이 중 서버의 성질을 건드린 것은 하나도 없습니다. 1% 는 1% 그대로예요. 늘어난 것은 개수뿐인데 사용자가 겪는 비율은 63배가 됐습니다. 100대 중 적어도 하나가 느리면 화면은 느린 것이고, 그 확률이 1 − 0.99100 이니까요.

2. 절반이 넘는 지점 — 폭 69

팬아웃 폭 68 → 69 꼬리를 맞는 요청 49.5% → 50.0% 미터 "절반을 넘는 폭" 이 계속 69 를 가리키고 있었다

여기서부터 중앙값 사용자가 꼬리를 맞습니다. p99 이야기가 아니라 p50 이야기예요. 서버의 1% 짜리 사건이 폭 69 를 넘는 순간 보통 사용자의 경험이 됩니다. 이 지점은 0.99N < 0.5 를 푼 값이라 폭과 무관하게 미터에 항상 떠 있습니다.

3. 서버를 10배 좋게 만든다 — 그래도 10명 중 1명

서버 하나가 느릴 확률 1% → 0.10% (폭 100 그대로) 꼬리를 맞는 요청 63.4% → 9.52% 개별 서버 대비 ×63.4 → ×95.2 · 평균 638 → 104ms

꼬리를 열 배 줄이는 일은 보통 분기 하나짜리 과제입니다. 그런데 결과는 여전히 열 명 중 한 명이에요. 게다가 증폭 배수는 오히려 커졌습니다(×63.4 → ×95.2) — 개별 서버를 좋게 만들수록 팬아웃이 그 이득을 더 크게 깎아먹습니다. 개선은 선형인데 곱해지는 쪽은 지수라서요.

4. 사본을 켠다 — 추가 부하 1% 로 63.4% → 0.995%

사본 한 번 더 켬 (쏘는 시점 30ms · 서버는 1% 그대로) 꼬리를 맞는 요청 63.4% → 0.995% 개별 서버 대비 ×63.4 → ×0.995 · 평균 638 → 39ms 추가 요청 1.00%

3번의 개선(9.52%)보다 여섯 배 좋은 결과를, 서버를 손대지 않고 냈습니다. 두 번 다 느려야 느린 것이니 잎의 꼬리 확률이 p 에서 p² 로 제곱되거든요. 증폭 배수가 ×1.00 이 됐다는 게 핵심입니다 — 사용자가 겪는 꼬리가 서버 하나가 겪는 꼬리와 같아졌어요. 팬아웃이 사라진 것처럼 보입니다.

5. 사본을 5ms 에 쏜다 — 꼬리는 그대로인데 부하가 100배

쏘는 시점 30ms → 5ms 꼬리를 맞는 요청 0.995% → 0.995% (한 자리도 안 움직인다) 평균 응답 39 → 23ms 추가 요청 1.00% → 100.0%

빠른 응답이 10ms 에 오는데 5ms 에 사본을 쏘면 모든 요청이 두 번 나갑니다. 평균은 더 좋아져요(39 → 23ms) — 공짜가 아니라 산 것입니다. 트래픽을 두 배로 내고 16ms 를 샀어요. 그리고 정작 꼬리는 한 자리도 안 줄었습니다. 사본이 꼬리를 자르는 일은 이미 30ms 에서 끝나 있었으니까요.

6. 라운드를 2로 — 폭 200 과 꼬리는 같고 평균은 다르다

화면당 라운드 1 → 2 (폭 100) 꼬리 63.4% → 86.6% · 평균 1275ms 폭 200 · 라운드 1 꼬리 86.6% · 평균 867ms

두 설정의 꼬리 확률이 소수점까지 정확히 같습니다. 식이 닿는 서버 수만 보거든요(100×2 = 200×1). 꼬리 확률은 "쪼갰는가"와 "넓혔는가"를 구별하지 못합니다. 그런데 평균은 1275ms 와 867ms 로 다릅니다 — 직렬 라운드는 느린 구간을 더하고, 병렬 폭은 겹치니까요. 서비스를 쪼개서 각각을 가볍게 만들어도 화면이 그대로인 이유가 여기 있습니다.

1% 가 어떻게 63% 가 되는가

화면이 느린 조건은 모든 서버가 느린 것이 아니라 적어도 하나가 느린 것입니다. 그래서 반대쪽을 세는 게 쉬워요 — 전부 빠를 확률은 (1−p)N 이고, 나머지가 전부 꼬리입니다.

사용자가 꼬리를 맞을 확률 = 1 − (1 − p)N
서버 하나의 성질 p 는 그대로 두고 N 만 키우면 이 값은 1 을 향해 지수로 붙습니다.

이 식이 불편한 이유는 대시보드가 전부 초록인 채로 이 일이 벌어지기 때문입니다. 서버의 평균도, p50 도, p99 도 안 움직였어요. 움직인 것은 화면 하나가 몇 대를 부르는가 하나뿐인데, 그건 보통 성능 지표로 관리하지 않는 숫자입니다.

이 식은 논문 안에서 두 번 확인된다

이 페이지의 축은 제가 만든 모델이 아니라 Dean 과 Barroso 의 The Tail at Scale(CACM 2013)에서 왔습니다. 논문의 문장은 이렇습니다 — “서버가 보통 10ms 에 응답하지만 99 퍼센타일 지연이 1초라면 … 사용자 요청이 그런 서버 100대에서 병렬로 응답을 모아야 할 때, 사용자 요청의 63% 가 1초를 넘긴다.”

그런데 더 값진 것은 논문이 같은 식 위의 두 번째 점을 준다는 것입니다 — “단일 서버에서 1초를 넘기는 요청이 10,000번에 한 번뿐인 서비스라도, 그런 서버 2,000대짜리 서비스에서는 사용자 요청의 거의 다섯 중 하나가 1초를 넘긴다.” 이 모델에 p = 0.01%, N = 2000 을 넣으면 18.1% 가 나옵니다. “거의 다섯 중 하나”와 맞습니다.

점 하나는 우연히 맞을 수 있지만 두 점은 식이 맞다는 뜻입니다. 이 페이지가 물려받은 설명을 그대로 구현하지 않았다는 근거예요 — 모델을 짜기 전에 원문에서 확인한 것이 이것입니다.

사본이 서버 개선을 이기는 이유

사본을 하나 더 보내면(hedged request) 잎이 느린 조건이 “느리다”에서 “두 번 다 느리다”로 바뀝니다. 확률이 p 에서 p² 가 되는 거예요. 서버를 개선하는 것은 p 를 나누는 일이라 선형이고, 사본은 지수입니다.

무엇을 하나폭 100 에서 결과
아무것도 안 함63.4% · 평균 638ms
서버를 10배 개선9.52% · 평균 104ms — 분기 하나짜리 과제
사본 한 번 더0.995% · 평균 39ms — 추가 부하 1%

추가 부하가 1% 인 이유는 사본이 느린 요청에만 나가기 때문입니다. 빠른 응답이 10ms 에 오는데 30ms 를 기다렸다 쏘니, 실제로 사본이 나가는 건 느린 1% 뿐이에요. 논문은 실제 시스템에서 이 임계를 95 퍼센타일에 두어 추가 부하를 약 5% 로 제한했다고 적고 있고, BigTable 벤치마크에서는 서버 100대에 흩어진 1,000개 키를 읽으며 10ms 뒤 사본을 보내 99.9 퍼센타일을 1,800ms 에서 74ms 로 줄이고 요청은 2% 만 더 보냈다고 보고합니다.

위 문단의 5% · 1,800ms · 74ms · 2% 는 구글의 실측치이지 이 실험대의 출력이 아닙니다. 실험대가 계산하는 것은 확률과 두 점의 가중 평균뿐입니다.

대신 실험대가 보여주는 것은 임계를 잘못 잡았을 때의 절벽입니다. 쏘는 시점을 10ms 아래로 내리면 사본이 모든 요청에 나가서 추가 부하가 100% 가 됩니다. 꼬리는 그대로예요. 같은 기법이 같은 결과를 내면서 비용만 100배가 되는 구간이 바로 옆에 있습니다.
