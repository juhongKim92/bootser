직접 조작하기

손잡이무엇이 바뀌나
데드라인 전파켜면 각 계층이 자기 기본값이 아니라 넘겨받은 잔여 예산만큼만 씁니다. 남은 게 없으면 아예 부르지 않고 즉시 실패합니다.
세 개의 타임아웃계층마다 따로 정한 값. 같은 값으로 맞춰 보세요 — 발동 시각 표의 순서가 뒤집힙니다.
계층별 시도각 계층이 재시도를 포함해 몇 번 시도하는가. 두 계층에 같이 걸리니 C 호출은 최대 이 값의 제곱입니다.
C 가 느린 비율C 는 65ms 아니면 1.2초에 답합니다. 이 슬라이더는 후자의 비율입니다.
C 의 느림지속적이면 그 요청은 다시 해도 느립니다(과부하·느린 쿼리·뜨거운 파티션). 일시적이면 다음 시도에 다른 결과가 나옵니다(패킷 유실·순간 정지).

시간축의 세로 파란 선이 클라이언트가 포기하는 순간입니다. 그 오른쪽 빗금 구간에서 일어나는 일은 전부 아무도 기다리지 않는 일이에요. 붉은 점선은 각 계층의 타임아웃이 발동하는 지점입니다. 점선이 파란 선 오른쪽에 있으면 그 타임아웃은 발동할 기회가 없다는 뜻입니다.

미터의 수치는 표본이 아닙니다. C 의 응답시간을 두 점(65ms · 1.2초)으로 줄였기 때문에 모든 경로를 확률 가중으로 전부 세어서 나온 정확한 기대값입니다. 같은 손잡이 조합이면 언제나 같은 숫자가 나옵니다.

이렇게 해보세요

1. 전부 1초 · 재시도 없음 — 발동 순서가 거꾸로다

클라이언트→A 1.0초 · A→B 1.0초 · B→C 1.0초 발동 시각 1000ms / 1025ms / 1050ms 지킬 수 없는 약속 1.00건 (호출 전부)

홉마다 25ms 가 듭니다. 안쪽 계층은 25ms, 50ms 늦게 요청을 받으니 타이머도 그만큼 늦게 시작하고, 그만큼 늦게 발동합니다. 바깥이 항상 먼저 포기하므로 안쪽 타임아웃은 발동할 기회가 없습니다. B 가 C 에게 준 1초는 B 자신이 기다려줄 수 있는 시간보다 길어요 — 지킬 수 없는 약속이고, 이 설정에서는 모든 호출이 그렇습니다.

2. 시도를 3회로 — 성공률이 소수점 한 자리도 안 움직인다

계층별 시도 1 → 3회 성공률 90.0% → 90.0% C 호출 1.00 → 1.80건 · 기한 뒤 시작 0.00 → 0.80건 느린 요청 하나: C 호출 9건 · 동시 최대 5건 · 마지막 작업 종료 5.28초

늘어난 0.80건이 전부 클라이언트가 떠난 뒤 시작됩니다. 성공률에 기여할 수 있는 시도는 첫 번째 하나뿐이에요. 1초를 준 요청 하나가 시스템 안에서 5.28초 동안, 한때는 C 를 동시에 5번 부르며 일합니다 — 14번이 이 낭비가 용량을 어떻게 무너뜨리는지 다룹니다.

3. 예산을 3초로 늘린다 — 재시도 없이 100%

세 값 모두 3.0초 · 시도 1회 성공률 90.0% → 100.0%

C 의 꼬리는 1.2초입니다. 1초 창으로는 절대 못 받고 3초 창이면 받아요. 성공률을 움직인 것은 재시도가 아니라 타임아웃이 응답시간 분포의 어디를 자르느냐였습니다.

4. 같은 3초를 1초씩 세 번으로 쪼갠다 — 100%에서 90%로

B→C 3.0 → 1.0초 · 시도 1 → 3회 (예산은 3초 그대로) 성공률 100.0% → 90.0% C 호출 1.00 → 1.80건 · 평균 응답 329 → 1099ms

재시도를 켜서 성공률을 10.0%p 깎았습니다. 1.2초 걸리는 응답은 1초 창으로 세 번 봐도 세 번 다 못 봅니다. 같은 예산을 한 번에 쓰면 받을 수 있었어요. 재시도는 시간을 만들어내지 않고 나눕니다.

5. 느림이 일시적이라면 — 같은 설정에서 99.9%

C 의 느림 지속적 → 일시적 (나머지는 4번 그대로) 성공률 90.0% → 99.9% · C 호출 1.80 → 1.11건

재시도가 값을 하는지는 실패가 다음 시도에 이어지는지에 달려 있습니다. 패킷 유실이나 순간 GC 정지는 안 이어지고, 과부하·느린 쿼리·뜨거운 파티션은 이어집니다. 그리고 예산을 쪼개는 대가는 어느 쪽이든 지불합니다 — 4번과 5번의 차이는 이득이 있느냐일 뿐, 창이 좁아진 건 똑같아요.

6. 손으로 계단식 — 발동 순서는 바로 서는데

클라이언트→A 1.0초 · A→B 0.9초 · B→C 0.3초 · 시도 3회 발동 시각 1000 / 925 / 350ms — 순서가 바로 섰다 지킬 수 없는 약속 1.80 → 0.30건 그런데 기한 뒤 시작 0.50건 · 성공률 90.0% 그대로

안쪽이 먼저 포기하도록 값을 손으로 줄였습니다. 재시도도 이제 실제로 발동해요. 남은 건 A 의 재시도입니다 — A 는 925ms 에 두 번째 시도를 보내는데 클라이언트는 1000ms 에 떠납니다. A 는 그걸 모릅니다. 손으로 고를 수 있는 것은 값이고, 값으로는 "지금 몇 ms 남았나"를 알 수 없습니다.

7. 데드라인 전파를 켠다 — 성공률은 그대로, 일은 1/1.8

1번 설정(전부 1초 · 시도 3회)에서 전파만 켬 성공률 90.0% 그대로 C 호출 1.80 → 1.00건 · 기한 뒤 시작 0.80 → 0.00건 지킬 수 없는 약속 1.80 → 0.00건 평균 응답 499 → 294ms · 실패한 요청은 3.05초 → 1.00초

C 가 받은 예산은 1000ms 가 아니라 900ms 입니다 — 클라이언트 기한에서 오갈 홉을 빼고 남은 값이죠. A 의 두 번째 시도는 예산이 없어 아예 나가지 않습니다. 그런데 성공률은 한 자리도 안 움직였어요. 이게 우연이 아닙니다.

왜 안쪽 타임아웃은 발동하지 못하는가

타임아웃은 부르는 쪽이 보내는 순간부터 잽니다. 그러니 안쪽 계층의 타이머는 언제나 더 늦게 시작해요. 세 값이 모두 t 라면 발동 시각은 이렇게 됩니다.

누가 걸었나발동 시각
클라이언트 → At
A → Bt + 1홉 — 클라이언트보다 늦다
B → Ct + 2홉 — 더 늦다
계층 타임아웃이 같으면 안쪽은 구조적으로 발동할 수 없습니다. 설정 파일에는 있고 코드는 실행되지만, 바깥이 항상 먼저 포기하므로 그 값이 무엇이든 결과가 같습니다. 죽은 설정입니다.

실제로 쓸 수 있는 시간은 더 짧습니다. C 의 답이 클라이언트까지 도달하려면 홉을 여섯 번 지나야 하니, 1초 예산에서 C 가 일할 수 있는 시간은 850ms 예요. 그런데 C 에게 알려준 값은 1초입니다. 그 차이만큼 C 는 아무도 안 받을 답을 만들고 있습니다.

전파는 성공률을 올리지 않는다

여기가 이 페이지에서 가장 뒤집히는 지점입니다. 타임아웃 3개 × 재시도 3단 × 느림 성격 2가지로 750개 조합을 전수 비교했습니다.

전파가 성공률을 올린 조합 0개, 낮춘 조합 0개. 750개 전부에서 소수점까지 같았습니다. 대신 평균 C 호출은 1.16 → 1.08건, 기한 뒤 시작은 0.06 → 0.00건, 고아 응답은 0.044 → 0.000건이 됐습니다.

우연이 아니라 산수가 그렇습니다. 전파 없이 C 의 응답을 받으려면 응답시간이 tC − 2홉 안에 들어와야 하고, 그 답이 쓸모 있으려면 부른 쪽 기한까지 도달해야 하니 기한 − 보낸시각 − 3홉 안에도 들어와야 합니다. 전파가 주는 예산은 정확히 기한 − 보낸시각 − 1홉 이라, 성공 조건이 뒤쪽 식과 글자 그대로 같아집니다.

전파가 자르는 것은 어차피 버려질 응답뿐입니다. 그래서 성공률을 못 올리고, 못 낮춥니다.

그러니 전파는 성공률 장치가 아니라 비용과 정직성의 장치입니다. 같은 성공률을 절반 남짓의 일로 내고, 실패를 3.05초가 아니라 1.00초에 알려줍니다. 하위 서비스는 처음으로 자기가 이미 늦었다는 사실을 알 수 있게 됩니다 — 그걸 알면 부르지 않을 수 있고, 부르지 않으면 그 용량이 아직 기한이 남은 요청에게 갑니다. 11번의 거부가 신호인 것과 같은 이야기예요.

세 값은 동시에 성립할 수 없다

기본 설정에는 서로 모순되는 세 값이 들어 있습니다.

값무엇을 요구하나
예산 1초홉 6개(150ms)를 빼면 실제 작업 창은 850ms
꼬리 1.2초느린 응답을 받으려면 창이 최소 1.25초
시도 3회재시도가 발동하려면 계층 타임아웃이 창의 1/3 이하 ≈ 283ms

283ms 창으로 1.2초짜리 응답을 잡을 방법은 없습니다. 재시도를 늘릴수록 창은 좁아지고, 창이 좁아질수록 꼬리는 더 확실하게 잘립니다. 셋 중 하나를 바꿔야 합니다.

무엇을 바꾸나실험대에서
예산을 올린다꼬리 1.2초 + 홉 6개 = 1.35초가 최소치입니다. 세 값을 모두 1.3초로 두면 90.0%, 1.4초로 올리면 100.0% 입니다(시도 1회). 대신 점유 시간이 늘어 용량이 줍니다 — 8번의 리틀의 법칙입니다
꼬리를 자른다C 를 빠르게 만들거나, 캐시를 두거나, 느린 경로에 폴백을 답니다. 성공률을 실제로 올리는 유일한 방향입니다
재시도를 포기한다느림이 지속적이면 재시도는 예산만 먹습니다. 실험대에서 지속적 90.0% vs 일시적 99.9% — 이 차이가 재시도를 켤 근거의 전부입니다

HTTP표준 헤더가 없어서 직접 넣어야 합니다. 절대 시각을 넘기면 시계 동기가 필요하고, 잔여 ms를 넘기면 넘기는 동안의 홉 지연이 빠집니다. 둘 다 완벽하지 않으니 여유값을 하나 빼두세요
connect 와 readconnectTimeout 만 잡고 readTimeout 을 안 잡은 경우가 흔합니다. 연결은 성공하고 응답이 안 오는 게 대부분의 장애 모양이라, 이건 타임아웃이 없는 것과 같습니다
JDBCsocketTimeout(또는 드라이버별 동등물)을 안 걸면 쿼리가 무한히 매달립니다. @Transactional(timeout) 이 자르는 것은 쿼리 취소 요청이지 전체 요청이 아닙니다 — 소켓이 죽어 있으면 그 취소도 안 나갑니다
RestClient · WebClient기본값이 무제한인 조합이 있습니다. 명시하지 않았다면 없는 것으로 보세요. 커넥션 풀 대기 시간도 별도 항목입니다 — 풀에서 기다린 시간은 read 타임아웃에 안 들어갑니다
계층 순서전파를 못 넣는다면 최소한 안쪽 값이 바깥보다 작아야 합니다. 같게 두면 안쪽은 죽은 설정입니다. 다만 값만으로는 A 의 재시도가 눈을 갖지 못합니다(6번)
측정타임아웃 발생 건수만 세지 마세요. "부른 쪽이 이미 떠난 뒤에 시작된 호출" 을 세야 이 문제가 보입니다. 요청 하나에 붙은 correlationId 와 요청 시작 시각만 있으면 계산됩니다

14번이 포기한 뒤에도 일이 계속되면 용량이 어떻게 무너지는가였다면, 이 페이지는 애초에 왜 그 일이 시작되는가입니다. 계층마다 따로 정한 값은 각자 합리적이었고, 곱해지는 순간 서로 모순됐습니다.
