인스턴스를 2대로 늘리는 순간 같은 작업이 두 번 돈다

배치가 몇 달째 잘 돌았습니다. 트래픽이 늘어 인스턴스를 하나 더 띄웠고, 그날부터 같은 파일이 두 번 처리되기 시작합니다. 코드는 그대로인데요. 이 결함은 한 대에서는 절대 재현되지 않습니다.

작업 하나를 놓고

초록 테두리는 작업을 집은 인스턴스, 빨간 테두리는 이미 남이 집은 걸 또 집은 인스턴스입니다. 노란 점선은 경합에서 져서 헛돈 인스턴스예요.

작업별 결과

초록 빈칸은 한 번만 실행된 작업, 빨간 칸의 숫자는 몇 번 실행됐는지, 노란 점선은 선점만 되고 끝나지 않은 좀비 행입니다. 계기의 회색 숫자는 이 조건에서의 기대값이에요.

직접 조작하기

조작무엇이 일어나나
인스턴스 수같은 작업 테이블을 폴링하는 애플리케이션 인스턴스 수입니다. 1에서 2로 옮기는 게 이 페이지의 전부예요
선점 방식인메모리 → 읽고 쓰기 → 조건부 UPDATE → SKIP LOCKED. 실제 프로젝트가 밟은 순서입니다
처리 중 사망작업을 집은 인스턴스가 처리 도중 죽는 비율. 인메모리 방식에서는 회색으로 죽습니다 — 상태를 안 쓰니 남길 흔적도 없거든요
회수 타임아웃선점만 되고 오래 끝나지 않은 행을 되돌릴지

이렇게 해보세요

1. 한 대에서 네 방식을 모두 눌러본다

인스턴스 1대 인메모리 초과 실행 0% 읽고 쓰기 초과 실행 0% 조건부 UPDATE 초과 실행 0% SKIP LOCKED 초과 실행 0%

넷 다 완벽합니다. 테스트를 아무리 돌려도 차이가 안 나요. 이게 이 결함이 운영까지 살아남는 이유입니다. 개발·스테이징이 한 대면 네 방식은 구별되지 않습니다.

2. 2대로 올린다 — 인메모리가 무너진다

인스턴스 2대 · 인메모리 초과 실행 0% → 100% 모든 작업이 두 번 실행된다

synchronized 는 한 JVM 안에서만 유효합니다. 다른 인스턴스는 그 컬렉션의 존재조차 모릅니다. 게다가 이 방식은 DB 상태를 바꾸지 않으니 그 행은 계속 PENDING 으로 보여요. 폴링하는 모든 인스턴스가 집습니다. 인스턴스를 6대로 올려보세요 — 500%가 됩니다.

3. 상태값을 쓰게 한다 — 고쳐진 것처럼 보인다

인스턴스 2대 · 읽고 쓰기 초과 실행 100% → 0.5% 인스턴스 6대로 올리면 → 2.5%

여기가 가장 위험한 자리입니다. 100%에서 0.5%로 떨어졌으니 고쳐진 것처럼 보입니다. 테스트도 통과하고, 며칠 지켜봐도 조용해요. 그런데 0.5%는 0이 아닙니다. 하루 10만 건이면 500건이 두 번 돕니다.

SELECT 로 읽고 UPDATE 로 쓰는 사이에 창이 남아 있기 때문이에요. 창이 좁아졌을 뿐 닫힌 게 아닙니다. 확률이 낮은 버그는 사라진 버그가 아니라 재현이 어려운 버그입니다.

4. 조건부 UPDATE 로 바꾼다

인스턴스 6대 · 조건부 UPDATE 초과 실행 2.5% → 0% 헛돈 시도 0 → 5.00 / 건

중복이 사라졌습니다. WHERE state='PENDING' 을 조건에 넣으면 DB 가 알아서 한 대만 통과시켜요. 대신 새 숫자가 하나 생겼습니다 — 진 다섯 대의 헛돈 시도입니다. 정확성은 얻었지만 여섯 대가 같은 행을 놓고 매번 싸우고 있어요.

5. SKIP LOCKED 로 바꾼다

인스턴스 6대 · SKIP LOCKED 초과 실행 0% 헛돈 시도 5.00 → 0

경합까지 사라집니다. 각 인스턴스가 이미 잠긴 행을 건너뛰고 서로 다른 행을 가져가거든요. 싸울 일 자체가 없습니다. 이게 PostgreSQL 에서 작업 큐를 만드는 표준 방식인 이유예요.

6. 처리 중 사망을 켠다 — 좀비 행

SKIP LOCKED · 처리 중 사망 15% · 회수 없음 좀비 행이 계속 쌓인다 선점만 되고 영원히 끝나지 않는 행 회수 타임아웃을 켜면 → 좀비 0

선점은 정확해졌는데 선점하고 죽으면 어떻게 되는가는 아직 답이 없습니다. 그 행은 RESERVED 로 굳어 아무도 다시 집지 않아요. 조용히 사라지는 작업들입니다. 선점 상태를 만들면 회수 경로를 반드시 같이 만들어야 합니다.

왜 한 대에서는 안 보이는가

이 결함의 성질이 여기 있습니다. 부하가 아니라 인스턴스 수에서 나옵니다.

부하로 생기는 문제는 부하를 주면 재현됩니다. 그런데 이건 아무리 부하를 줘도 한 대에서는 안 나와요. 한 JVM 안에서는 synchronized 가 정말로 동작하고, read-then-write 창에 끼어들 다른 인스턴스가 없으니까요.

환경인스턴스이 결함
단위 테스트1안 보인다
로컬 개발1안 보인다
스테이징보통 1안 보인다
운영2 이상여기서만 터진다
그래서 신고 내용이 "가끔 파일이 두 번 처리돼요" 같은 모양으로 옵니다. 재현이 안 되니 일시적 오류로 분류되고, 몇 주 뒤 같은 신고가 다시 옵니다. 로컬에서 인스턴스 두 개를 띄우는 것만으로 이 사이클을 끊을 수 있습니다.

네 가지 방식

1. 인메모리 컬렉션 + synchronized

synchronized (waitList) {
    if (!waitList.contains(id) && !runningList.contains(id)) {
        waitList.add(id);          // ← 이 JVM 의 메모리
    }
}

검사와 추가를 같은 임계 영역에 넣은 건 옳습니다. 한 JVM 안의 check-then-act 경쟁 조건은 이걸로 막혀요. 다만 막히는 범위가 그 JVM 까지입니다.

2. 읽고 나서 상태를 쓴다

Job job = repo.findFirstByStateOrderById(PENDING);   // ← 읽는다
if (job != null) {
    job.setState(RESERVED);                          // ← 쓴다
    // 이 사이에 다른 인스턴스가 같은 행을 읽으면 둘 다 통과한다
}

인메모리에서 DB 로 옮긴 방향은 정확합니다. 남은 문제는 읽기와 쓰기가 두 번의 왕복이라는 것뿐이에요. 그 사이가 아무리 짧아도 창은 창입니다.

3. 조건부 UPDATE — 원자적 선점

UPDATE job
   SET state = 'RESERVED', reserved_by = :me, reserved_at = now()
 WHERE id = :id
   AND state = 'PENDING';        -- ← 이 조건이 전부다

-- rowCount == 1 일 때만 진행한다. 0 이면 남이 가져간 것

읽기와 쓰기가 한 문장이 되면서 창이 없어집니다. DB 가 행 잠금으로 직렬화해주니 여러 대가 동시에 던져도 정확히 한 대만 rowCount = 1 을 받아요. 인메모리 락도, 별도 분산 락도 필요 없습니다.

4. SELECT … FOR UPDATE SKIP LOCKED

SELECT id FROM job
 WHERE state = 'PENDING'
 ORDER BY id
 LIMIT 10
 FOR UPDATE SKIP LOCKED;         -- 이미 잠긴 행은 건너뛴다

조건부 UPDATE 는 정확하지만, 모두가 같은 행을 노립니다. 인스턴스가 늘수록 헛돈 시도가 정비례해 늘어요. SKIP LOCKED 는 잠긴 행을 아예 건너뛰므로 각자 다른 묶음을 집습니다. 경합이 0이 됩니다.

PostgreSQL 9.5, MySQL 8.0 부터 쓸 수 있습니다. LIMIT 을 늘리면 한 번에 여러 건을 집어 폴링 횟수도 줄일 수 있어요.

선점하고 죽으면

선점을 정확하게 만들면 다음 질문이 옵니다. 집어놓고 죽은 작업은 누가 되돌리나.

아무도 안 되돌립니다. 그 행은 RESERVED 인 채로 영원히 남아요. 조회에서도 안 걸리고, 실패로도 안 잡히고, 그냥 없어진 것처럼 됩니다.

-- 오래 붙잡혀 있는 선점 행을 되돌린다
UPDATE job
   SET state = 'PENDING', reserved_by = NULL, reserved_at = NULL,
       attempt_count = attempt_count + 1
 WHERE state = 'RESERVED'
   AND reserved_at < now() - interval '10 minutes'
   AND attempt_count < 5;        -- 무한 재시도 방지

여기에 함정이 있습니다. 타임아웃은 최대 처리 시간보다 확실히 길어야 합니다. 아직 살아서 일하는 인스턴스의 작업을 회수해버리면, 정확하게 만든 선점이 도로 중복 실행이 되니까요.

처리 시간이 들쭉날쭉하면 타임아웃 대신 하트비트를 씁니다. 처리 중에 주기적으로 reserved_at 을 갱신하고, 회수 기준을 "마지막 갱신이 오래됨"으로 두는 거죠. 살아 있는 작업은 계속 갱신되니 회수되지 않습니다.

attempt_count 를 같이 두는 걸 잊지 마세요. 회수 경로만 만들면 영원히 회수되고 영원히 실패하는 작업이 매번 자원을 태웁니다. 상한을 넘으면 종료 상태로 보내야 합니다.

그래도 정확히 한 번은 아니다

선점을 원자적으로 만들고 회수까지 넣어도 at-least-once 입니다. 작업을 끝내고 DONE 을 쓰기 직전에 죽으면, 회수되어 다시 실행됩니다.

그래서 마지막 방어선은 언제나 같습니다 — 작업 자체를 멱등하게. 결과를 쓸 때 작업 id 로 유니크 제약을 걸거나, upsert 로 쓰거나, 이미 처리된 것을 확인하고 건너뛰거나.

선점은 중복을 줄이는 장치이고, 멱등성은 중복이 나도 안전한 장치입니다. 둘은 대체재가 아니라 층입니다.

분산 락은 어떤가

Redis 기반 분산 락(Redisson 등)으로도 같은 문제를 풀 수 있습니다. 다만 작업 큐에는 조건부 UPDATE 나 SKIP LOCKED 쪽이 대체로 낫습니다.

  • 의존성이 하나 늘어납니다. 이미 DB 에 작업 테이블이 있는데 락을 위해 Redis 를 끌어오는 셈이에요
  • 락 만료와 처리 시간이 어긋나면 락이 풀린 채로 계속 일하는 상황이 생깁니다. 좀비 회수의 타임아웃 함정과 같은 구조인데, 이쪽은 조용히 일어납니다
  • 작업 상태와 락이 다른 저장소에 있으면 둘 사이의 정합성을 또 맞춰야 합니다. 같은 트랜잭션에 못 넣거든요

스케줄러 자체를 한 대만 돌리려는 목적(ShedLock 같은)이라면 이야기가 다릅니다. 그건 작업 선점이 아니라 실행 주체 선택이고, 이 페이지가 다루는 문제와는 층이 다릅니다.

현장에서 확인할 것

로컬에서 두 개를 띄우세요. 포트만 다르게 해서 두 인스턴스를 올리고 같은 DB 를 보게 하면, 이 페이지의 결함이 대부분 몇 분 안에 드러납니다. 한 대로 하는 테스트는 이 영역에서 아무것도 증명하지 못합니다.

이 쿼리들을 대시보드에 두세요.

-- 좀비 행: 선점된 지 오래됐는데 아직 안 끝난 것
SELECT state, count(*), min(reserved_at), max(now() - reserved_at) AS oldest
FROM job
WHERE state = 'RESERVED'
GROUP BY state;

-- 재시도가 쌓이는 작업 — 회수 루프에 갇힌 것들
SELECT id, attempt_count, reserved_by, reserved_at
FROM job
WHERE attempt_count >= 3
ORDER BY attempt_count DESC
LIMIT 20;

첫 쿼리의 oldest 가 계속 늘어나면 회수 경로가 없다는 뜻입니다. 두 번째의 건수가 늘어나면 회수는 되는데 매번 같은 이유로 실패하고 있다는 뜻이고요.

중복 실행을 직접 세세요. 작업 결과 테이블에 작업 id 로 유니크 제약이 있다면, 제약 위반 횟수가 곧 중복 실행 횟수입니다. 제약이 없다면 지금 넣는 게 좋습니다 — 막아주기도 하고 세어주기도 하니까요.

인스턴스 수를 로그에 남기세요. 자기 인스턴스 식별자를 reserved_by 에 쓰고 로그 MDC 에도 실으면, "어느 인스턴스가 이 작업을 집었나"를 사후에 추적할 수 있습니다. 중복이 났을 때 이게 없으면 로그만 보고는 알 수 없습니다.

순서. 중복 실행을 만나면 이렇게 봅니다.

  1. 인스턴스가 몇 대인지 확인한다 — 1대면 이 페이지의 문제가 아니다
  2. 선점이 한 문장인지 확인한다. 읽고 쓰는 두 왕복이면 그게 원인이다
  3. 선점 상태에 회수 경로가 있는지 확인한다
  4. 회수 타임아웃이 최대 처리 시간보다 긴지 확인한다
  5. 그리고 작업이 멱등한지 확인한다 — 위 넷을 다 해도 남는 층이다
이 페이지의 모델은 개념을 보여주기 위해 단순화한 것입니다. read-then-write 의 중복 확률은 폴링 주기 1초, 읽기–쓰기 간격 5밀리초를 가정해 계산했어요. 실제 확률은 폴링 주기, 쿼리 지연, 인스턴스들의 폴링 시점이 얼마나 겹치는지에 따라 크게 달라집니다. 중요한 건 그 값이 작다는 게 아니라 0이 아니라는 것입니다.
