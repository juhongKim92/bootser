컨테이너 메모리를 두 배로 줬는데 힙은 그대로다

OOMKilled 이 나서 컨테이너를 250MB 에서 500MB 로 늘렸습니다. 그런데 힙 상한은 126MB 에서 한 바이트도 안 움직입니다. 249MB부터 504MB까지가 평지고, 그 구간을 만드는 것은 컨테이너와 아무 상관없는 20년 된 96MB 짜리 기본값입니다. JVM 에 62번 물어서 확인했습니다.

직접 조작하기

손잡이무엇이 바뀌나
컨테이너 메모리cgroup 한계입니다. JVM 은 이걸 물리 메모리로 봅니다 — -XX:MaxRAM 이 그 값을 대신 넣는 자리예요. 249~504MB 를 지나가 보세요.
상한을 정하는 방식인체공학은 JVM 이 알아서 정하는 것(기본), 나머지는 -Xmx 를 컨테이너 비율로 직접 주는 것입니다. 직접 주면 아래 산수가 통째로 사라집니다.
MaxRAMPercentage큰 메모리에서 쓰는 비율. 기본 25입니다 — 1GB 컨테이너에 힙 256MB 라는 뜻이에요.
MinRAMPercentage작은 메모리에서 쓰는 비율. 기본 50 이고, 이 값이 평지의 왼쪽 끝을 정합니다.
힙 밖 실사용메타스페이스 · 코드캐시 · 스레드 스택 · 다이렉트 버퍼가 실제로 쓰는 양. 이 값은 명세가 아니라 우리가 넣은 입력입니다 — 여러분 환경에서 재야 하는 값이에요. 올려서 여유를 음수로 만들면 OOMKilled 자리가 나옵니다.

모든 값이 결정됩니다 — 난수도 표본도 없어요. 힙 상한은 JVM 이 실제로 인쇄한 값과 62점에서 일치합니다(Temurin 25.0.4.1+1).

이렇게 해보세요

1. 128MB — 절반을 힙으로 준다

컨테이너 128MB · 인체공학 · Max 25% · Min 50% 힙 64.0MB (50.0%) · 초기 힙 2.0MB · 여유 4.0MB

작은 메모리에서는 MinRAMPercentage 인 50%를 씁니다 — 소스의 주석이 "Small physical memory, so use a minimum fraction of it for the heap" 라고 적어둔 그 분기예요. 여유가 4MB 뿐이라는 게 이미 경고인데, 그건 아래 7단계에서 다시 봅니다.

2. 249MB — 여기서 평지가 시작된다

컨테이너 128 → 249MB 힙 126.0MB (50.6%) · 두 배(498MB) 줘도 늘어나는 힙 0MB

힙이 126MB 가 됐는데, 여기서 컨테이너를 두 배로 늘려도 126MB 입니다. 249MB 의 절반은 124.5MB 인데 상한선이 124.8MB 라 거의 붙었고, 2 MiB 정렬로 올려서 126MB 가 됐어요. 이 위쪽은 전부 그 상한선에 걸립니다. 이 미터 하나가 이 페이지 전체입니다.

3. 504MB — 두 배를 지나도 여전히 126MB

컨테이너 249 → 504MB (두 배 넘게) 힙 126.0MB · 비율 50.6 → 25.0% · 여유 318.0MB

메모리를 두 배 넘게 줬습니다. 힙은 한 바이트도 안 늘었고, 비율만 절반으로 떨어졌습니다. 곡선의 점이 세로로 흘러내리는 게 그거예요 — 힙은 가로로 붙어 있는데 비율은 계속 내려갑니다. 그리고 318MB 가 아무도 안 쓰는 채로 남습니다.

4. 512MB — 8MB 더 줬더니 드디어 움직인다

컨테이너 504 → 512MB (8MB 만 더) 힙 126.0 → 128.0MB · 두 배 주면 +128MB

512MB 의 25%가 128MB 라 드디어 상한선(124.8MB)을 넘습니다. 평지를 벗어나는 순간부터 비율이 약속대로 일합니다 — 여기서부터는 컨테이너를 두 배 주면 힙도 두 배예요. 평지의 오른쪽 끝은 126 ÷ 25% = 504MB 입니다.

5. 1024MB — 기본값의 진짜 모습

컨테이너 512 → 1,024MB 힙 256MB (25.0%) · 여유 708MB

1GB 컨테이너에 힙 256MB 입니다. 남은 768MB 를 메타스페이스와 코드캐시와 스레드 스택이 다 쓰지 않아요 — 이 실험대의 기본값(60MB)으로는 708MB 가 남습니다. 25% 는 아주 보수적인 값이고, 대부분의 컨테이너가 그래서 메모리를 놀립니다.

6. MaxRAMPercentage 를 75로 — 놀던 메모리를 쓴다

Max 25 → 75% (컨테이너 1,024MB 그대로) 힙 256 → 768MB · 여유 708 → 196MB

놀던 메모리가 힙으로 갑니다. 그리고 평지가 사라집니다 — 상한선(124.8MB)을 75%로 넘는 지점이 167MB 라 평지가 들어갈 자리가 없어요. 비율을 올리는 것은 힙을 키우는 것만이 아니라 평지를 없애는 것입니다. 다만 196MB 로 힙 밖을 다 감당할 수 있는지는 재 봐야 합니다.

7. 힙 밖을 800MB 로 — OOMKilled

Max 를 25% 로 되돌리고 힙 밖 실사용 60 → 800MB 힙 256MB + 힙 밖 800MB = 1,056MB · 여유 −32MB

힙은 상한을 안 넘었습니다. OutOfMemoryError 도 안 납니다. cgroup 이 프로세스를 죽입니다 — 힙 덤프도, 스택도, 자바 쪽 흔적이 하나도 안 남아요. 로그는 깨끗한데 파드가 재시작합니다. 그리고 이때 컨테이너를 늘리는 것이 흔한 처방인데, 2~3단계 구간에 있으면 그게 안 듣습니다.

식이 한 줄이다

OpenJDK 의 arguments.cpp 에 있는 Arguments::set_heap_size() 가 전부입니다.

if (FLAG_IS_DEFAULT(MaxHeapSize)) {
  julong reasonable_max = phys_mem * MaxRAMPercentage / 100;
  const julong reasonable_min = phys_mem * MinRAMPercentage / 100;
  if (reasonable_min < MaxHeapSize) {
    // Small physical memory, so use a minimum fraction of it for the heap
    reasonable_max = reasonable_min;
  } else {
    // Not-small physical memory, so require a heap at least as large as MaxHeapSize
    reasonable_max = MAX2(reasonable_max, (julong)MaxHeapSize);
  }

정리하면 이렇습니다.

힙 = align_up( max(RAM × Max%, min(RAM × Min%, 124.8MB)), 2 MiB )

가운데 min 이 평지를 만듭니다. 그리고 124.8MB 가 어디서 왔는지가 이 페이지에서 가장 이상한 부분입니다.

평지의 정체는 96MB 짜리 기본값이다

gc_globals.hpp 의 네 줄이 이 편의 상수 전부입니다.

플래그기본값
MaxRAMPercentage25.0
MinRAMPercentage50.0
InitialRAMPercentage1.5625
MaxHeapSizeScaleForWordSize(96*M) = 124.8 MiB

마지막 줄이 상한선입니다. MaxHeapSize 의 기본값 — 비율도 아니고 컨테이너와도 무관한, 그냥 96MB 에 1.3배를 한 상수입니다. 코드의 주석이 "require a heap at least as large as MaxHeapSize" 라고 적어둔 그 의도는 "큰 기계에서 힙이 너무 작아지지 않게" 였는데, 컨테이너 시대에는 그게 힙이 너무 커지지 않게 하는 쪽으로 작동합니다.

그래서 평지의 양 끝이 이 상수에서 나옵니다. 왼쪽은 124.8 ÷ 50% 언저리, 오른쪽은 126 ÷ 25% = 504MB. 손잡이 둘(Min · Max)을 돌리면 평지가 넓어지고 좁아지고 아예 없어지기도 합니다 — 6단계가 그것입니다.

249MB 에서 126MB 가 나오는 이유

249MB 의 절반은 124.5MB 입니다. 상한선 124.8MB 보다 작으니 "작은 메모리" 분기를 타고 124.5MB 가 됩니다. 그런데 화면에는 126MB 가 나와요.

힙 정렬 때문입니다 — 2 MiB 단위로 올립니다. 실측으로 확인한 것이고, 짝수 MB 만 넣어 보면 안 보입니다. 홀수를 넣어야 보여요.

언제나 올림입니다. 이 실험대의 평지 구간도 식으로 풀지 않고 훑어서 구합니다 — 처음에 124.8 ÷ 비율 로 풀었더니 250~499MB 가 나왔는데 실측은 249~504MB 였어요. 정렬이 양 끝을 한 칸씩 밀어 놓습니다.

검산점이 표가 아니라 생성기다

이 사이트의 다른 편들은 문서가 준 표와 맞춰 봤습니다 — 26번은 RFC 6928 의 왕복 수 표, 27번은 man page 의 "약 127초" 였죠. 이 편은 다릅니다.

JVM 이 임의 입력에 답을 인쇄합니다.
java -XX:MaxRAM=249m -XX:+PrintFlagsFinal -version | grep MaxHeapSize
그래서 유한한 표를 맞추는 것이 아니라 생성기와 겨룰 수 있습니다 — 손잡이 전 구간을 훑어서요.

그 출력을 62점 떠서 저장소에 굳혀 뒀습니다(tools/heap-fixture.mjs). 검사는 그 자료와 견주므로 JDK 없이 돌아갑니다. Temurin 25.0.4.1+1 과 Zulu 17 에서 각각 떠 보고 모든 점이 일치하는 것을 확인했어요.
