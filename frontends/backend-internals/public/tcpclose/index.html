단말이 전송을 마치고 소켓을 닫았습니다. 서버에는 본문의 뒷부분이 없어요. "FIN 이 데이터를 앞질러 도착했다"고 생각하기 쉽지만 그건 불가능합니다. 실제로 일어난 일은 다르고, 클라이언트 코드는 세 경우 모두 close() 한 줄로 똑같습니다.

직접 조작하기

손잡이무엇이 바뀌나
종료 방식네 경우 모두 애플리케이션 코드는 close() 한 줄입니다. 선로에 나가는 것만 달라집니다.
서버 응답 크기0 으로 내려보세요. 같은 클라이언트 코드가 갑자기 안전해집니다 — 읽지 않을 응답이 없으니까요.
TLS 종단로드밸런서에서 종단하면 커넥션이 둘로 쪼개집니다. 유실 지점이 하나 더 생깁니다.
close_notify안 보내면 바이트는 다 도착하는데도 받는 쪽이 "끝난 것"과 "잘린 것"을 구별할 수 없습니다.
half-close 전파프록시가 한 방향 종료를 그대로 넘기는지. nginx 기본값은 off 입니다.

수신 버퍼는 양쪽 모두 64KB로 두었습니다. TLS 레코드는 최대 16,384바이트(RFC 8446 §5.1)입니다.

유실량이 아니라 유실 상한을 표시합니다. RST 로 사라지는 것은 "수신 측 커널 버퍼에 아직 애플리케이션이 안 읽은 바이트"인데, 그 값은 읽는 속도에 달려 있어 알 수 없습니다. 그래서 min(본문, 수신 버퍼) 라는 상한만 계산합니다. 지어낸 숫자를 보여주지 않으려고요.

이렇게 해보세요

1. 응답을 읽고 닫는다 — FIN, 유실 상한 0

응답 읽고 close · 본문 16KB · 응답 1KB · TLS 없음 선로에 나간 신호 FIN · 유실 상한 0 정상 종료 판정 3 / 3

기준선입니다. FIN 이 나가면 유실은 구조적으로 0 입니다. FIN 은 시퀀스 번호 공간의 한 자리를 차지해 바이트 스트림 맨 끝에 놓이고, 수신 TCP 는 중간에 구멍이 있으면 그 뒤를 애플리케이션에 올리지 못합니다. "구멍 있는 깨끗한 EOF" 는 존재하지 않습니다. 스트림 그림에서 종료 신호가 언제나 맨 뒤에 붙어 있는 게 그 뜻이에요.

2. 응답을 안 읽고 닫는다 — 같은 코드, 이번엔 RST

종료 방식만 바꿈 (응답 1KB 는 그대로) 선로에 나간 신호 FIN → RST 유실 상한 0 → 16 KB · 정상 종료 판정 3/3 → 2 / 3

수신 버퍼에 안 읽은 1KB 가 남은 상태로 close() 를 부르면, 커널은 FIN 이 아니라 RST 를 보냅니다. RFC 9293 §3.6.1 이 그렇게 적어뒀어요 — "if such a host issues a CLOSE call while received data is still pending … its TCP implementation SHOULD send a RST to show that data was lost". 그리고 RST 를 받은 쪽은 자기 수신 버퍼를 버립니다. 애플리케이션 판정은 여전히 "정상" 입니다 — close() 를 불렀으니까요.

3. 서버 응답을 0 으로 — 같은 코드가 안전해진다

응답 크기 1KB → 0 (종료 방식은 "안 읽고 close" 그대로) 선로에 나간 신호 RST → FIN · 유실 상한 0

클라이언트는 한 글자도 안 바뀌었습니다. 그런데 안전해졌어요. 읽지 않을 응답이 없으면 미독 데이터도 없으니까요. 이게 이 사고가 재현이 어려운 이유입니다 — 서버가 100 Continue 나 에러 응답을 보내기 시작한 날, 또는 응답에 헤더가 하나 늘어난 날 갑자기 터집니다. 클라이언트 코드에는 아무 변화가 없습니다.

4. SO_LINGER 를 0 으로 — 응답이 없어도 RST

종료 방식 SO_LINGER 0 (응답은 여전히 0) 선로에 나간 신호 FIN → RST

미독 데이터와 무관하게 무조건 RST 입니다. 커넥션을 빨리 회수하려고 setSoLinger(true, 0) 이나 ChannelOption.SO_LINGER 를 0 으로 켜두는 경우가 있는데, 그건 "TIME_WAIT 를 없애는 옵션"이 아니라 "데이터를 버리는 옵션"입니다.

5. TLS 를 백엔드에서 종단하고 close_notify 를 안 보낸다

TLS 종단 백엔드 · close_notify 안 보냄 정상 종료 판정 2 / 3 (TLS 가 비정상) 잘리는 단위가 바이트 → 16 KB (레코드)

RFC 8446 §6.1 은 "Each party MUST send a close_notify alert before closing its write side" 라고 합니다. 안 보내면 받는 쪽은 "보내는 쪽이 끝낸 것"과 "공격자가 중간에서 끊은 것"을 구별할 수 없습니다(절단 공격). 구현에 따라 에러로 처리하거나 조용히 받아들입니다. 그리고 TLS 는 레코드 단위로 암호화하니 커넥션이 레코드 중간에서 죽으면 바이트 몇 개가 아니라 레코드 하나가 통째로 못 읽힙니다.

6. TLS 종단을 로드밸런서로 — 유실 지점이 하나 더 생긴다

TLS 종단 백엔드 → 로드밸런서 커넥션 구간 1개 → 2개 · 유실 지점 2곳 유실 상한 16KB → 32 KB

TLS 를 종단하는 순간 커넥션이 둘로 쪼개집니다. AWS NLB 문서가 TLS 리스너에 대해 "uses a server certificate to terminate the front-end connection" 이라고 적어둔 그대로예요. TCP 순서 보장은 홉 단위라 앞단과 뒷단 사이에는 이어지지 않습니다 — 5번에서 QoS 가 홉 단위 보장이었던 것과 같은 구조입니다.

7. shutdown(WR) → 응답 읽기 → close — 전부 정상

종료 방식 shutdown(WR) · close_notify 보냄 선로에 나간 신호 FIN · 유실 상한 0 · 정상 종료 판정 3 / 3

쓰기만 먼저 닫아 "더 보낼 게 없다"를 알리고, 서버 응답을 끝까지 읽은 뒤에 닫습니다. 미독 데이터가 없으니 RST 가 나갈 이유가 없어요. 세 계층이 모두 "정상 종료" 라고 답하는 유일한 경우입니다.

FIN 은 데이터를 앞지를 수 없다

먼저 틀린 설명을 치워두겠습니다. 관찰되는 증상이 정확히 그 모양이라 이 설명이 자연스럽게 만들어지는데, 성립하지 않습니다.

왜 불가능한가
FIN 은 시퀀스 번호 공간의 한 자리를 차지합니다. RFC 9293 §3.4 의 표현으로는 "the FIN is considered to occur after the last actual data octet" — 바이트 스트림의 맨 끝에 놓이는 하나의 위치입니다
수신 TCP 는 순서대로만 애플리케이션에 올립니다. 중간이 비면 그 뒤에 도착한 것을 들고 기다립니다
따라서 EOF 는 언제나 모든 바이트가 전달된 뒤에 나타납니다. "구멍 있는 깨끗한 EOF" 라는 상태가 존재하지 않습니다
FIN 세그먼트가 앞선 데이터 세그먼트보다 물리적으로 먼저 도착하는 것은 가능합니다 — 경로가 재배열되면요. 하지만 그게 EOF 로 올라가지 않습니다. 데이터가 끝까지 안 오면 EOF 가 아니라 타임아웃 에러가 납니다.

이건 RFC 의 한 문장으로 규정된 게 아니라 순서 보장이라는 서비스 모델의 귀결입니다. 그래서 인용이 아니라 논증으로 적었습니다.

"정상 종료" 의 정의가 계층마다 다르다

실험대의 판정 세 줄이 이 페이지의 축입니다. 같은 순간을 세 계층이 다르게 봅니다.

계층무엇을 보고 판정하나2번 설정에서
애플리케이션close() 를 불렀나정상 — 코드에 close() 밖에 없다
TLSclose_notify 를 보냈나 (RFC 8446 §6.1)정상 (여기서는 TLS 없음)
TCPFIN 이냐 RST 냐비정상 — RST 다
그래서 "정상 종료했는데 데이터가 유실됐다"는 모순이 아닙니다. 두 문장이 서로 다른 계층을 말하고 있을 뿐입니다. 애플리케이션 개발자와 네트워크 담당자가 같은 사건을 두고 다른 결론에 도달하는 자리이기도 하고요.

RFC 가 규정하는 것과 구현이 하는 것

이 페이지를 만들면서 근거를 1차 출처로 확인했는데, 세 주장 중 하나만 규격에 있었습니다. 나머지는 구현 동작이거나 논증입니다. 구별해서 적어두겠습니다.

주장근거의 성격
미독 데이터가 있으면 close() 가 RST 를 보낸다규격에 있다. RFC 9293 §3.6.1 (SHLD-3). 다만 SHOULD 이지 MUST 가 아닙니다 — 구현 재량이 있습니다
RST 를 받은 쪽이 수신 버퍼를 버린다구현 동작입니다. §3.5.3 은 "aborts the connection and advises the user" 까지만 말하고 버퍼 처분을 규정하지 않습니다. 실제 구현이 전부 그렇게 동작하는 것이지 규격이 요구하는 게 아닙니다
구멍 있는 EOF 는 없다논증입니다. 순서 보장 서비스 모델의 귀결이고, 이걸 한 문장으로 규정한 조항은 없습니다
프록시가 앞단 RST 를 받으면 뒷단 버퍼를 어떻게 하나모릅니다. 문서화돼 있지 않습니다. nginx proxy_half_close 기본값이 off(한 방향이 닫히면 양쪽을 닫는다)인 것까지가 확인된 사실이고, 그 이상은 단정하지 않았습니다

맞는 처방과 무효한 처방

이 사고를 실제로 겪은 팀의 기록에서 가장 배울 점은 처방 두 개의 차이였습니다.

처방결과
서버가 연결이 끊긴 것을 감지한 뒤 몇 초 기다렸다가 마무리한다완전히 무효. 버리는 주체가 서버 쪽이 아니었으니 서버가 기다려도 달라질 게 없습니다. 넣었다가 삭제했습니다
서버가 종료 신호를 에코하고, 클라이언트는 그 응답을 받은 뒤에 닫는다동작합니다. 클라이언트가 응답을 읽어야 하니 미독 데이터가 없어져 RST 가 사라지고, 서버 처리 완료도 확인되고, close_notify 타이밍도 정리됩니다
두 번째 처방은 이 페이지의 네 메커니즘 중 무엇이 범인이든 동작합니다. 그러니 결과만 보면 "원인을 몰라도 됐다"고 할 수 있어요. 그런데 같은 팀이 무효한 처방을 한 번 먼저 넣었습니다. 원인을 모르면 맞는 처방을 고를 근거가 없기 때문입니다.

14번과 20번에서 타임아웃을 늘리는 처방을 다뤘는데, 같은 기준이 여기도 적용됩니다 — 정상 케이스의 분포를 알고 늘렸으면 정답, 모르고 늘렸으면 유예입니다.
