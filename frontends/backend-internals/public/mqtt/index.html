한 번만 전달한다는 약속의 값

QoS 2 를 쓰면 메시지가 정확히 한 번 도착합니다. 그 문장은 사실이지만, 어디까지가 그 약속이고 값을 어디서 치르는지는 잘 이야기되지 않습니다. 세 레벨을 나란히 돌려보겠습니다.

QoS 0최대 한 번

보내고 잊습니다. 확인도, 재전송도 없습니다.

QoS 1최소 한 번

확인을 받을 때까지 다시 보냅니다. 그래서 두 번 도착할 수 있습니다.

QoS 2정확히 한 번

네 번의 왕복으로 중복을 없앱니다. 그만큼 느리고 비쌉니다.

세 레인은 같은 속도로 패킷을 하나씩 소비합니다. 그래서 같은 시간에 끝낸 메시지 수가 곧 그 레벨의 값입니다. 위쪽 칩은 방금 오간 패킷이고(빨간 취소선은 유실, 점선은 타임아웃 대기), 아래 칸들은 메시지별 결과입니다 — 초록 빈칸은 한 번 전달, × 는 유실, 2 는 중복. 계기의 회색 숫자는 이 조건에서의 기대값이에요.

기다릴 필요 없이 슬라이더를 바로 움직여보세요. 계기는 조건이 바뀔 때마다 새로 잡힙니다.

이렇게 해보세요

1. 실패율 0% 에서 패킷 수만 센다

전송 실패율 0 QoS 0 메시지당 패킷 1개 QoS 1 메시지당 패킷 2개 QoS 2 메시지당 패킷 4개 세 레인 모두 유실 0 · 중복 0

아무것도 잃지 않는 네트워크에서는 세 레벨의 결과가 똑같습니다. 다른 건 값뿐이에요. QoS 2 는 아무 문제가 없을 때조차 QoS 0 의 네 배를 씁니다. 레인의 진행 속도가 눈에 띄게 다른 것도 보세요.

2. 20% 로 올린다 — 여기가 이 페이지의 핵심

전송 실패율 20 QoS 0 유실 20% 패킷 1.00 QoS 1 중복 25% 패킷 2.81 QoS 2 유실 0 · 중복 0 패킷 5.63

세 레벨이 각자 다른 방식으로 대가를 치릅니다. QoS 0 은 메시지를 잃고, QoS 1 은 메시지를 두 번 주고, QoS 2 는 패킷을 두 배로 씁니다. 공짜인 선택지는 없습니다.

QoS 1 의 중복률이 유실률보다 크다는 점을 눈여겨보세요. 20% 실패에서 25% 중복입니다. 왕복 두 번 중 어느 쪽이 실패해도 재전송이 일어나기 때문이에요.

3. 40% 까지 올린다

전송 실패율 40 QoS 1 중복 66.7% 패킷 4.44 QoS 2 중복 0 패킷 8.89 QoS 2 유실 0.8% 재전송 상한(12회)에 걸린 것 QoS 2 레인의 결과 칸이 눈에 띄게 느리게 찬다

QoS 2 의 패킷이 메시지당 9개에 육박합니다. 중복은 여전히 0 이지만 처리량이 무너지고, 재전송 상한에 걸려 아예 포기되는 메시지까지 0.8% 생깁니다. 네트워크가 나쁠수록 exactly-once 의 값이 가파르게 오르는데, 하필 네트워크가 나쁠 때 그 값을 치러야 한다는 게 곤란한 점이에요.

4. QoS 1 레인의 칩을 한 줄씩 읽는다

일시정지를 누르고 QoS 1 의 칩을 본다 PUBLISH → 구독자 → PUBACK(취소선) → 타임아웃 → PUBLISH → 구독자(중복) 메시지는 이미 도착했는데 다시 보냈다

중복이 생기는 순간이 여기 그대로 보입니다. 구독자는 이미 받았고, 발행자만 그 사실을 모릅니다. 확인 응답이 사라졌으니까요. 발행자에게는 "PUBLISH 가 유실됐다" 와 "PUBACK 이 유실됐다" 가 완전히 똑같이 보입니다. 구별할 방법이 없으니 다시 보내는 것 말고는 할 수 있는 게 없습니다.

5. QoS 2 레인에서 PUBCOMP 가 유실될 때를 기다린다

실패율 30~40 에서 QoS 2 를 지켜본다 PUBREL → 구독자 → PUBCOMP(취소선) → 타임아웃 → PUBREL → 전달 없음 PUBREL 은 다시 갔는데 구독자 칩이 안 붙는다

QoS 2 가 중복을 없애는 방식이 여기 있습니다. 브로커는 PUBREL 을 처리하면서 그 패킷 id 를 버립니다. 같은 PUBREL 이 다시 와도 기억에 없으니 전달하지 않고 PUBCOMP 만 돌려줘요. 재전송은 일어나지만 중복 전달은 일어나지 않습니다.

QoS 는 무엇을 약속하는가

세 레벨은 "몇 번 도착하는가"에 대한 서로 다른 약속입니다.

레벨약속실패했을 때
QoS 0최대 한 번 (at most once)그냥 사라진다
QoS 1최소 한 번 (at least once)다시 보낸다 → 두 번 도착할 수 있다
QoS 2정확히 한 번 (exactly once)다시 보내되 중복은 걸러낸다

이름이 정확합니다. QoS 1 은 "한 번"이 아니라 "최소 한 번"입니다. 중복은 예외 상황이 아니라 설계에 포함된 정상 동작이에요. QoS 1 을 쓰기로 했다면 중복 처리는 선택이 아닙니다.

왜 QoS 1 은 중복을 만드는가

발행자가 PUBLISH 를 보내고 PUBACK 을 기다립니다. 시간이 지나도 안 오면 다시 보냅니다. 문제는 "안 왔다"의 원인이 두 가지라는 겁니다.

① PUBLISH 가 가는 길에 사라졌다   → 구독자는 못 받았다 → 재전송이 맞다
② PUBACK 이 오는 길에 사라졌다    → 구독자는 이미 받았다 → 재전송하면 중복

발행자 입장에서 두 경우는 완전히 구별되지 않습니다. 보이는 건 "응답이 없다" 하나뿐이에요. 그래서 안전한 쪽(재전송)을 택하고, 그 대가로 중복이 생깁니다.

실험대의 기대 중복률이 p / (1-p) 인 이유가 이것입니다. 실패율 20% 면 25%, 40% 면 66.7% 예요. 유실률보다 중복률이 항상 큽니다. 왕복 두 구간 중 어느 쪽이 끊겨도 재전송이 일어나니까요.

QoS 2 는 어떻게 중복을 없애는가

왕복을 한 번 더 놓아서 "이제 버려도 된다"는 시점을 양쪽이 합의합니다.

발행자                          브로커
   │──── PUBLISH (id=7) ────────▶│  id 7 을 기억해 둔다
   │◀─── PUBREC   (id=7) ────────│  "받았다"
   │──── PUBREL   (id=7) ───────▶│  전달하고 id 7 을 버린다
   │◀─── PUBCOMP  (id=7) ────────│  "끝났다"

핵심은 패킷 id 를 기억하는 구간입니다. 그 구간 안에서 같은 id 의 PUBLISH 가 다시 오면 브로커는 중복으로 판단해 버립니다. PUBREL 이후에 같은 id 가 다시 와도 이미 버렸으니 전달하지 않고 PUBCOMP 만 돌려줍니다.

즉 QoS 2 의 exactly-once 는 마법이 아니라 중복 제거(dedup)를 프로토콜에 넣은 것입니다. 재전송은 QoS 1 과 똑같이 일어나요. 다만 걸러낼 뿐입니다.

전달을 PUBLISH 시점에 할지 PUBREL 시점에 할지는 스펙이 두 방식을 모두 허용합니다. 이 실험대는 PUBREL 시점으로 그렸습니다. 어느 쪽이든 결론은 같아요 — 패킷 id 를 기억하는 동안 같은 id 를 걸러낸다는 것이 중복 제거의 전부입니다.

값을 치르는 곳

실험대의 기대값을 표로 옮기면 이렇습니다. q = 1 − 실패율 이라 할 때 QoS 1 은 메시지당 (1+q)/q² 패킷, QoS 2 는 그 두 배입니다. 시도당 2패킷이 아니라 1+q 인 이유는, PUBLISH 가 유실되면 PUBACK 은 아예 생기지 않기 때문이에요.

QoS 2 의 패킷은 언제나 QoS 1 의 정확히 두 배입니다. 왕복이 두 번이니까요. 그리고 지연도 두 배입니다 — 발행자가 "끝났다"를 확인하려면 네트워크를 네 번 건너야 합니다.

배터리로 도는 센서나 셀룰러 회선에서는 이 차이가 그대로 비용입니다. MQTT 가 애초에 그런 환경을 겨냥해 만들어진 프로토콜이라는 걸 생각하면, QoS 2 를 기본값처럼 쓰는 건 프로토콜의 설계 의도와 어긋나는 선택이에요.

가장 흔한 오해 — QoS 는 홉 단위다

이게 실무에서 가장 자주 틀리는 지점입니다. QoS 는 발행자와 구독자 사이의 약속이 아닙니다. 발행자↔브로커 구간과 브로커↔구독자 구간이 각각 별개의 QoS를 갖습니다.

발행자 --QoS 2--▶ 브로커 --QoS 0--▶ 구독자
       (발행할 때 지정)      (구독할 때 지정)

실제 전달 품질 = 두 값 중 낮은 쪽

구독자가 QoS 0 으로 구독하고 있으면, 발행을 QoS 2 로 아무리 정성껏 해도 구독자에게 가는 마지막 구간에서 그냥 사라집니다. 브로커까지는 정확히 한 번 도착했다는 게 위안이 되지 않죠.

"QoS 2 로 보냈는데 메시지가 안 왔다"는 문의의 상당수가 여기입니다. 발행 코드만 보지 말고 구독 쪽 QoS 를 먼저 확인하세요.

이 실험대의 "유실"은 TCP 패킷 손실이 아니다

정확히 짚고 넘어갈 것이 있습니다. MQTT 는 TCP 위에서 돕니다. 그리고 TCP 는 이미 재전송을 합니다. IP 패킷 하나가 빠졌다고 MQTT 메시지가 사라지지 않아요. TCP 가 알아서 다시 보내고, MQTT 는 그런 일이 있었는지도 모릅니다.

그러면 MQTT 수준에서 메시지는 언제 사라질까요. 연결이 끊어질 때입니다. 그 순간 아직 확인받지 못한 채 떠 있던(in-flight) 메시지들이 문제가 됩니다.

이 실험대의 실패율 슬라이더는 그 상황을 한 번의 확률로 압축한 것입니다. 실제로는 이렇게 균일하게 흩뿌려지지 않고, 연결이 끊기는 순간에 몰려서 발생합니다.

재전송 시점도 마찬가지로 단순화했습니다. 실험대는 타임아웃마다 다시 보내지만, MQTT 5.0 은 연결이 살아 있는 동안의 재전송을 하지 않고 세션이 다시 이어질 때 미확인 패킷을 보내도록 정리했습니다. 그래서 실제 중복은 이 화면처럼 잘게 흩어지지 않고 재연결 직후에 몰려서 나타납니다.

DUP 플래그로 중복을 거르면 되지 않나

재전송된 PUBLISH 에는 DUP 플래그가 1 로 붙습니다. 이걸로 중복을 판정하고 싶어지는데, 그러면 안 됩니다.

DUP 는 "이 패킷을 다시 보냈다"는 발행자 쪽 사정일 뿐입니다. 첫 전송이 유실됐다면 구독자에게는 DUP=1 인 그 메시지가 처음 보는 메시지예요. 그걸 버리면 멀쩡한 메시지를 잃습니다. 반대 방향도 마찬가지입니다 — 브로커가 구독자에게 보내는 패킷의 DUP 는 브로커의 사정이지 발행자의 사정이 아닙니다.

중복 판정은 애플리케이션 레벨의 식별자로 해야 합니다. 페이로드에 메시지 id 를 싣고 수신 쪽에서 최근에 본 id 를 기억하는 방식이죠. 결국 이게 다음 절의 결론이기도 합니다.

현장에서 확인할 것

대부분의 경우 QoS 1 + 멱등 처리가 답입니다. 수신 쪽이 같은 메시지를 두 번 받아도 결과가 같도록 만들어두면, QoS 2 의 왕복 두 번을 살 이유가 거의 없어집니다.

-- 메시지 id 로 중복을 막는다 (수신 쪽)
INSERT INTO reading (msg_id, device_id, value, at)
VALUES (:msgId, :deviceId, :value, :at)
ON CONFLICT (msg_id) DO NOTHING;

제약 조건 하나가 QoS 2 가 프로토콜로 하는 일을 애플리케이션에서 해줍니다. 게다가 이쪽이 더 넓게 막습니다 — 아래에서 설명할, QoS 2 로도 못 막는 경우까지 함께 걸러지거든요.

exactly-once 는 브로커까지의 약속입니다. 구독자가 메시지를 받아 처리한 뒤, 확인 응답을 보내기 전에 프로세스가 죽으면 어떻게 될까요. 재연결하면 그 메시지가 다시 옵니다. 프로토콜은 약속을 지켰지만 애플리케이션은 같은 일을 두 번 했습니다. 이 구간은 QoS 2 로 막을 수 없습니다.

세션이 유지되어야 QoS 가 의미를 갖습니다. QoS 1·2 의 재전송은 브로커가 세션 상태를 기억하고 있어야 가능합니다.

  • MQTT 3.1.1 — cleanSession=false 로 접속해야 합니다. true 면 끊기는 순간 대기 중이던 메시지가 전부 사라집니다
  • MQTT 5.0 — Clean Start=false + Session Expiry Interval 을 재접속에 걸리는 시간보다 넉넉히 잡습니다. 만료되면 3.1.1 의 cleanSession=true 와 같아집니다
  • 클라이언트 id 가 매번 바뀌면(재시작마다 UUID 생성) 세션을 못 찾습니다. QoS 를 올려놓고 이것 때문에 메시지를 잃는 경우가 흔합니다

구독 쪽 QoS 를 확인하세요. 앞에서 다룬 홉 단위 문제입니다. 발행 QoS 와 구독 QoS 중 낮은 쪽이 실제 품질입니다.

in-flight 개수가 처리량을 정합니다. QoS 1·2 는 확인을 기다리는 메시지 수에 상한이 있습니다(MQTT 5 의 Receive Maximum). 이 값이 작은데 왕복 지연이 크면 대역폭이 남아도 처리량이 안 나옵니다. QoS 2 는 왕복이 두 배라 같은 상한에서 처리량이 절반이 됩니다.

재전송에는 반드시 상한을 두세요. 이 실험대도 12회에서 끊습니다. 실패율 40% 에서는 이 상한이 실제로 물려서, QoS 2 메시지의 0.8% 가량이 끝내 전달되지 못하고 포기됩니다 — 위 표의 기대값이 상한 없는 경우를 가정하고 있어 실측이 조금 낮게 나오는 이유이기도 합니다. 상한 없는 재시도는 상대가 계속 실패할 때 그 상대를 함께 두들깁니다. 끝나지 않는 재시도 루프는 조용히 자원을 태우다가 전혀 다른 곳에서 장애로 나타나요.
