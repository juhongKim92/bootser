둘 다 확인했고 둘 다 통과했다

당직자는 최소 한 명 남아야 합니다. 빠지려는 사람은 먼저 확인해요 — "나 말고 한 명 더 있네." 두 사람이 동시에 확인하면 둘 다 한 명 더 있다고 보고 둘 다 빠집니다. 각자 자기 행만 건드렸으니 락도 안 걸리고 예외도 안 납니다.

직접 조작하기

손잡이무엇이 바뀌나
격리 수준네 방식을 같은 난수 씨앗에서 다시 돌립니다. 그래서 같은 사건이 같은 순서로 일어나고, 결과 차이는 오직 방식 때문입니다.
당직자 수많을수록 동시에 빠지려는 사람이 늘어 겹칠 일이 많아집니다.
읽기 → 쓰기 간격세고 나서 실제로 쓰기까지 걸리는 시간. 0이면 겹칠 수가 없습니다.

각 트랜잭션이 하는 일은 이게 전부입니다.

BEGIN; n = SELECT count(*) FROM oncall WHERE on_duty; -- 읽기는 한 번뿐 if (n >= 2) UPDATE oncall SET on_duty = false WHERE id = :me; COMMIT;

여기서 중요한 것은 WHERE id = :me 입니다. 각자 자기 행만 씁니다. 서로 다른 행이니 행 락이 겹치지 않고, 그래서 데이터베이스가 보기에 두 트랜잭션은 아무 관계가 없습니다.

이렇게 해보세요

1. 간격이 0이면 네 방식이 구별되지 않는다

읽기 → 쓰기 간격 0초 겹친 트랜잭션 거의 0 · 불변식 깬 커밋 0건 · 최소 당직 1명

세자마자 쓰면 다른 사람이 끼어들 틈이 없습니다. 격리 수준 버튼을 네 개 다 눌러보세요 — 숫자가 하나도 안 바뀝니다. 충돌이 없으면 격리 수준은 아무 의미가 없어요. 개발 장비에서 재현이 안 되는 이유가 이겁니다.

2. 간격을 0.6초로 — 둘 다 세고 둘 다 빠진다

Read Committed · 당직자 5명 · 간격 0.6초 1,200초 동안 커밋 367건 · 불변식 깬 커밋 6건 · 최소 당직 0명

진행 중인 트랜잭션 줄을 보세요. 두 사람이 각각 "2명 봤음"을 들고 있는데 지금 당직은 이미 1명입니다. 둘 다 조건을 통과했고 둘 다 씁니다. 예외도 롤백도 없습니다. 로그에는 정상 커밋 두 건만 남아요.

3. Repeatable Read 로 바꾼다 — 숫자가 하나도 안 바뀐다

Repeatable Read · 나머지 동일 커밋 367건 · 불변식 깬 커밋 6건 · 최소 당직 0명 Read Committed 와 완전히 동일

이 페이지의 핵심이 여기입니다. 격리 수준을 올렸는데 결과가 소수점 하나까지 같습니다. 이유는 두 가지예요. 첫째, 앱이 한 번만 읽습니다 — 반복 읽기를 안 하니 "반복 읽기 보장"이 쓸 자리가 없어요. 둘째, 각자 자기 행만 씁니다 — 같은 행을 고쳤다면 PostgreSQL 의 Repeatable Read 가 40001 을 던졌을 텐데, 다른 행이라 먼저 쓴 사람이 이기고 말고 할 것도 없습니다.

4. 당직자를 8명으로 늘린다

Read Committed · 8명 · 간격 0.6초 겹친 트랜잭션 57회 → 171회 · 불변식 깬 커밋 6건 → 10건

사람이 늘면 동시에 빠지려는 조합이 늘고 겹침이 세 배가 됩니다. 부하가 늘면 확률이 아니라 빈도가 늘어납니다. 스테이징에서 안 나던 게 프로덕션에서 나는 자리예요 — 코드는 같고 동시성만 다릅니다.

5. Serializable — 막아주는 대신 예외를 던진다

Serializable · 나머지 동일 불변식 깬 커밋 0건 · 최소 당직 1명 대신 직렬화 실패 62번 (커밋 367 → 332)

PostgreSQL 의 Serializable 은 락이 아니라 SSI 입니다. 내가 읽은 술어를 내가 커밋하기 전에 누가 바꿨으면 커밋 시점에 40001 could not serialize access 를 던져요. 불변식은 지켜집니다. 그런데 62번 던진 예외를 누가 받느냐가 남습니다. 재시도 코드가 없으면 정합성 문제가 500 에러로 형태만 바뀐 겁니다.

6. SELECT ... FOR UPDATE — 충돌을 물질화한다

Read Committed + FOR UPDATE 불변식 깬 커밋 0건 · 직렬화 실패 0번 겹친 트랜잭션 0회 — 대신 줄을 선다

세는 쿼리에서 읽는 행들을 잠그면 두 번째 사람은 첫 번째가 커밋할 때까지 아예 읽지 못합니다. 겹침 자체가 0이 돼요. 서로 관계없어 보이던 두 트랜잭션에 억지로 관계를 만들어준 겁니다 — 이걸 충돌의 물질화라고 부릅니다. 예외가 없어 재시도 코드도 필요 없지만, 대기가 생기고 데드락 여지가 열립니다.

왜 Repeatable Read 가 안 막는가

이름이 약속하는 것은 같은 것을 다시 읽으면 같은 값이 나온다는 것뿐입니다. 이 코드는 다시 읽지 않아요. 한 번 읽고, 그 값으로 판단하고, 씁니다. 반복 읽기 보장은 쓸 자리가 없습니다.

실험대의 트랜잭션 줄에 "다시 세면" 칸을 둔 이유가 그겁니다. Read Committed 에서는 그 값이 현재 커밋된 수라 처음 읽은 값과 달라져 있고, Repeatable Read 에서는 스냅샷이 얼어 있어 처음 값 그대로예요. 두 수준은 분명히 다르게 동작합니다. 그 차이가 이 버그를 막지 못할 뿐입니다.

막아주는 것은 격리 수준의 높이가 아니라, 데이터베이스가 두 트랜잭션 사이에 관계가 있다는 걸 알 수 있느냐입니다. 자기 행만 쓰면 관계가 안 보입니다.

PostgreSQL 의 Repeatable Read 는 표준 RR 보다 오히려 강합니다 — 스냅샷 격리라서 팬텀도 안 보여요. 그런데도 write skew 는 못 막습니다. "MySQL 에서 되던 게 PostgreSQL 에서 안 된다"거나 그 반대의 이야기가 여기서 나오지만, 이 버그에 관해서는 둘 다 못 막습니다.

재고 차감처럼 같은 행을 두고 다투는 문제는 9번(작업 선점)에서 다룬 구조 그대로입니다. write skew 가 어려운 건 다투는 지점이 행이 아니라 조건이라서예요. 그래서 락을 걸 대상이 눈에 안 보입니다.
