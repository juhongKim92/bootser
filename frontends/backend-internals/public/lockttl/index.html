인스턴스같은 작업을 노리는 대수. 락이 만료되면 다음 인스턴스가 잡습니다.

시간축에서 초록 테두리가 락을 실제로 보유한 구간이고, 붉은 빗금이 락을 잃었는데도 계속 일하는 구간입니다. 회색 막대는 프로세스가 멈춰 있는 시간이에요. 맨 아래 자원 줄의 사각형이 쓰기이고, 숫자는 그 쓰기의 토큰입니다.

미터의 수치는 표본이 아닙니다. 정지는 있거나 없거나 둘 중 하나라 모든 경로를 확률 가중으로 전부 세어서 나온 정확한 기대값입니다.

이렇게 해보세요

1. 정지도 장애도 없다 — 그런데 둘이 들어온다

락 TTL 3.0초 · 작업 5.0초 · 정지 확률 0% · 인스턴스 2대 같은 일 실행 2.00회 · 중복 실행률 100.0% 락을 잃고도 일한 시간 4000ms

아무것도 고장나지 않았습니다. 정지도 없고 네트워크도 멀쩡해요. 그냥 작업이 TTL보다 길 뿐입니다. 3초에 락이 만료되고, 두 번째 인스턴스가 그 순간 정당하게 락을 잡습니다. 이제 둘이 임계구역 안에 있어요. 첫 번째 워커는 자기가 락을 잃었다는 사실을 알 방법이 없습니다 — 만료는 락 서버가 조용히 하는 일이니까요.

2. 펜싱 토큰을 켠다 — 중복 실행률이 한 자리도 안 움직인다

펜싱 토큰 끔 → 켬 같은 일 실행 2.00 → 2.00회 · 중복 실행률 100.0% → 100.0% 거부된 쓰기 0.00 → 0.00건

펜싱 토큰은 둘이 들어오는 것을 막지 않습니다. 막을 수가 없어요 — 이미 일이 시작된 뒤에 자원이 하는 일이니까요. 이 설정에서는 거부되는 쓰기조차 없습니다. 토큰 1이 5초에, 토큰 2가 8초에 쓰니 순서가 맞기 때문이에요. 펜싱이 필요해지는 건 순서가 뒤집힐 때입니다.

3. 정지를 넣는다 — 결과가 틀린다

정지 확률 0% → 20% · 정지 길이 8.0초 (펜싱 끔) 낡은 쓰기가 최종 0.0% → 16.0% 토큰 2가 8초에 쓰고, 토큰 1이 13초에 덮어쓴다

첫 워커가 8초 멈췄다 깨어납니다. 그 사이 두 번째 워커가 일을 끝내고 썼어요. 그런데 첫 워커는 깨어나서 자기 일을 마치고 그대로 씁니다. 낡은 값이 새 값을 덮습니다. 예외도 로그도 없어요 — 15번과 같은 종류의 사고입니다. 결과만 틀립니다.

4. 이제 펜싱 토큰을 켠다 — 이번엔 일한다

펜싱 토큰 켬 낡은 쓰기가 최종 16.0% → 0.0% · 거부된 쓰기 0.16건 중복 실행률 100.0% 그대로 · 같은 일 실행 2.00 그대로

자원이 토큰 2를 이미 봤으니 토큰 1의 쓰기를 거부합니다. 결과가 맞아졌어요. 그런데 중복 실행은 한 자리도 안 줄었습니다. 여전히 같은 일을 두 번 했고, 여전히 둘이 임계구역에 있었어요. 펜싱이 산 것은 정확성이고, 산 적이 없는 것은 상호배제입니다.

5. 자동 갱신을 켠다 — 중복이 사라진다, 정지가 짧은 한

자동 갱신 켬 · 갱신 간격 1000ms · 정지 길이 4.0초 중복 실행률 100.0% → 20.0% · 같은 일 실행 2.00 → 1.20회 남은 20.0%는 정지가 일어난 경우 전부

watchdog 이 1초마다 만료를 밀어주니, 작업이 TTL보다 길어도 락을 유지합니다. 1번의 문제가 사라졌어요. 남은 20.0%는 정지 확률과 정확히 같습니다 — 정지 중에는 갱신 스레드도 멈춰 있으니까요. 갱신은 스레드 하나가 하는 일이고, GC 정지는 그 스레드도 세웁니다.

6. 갱신을 10배 자주 한다 — 4초 정지에는 여전히 무력하다

갱신 간격 1000 → 100ms (10배 자주) 정지 2.5초: 20.0% → 0.0% (막았다) 정지 4.0초: 20.0% → 20.0% (못 막았다)

자주 갱신하면 견딜 수 있는 정지가 TTL − 갱신 간격까지 늘어납니다. 2.5초 정지는 이제 막아요. 그런데 상한은 TTL 그 자체입니다. 갱신 간격을 0으로 만들어도 TTL − 0 = TTL이고, 4초 정지는 3초 TTL을 넘습니다. 2번에서 힙 128GB의 G1이 538ms 멈추는 것을 봤는데, 스왑이나 풀 GC는 초 단위로 갑니다.

7. TTL을 작업+정지 위로 올린다 — 중복 0%, 대신 9초

락 TTL 3.0 → 9.0초 (작업 5초 + 정지 4초) 중복 실행률 0.0% · 같은 일 실행 1.00회 죽은 워커가 잡은 락을 기다리는 시간 최대 9.0초

드디어 중복이 0이 됐습니다. 대가는 인스턴스가 죽었을 때 드러납니다 — 죽은 프로세스는 락을 놓지 못하니, 다음 인스턴스는 만료까지 9초를 그냥 기다립니다. TTL은 두 가지 값을 동시에 정합니다. 안전 여유이면서 장애 복구 지연이에요.

펜싱 토큰은 무엇을 막고 무엇을 못 막는가

실험대의 비교표가 이 페이지의 요점입니다. 같은 설정에서 방어만 바꿔보면 펜싱 토큰이 움직이는 열은 하나뿐입니다.

방어중복 실행낡은 쓰기가 최종
없음100.0%16.0%
펜싱 토큰100.0% — 그대로0.0%
자동 갱신20.0%0.0%
락은 상호배제를 보장하지 못합니다. 만료가 있는 락이 주는 것은 "대개 한 명만 돈다"는 최적화이고, 정확성은 자원 쪽에서 나옵니다. 자원이 참여하지 않으면 방법이 없습니다.

그래서 실무의 질문은 "어떤 락을 쓸까"가 아니라 "내 자원이 토큰을 검사할 수 있나"입니다. 대개 못 합니다. 조건부 업데이트(WHERE version = ?), 조건부 쓰기(S3 If-Match), 유니크 제약 정도가 쓸 수 있는 도구고, 그냥 UPDATE ... SET 이나 외부 API 호출은 검사할 자리가 없습니다.

검사할 자리가 없으면 남는 길은 멱등성입니다 — 같은 일을 두 번 해도 결과가 같게 만드는 것. 중복 실행을 막으려 애쓰는 대신 중복 실행이 안전하게 만드는 쪽으로 옮기는 겁니다. 5번의 QoS 1이 정확히 같은 결론에 도달했어요. 한 번만 전달한다는 약속은 비싸고, 대개 중복을 허용하고 멱등하게 만드는 편이 싸다는 것.

정지가 TTL을 넘는 순간

낡은 쓰기가 최종 상태가 되는 조건은 정확히 하나입니다.

정지 > TTL. 실험대에서 정지 3000ms는 0.0%, 3100ms는 16.0%입니다. 절벽이에요. 정지한 워커가 대체자보다 늦게 깨어나면, 그 워커의 낡은 쓰기가 마지막에 도착합니다.

자동 갱신을 켜면 경계가 TTL − 갱신 간격으로 옮겨갑니다. 정지가 갱신 주기의 어디서 시작되는지에 따라 실제 여유는 TTL − 갱신 간격과 TTL 사이인데, 안전성은 최악에서 정해지므로 실험대는 갱신 직전에 정지가 시작된 경우를 그립니다.

중요한 것은 어느 쪽이든 상한이 TTL이라는 점입니다. 그리고 TTL을 정지의 최악값 위로 올리려면 그 값이 곧 장애 복구 지연이 됩니다. 좋은 값이 없습니다 — 있는 것은 어느 쪽 대가를 낼지에 대한 선택뿐이에요.

Redlock 은 이 문제를 건드리지 않는다

락 서버를 여러 대로 늘리는 것(Redlock)은 락 저장소의 가용성 문제를 풉니다. 이 페이지의 사고는 저장소에서 나지 않았어요.

어디서 났나Redlock 이 바꾸나
클라이언트가 멈췄다 (GC · 스왑)아니오. 노드를 몇 대로 늘려도 멈춘 클라이언트는 갱신을 못 보낸다
작업이 TTL보다 길었다아니오. TTL은 그대로다
자원이 토큰을 안 본다아니오. 자원 쪽 이야기다
락 서버 한 대가 죽었다예. Redlock 이 실제로 푸는 문제는 이것이다

실험대의 손잡이 중 락 서버가 몇 대인지를 정하는 것이 없는 이유가 이겁니다. 넣어도 어떤 미터도 움직이지 않아요.
