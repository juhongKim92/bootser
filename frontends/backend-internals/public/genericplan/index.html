여섯 번째 실행부터 느려진다

배포하고 한참 뒤에 특정 쿼리만 느려집니다. 실행 계획을 떠보면 멀쩡해요. 그런데 애플리케이션에서는 느립니다 — 옵티마이저가 보고 있는 파라미터가 여러분이 넣은 값이 아니기 때문입니다.

200 종
실행별 소요 시간

막대 하나가 실행 한 번입니다. 세로는 로그 눈금이에요 — 안 그러면 폭발한 실행 하나가 나머지를 전부 바닥에 눕힙니다. 초록은 커스텀 계획, 노랑은 커스텀이 고른 시퀀셜 스캔, 빨강은 제네릭 계획이 흔한 값을 만난 실행입니다. 테이블은 100만 행, 인덱스 스캔은 매칭 행에 비례하고 시퀀셜 스캔은 150ms 고정입니다.

지금 조건에서 두 계획이 각각
01 / 06

직접 조작하기

같은 프리페어드 문을 계속 실행합니다. 파라미터는 두 종류예요 — 테이블의 60%를 차지하는 흔한 값과, 0.1%뿐인 드문 값.

조작무엇이 일어나나
흔한 값 비율전체 실행 중 흔한 값으로 조회하는 비율. 나머지는 드문 값입니다
n_distinct통계에 기록된 서로 다른 값의 개수. 제네릭 계획의 추정 선택도가 1/n_distinct 로 정해집니다
plan_cache_modePostgreSQL 12 부터 있는 설정. auto 가 기본입니다

비용은 이렇게 잡았습니다.

테이블         100만 행
인덱스 스캔     매칭 행 하나당 0.004ms   → 선택도에 비례
시퀀셜 스캔     150ms 고정              → 선택도와 무관
계획 수립       0.4ms                   → 커스텀은 실행마다 문다

교차점  s* = 150 / (0.004 × 1,000,000) = 3.75%
        이 아래면 인덱스가 싸고, 위면 시퀀셜이 싸다

이렇게 해보세요

1. 흔한 값 비율을 0으로 둔다 — 제네릭이 이긴다

흔한 값 0% · auto 커스텀 4.4ms (인덱스 4.0 + 계획 0.4) 제네릭 4.0ms (계획을 다시 안 세운다)

파라미터가 늘 비슷하면 제네릭이 더 빠릅니다. 계획을 한 번만 세우니까요. 짧은 쿼리에서는 계획 수립이 전체의 10%를 넘기도 합니다 — 프리페어드 문과 계획 캐시가 존재하는 이유가 이겁니다.

여기서 출발하는 게 중요합니다. "제네릭 계획이 나쁘다"가 아니에요. 나쁜 건 편향된 분포입니다.

2. 흔한 값 비율을 25%로 올린다 — 여섯 번째에 계단이 생긴다

흔한 값 25% · auto 1~5회 커스텀 — 값을 보고 계획을 고른다 6회째 제네릭으로 굳는다 7회~ 막대가 통째로 올라간다 평균 40.9ms → 603ms (15배) 계단이 안 생기면 초기화를 눌러 다시 — 확률이 있다

그래프에 계단이 생기는 걸 보세요. 처음 다섯 번은 PostgreSQL 이 값을 보고 계획을 세웁니다. 여섯 번째에 제네릭 계획을 만들어 비용을 비교하고, 싸 보이면 그 뒤로 계속 씁니다.

빨간 막대가 그 대가예요. 제네릭은 1/n_distinct = 0.5% 로 추정해 인덱스 스캔을 골랐는데, 실제로 60%짜리 값이 들어오면 100만 행 중 60만 행을 인덱스로 훑습니다. 2.4초예요. 커스텀이었다면 시퀀셜로 150ms 에 끝냈을 일입니다.

전환이 안 되는 경우도 있습니다. 처음 다섯 번이 전부 드문 값이면 커스텀 평균이 싸게 잡혀 제네릭이 비싸 보이거든요 — 흔한 값 25%에서 넷 중 한 번쯤 그렇습니다. 초기화를 누르면 다시 뽑습니다. 이게 버그가 아니라 이 문제의 성질이라는 게 레시피 6의 이야기입니다.

3. force_custom_plan 으로 바꾼다

plan_cache_mode = force_custom_plan 평균 603ms → 40.9ms 최악 2.4s → 150ms 대신 실행마다 계획 수립 0.4ms

문제가 사라집니다. 매번 값을 보고 계획을 세우니 흔한 값에는 시퀀셜, 드문 값에는 인덱스가 붙어요. 0.4ms 를 내고 15배를 사는 거래입니다.

4. force_generic_plan 으로 바꿔 최악을 본다

plan_cache_mode = force_generic_plan 빨간 막대만 남는다 흔한 값 실행이 전부 2.4초

전환을 기다리지 않고 바로 확인하는 방법입니다. 현장에서도 이렇게 씁니다 — SET plan_cache_mode = force_generic_plan; 을 켜고 EXPLAIN 을 떠보면 애플리케이션이 실제로 쓰는 계획이 나옵니다. 값을 박아 넣고 EXPLAIN 을 뜨면 절대 안 보이는 계획이에요.

5. n_distinct 를 20으로 내린다 — 전환이 안 일어난다

n_distinct 200 → 20 (추정 선택도 5%) 제네릭 추정 20ms → 150ms (시퀀셜을 고른다) 커스텀 평균 40.9ms 150 > 40.9 → 전환하지 않는다

추정 선택도가 교차점 3.75%를 넘으면 제네릭도 시퀀셜을 고릅니다. 그러면 추정 비용이 150ms 라 커스텀 평균보다 비싸 보이고, PostgreSQL 은 전환하지 않습니다. 이게 정상 동작이에요 — 옵티마이저는 자기가 아는 정보로는 옳게 판단하고 있습니다.

뒤집으면 이런 뜻입니다. 제네릭이 위험한 건 추정이 실제보다 작을 때예요. 그래야 인덱스를 고르고, 그래야 큰 값에서 터집니다.

6. 흔한 값 비율을 5%로 내린다 — 또 전환이 안 된다

흔한 값 5% · n_distinct 200 커스텀 평균 11.7ms (대부분 드문 값이라 싸다) 제네릭 추정 20ms 20 > 11.7 → 전환하지 않는다

여기가 미묘한 지점입니다. 흔한 값이 드물게 들어오면 처음 다섯 번은 거의 확실히 드문 값이고, 커스텀 평균이 아주 싸게 잡혀 제네릭이 비싸 보입니다.

그런데 이건 운입니다. 처음 다섯 번에 흔한 값이 몇 개 섞이면 커스텀 평균이 올라가고 제네릭이 이깁니다. 같은 코드, 같은 데이터인데 커넥션마다 다르게 동작해요. 초기화 트래픽이 무엇이었냐가 그 커넥션의 남은 수명을 정합니다.

왜 여섯 번째인가

PostgreSQL 의 계획 캐시는 이렇게 동작합니다.

1~5회    커스텀 계획 — 파라미터 값을 보고 매번 새로 세운다
         이때 각 계획의 추정 비용을 기록해 둔다

6회째    제네릭 계획을 한 번 만들어 추정 비용을 낸다
         제네릭 추정 <= 커스텀 평균  →  그 뒤로 계속 제네릭
         아니면                      →  계속 커스텀

다섯 번이라는 숫자는 상수입니다. 튜닝할 수 없어요. 그래서 증상이 여섯 번째 실행에 정확히 맞춰 나타납니다. 부하 테스트를 다섯 번만 돌리면 아무 문제도 안 보입니다.

한번 제네릭으로 굳으면 되돌아가지 않습니다. 그 프리페어드 문이 살아 있는 동안 계속 제네릭이에요. 커넥션이 끊기거나 DEALLOCATE 되어야 처음부터 다시 셉니다.

옵티마이저는 평균으로 판단한다

이 페이지의 축은 한 줄입니다.

cost(E[s])  ≠  E[cost(s)]

평균 선택도로 계산한 비용  ≠  실제 비용의 평균

제네릭 계획을 세울 때 옵티마이저는 파라미터 값을 모릅니다. 그래서 WHERE col = $1 의 선택도를 1/n_distinct 로 잡아요 — 모든 값이 고르게 분포한다는 가정입니다.

편향된 컬럼에서 이 가정은 어느 실행과도 맞지 않습니다. 값이 200종인데 그중 하나가 전체의 60%라면, 평균인 0.5%짜리 값은 실제로 존재하지도 않아요. 옵티마이저는 있지도 않은 값을 위한 계획을 세우고, 모든 실행이 그 계획으로 돌아갑니다.

그래서 평균이 좋아 보일수록 위험합니다. 추정 선택도가 교차점 아래로 내려갈수록 제네릭은 자신 있게 인덱스를 고르고, 꼬리에서 더 크게 터집니다. 레시피 5가 그 반대 방향을 보여줍니다 — 추정이 클수록 오히려 안전해요.

진짜로 쓰이는 계획을 보는 법

가장 흔한 오진이 여기서 나옵니다. 느린 쿼리를 잡으려고 EXPLAIN ANALYZE 를 뜨는데, 값을 박아 넣고 뜨면 커스텀 계획이 나옵니다. 애플리케이션이 쓰는 계획이 아니에요.

-- 이건 커스텀 계획이다. 애플리케이션이 쓰는 게 아닐 수 있다
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'PENDING';

-- 애플리케이션이 실제로 쓰는 계획
SET plan_cache_mode = force_generic_plan;
PREPARE p(text) AS SELECT * FROM orders WHERE status = $1;
EXPLAIN ANALYZE EXECUTE p('PENDING');
RESET plan_cache_mode;

둘의 계획이 다르면 이 페이지의 문제입니다. force_generic_plan 은 PostgreSQL 12 부터 쓸 수 있고, 그 전 버전이라면 PREPARE 후 여섯 번 EXECUTE 해서 확인해야 합니다.

자바에서는 언제 프리페어드가 되나

여기에 층이 하나 더 있습니다. JDBC 의 PreparedStatement 가 곧 서버 프리페어드는 아닙니다.

조건무엇이 달라지나
PgJDBC prepareThreshold기본 5. 같은 SQL 을 같은 커넥션에서 5번 실행해야 서버 프리페어드가 됩니다. 그 전까지는 매번 파싱합니다
커넥션 교체HikariCP maxLifetime 등으로 커넥션이 갈리면 카운터가 0부터 다시입니다
PgBouncer transaction 모드커넥션이 트랜잭션마다 바뀌므로 서버 프리페어드가 잡히지 않습니다. 이 문제 자체가 안 생기는 대신 계획 재사용 이득도 없습니다
HibernateSQL 문자열이 같아야 재사용됩니다. IN (?, ?, ?) 처럼 파라미터 개수가 바뀌면 다른 문입니다

합치면 이렇습니다 — PgJDBC 5회 × PostgreSQL 5회. 커넥션 하나에서 같은 쿼리를 열 번쯤 돌려야 제네릭 계획이 나옵니다. 그래서 트래픽이 적을 때는 영영 안 나타나다가, 트래픽이 늘면서 갑자기 나타납니다.

현장에서 확인할 것

먼저 이 질문. "이 쿼리의 파라미터 분포가 고른가?" 상태값, 타입, 테넌트 id, 국가 코드 — 이런 컬럼은 대개 안 고릅니다. 고르지 않으면 후보입니다.

-- 편향을 직접 본다. 상위 값이 전체의 몇 %인가
SELECT status, count(*),
       round(count(*) * 100.0 / sum(count(*)) OVER (), 2) AS pct
FROM orders GROUP BY status ORDER BY 2 DESC LIMIT 10;

-- 통계가 무엇을 알고 있나
SELECT attname, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';

n_distinct 와 most_common_freqs 를 나란히 보세요. 상위 값의 빈도가 1/n_distinct 보다 훨씬 크면 제네릭 추정이 그만큼 빗나갑니다.

느린 실행을 잡아두세요. 평균만 보면 안 보입니다.

# postgresql.conf — 느린 실행의 실제 계획을 로그로 남긴다
auto_explain.log_min_duration = '500ms'
auto_explain.log_analyze = on
auto_explain.log_parameter_max_length = 0   # 값은 남기지 않는다(민감정보)

pg_stat_statements 의 mean_exec_time 은 이 문제에 무디게 반응합니다. 같은 문 하나에 4ms 와 2,400ms 가 섞여 있어도 평균은 그럴듯해 보이거든요. max_exec_time 과 stddev_exec_time 을 같이 보세요.

고치는 순서.

  1. 통계를 먼저 본다. ANALYZE 가 오래됐거나 default_statistics_target 이 낮아 MCV 가 부족한 경우가 있습니다
  2. 계획이 정말 갈리는지 확인한다. force_generic_plan 으로 EXPLAIN 을 떠 비교합니다
  3. 쿼리를 고칠 수 있는지 본다. 불필요한 정렬이나 파생 테이블이 인덱스 사용을 막고 있으면, 그걸 걷어내는 게 설정보다 낫습니다
  4. 그래도면 plan_cache_mode. 세션 단위로 force_custom_plan 을 걸 수 있습니다. 계획 수립 비용을 다시 내는 것이니 짧은 쿼리에서는 손해일 수 있어요
  5. 편향이 심한 값만 별도 경로로. 흔한 값은 아예 다른 쿼리를 쓰는 것도 방법입니다

4번을 3번보다 뒤에 둔 이유가 있습니다. force_custom_plan 은 증상을 없애지 원인을 없애지 않습니다. 계획이 갈리는 근본 이유가 쿼리 구조에 있으면 그걸 고치는 게 먼저예요.

이 페이지의 모델은 개념을 보여주기 위해 단순화한 것입니다. 실제 PostgreSQL 의 비용은 페이지 수·상관도·캐시 적중률·병렬 실행까지 반영하고, 제네릭 계획의 선택도 추정도 1/n_distinct 외에 널 비율과 MCV 합을 함께 씁니다. 전환 판정도 여기서는 실행 시간으로 비교했지만 실제로는 옵티마이저의 추정 비용끼리 비교합니다. 중요한 건 숫자가 아니라 구조입니다 — 값을 모른 채 세운 계획이 모든 실행에 쓰인다는 것.
