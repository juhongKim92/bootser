17밀리초 쿼리가 커넥션 풀을 말린다

커넥션 누수 경고가 떴습니다. 스택 최상단에 찍힌 쿼리를 열어보니 17밀리초짜리입니다. 인덱스도 잘 타고 있고요. 그런데 풀은 계속 마릅니다 — 그 쿼리는 범인이 아니기 때문입니다.

직접 조작하기

이 실험대에도 시간이 흐르지 않습니다. 손잡이를 움직이면 그 조건을 통째로 다시 계산해요. 쿼리 시간은 고정입니다 — 쿼리는 처음부터 빠르니까요.

고정값값
사전 처리5ms — 검증·역직렬화. DB 를 안 씁니다
쿼리 117ms — 누수 경고 스택이 가리키는 그 쿼리
쿼리 28ms
응답 렌더25ms — 직렬화. DB 를 안 씁니다

실제로 DB 를 쓰는 시간은 어느 구성에서나 25ms 로 같습니다. 이 페이지에서 달라지는 건 오직 쥐고 있는 시간이에요.

이렇게 해보세요

1. 외부 호출을 0으로 두고 시작한다

OSIV 켜짐 · 50 req/s · 외부 호출 0 · 풀 10 점유 시간 50ms (그중 DB 25ms) 필요 커넥션 2.5 이용률 25%

여기까지는 아무 문제가 없습니다. OSIV 가 켜져 있어도 요청이 짧으면 티가 안 나요. 대부분의 서비스가 이 상태로 몇 년을 잘 삽니다. 문제는 요청 안에 느린 무언가가 들어오는 순간 시작됩니다.

2. 외부 호출 300ms 를 넣는다 — S3 업로드 하나

외부 호출 300ms 로 점유 시간 350ms (그중 DB 25ms — 7%) 필요 커넥션 17.5 ← 풀은 10개 처리 상한 28.6 req/s ← 지금 50 req/s 가 들어온다

쿼리는 하나도 안 느려졌는데 풀이 마릅니다. 점유 시간 350ms 중 DB 를 실제로 쓰는 건 25ms, 7% 뿐이에요. 나머지 93% 는 S3 응답을 기다리며 커넥션을 쥐고만 있습니다. 위의 빗금 구간이 그겁니다.

그리고 이 시점에 로그에 찍히는 건 "커넥션을 못 얻었다"는 타임아웃과, 뒤에서 설명할 누수 경고입니다. 둘 다 S3 를 가리키지 않아요.

3. OSIV 를 끈다 — 기대만큼 안 줄어든다

OSIV 끔 (외부 호출은 여전히 트랜잭션 안) 점유 시간 350ms → 325ms 필요 커넥션 17.5 → 16.25 ← 여전히 풀 10개보다 많다

OSIV 를 끄면 응답 렌더링 구간(25ms)만큼 줄어듭니다. 그런데 그게 전부예요. 외부 호출이 트랜잭션 안에 있는 한 커넥션은 그대로 잡혀 있습니다. OSIV 는 이 문제의 일부일 뿐이라는 게 여기서 드러납니다.

4. 외부 호출을 트랜잭션 밖으로 뺀다

OSIV 끔 + 외부 호출 분리 점유 시간 325ms → 25ms 필요 커넥션 16.25 → 1.25 처리 상한 30.8 → 400 req/s (13배)

이게 진짜 해법입니다. 커넥션을 잡고 쿼리 1을 실행하고 반납한 뒤 S3 에 다녀오고, 다시 잡아 쿼리 2를 실행합니다. 점유 시간이 외부 호출 시간과 완전히 무관해집니다 — 외부 호출을 5초로 밀어도 점유 시간은 25ms 그대로예요. 직접 해보세요.

5. 외부 호출을 3초로 올리고 누수 경고를 본다

OSIV 켜짐 · 외부 호출 3000ms 점유 시간 3.05s → leak-detection-threshold 초과 경고 스택 최상단 17ms 짜리 쿼리 1

여기가 이 페이지의 핵심입니다. 누수 경고가 지목하는 건 커넥션을 빌린 지점이지 오래 붙잡고 있는 지점이 아닙니다. 첫 쿼리가 커넥션을 빌렸으니 그 스택이 찍혀요. 그 쿼리를 아무리 튜닝해도 17ms 가 16ms 가 될 뿐, 풀은 계속 마릅니다.

6. 풀을 5배로 키워본다

OSIV 켜짐 · 외부 호출 300ms · 풀 10 → 50 부하 50 req/s 필요 17.5 → 풀 50 으로 버틴다 부하 200 req/s 필요 70 → 다시 고갈

풀을 키우면 당장은 버팁니다. 그리고 부하가 4배가 되면 다시 같은 자리로 돌아옵니다. 점유 시간을 줄이지 않으면 풀 크기는 시간을 사는 것뿐이에요. 게다가 커넥션은 DB 쪽 자원이라 무한정 늘릴 수도 없습니다.

왜 스택 최상단이 범인이 아닌가

HikariCP 의 누수 탐지는 이렇게 동작합니다. 커넥션을 빌려줄 때 타이머를 걸고, leak-detection-threshold 안에 반납되지 않으면 경고를 찍습니다.

중요한 건 그 경고에 실리는 스택이 타이머가 울린 시점이 아니라 커넥션을 빌린 시점에 캡처된 것이라는 점입니다. 그럴 수밖에 없어요 — 커넥션을 붙잡고 있는 스레드가 지금 어디에 있는지는 누수 탐지 스레드가 알 방법이 없으니까요. 빌려줄 때 찍어둔 스택만 갖고 있습니다.

Connection leak detection triggered for conn0, stack trace follows
    at com.example.repository.OrderRepository.findByUser(...)   ← 17ms 쿼리
    at com.example.service.OrderService.getOrders(...)
    ...

그래서 요청에서 가장 먼저 실행된 쿼리가 항상 지목됩니다. 그 쿼리가 느려서가 아니라, 그 쿼리가 커넥션을 빌렸기 때문이에요.

경고를 읽는 순서를 뒤집으세요. 스택이 가리키는 쿼리를 튜닝하는 게 아니라, "이 스레드가 커넥션을 빌린 뒤 무엇을 더 했는가"를 봐야 합니다. 같은 요청의 뒷부분에 외부 호출이나 무거운 렌더링이 있는지 찾는 게 먼저입니다.

OSIV — 편의의 값

spring.jpa.open-in-view 는 기본값이 true 입니다. 영속성 컨텍스트를 요청이 끝날 때까지 열어두어, 서비스 계층을 벗어난 뒤에도 지연 로딩이 되게 해줍니다. LazyInitializationException 을 안 보게 해주는 고마운 기능이죠.

대가는 커넥션 점유 시간입니다. 컨텍스트가 열려 있는 동안 커넥션이 붙잡혀 있으니, 트랜잭션이 끝난 뒤의 직렬화·뷰 렌더링 구간까지 풀에서 하나가 빠져 있는 셈이 됩니다.

Spring Boot 는 이걸 알고 있어서 기동할 때 경고를 남깁니다.

spring.jpa.open-in-view is enabled by default. Therefore, database
queries may be performed during view rendering. Explicitly configure
spring.jpa.open-in-view to disable this warning

이 줄을 본 적이 있다면, 명시적으로 꺼두라는 뜻입니다.

spring:
  jpa:
    open-in-view: false

끄면 지연 로딩이 서비스 계층 밖에서 터집니다. 그게 정상이에요 — 조회 시점에 무엇을 가져올지 명시하라는 뜻이니까요. DTO 프로젝션이나 fetch join 으로 옮기면 쿼리 수도 같이 줄어듭니다.

정확히 말하면 커넥션을 잡고 놓는 시점은 Hibernate 의 connection.handling_mode 에 따라 달라집니다. 이 실험대는 "첫 쿼리에서 빌려 요청 끝까지 쥔다" 는 최악의 경우로 그렸습니다. 운영에서 관측되는 모습이 대체로 이쪽이기도 하고요. 본인 환경에서는 실제 점유 시간을 메트릭으로 확인하시는 편이 확실합니다.

리틀의 법칙 하나면 된다

이 페이지의 모든 계산은 한 줄에서 나옵니다.

필요 커넥션 수 = 초당 요청 수 × 커넥션 점유 시간(초)

50 req/s 에 점유 350ms 면 50 × 0.35 = 17.5 개가 동시에 필요합니다. 풀이 10개면 모자라요. 뒤집으면 처리 상한도 바로 나옵니다.

처리 상한 = 풀 크기 ÷ 점유 시간(초)
          = 10 ÷ 0.35 = 28.6 req/s

여기서 중요한 건 이 식에 쿼리 시간이 안 들어간다는 점입니다. 들어가는 건 점유 시간이에요. 쿼리를 두 배 빠르게 만들어도 점유 시간의 7% 만 줄어듭니다. 그래서 쿼리 튜닝으로는 이 문제가 안 풀립니다.

트랜잭션 경계 안에 네트워크를 넣지 않는다

OSIV 를 꺼도 남는 절반이 이겁니다. 트랜잭션이 열려 있는 동안은 커넥션이 반드시 잡혀 있으니, 트랜잭션 경계가 곧 점유 구간입니다.

@Transactional                       // ← 여기서 시작
public void upload(MultipartFile f) {
    Order o = repo.findById(id);      // 17ms
    s3.putObject(bucket, key, f);     // 3초. 커넥션은 계속 잡혀 있다
    o.markUploaded();                 // 8ms
}                                     // ← 여기서 반납

클래스 레벨에 @Transactional 을 걸어두면 이런 메서드가 조용히 생깁니다. 고치는 방향은 셋입니다.

상황방법
읽기 전용 외부 왕복@Transactional(NOT_SUPPORTED) — 왕복 동안 커넥션을 안 쥔다
커밋 후에 발행·알림@TransactionalEventListener(AFTER_COMMIT) — 커밋·반납 뒤에 실행된다
외부 호출 결과를 저장해야 함트랜잭션을 둘로 쪼갠다. 읽기 → (커넥션 반납) → 외부 호출 → 쓰기

발행 실패를 흘려보내면 안 되는 경로라면 Outbox 패턴으로 올라가면 됩니다. 이벤트를 같은 트랜잭션에서 테이블에 적어두고, 별도 프로세스가 읽어 발행하는 방식이죠. 트랜잭션 안에서 하는 일이 로컬 INSERT 하나로 줄어듭니다.

자기 자신을 프록시로 주입해 호출하는 self-proxy 로 트랜잭션을 쪼개는 방법이 돌아다니는데, 권하지 않습니다. 순환 참조를 만들고 AOP 를 알아야만 읽히거든요. @TransactionalEventListener 가 정확히 이 목적의 표준 도구입니다.

풀을 키우면 되지 않나

당장은 됩니다. 그리고 세 가지가 발목을 잡습니다.

  • 부하가 늘면 다시 같은 자리입니다. 점유 시간이 그대로면 필요 커넥션은 부하에 정비례해 늘어납니다 (레시피 6)
  • 커넥션은 DB 쪽 자원입니다. PostgreSQL 은 연결마다 프로세스를 띄우고 메모리를 잡습니다. 앱 인스턴스 수 × 풀 크기가 max_connections 를 넘으면 그때부터는 DB 가 거절합니다
  • 풀이 크다고 빨라지지 않습니다. HikariCP 문서가 오히려 작은 풀을 권합니다. 코어 수를 넘는 동시 실행은 컨텍스트 스위칭과 락 경합만 늘려요

인스턴스가 많아 연결 수 자체가 문제라면 PgBouncer 같은 커넥션 풀러를 앞에 두는 선택지가 있습니다. 다만 그건 연결 수 문제의 해법이지 점유 시간 문제의 해법은 아닙니다. 점유 시간이 길면 풀러 뒤에서 똑같이 막힙니다.

현장에서 확인할 것

먼저 켜야 할 것 두 개. 이게 없으면 이 페이지의 문제가 보이지 않습니다.

spring:
  jpa:
    open-in-view: false
  datasource:
    hikari:
      leak-detection-threshold: 20000   # 20초. 0 이면 꺼짐(기본)
      # 풀 크기는 코어 수에 맞춰. 크게 잡는 게 답이 아니다
      maximum-pool-size: 10

leak-detection-threshold 는 기본이 꺼져 있습니다. 켜지 않으면 커넥션을 몇 분씩 붙잡고 있어도 로그에 아무것도 안 남아요.

볼 지표. Hikari 는 Micrometer 로 다 내보냅니다.

지표무엇을 말해주나
hikaricp_connections_active지금 쓰이는 커넥션. 리틀의 법칙의 좌변입니다
hikaricp_connections_pending커넥션을 못 얻어 대기 중인 스레드. 0 이 아니면 이미 고갈
hikaricp_connections_usage점유 시간 분포. 이 페이지의 주인공. p99 가 쿼리 시간보다 한참 크면 그 차이가 답이다
hikaricp_connections_acquire커넥션을 얻기까지 기다린 시간

usage 와 실제 쿼리 시간을 나란히 놓는 게 핵심입니다. 둘의 격차가 곧 "쥐고만 있던 시간"이고, 이 페이지는 그 격차를 그림으로 그린 것뿐이에요.

DB 쪽에서 확인.

-- 트랜잭션을 열어두고 아무것도 안 하는 세션
SELECT pid, state, now() - state_change AS idle_for,
       now() - xact_start AS xact_age, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start
LIMIT 20;

idle in transaction 이 길게 잡혀 있으면 그 세션이 커넥션을 쥔 채 애플리케이션 쪽에서 다른 일을 하고 있다는 뜻입니다. 그 "다른 일"이 대개 외부 호출이에요. query 컬럼에는 마지막으로 실행한 쿼리가 남으니, 그게 범인이 아니라 그 뒤에 무엇을 했는지를 코드에서 찾아야 합니다.

순서. 커넥션 고갈을 만나면 이 순서로 봅니다.

  1. pending 이 0 이 아닌 시각을 찾는다 — 언제부터인지
  2. usage p99 와 쿼리 시간 p99 를 비교한다 — 격차가 있으면 점유 문제
  3. 그 격차 구간에서 무엇을 하는지 코드로 확인한다 — 외부 호출, 렌더링, OSIV
  4. 풀 크기는 마지막에 만진다
이 페이지의 모델은 개념을 보여주기 위해 단순화한 것입니다. 실제로는 요청마다 쿼리 수와 외부 호출 시간이 제각각이고, 도착이 몰리면 짧은 순간에도 대기가 생깁니다. 리틀의 법칙은 평균에 대한 식이라 "평균적으로 몇 개가 필요한가"를 알려줄 뿐, 순간 최대를 말해주지는 않습니다. 실제 풀 크기는 여기에 여유를 얹어 잡아야 합니다.
