거부는 버그가 아니라 신호다

로그에 RejectedExecutionException 이 쏟아집니다. 큐 상한을 없애면 조용해지죠. 그리고 몇 분 뒤 OutOfMemoryError 가 옵니다 — 거부를 없앤 게 아니라 거부를 OOM 과 맞바꾼 겁니다.

8 개
500 건
생산자 → 큐 → 소비 스레드
들어옴200/s
나감0/s · 용량 0

가운데 막대가 큐입니다. 세로선은 상한이고, 무제한일 때는 사라지면서 눈금이 OOM 임계로 바뀝니다. 아래 칸은 소비 스레드예요 — 초록은 일하는 중, 노란 칸은 CallerRuns 로 생산자 스레드가 직접 처리하는 중입니다. 태스크 하나가 큐에서 256KB 를 잡고 있고 여유 힙은 512MB 로 뒀습니다.

직접 조작하기

태스크 하나에 120ms 가 걸립니다. 코어는 8개예요. 이 두 값이 처리 용량을 정합니다.

조작무엇이 일어나나
생산 속도초당 몇 개가 큐로 들어오는지
소비 스레드몇 개가 동시에 처리하는지. 작업 성격에 따라 효과가 완전히 다릅니다
작업 성격I/O 대기(용량 = 스레드 ÷ 0.12) / CPU·외부 프로세스(용량 = min(스레드, 8) ÷ 0.12)
큐 정책가득 찼을 때 무엇을 할지. 이 페이지의 주인공입니다
큐 상한무제한일 때는 회색으로 죽습니다

이렇게 해보세요

1. 용량 안에서 시작한다

생산 50/s · 스레드 8 · I/O · 유계+Abort 용량 66.7/s 큐 0 부근 거부 0

생산이 용량보다 적으면 큐가 안 쌓입니다. 정책이 무엇이든 아무 차이가 없어요. 세 정책을 번갈아 눌러봐도 화면이 똑같습니다. 큐 정책은 부하가 용량을 넘을 때만 의미가 생깁니다.

2. 생산을 200/s 로 올린다

생산 200/s · 용량 66.7/s 큐 500 에서 멈춤 거부 133.3/s ← 초당 133건이 버려진다 처리 66.7/s

큐가 3.8초 만에 차고 그때부터 거부가 시작됩니다. 로그가 시뻘개지죠. 그런데 이건 시스템이 정직하게 말하고 있는 겁니다 — "초당 66.7건밖에 못 하는데 200건이 들어온다"고요.

거부 패널의 completed tasks 를 보세요. 이 숫자가 안 늘고 있다면 소비가 아예 진행되지 않고 있다는 뜻이고, 그건 큐 문제가 아니라 소비자가 막혔다는 신호입니다.

3. 큐를 무제한으로 바꾼다 — 조용해진다

무제한 큐 거부 133.3/s → 0 큐 500 → 계속 증가 힙 0 → 512MB 15.4초 뒤 OutOfMemoryError

예외가 사라졌습니다. 로그가 깨끗해졌어요. 그리고 큐가 초당 133건씩 쌓이면서 힙을 먹습니다. 15초 뒤 프로세스가 죽습니다.

바뀐 건 실패가 드러나는 방식뿐입니다. 거부는 어느 태스크가 언제 실패했는지 알려주지만, OOM 은 프로세스 전체를 죽이고 스택은 하필 그때 메모리를 요청한 애먼 코드를 가리킵니다.

4. CallerRuns 로 바꾼다

유계 + CallerRuns 거부 0 큐 500 에서 안정 처리 66.7 → 75.0/s (생산자가 한 몫 거든다) 생산 200 → 75.0/s 로 묶인다

거부도 없고 OOM 도 없습니다. 큐가 가득 차면 생산자 스레드가 태스크를 직접 처리하거든요. 그동안 생산자는 새 태스크를 못 만듭니다. 그게 백프레셔예요 — 느려지는 것으로 밀어내는 것입니다.

공짜는 아닙니다. 생산 속도가 200에서 75로 묶였어요. 일이 사라지진 않았지만 업로드가 세 배 가까이 느려집니다. 그게 정직한 결과이고, 사용자에게도 그렇게 보이는 게 맞습니다.

5. 스레드를 32개로 늘린다 — I/O 라면 통한다

I/O 대기 · 스레드 8 → 32 용량 66.7 → 266.7/s 큐 500 → 0

S3 업로드처럼 대기가 지배적인 작업이면 스레드를 늘린 만큼 용량이 늡니다. 스레드가 대부분의 시간을 응답을 기다리며 놀고 있으니까요. 여기서는 Virtual Thread 가 정확히 제 역할을 합니다.

6. 작업 성격만 CPU·프로세스로 바꾼다

스레드는 32개 그대로, 성격만 변경 용량 266.7 → 66.7/s ← 8개일 때와 똑같다 큐 0 → 500 포화

여기가 이 페이지의 두 번째 반전입니다. 스레드를 네 배로 늘렸는데 용량이 그대로예요. FFmpeg 를 띄우거나 이미지를 인코딩하는 일은 코어를 실제로 씁니다. 코어가 8개면 동시에 진행되는 건 8개뿐이고, 스레드를 더 만들어봐야 서로 CPU 를 뺏을 뿐입니다.

Virtual Thread 로 이런 일을 뿌리면 더 나빠집니다. 스레드가 값싸니 동시 프로세스 수만 폭증하고, 그건 곧 메모리와 컨텍스트 스위칭이에요.

7. 생산 속도를 50/s 로 내린다

CPU 작업 · 스레드 8 · 생산 200 → 50 큐 0 거부 0 정책 무엇이든 상관없다

이게 진짜 해법입니다. 큐 정책은 넘칠 때 무엇을 할지를 정하는 것이지 넘치지 않게 하는 게 아니에요. 생산이 용량 아래로 내려오면 세 정책이 다시 구별되지 않습니다 — 레시피 1로 돌아온 겁니다.

거부를 읽는 법

이 예외는 이렇게 생겼습니다. 안에 필요한 정보가 다 들어 있어요.

Task rejected from ThreadPoolExecutor
  [Running, pool size = 8, active threads = 8,
   queued tasks = 500, completed tasks = 0]
항목무엇을 말해주나
pool size만들어진 스레드 수
active threads지금 일하는 수. pool size 와 같으면 스레드는 놀고 있지 않다
queued tasks대기 중. 상한과 같으면 가득 찬 것
completed tasks가장 중요한 숫자. 이게 안 늘면 소비가 아예 진행되지 않고 있다

completed tasks = 0 은 특히 나쁜 신호입니다. 큐가 넘치는 게 느려서가 아니라 소비자가 어딘가에서 막혀 있다는 뜻이거든요 — 데드락, 외부 호출 무한 대기, 커넥션 고갈 같은 것들이요. 이 경우 큐를 키우는 건 아무 의미가 없습니다.

거부를 지표로 만드세요. 예외를 삼키지 말고 카운터를 올려서 대시보드에 띄우면, 그때부터 거부는 장애 신호가 아니라 용량 지표가 됩니다. "초당 몇 건이 거부되는가"는 "얼마나 부족한가"와 같은 말이에요.

세 가지 정책이 사고파는 것

정책포기하는 것지키는 것
유계 + Abort초과분을 버린다메모리, 지연 시간
유계 + CallerRuns생산자가 느려진다메모리, 일의 완결성
무제한프로세스—

세 번째 줄이 요점입니다. 무제한 큐는 아무것도 포기하지 않는 것처럼 보이지만, 부하가 용량을 넘는 한 언젠가 반드시 힙을 채웁니다. 미루는 것이지 막는 게 아니에요.

// 유계 + 기본 정책(Abort) — 넘치면 RejectedExecutionException
new ThreadPoolExecutor(8, 8, 0L, MILLISECONDS,
        new ArrayBlockingQueue<>(500));

// 유계 + CallerRuns — 넘치면 부른 쪽이 직접 처리한다
new ThreadPoolExecutor(8, 8, 0L, MILLISECONDS,
        new ArrayBlockingQueue<>(500),
        new ThreadPoolExecutor.CallerRunsPolicy());

// 무제한 — 거부는 사라지고 OOM 이 온다
new ThreadPoolExecutor(8, 8, 0L, MILLISECONDS,
        new LinkedBlockingQueue<>());

기본값이 이미 무제한이다

직접 LinkedBlockingQueue 를 쓴 적이 없어도 이 상태일 수 있습니다. 표준 팩토리 메서드들이 그렇게 만들어져 있거든요.

팩토리무엇이 무제한인가
newFixedThreadPool(n)큐가 무제한입니다. 스레드는 n개로 고정되지만 대기열은 힙이 허락하는 만큼
newSingleThreadExecutor()같습니다. 큐 상한이 없습니다
newCachedThreadPool()반대로 스레드가 무제한입니다. 큐는 사실상 없고 태스크마다 스레드를 만듭니다
newVirtualThreadPerTaskExecutor()태스크마다 가상 스레드. 상한이 없습니다

이름이 "fixed" 라 안전해 보이지만 고정된 건 스레드 수뿐입니다. 상한을 두려면 ThreadPoolExecutor 를 직접 만드는 수밖에 없어요.

스레드를 늘리면 되지 않나

레시피 5와 6이 그 답입니다. 작업이 무엇을 기다리느냐에 달려 있습니다.

작업스레드를 늘리면왜
S3 업로드, 외부 API, DB 조회용량이 는다대부분의 시간을 응답 대기로 보낸다. CPU 는 놀고 있다
이미지 인코딩, 압축, 암호화코어 수까지만CPU 를 실제로 쓴다. 그 이상은 서로 뺏는다
FFmpeg 같은 외부 프로세스오히려 나빠진다프로세스 생성 비용 + 메모리. 동시 실행 수는 물리 자원에 묶인다

마지막 줄이 Virtual Thread 를 잘못 쓰는 전형입니다. 가상 스레드의 이점은 블로킹 I/O 대기 중에 캐리어 스레드를 반납하는 것인데, ProcessBuilder 로 프로세스를 띄우는 일에는 그 이점이 없습니다. 오히려 스레드가 값싸진 만큼 동시 프로세스 수만 폭증해요.

외부 프로세스 실행은 고정 크기 풀 + 유계 큐 뒤에 두세요. 동시 실행 수는 코어 수나 GPU 세션 수 같은 물리 자원에 묶이는 값이지, 값싼 스레드로 늘릴 수 있는 대상이 아닙니다.

진짜 해법은 생산 쪽에 있다

레시피 7이 보여주는 것입니다. 큐 정책은 넘칠 때 무엇을 할지를 정할 뿐, 넘치지 않게 해주지 않아요. 부하가 용량을 넘는 상태가 계속되면 어느 정책이든 대가를 치릅니다.

그래서 순서는 이렇습니다.

  1. 생산량을 줄일 수 있는가. 같은 결과를 더 적은 태스크로 낼 방법이 있는지 — 대개 여기에 답이 있습니다
  2. 서비스 시간을 줄일 수 있는가. 태스크 하나가 120ms 에서 30ms 가 되면 용량이 네 배입니다
  3. 소비 용량을 늘릴 수 있는가. 다만 위 표대로, 작업 성격에 따라 천장이 다릅니다
  4. 그래도 넘친다면 백프레셔. 이건 넘침을 안전하게 만드는 장치이지 없애는 장치가 아닙니다

1번이 가장 자주 간과되고 가장 효과가 큽니다. 프레임마다 외부 프로세스를 한 번씩 띄우던 것을 한 번 띄워 스트림으로 받는 식으로 바꾸면 태스크 수가 통째로 1/N 이 됩니다. 그러면 큐 정책을 무엇으로 하든 상관없어져요 — 레시피 1의 상태로 돌아가니까요.

CallerRuns 를 쓸 때 주의할 것

기본값으로 삼을 만한 정책이지만 부작용을 알고 써야 합니다. 생산자를 블로킹한다는 게 전부거든요.

  • 생산자가 HTTP 요청 스레드라면 — 그 요청이 느려집니다. 백프레셔가 클라이언트까지 전달되는 거라 대체로 옳지만, 요청 스레드 풀이 고갈될 수 있습니다
  • 생산자가 스케줄러 스레드라면 — 그 스레드가 막히는 동안 다른 스케줄 작업도 전부 멈춥니다. 스케줄러 풀 크기가 1이면 특히 위험해요
  • 순서가 보장되지 않습니다 — 생산자가 직접 처리한 태스크가 큐에 있는 것보다 먼저 끝납니다
  • 생산자가 락을 쥐고 있다면 — 그 락을 쥔 채로 태스크를 처리하게 됩니다. 데드락 위험이 여기서 나옵니다

이런 게 걸리면 Semaphore 로 인플라이트 수를 제한하는 쪽이 낫습니다. 생산자가 acquire() 에서 기다리게 되므로 효과는 같고, 무엇을 기다리는지가 코드에 명시적으로 드러나요.

private final Semaphore inFlight = new Semaphore(500);

void submit(Task task) throws InterruptedException {
    inFlight.acquire();                       // 자리가 없으면 여기서 막힌다
    executor.execute(() -> {
        try { task.run(); }
        finally { inFlight.release(); }
    });
}

현장에서 확인할 것

먼저 지표부터. 이게 없으면 큐가 차오르는 걸 OOM 이 나서야 압니다.

지표무엇을 말해주나
큐 깊이상한에 붙어 있으면 이미 포화. 단조 증가하면 무제한 큐다
거부 건수용량 부족의 크기. 0이 목표가 아니라 관측되는 것이 목표
completed tasks 증가율안 늘면 소비자가 막힌 것. 큐 문제가 아니다
활성 스레드 / 풀 크기같으면 포화. 활성이 낮은데 큐가 차면 다른 데서 막힌 것
힙 사용량 추세톱니 없이 우상향이면 어딘가 쌓이고 있다

Spring 이라면 ThreadPoolTaskExecutor 가 Micrometer 로 executor.queued, executor.active, executor.completed 를 다 내보냅니다. 이름만 붙여주면 됩니다.

힙 덤프를 뜨면 바로 보입니다. OOM 이 이미 났다면 지배 객체(dominator)를 보세요. LinkedBlockingQueue$Node 가 상위에 있으면 이 페이지의 문제입니다. 큐에 매달린 태스크가 무엇을 참조하고 있는지도 같이 확인하세요 — 태스크 자체는 작아도 이미지 버퍼나 요청 컨텍스트를 붙들고 있으면 실제 점유는 훨씬 큽니다.

부하 테스트는 용량 위에서 하세요. 용량 아래에서 돌리면 세 정책이 전부 똑같이 보입니다(레시피 1). 정책을 검증하려면 일부러 넘겨야 합니다.

순서. 큐가 넘치는 걸 발견하면 이렇게 봅니다.

  1. completed tasks 가 늘고 있는가 — 안 늘면 소비자가 막힌 것이고 큐 이야기가 아니다
  2. 생산 속도와 처리 용량을 숫자로 비교한다. 얼마나 부족한지 모르면 아무것도 못 정한다
  3. 생산량을 줄일 방법을 먼저 찾는다
  4. 큐 정책은 마지막에 만진다. 그리고 무제한은 선택지가 아니다
이 페이지의 모델은 개념을 보여주기 위해 단순화한 것입니다. 서비스 시간 120ms 고정, 코어 8개, 태스크당 힙 256KB 로 뒀고, 실제로는 서비스 시간이 분포를 갖고 GC 도 함께 움직입니다. 특히 OOM 시점은 태스크가 무엇을 참조하느냐에 따라 크게 달라집니다 — 중요한 건 몇 초냐가 아니라 무제한 큐에서는 반드시 온다는 것입니다.
