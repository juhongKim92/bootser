PostgreSQL에서 열려 있는 트랜잭션 하나가 어떻게 VACUUM 전체를 멈춰 세우고 테이블을 부풀리는지, 직접 조작하며 확인합니다.

직접 조작하기

재생 버튼은 정해진 각본을 보여줄 뿐입니다. 세션 버튼을 직접 누르면 각본을 벗어나 원하는 상황을 만들 수 있어요. 재생 중에 아무 버튼이나 누르면 재생이 멈추고 그 상태에서 이어집니다.

버튼이 하는 일

버튼동작
BEGIN트랜잭션을 엽니다. 아직 스냅샷은 잡지 않습니다. 이 상태만으로는 VACUUM을 막지 않아요
SELECT스냅샷을 획득합니다. 이 순간부터 horizon이 이 세션에 묶입니다. 쓰기를 하지 않으므로 xid는 할당되지 않습니다
UPDATE ×3살아 있는 행 3개를 갱신합니다. 구버전 3개에 xmax가 찍히고, 신버전 3개가 빈 슬롯에 새로 기록됩니다
DELETE ×33개에 xmax만 찍습니다. 신버전이 없으니 슬롯을 새로 쓰지 않습니다
COMMIT이 트랜잭션의 xid를 커밋 목록에 넣고 세션을 닫습니다. 붙잡고 있던 horizon이 풀립니다
VACUUM회수를 시도합니다. 언제든 몇 번이든 누를 수 있습니다

트랜잭션이 열려 있지 않은 상태에서 SELECT나 UPDATE를 누르면 BEGIN이 자동으로 실행되고, 로그에 그렇게 남습니다.

화면 읽는 법

  • 슬롯 하나가 튜플 하나입니다. 위 숫자가 xmin, 아래가 xmax. 색이 곧 상태예요
  • 축의 황토색 구간은 horizon보다 앞선 xid, 즉 지워도 안전한 영역입니다. 파란 테두리 칩은 열린 트랜잭션이 붙잡고 있는 지점이고 위에 세션 문자가 붙습니다
  • 테이블 크기는 페이지 수 × 8KB입니다. 슬롯이 비어도 페이지가 남아 있으면 크기는 그대로예요
  • 블로트는 전체 튜플 중 죽은 튜플의 비율입니다

이렇게 해보세요

1. BEGIN만으로는 막히지 않는다

초기화 A BEGIN B UPDATE ×3 → COMMIT VACUUM → 회수됨 A SELECT ← 여기서 스냅샷을 잡는다 B UPDATE ×3 → COMMIT VACUUM → 회수 0개

범인은 BEGIN이 아니라 첫 구문입니다. 그래서 pg_stat_activity에서 상태만 보지 말고 backend_xmin이 잡혀 있는지를 함께 봐야 합니다.

2. 막는 주체는 계속 바뀐다

초기화 A SELECT B UPDATE ×3 → COMMIT VACUUM → 0개. A가 막는다 B SELECT ← B도 트랜잭션을 연다 A COMMIT VACUUM → 3개 회수. B 스냅샷은 더 최근이라 통과 A UPDATE ×3 → COMMIT VACUUM → 0개. 이번엔 B가 막는다

horizon은 열려 있는 것들 중 가장 오래된 하나가 결정합니다. 긴 트랜잭션 하나를 잡았다고 끝나지 않고, 다음으로 오래된 것이 곧바로 그 자리를 이어받습니다. 축에서 파란 칩이 A에서 B로 옮겨가는 걸 보세요.

3. 블로트를 만드는 건 UPDATE다

초기화 B DELETE ×3 → COMMIT (여러 번 반복) 크기를 본다 → 늘지 않는다 초기화 B UPDATE ×3 → COMMIT (같은 횟수) 크기를 본다 → 페이지가 늘어난다

DELETE는 죽음만 표시하고 새 튜플을 만들지 않습니다. UPDATE는 구버전을 남기면서 신버전을 새로 쓰기 때문에 한 번에 두 배로 공간을 씁니다. 대량 갱신 배치가 특히 위험한 이유예요.

4. 꼬리 페이지만 잘려 나간다

초기화 B UPDATE ×3 → COMMIT (페이지가 늘어날 때까지 반복) VACUUM 맨 뒷 페이지가 완전히 비었는지 확인 비었으면 → 크기가 줄고 "절단" 로그가 뜬다 한 칸이라도 살아 있으면 → 크기 그대로

VACUUM은 데이터를 앞으로 당겨오지 않습니다. 그래서 파일 중간에 구멍이 나면 그 상태로 두고, 뒤쪽이 통째로 비었을 때만 잘라서 OS에 돌려줍니다.

5. 커밋 전에는 죽음도 확정되지 않는다

초기화 B UPDATE ×3 ← COMMIT 하지 않는다 슬롯을 본다 → 점선 3개(커밋 전) 등장 죽은 튜플 0개 ← 구버전이 아직 live 로 보인다 VACUUM → 할 일이 없다 B COMMIT → 구버전 3개가 그제서야 dead VACUUM → 회수됨

커밋 전에는 구버전을 지울 수 없습니다. 롤백되면 그 구버전이 다시 정답이 되어야 하니까요. 점선 슬롯은 반대로 아직 아무에게도 보이지 않는 신버전입니다. 동시에 그 트랜잭션은 자기 xid로 horizon도 붙잡고 있어요 — 축에서 확인해보세요.

PostgreSQL은 행을 수정하지 않는다

다른 DBMS에서 넘어온 사람이 가장 먼저 부딪히는 지점입니다. PostgreSQL의 UPDATE는 기존 행을 고치지 않습니다. 구버전에 죽은 시각을 찍고, 신버전을 다른 자리에 새로 씁니다. DELETE도 마찬가지로 데이터를 지우는 게 아니라 죽음을 표시할 뿐입니다.

모든 튜플은 두 개의 시스템 컬럼을 갖습니다. 직접 조회할 수 있어요.

SELECT xmin, xmax, * FROM orders LIMIT 5;
  • xmin — 이 버전을 만든 트랜잭션 ID
  • xmax — 이 버전을 죽인 트랜잭션 ID (살아 있으면 0)

이 구조 덕분에 읽기가 쓰기를 막지 않습니다. 읽는 쪽은 자기 스냅샷에 맞는 버전을 골라 읽으면 되니까요. 대신 쓰레기가 쌓입니다. 그 쓰레기를 치우는 게 VACUUM입니다.

VACUUM이 함부로 지우지 못하는 이유

죽은 튜플이라고 해서 즉시 지울 수 있는 게 아닙니다. 그 버전을 볼 자격이 있는 트랜잭션이 아직 살아 있을 수 있으니까요.

그래서 PostgreSQL은 경계선을 하나 계산합니다. 현재 열려 있는 트랜잭션들이 가진 가장 오래된 스냅샷, 이것이 xmin horizon입니다. 이 선보다 나중에 죽은 튜플은 건드릴 수 없습니다.

열린 트랜잭션이 하나라도 오래 살아 있으면, 그 트랜잭션이 아무 일도 하지 않더라도 데이터베이스 전체의 정리 작업이 그 시점에 묶입니다. 특정 테이블만이 아니라 전역입니다.

위 실험대에서 세션 A는 SELECT 한 번 하고 아무것도 하지 않습니다. 그런데 세션 B가 만들어내는 모든 쓰레기가 회수 불가 상태로 남죠. 이것이 운영 중 가장 흔한 블로트 시나리오입니다.

회수해도 파일은 줄지 않는다

VACUUM이 죽은 튜플을 치우면 그 자리는 재사용 가능해집니다. 하지만 파일 크기가 줄지는 않습니다. VACUUM은 데이터를 앞으로 당겨오지 않기 때문에, 중간에 구멍이 나 있으면 그 상태로 둡니다.

예외가 하나 있습니다. 파일 맨 뒤쪽 페이지가 완전히 비었을 때만 잘라내서 OS에 돌려줍니다. 실험대에서 페이지가 줄어드는 경우와 줄지 않는 경우를 비교해보세요.

실제로 디스크를 되찾으려면 다음 중 하나가 필요합니다.

  • VACUUM FULL — 테이블을 통째로 다시 씁니다. ACCESS EXCLUSIVE 락이 걸려 그동안 읽기조차 막힙니다. 원본만큼의 여유 디스크도 필요합니다
  • pg_repack — 사실상 무중단으로 같은 일을 합니다. 운영 환경에서는 대개 이쪽입니다
  • 파티션 테이블이면 해당 파티션을 DROP

현장에서 확인할 것

테이블이 계속 커지는데 원인을 모르겠다면, 먼저 오래된 트랜잭션부터 찾습니다.

SELECT pid, state, age(backend_xid) AS xid_age,
       now() - xact_start AS duration, query
FROM pg_stat_activity
WHERE state != 'idle' OR backend_xid IS NOT NULL
ORDER BY xact_start
LIMIT 10;

idle in transaction 상태가 몇 시간씩 잡혀 있다면 그게 범인일 가능성이 높습니다. 애플리케이션에서 트랜잭션을 열어두고 커밋하지 않은 커넥션이죠.

블로트 규모는 이렇게 봅니다.

SELECT relname,
       n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;

예방책은 몇 가지 안 됩니다.

  • idle_in_transaction_session_timeout 설정 — 방치된 트랜잭션을 강제 종료합니다. 가장 효과가 큽니다
  • 긴 분석 쿼리는 읽기 전용 복제본으로 분리 (hot_standby_feedback 설정에 따라 주 서버 horizon에 영향을 줄 수 있으니 주의)
  • 커넥션 풀에서 트랜잭션 경계를 명확히 — 특히 자동 커밋을 끈 채 커넥션을 반납하는 코드
  • 대량 UPDATE는 나눠서 실행하고, 사이사이 autovacuum이 따라올 시간을 줍니다
이 페이지의 모델은 교육용으로 단순화한 것입니다. 실제 PostgreSQL은 HOT 업데이트, 힌트 비트, 프리즈, 멀티 트랜잭션 등 여기 없는 요소를 더 다룹니다. 다만 xmin horizon이 회수를 막는 구조는 실제와 같습니다.
