직접 조작하기

1분마다 도는 적재 배치입니다. 매 주기 파일 12개가 도착하고, 파일 하나당 3,000행을 COPY 합니다. 그중 일부는 후행 테이블이 없는 불량 파일이에요.

조작무엇이 일어나나

영구 실패 상태불량 파일을 종료 상태로 보내 재시도 대상에서 뺄지

이렇게 해보세요

1. 아무것도 안 켜고 그냥 둔다

COPY 뒤에 검증 · 상한 없음 · 종료 상태 없음 · 불량 10% 시퀀스 0 → 2,147,483,647 적재 행 0 → 3,500만 남짓 소진까지 약 18시간

두 막대가 벌어지는 걸 그냥 지켜보세요. 위 막대는 상한을 향해 달리는데 아래 막대는 바닥에 붙어 있습니다. 적재된 행보다 태워버린 값이 60배예요. 하루도 안 돼서 적재가 전면 중단됩니다.

2. 시도 횟수 상한만 넣는다

시도 횟수 상한 5회 소진까지 18시간 → 약 30일 재시도 풀 무한히 증가 → 5주기분에서 멈춤

크게 나아졌습니다. 재시도 풀이 무한히 자라던 게 다섯 주기분에서 멈추기 때문이에요. 소비량이 2차 증가에서 선형으로 바뀝니다. 그래도 누수 자체는 그대로입니다 — 불량 파일 하나가 다섯 번씩 시퀀스를 태우고 나갈 뿐이죠.

3. 영구 실패 상태로 바꾼다

영구 실패 상태 있음 (시도 상한 대신) 소진까지 30일 → 약 41일 재시도 풀 0 — 첫 시도 후 바로 빠진다

불량 파일이 한 번만 태우고 종료 상태로 빠집니다. 재시도 루프가 완전히 끊겼어요. 그런데 아직 태운 값이 2억을 넘습니다 — 한 번씩은 여전히 COPY 하고 롤백하니까요.

4. 검증을 COPY 앞으로 옮긴다 — 이 페이지의 핵심

COPY 앞에 검증 태운 값 2억 → 0 소진까지 41일 → 46일

누수가 완전히 사라집니다. 불량 파일은 COPY 자체를 안 하니 시퀀스를 건드릴 일이 없어요. 손잡이 하나를 옮겼을 뿐인데 태운 값이 0이 됐습니다.

교훈은 한 줄로 줄어듭니다 — 검증은 되돌릴 수 없는 일보다 먼저. 트랜잭션은 행을 되돌려주지만 시퀀스는 되돌려주지 않습니다.

5. 다 고쳐도 46일이면 찬다

모든 장치를 켠 상태에서 그냥 둔다 태운 값 0 소진까지 46일 ← 정상 적재만으로

여기가 두 번째 결론입니다. 누수를 다 막아도 int4 는 46일이면 찹니다. 하루 4,600만 행을 넣는 테이블에 21억은 그냥 작아요. 코드를 고치는 것과 컬럼을 bigint 로 바꾸는 것은 별개의 작업이고, 둘 다 필요합니다.

왜 시퀀스는 롤백되지 않는가

이게 이 페이지의 출발점입니다. PostgreSQL 의 시퀀스는 트랜잭션 밖에서 동작합니다.

BEGIN;
  INSERT INTO gps_history ...;   -- nextval() 이 1,000개를 발급
  -- 검증 실패
ROLLBACK;

-- 행: 없음.  시퀀스: 1,000 만큼 전진한 채로 남음

일부러 그렇게 만든 겁니다. 시퀀스가 롤백된다면 동시에 도는 트랜잭션들이 서로를 기다려야 하거든요. 번호 하나 받으려고 줄을 서게 되는 셈이죠. 시퀀스는 유일성만 약속하고 연속성은 약속하지 않습니다.

그래서 이런 것들이 전부 정상 동작입니다.

  • 롤백된 트랜잭션이 쓴 번호는 영원히 비어 있습니다
  • cache 설정이 있으면 세션이 끝날 때 캐시분이 통째로 버려집니다
  • 충돌로 죽은 세션이 잡고 있던 번호도 안 돌아옵니다
그러니 id 값을 세는 데 쓰면 안 됩니다. "마지막 id 가 21억이니 행이 21억 개"라는 추정이 이 장애를 늦게 발견하게 만드는 원인이기도 합니다. 행 수는 count(*) 로 세야 해요.

검증이 부수효과 뒤에 있으면

문제의 코드는 대개 이렇게 생겼습니다.

@Transactional
public void migrate(File file) {
    copyGpsRows(file);                        // ① 3,000행 COPY — 시퀀스 3,000 소비
    copyDriveRows(file);

    if (!hasAdasTable(file)) {                // ② 여기서 검증
        throw new IllegalStateException(...); // ③ 롤백 — 행은 사라지고 시퀀스는 남는다
    }
    markMigrated(file);                       // ④ 여기까지 못 온다
}

①과 ②의 순서만 바꾸면 됩니다. 검증이 먼저면 불량 파일은 COPY 근처에도 못 가요.

public void migrate(File file) {
    if (!hasAdasTable(file)) {                // ① 먼저 검증
        markPermanentlyFailed(file);          //    종료 상태로 보내고 끝
        return;
    }
    copyGpsRows(file);                        // ② 통과한 것만 COPY
    ...
}

일반화하면 이렇습니다. 되돌릴 수 없는 일을 하기 전에 되돌릴 수 있는 검증을 끝내라. 롤백이 안 되는 건 시퀀스만이 아니에요.

되돌아가지 않는 것예
시퀀스nextval() 은 전진만 한다
외부 호출결제 승인, 메일 발송, 푸시
파일 시스템업로드, 삭제, 이동
메시지 발행Kafka, MQTT — 발행한 건 회수 안 된다
다른 트랜잭션이 이미 본 것커밋 전에 읽혔다면 이미 늦었다

재시도 루프의 3요건

누수를 막아도 재시도 루프 자체가 남습니다. 실패한 작업이 영원히 다시 시도되는 구조는 그 자체로 위험해요. 최소 세 가지가 필요합니다.

1. 영구 실패 상태

재시도 대상에서 빠져나갈 상태가 반드시 있어야 합니다. 이게 없으면 실패한 레코드가 큐에 영원히 남습니다.

-- 상태값 하나를 더 두는 것으로 끝난다
migrate_flag: 'N'  대기      → 재시도 대상
              'Y'  완료
              'E'  영구 실패  → 재시도 대상에서 제외

실험대에서 이 토글 하나가 재시도 풀을 0으로 만듭니다. 가장 값싼 장치인데 가장 자주 빠져 있어요.

2. 시도 횟수 상한

영구 실패로 분류할 수 없는 실패(일시적 네트워크 오류 등)에는 횟수 상한이 답입니다. attempt_count 컬럼 하나면 됩니다.

상한만 있고 영구 실패 상태가 없으면 어떻게 될까요. 실험대의 레시피 2가 그겁니다 — 나아지지만 누수는 남습니다. 둘은 서로를 대체하지 않습니다.

3. 재시도 대상은 화이트리스트로

가장 자주 뒤집혀 있는 항목입니다. 보통 이렇게 씁니다.

try { work(); }
catch (IOException | TimeoutException e) { fail(job); }   // 이것만 실패 처리
catch (Exception e) { requeue(job); }                     // 나머지는 재시도 ← 위험

기본값이 "재시도" 로 되어 있습니다. 새로운 예외가 등장하면 자동으로 무한 재시도 경로를 탑니다. 디스크 가득 참, 권한 만료, 잘못된 데이터 — 재시도해봐야 영원히 실패할 것들이 전부 여기로 들어와요.

if (isRetryable(e)) requeue(job);   // 일시적이라고 아는 것만 재시도
else                fail(job);      // 기본값은 실패

기본값을 뒤집는 것만으로 모르는 실패가 루프에 들어가지 않습니다.

여기에 지수 백오프를 얹으세요. 매분 재시도는 상대가 힘들 때 그 상대를 같이 두들깁니다. 상대가 외부 API 라면 그쪽 장애를 연장시키고, 자기 DB 라면 자기 장애를 연장시켜요.

21억은 생각보다 작다

레시피 5가 보여주는 두 번째 결론입니다. integer 의 상한 2,147,483,647 은 요즘 데이터 규모에서 그렇게 큰 숫자가 아닙니다.

초당 삽입int4 상한 도달
100약 8개월
500약 50일
1,000약 25일
5,000약 5일

여기에 롤백·캐시로 버려지는 몫이 더해지면 훨씬 빨라집니다. 그리고 도달하는 순간이 곧 전면 장애예요 — 성능이 나빠지는 게 아니라 삽입이 그냥 안 됩니다.

더 나쁜 건 그때 해야 할 일입니다. integer → bigint 전환은 큰 테이블에서 ACCESS EXCLUSIVE 락을 잡고 전체를 다시 씁니다. 수십 GB 짜리라면 그 시간 내내 그 테이블을 못 씁니다. 이미 장애 중인데 복구에 또 시간이 드는 거죠.

-- 컬럼과 시퀀스 양쪽을 다 바꿔야 한다
ALTER TABLE gps_history ALTER COLUMN id TYPE bigint;   -- 전체 재작성
ALTER SEQUENCE gps_history_id_seq AS bigint MAXVALUE 9223372036854775807;
SELECT setval('gps_history_id_seq', (SELECT max(id) FROM gps_history));

그래서 새 테이블은 처음부터 bigint 로 만드는 게 정석입니다. 8바이트가 아까워서 4바이트를 쓸 이유가 대부분 없어요.

현장에서 확인할 것

시퀀스 사용률에 알람을 거세요. 도달하기 전에 알 수 있는 유일한 방법입니다.

-- 전체 시퀀스의 사용률
SELECT schemaname, sequencename,
       last_value,
       max_value,
       round(last_value::numeric / max_value * 100, 2) AS pct_used
FROM pg_sequences
WHERE last_value IS NOT NULL
ORDER BY pct_used DESC
LIMIT 20;

70% 를 경고선으로 잡으면 bigint 전환을 장애가 아니라 계획된 작업으로 할 수 있습니다. 그 차이가 큽니다.

시퀀스와 실제 행 수를 나란히 보세요. 이 페이지의 두 막대가 그겁니다.

SELECT (SELECT last_value FROM gps_history_id_seq)          AS seq,
       (SELECT count(*) FROM gps_history)                   AS rows,
       (SELECT last_value FROM gps_history_id_seq)
         - (SELECT count(*) FROM gps_history)                AS gap;

정상적인 삭제로도 격차는 생깁니다. 다만 격차가 행 수의 몇 배로 벌어져 있다면 어딘가에서 넣었다 버리는 일이 반복되고 있다는 뜻이에요. 이 모순이 원인을 찾는 가장 빠른 단서입니다.

마지막 줄이 중요합니다. 영구 실패 상태를 만들어두고 아무도 그 상태로 안 가는 경우가 흔해요. 분류 로직이 실제로 동작하는지는 그 건수로만 알 수 있습니다.

배치 로그에 건별 결과를 남기세요. 한 건 실패가 배치 전체를 중단시키지 않도록 try/catch 로 격리하고, 어떤 파일이 왜 실패했는지 남깁니다. 그래야 'E' 로 빠진 것들을 나중에 사람이 다시 볼 수 있습니다.

이 페이지의 모델은 개념을 보여주기 위해 단순화한 것입니다. 배치 주기 1분, 배치당 파일 12개, 파일당 3,000행으로 고정했고, 재시도 풀은 실수로 누적합니다. 실제 소진 시각은 데이터 유입량·불량 비율의 변동·시퀀스 cache 설정에 따라 달라져요. 중요한 건 며칠이냐가 아니라 두 막대가 벌어진다는 사실입니다.
