응답을 순서로 맞추면 언제 어긋나는가

단말에 설정을 물어보고 응답을 기다립니다. 요청이 하나면 아무 문제가 없어요. 그런데 응답 하나가 늦게 오는 순간, 그 뒤의 모든 요청이 남의 답을 자기 답으로 받습니다 — 그리고 아무도 그걸 눈치채지 못합니다.

칸 하나가 요청 하나의 결말입니다. 초록은 자기 응답을 받은 것, 빨강은 남의 응답을 받은 것(오매칭), 노란 점선은 아무것도 못 받고 타임아웃된 것이에요. 아래 줄은 지금 응답을 기다리는 요청들입니다 — 단일 슬롯에서는 하나밖에 못 들고 있는 것이 보입니다.

직접 조작하기

같은 단말에 같은 명령을 계속 보냅니다. 요청은 끊기지 않고 이어지고, 응답은 잠시 뒤에 돌아와요.

조작무엇이 일어나나
동시 요청같은 단말에 동시에 떠 있는 요청 수. 직렬화에서는 1로 고정됩니다
매칭 방식도착한 응답을 어느 요청에 붙일지 정하는 규칙
응답 교란순서 뒤집힘 / 지각 응답(타임아웃 뒤 도착) / 중복 응답(재전송)
교란 강도응답 중 몇 %가 그렇게 되는지

이렇게 해보세요

1. 요청 하나로 시작한다

동시 요청 1 · 단일 슬롯 · 교란 없음 정확 100% 오매칭 0

완벽합니다. pendingMap.put(serial, future) 로도 아무 문제가 없어요. 대부분의 코드가 이 상태로 시작하고, 이 상태로 리뷰를 통과합니다.

2. 동시 요청을 4건으로 올린다 — 단일 슬롯이 무너진다

동시 요청 4 · 단일 슬롯 · 교란 없음 정확 100% → 0% 오매칭 0 → 100% 사건 기록: "#12 의 future 가 #13 으로 덮어써졌다"

네트워크는 멀쩡한데 전부 오매칭입니다. put 이 앞의 future 를 통째로 덮어쓰기 때문이에요. 슬롯에는 늘 가장 최근 요청이 들어 있는데, 도착하는 응답은 가장 오래된 요청 것입니다. 대기 목록을 보세요 — 하나밖에 못 들고 있습니다.

3. FIFO 큐로 바꾼다 — 고쳐진 것처럼 보인다

FIFO 큐 · 교란 없음 정확 0% → 100% 오매칭 100% → 0%

키마다 큐를 두고 먼저 기다린 요청부터 완료시키면 덮어쓰기가 사라집니다. 화면이 완전히 깨끗해졌어요. 실제 프로젝트가 여기서 멈췄고, 그럴 만합니다 — 재현되던 증상이 사라졌으니까요.

4. 응답 순서를 뒤집는다

FIFO 큐 · 순서 뒤집힘 40% 오매칭 0% → 50% 부근

FIFO 는 "먼저 보낸 요청의 응답이 먼저 온다"는 가정 위에 서 있습니다. 그런데 아무도 그걸 보장하지 않아요. 단말이 처리 순서를 바꾸거나, 재전송이 끼거나, 네트워크가 재배열하면 그대로 어긋납니다.

더 나쁜 건 스스로 복구하지 못한다는 점입니다. 한 칸 밀리면 그 뒤로 계속 한 칸씩 밀린 채로 갑니다. 정렬이 다시 맞을 이유가 없거든요.

5. 직렬화로 바꾼다 — 순서는 막힌다

직렬화 · 순서 뒤집힘 40% 오매칭 50% → 0% 처리량 1/3 로 떨어진다

동시에 한 건만 보내면 뒤집힐 순서 자체가 없습니다. 정확해졌어요. 대신 같은 시간에 처리하는 요청 수가 크게 줄어듭니다. 정확성을 처리량으로 산 겁니다.

6. 직렬화 상태에서 지각 응답을 켠다 — 다시 무너진다

직렬화 · 지각 응답 40% 오매칭 0% → 60% 부근

여기가 이 페이지에서 가장 중요한 자리입니다. 동시 요청이 한 건뿐인데도 오매칭이 납니다.

요청 A 가 타임아웃되어 큐에서 빠집니다. 그 다음 요청 B 가 들어가요. 그리고 A 의 응답이 뒤늦게 도착해 B 를 완료시킵니다. B 의 호출자는 A 의 설정값을 자기 것으로 받습니다. 동시성 문제가 아니라 식별자가 없어서 생기는 문제라는 게 여기서 드러납니다.

7. 중복 응답을 켠다 — FIFO 가 완전히 무너진다

FIFO 큐 · 중복 응답 40% 오매칭 100% 부근

재전송으로 같은 응답이 두 번 오면 두 번째 사본이 다음 요청의 future 를 완료시킵니다. 응답 하나가 두 요청을 끝내버리는 거죠. 한 번 어긋난 정렬은 복구되지 않으니 그 뒤로 전부 밀립니다.

MQTT QoS 1 을 쓴다면 중복은 예외가 아니라 약속된 동작입니다. 위치 매칭과 QoS 1 은 같이 쓰면 안 되는 조합이에요.

8. correlationId 로 바꾼다

correlationId · 중복 응답 40% 오매칭 0% 교란을 순서·지각·중복 어느 것으로 바꿔도 0%

응답에 어느 요청의 답인지가 실려 있으면 순서가 어떻든 상관없습니다. 지각한 응답은 짝이 이미 사라졌으니 조용히 버려지고, 중복 사본은 이미 완료된 id 라 버려져요. 세 교란 전부에 무해합니다.

지각 응답에서 유실은 여전히 납니다. 그건 맞아요 — 타임아웃된 요청은 실패한 게 맞으니까요. 중요한 건 그 실패가 다른 요청을 오염시키지 않는다는 점입니다.

왜 오매칭이 유실보다 나쁜가

이 페이지의 계기가 셋으로 나뉜 이유입니다. 셋은 심각도가 전혀 다릅니다.

결말호출자가 보는 것심각도
유실타임아웃 예외시끄럽다. 재시도하면 된다
오매칭정상 응답조용하다. 틀린 값을 맞다고 믿는다
정확정상 응답—

유실은 스스로 신고합니다. 로그에 남고, 지표에 잡히고, 재시도 대상이 됩니다. 오매칭은 아무것도 안 남깁니다. 단말 A 의 설정 화면에 단말 B 의 값이 떠 있어도, 시스템 관점에서는 모든 요청이 성공한 겁니다.

그래서 이 유형은 "가끔 값이 이상해요" 로 신고됩니다. 재현이 안 되고, 로그에는 성공만 찍혀 있고, 대개 프론트엔드 캐시 문제로 의심받습니다. 실제로 값을 잘못 붙인 곳은 훨씬 아래층인데요.

세 겹으로 쌓여 있던 문제

실제 사례에서 "응답이 안 온다"는 하나의 증상 아래 원인이 세 개 겹쳐 있었습니다.

  1. 응답 토픽을 구독하지 않았다 — 그래서 모든 요청이 타임아웃
  2. 타임아웃을 3초에서 10초로 올렸다 — 증상만 미뤘고 원인은 그대로
  3. future 가 덮어써지고 있었다 — 8일 뒤에야 밝혀짐

세 번째를 고치면서 FIFO 큐를 도입했고, 덮어쓰기는 확실히 사라졌습니다. 다만 네 번째 겹이 남아 있었어요 — 이 페이지의 레시피 4~7 이 그겁니다.

타임아웃 상향(2번)은 특히 뼈아픕니다. 증상을 8일 동안 가려뒀거든요. 완화 조치는 진단이 아니라 유예이고, 유예할 때는 원인 티켓을 반드시 같이 남겨야 합니다.

correlationId 를 넣는 법

MQTT 5 는 이걸 프로토콜에 넣어뒀습니다. 페이로드를 건드릴 필요가 없어요.

// 요청 — 표준 속성으로 실어 보낸다
MqttProperties props = new MqttProperties();
props.setCorrelationData(correlationId.getBytes());
props.setResponseTopic("device/" + serial + "/config/resp");

// 응답 수신 — 그 값으로 대기 중인 요청을 찾는다
byte[] cd = message.getProperties().getCorrelationData();
CompletableFuture<Config> f = pending.remove(new String(cd));
if (f != null) f.complete(parse(message));      // 짝이 없으면 조용히 버린다

MQTT 3.1.1 이거나 단말 펌웨어를 바꿀 수 없다면 페이로드에 넣습니다. 단말이 그 값을 그대로 되돌려주기만 하면 되니 대개 가장 작은 변경이에요.

{ "reqId": "9f2c...", "cmd": "getConfig" }      →
                                                ← { "reqId": "9f2c...", "config": {...} }

핵심은 마지막 줄입니다. 짝이 없는 응답은 버립니다. 위치 매칭과의 차이가 여기 있어요 — 위치 매칭은 짝이 없는 응답을 아무한테나 붙이지만, id 매칭은 버립니다.

펌웨어를 못 바꾼다면

단말 쪽 협의에 시간이 걸리는 경우가 많습니다. 그동안 쓸 수 있는 것들인데, 어느 것도 완전하지 않다는 걸 알고 써야 합니다.

임시 대응막는 것못 막는 것
직렬화 (동시 1건)순서 뒤집힘지각 · 중복 (레시피 6)
툼스톤 — 타임아웃된 키를 잠시 남겨둔다지각 응답순서 뒤집힘
둘 다셋 다 대부분처리량, 그리고 남는 창

툼스톤은 타임아웃으로 제거한 요청의 자리를 잠깐 비워두는 것입니다. 그 자리에 늦게 도착한 응답이 오면 다음 요청에 붙이지 않고 버려요. 지각 응답만 골라 막는 값싼 장치인데, 얼마나 오래 남길지가 또 하나의 추측이 됩니다.

임시 대응을 넣더라도 correlationId 협의는 지금 시작하세요. 펌웨어 변경은 리드타임이 길고, 그 사이 임시 대응이 "이미 고쳐진 것"으로 기록되면 영영 안 바뀝니다.

이 문제는 MQTT 만의 것이 아니다

요청과 응답이 서로 다른 채널로 오가는 모든 구조가 같은 형태입니다.

  • Kafka 요청-응답 — 요청 토픽과 응답 토픽이 분리되어 있습니다. 헤더에 correlation id 를 싣는 게 관행인 이유예요
  • WebSocket RPC — 한 소켓 위에 여러 요청이 오갑니다. 프레임에 id 가 없으면 순서에 기대게 됩니다
  • 단말·장비 시리얼 통신 — 프로토콜에 시퀀스 번호가 있는 이유가 이것입니다
  • 비동기 콜백 API — 콜백이 어느 호출의 것인지 파라미터로 안 오면 같은 문제입니다

HTTP 가 이 문제를 잘 안 겪는 건 커넥션이 요청-응답 짝을 대신 들고 있기 때문입니다. 같은 소켓의 응답은 그 요청의 것이 맞거든요. 그 보장을 잃는 순간 — 멀티플렉싱을 하거나, 응답을 다른 채널로 받는 순간 — 짝을 직접 들고 있어야 합니다.

현장에서 확인할 것

먼저 이 질문에 답해보세요. "같은 대상에 같은 명령이 동시에 두 번 들어오면 어떻게 되는가." 답이 바로 안 나오면 대개 이 페이지의 상태입니다.

대기 자료구조를 보세요. 키가 무엇인지가 전부입니다.

Map<String, CompletableFuture<T>> pending;   // 키가 serial 이면 → 단일 슬롯
Map<String, Queue<CompletableFuture<T>>> pending;  // 키가 serial 이면 → FIFO
Map<String, CompletableFuture<T>> pending;   // 키가 correlationId 면 → 안전

세 번째와 첫 번째가 타입이 똑같습니다. 코드 리뷰에서 이 차이를 놓치기 쉬운 이유예요. 봐야 할 건 자료구조가 아니라 키에 무엇이 들어가는지입니다.

지표로 만들 것.

지표무엇을 말해주나
짝 없는 응답 수버려진 응답. 0이 아니면 지각·중복이 실재한다
대기 맵 크기단조 증가하면 완료되지 않은 future 가 쌓이는 중
타임아웃 비율구독 누락이나 덮어쓰기의 첫 신호
요청-응답 지연 분포타임아웃을 얼마로 잡을지의 유일한 근거

첫 줄이 특히 값싸고 효과적입니다. correlationId 를 넣고 나면 짝 없는 응답이 그냥 카운터로 보입니다. 위치 매칭에서는 그 응답들이 조용히 남의 요청에 붙어버려서 셀 수조차 없었던 것들이에요.

테스트는 동시에 두 번 보내는 것부터. 같은 대상에 같은 명령을 동시에 두 번 보내고 두 응답이 각자 제 값을 받는지 확인하는 테스트 하나면, 레시피 2가 재현됩니다. 응답을 일부러 뒤집어 보내는 테스트를 더하면 레시피 4까지 잡힙니다.

이 페이지의 모델은 개념을 보여주기 위해 단순화한 것입니다. 왕복 시간, 타임아웃, 교란 비율을 고정값으로 뒀고 실제로는 전부 분포를 갖습니다. 특히 오매칭률의 절대값은 교란이 어떻게 분포하느냐에 크게 좌우됩니다 — 중요한 건 몇 퍼센트냐가 아니라, 위치로 짝지으면 한 번 어긋난 뒤 스스로 복구하지 못한다는 것입니다.
