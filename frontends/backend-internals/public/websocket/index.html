서버를 늘렸더니 메시지가 안 간다

한 대일 때는 완벽하게 돌던 채팅이 두 대로 늘리는 순간 절반만 도착합니다. 코드는 한 줄도 안 바꿨는데요. WebSocket 이 서버에 상태를 들고 있다는 사실이 여기서 청구서로 돌아옵니다.

회색 점은 그 서버에 붙어 있는 방 구성원, 초록 점은 이번 메시지를 받은 사람입니다. 실선 초록 테두리는 메시지를 받은 서버, 빨간 점선은 받았지만 줄 사람이 없는 서버예요. 매 발행마다 구성원의 접속 분포를 새로 뽑습니다 — 실제로는 클라이언트가 한 서버에 붙어 있지만, 여러 방·여러 시점의 평균을 한 화면에서 보여주려고요. 계기의 회색 숫자는 이 조건에서의 기대값입니다.

조작무엇이 일어나나
서버 수WebSocket 서버 대수입니다. 클라이언트는 로드밸런서를 통해 아무 서버에나 붙습니다
방 크기이 방에 몇 명이 있는지. 작을수록 브로드캐스트가 헛일이 됩니다
재연결 중잠깐 끊겨서 어느 서버에도 붙어 있지 않은 비율입니다
전파 방식로컬만 / 전체 브로드캐스트 / 방별 채널

이렇게 해보세요

1. 서버를 한 대에서 넷으로 늘린다

로컬만, 방 12명, 재연결 0% 서버 1대 도달률 100% 서버 2대 도달률 50% 서버 4대 도달률 25% 서버 8대 도달률 12.5%

코드는 그대로인데 서버 대수만 늘렸습니다. 도달률이 정확히 1/N 로 떨어져요. 이벤트를 받은 서버는 자기한테 붙은 소켓만 알고 있고, 다른 서버에 붙은 사람들의 존재조차 모릅니다. 스케일 아웃했더니 기능이 망가지는 드문 사례예요.

2. 전체 브로드캐스트로 바꾼다

서버 4대, 방 12명 로컬만 도달률 25% Redis 팬아웃 0 전체 브로드캐스트 도달률 100% Redis 팬아웃 4.00

Redis 채널 하나를 두고 모든 서버가 구독합니다. 어느 서버로 이벤트가 들어오든 Redis 를 거쳐 전부에게 퍼집니다. 도달률이 100% 로 돌아왔어요. 대신 메시지 하나가 서버 대수만큼 복제됩니다.

3. 방을 작게 만들어 팬아웃의 값을 본다

전체 브로드캐스트, 서버 8대, 방 3명 Redis 팬아웃 8.00 헛일 67.0% 빨간 점선 카드가 여럿 뜬다 — 받았지만 줄 사람이 없다

여기가 브로드캐스트의 진짜 비용입니다. 방에 세 명뿐인데 여덟 대 전부가 메시지를 받아 역직렬화하고, 자기 방 목록을 뒤진 뒤, 줄 사람이 없다는 걸 확인하고 버립니다. 1:1 대화가 많은 서비스에서 서버를 늘리면 이 헛일이 그대로 CPU 로 갑니다.

4. 방별 채널로 바꾼다

서버 8대, 방 3명 전체 브로드캐스트 팬아웃 8.00 헛일 67.0% 방별 채널 팬아웃 2.64 헛일 0%

방마다 채널을 따로 두고, 서버는 자기가 들고 있는 방의 채널만 구독합니다. 구성원이 없는 서버에는 애초에 배달되지 않아요. 팬아웃이 8에서 2.64로 떨어집니다. 공짜는 아닙니다 — 채널 수가 방 수만큼 늘고, 누가 들어오고 나갈 때마다 구독·해지가 발생합니다.

5. 재연결 중인 사람을 만든다

방별 채널, 서버 4대, 방 12명, 재연결 20% 도달률 80% 누적 유실 계속 늘어난다

Pub/Sub 으로 바꿔도 이건 안 막힙니다. Redis Pub/Sub 은 저장하지 않습니다. 발행 시점에 구독 중이 아니면 그 메시지는 그냥 없어져요. 재연결에 3초가 걸린다면 그 3초 동안의 모든 메시지가 영구히 사라집니다. 도달률 100%는 연결이 유지되는 동안만의 이야기입니다.

왜 서버를 늘리면 깨지는가

HTTP 는 상태가 없어서 서버를 늘리는 게 쉽습니다. 어느 서버가 처리하든 결과가 같으니까요. WebSocket 은 반대입니다. 연결 자체가 상태이고, 그 상태는 특정 서버의 메모리 안에 있습니다.

// 흔한 첫 구현
Map<String, Set<WebSocketSession>> roomSessions;   // ← 이 서버의 메모리

void broadcast(String room, String payload) {
    for (WebSocketSession s : roomSessions.get(room)) {   // ← 이 서버에 붙은 것만
        s.sendMessage(new TextMessage(payload));
    }
}

이 코드는 서버가 한 대일 때 완벽하게 동작합니다. 그리고 두 대가 되는 순간 절반에게 도달하지 못합니다. 버그가 아니라, 애초에 한 대를 전제로 쓴 코드예요.

이 문제는 부하가 아니라 대수에서 나옵니다. 그래서 개발·스테이징(1대)에서는 절대 재현되지 않고 운영(N대)에서만 터집니다. 게다가 "가끔 메시지가 안 와요"로 신고되기 때문에 네트워크 문제로 오인되기 쉽습니다.

스티키 세션은 답이 아니다

가장 먼저 떠오르는 해법은 로드밸런서로 같은 방 사람을 같은 서버에 몰아주는 것입니다. 실제로 동작은 합니다. 다만 대가가 큽니다.

  • 부하가 기웁니다. 큰 방 하나가 서버 한 대를 잡아먹습니다
  • 배포할 때마다 전원 재연결. 그 서버를 내리면 그 방 전체가 끊깁니다
  • 방을 넘나드는 메시지를 못 보냅니다. 알림, 멘션, 친구 목록 상태 같은 건 방 경계를 넘습니다
  • 방이 커지면 한 서버에 안 들어갑니다. 결국 같은 문제로 돌아옵니다

스티키 세션은 연결을 한 서버에 고정하는 용도로는 여전히 유용합니다(재연결 시 같은 서버로 붙이기). 다만 메시지 전파의 해법은 아닙니다.

Pub/Sub 이 하는 일

서버끼리 서로를 알 필요가 없게 만드는 게 핵심입니다. 각 서버는 Redis 만 알면 됩니다.

// 이벤트를 받은 서버 — 자기 소켓에 직접 쓰지 않는다
redis.convertAndSend("room:" + roomId, payload);

// 모든 서버가 구독자로서 같은 코드를 갖는다
void onMessage(String channel, String payload) {
    String room = channel.substring("room:".length());
    for (WebSocketSession s : roomSessions.get(room)) {   // ← 이제 자기 몫만
        s.sendMessage(new TextMessage(payload));
    }
}

중요한 건 발행하는 쪽이 자기 소켓에도 직접 쓰지 않는다는 점입니다. Redis 를 거쳐 돌아온 메시지를 받아서 씁니다. 그래야 경로가 하나가 되고, 순서와 중복 문제를 한 곳에서만 신경 쓰면 됩니다. 직접 쓰기와 Pub/Sub 을 섞으면 자기 서버 사람만 메시지를 두 번 받는 버그가 생깁니다.

채널을 어떻게 나눌 것인가

실험대의 두 Pub/Sub 방식이 이 선택입니다.

방식팬아웃대가
채널 1개서버 대수 N구성원 없는 서버도 전부 받아 역직렬화하고 버린다
방별 채널구성원이 있는 서버 수채널 수가 방 수만큼. 입퇴장마다 구독·해지

기대 팬아웃은 N(1 − (1 − s)^k) 입니다. s 는 구성원 한 명이 특정 서버에 붙어 있을 확률, k 는 방 크기예요. (1 − s)^k 가 "그 서버에 이 방 사람이 하나도 없을 확률"이고, 이게 곧 브로드캐스트의 헛일 비율입니다.

규칙은 단순합니다. 방이 서버 대수보다 크면 브로드캐스트로 충분하고, 작으면 낭비가 지배적입니다. 1:1 대화나 개인 알림처럼 방 크기가 1~2 인 서비스는 서버를 늘리는 만큼 헛일이 늘어납니다.

Redis Cluster 를 쓴다면 주의하세요. 일반 PUBLISH 는 채널을 나눠도 클러스터의 모든 노드로 전파됩니다. 채널별로 노드를 나누려면 Redis 7 의 샤드 Pub/Sub(SPUBLISH / SSUBSCRIBE)을 써야 합니다. 방별 채널로 바꿨는데 Redis 부하가 안 줄었다면 여기를 보세요.

Pub/Sub 은 저장하지 않는다

이게 가장 늦게 발견되는 성질입니다. Redis Pub/Sub 은 발행 시점에 구독 중인 대상에게만 전달합니다. 큐도, 재생도, 확인 응답도 없습니다.

그래서 이런 순간에 구멍이 납니다.

  • 클라이언트 재연결 중 — 지하철, 엘리베이터, 네트워크 전환. 실험대의 "재연결 중" 슬라이더가 이겁니다
  • 서버 재시작·배포 — 그 서버가 구독을 놓은 사이 발행된 메시지는 없습니다
  • Redis 재시작 — 구독 상태 자체가 사라집니다

도달률 계기가 100% 를 가리켜도 그건 연결이 붙어 있는 동안의 이야기입니다. 사용자가 체감하는 건 "대화가 중간에 비었다" 예요.

공백을 메우는 방법

Pub/Sub 은 실시간 전달만 담당하게 두고, 기록은 따로 두는 게 정석입니다.

1. 메시지를 먼저 저장한다        → 단조 증가하는 seq 를 받는다
2. 그 seq 를 실어 Pub/Sub 으로 발행
3. 클라이언트는 마지막으로 받은 seq 를 기억
4. 재연결 시 그 다음부터 다시 받아온다
   GET /rooms/{id}/messages?after={lastSeq}

이 구조에서 Pub/Sub 은 "새 게 생겼다"는 신호일 뿐이고, 정확성은 저장소가 책임집니다. 신호를 놓쳐도 다음 재연결에서 메워지므로, Pub/Sub 의 무보장이 문제가 되지 않아요.

순서도 마찬가지입니다. Pub/Sub 은 채널 안에서는 순서를 지키지만 여러 채널 사이의 순서는 보장하지 않고, 재연결로 흐름이 끊기면 그마저 의미가 없어집니다. 클라이언트가 seq 로 정렬하고 빈 구간을 감지해 다시 요청하게 만드는 편이 확실합니다.

더 강한 보장이 필요하면 Redis Streams(저장 + 소비자 그룹 + 재생)나 Kafka 로 올라가는 선택지가 있습니다. 다만 대부분의 채팅·알림은 Pub/Sub + 저장소 + seq 재동기화 조합으로 충분합니다. 전달 보장을 브로커에 요구하기 시작하면 운영 복잡도가 한 단계 올라갑니다.

현장에서 확인할 것

서버를 두 대로 띄우고 테스트하세요. 한 대에서는 이 페이지의 문제가 하나도 재현되지 않습니다. 로컬에서 포트를 달리해 두 개 띄우고 서로 다른 인스턴스에 붙어보는 것만으로 대부분 잡힙니다.

자기 소켓에 직접 쓰는 코드가 남아 있는지 보세요. Pub/Sub 을 도입하고도 발행 경로에서 session.sendMessage() 를 직접 호출하면, 같은 서버 사람만 두 번 받습니다. 원인을 찾기 까다로운 증상이에요.

구독 해지를 하고 있는지 확인하세요. 방별 채널을 쓰면서 마지막 사람이 나갈 때 unsubscribe 하지 않으면 채널 구독이 계속 쌓입니다. 서버가 오래 뜰수록 팬아웃이 브로드캐스트에 수렴해요.

배포 중 재연결 폭주에 대비하세요. 서버 한 대를 내리면 거기 붙어 있던 연결이 한꺼번에 재연결을 시도하고, 그 직후 전부 재동기화 API 를 호출합니다. 클라이언트에 지수 백오프와 지터를 넣지 않으면 배포할 때마다 자기 자신을 DDoS 하게 됩니다.

이 페이지의 모델은 개념을 보여주기 위해 단순화한 것입니다. 실제로는 클라이언트가 한 서버에 붙어 머무르고, 방 크기와 접속 분포가 균일하지도 않습니다. 실험대는 매 발행마다 분포를 새로 뽑아 평균적인 모습을 보여줍니다 — 특정 순간의 한 서비스가 아니라 여러 방·여러 시점의 평균으로 읽어주세요.
