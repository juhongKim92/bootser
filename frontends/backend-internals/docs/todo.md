### 실시간 통신

- [x] 05. MQTT QoS 0/1/2 — 한 번만 전달한다는 약속의 값 (`/mqtt/`)
  - 세 레인이 **같은 속도로 패킷을 하나씩** 소비한다. 같은 패킷 예산에서 끝낸
    메시지 수가 곧 그 레벨의 값이 되도록 설계했다
  - 계기에 실측과 기대값을 나란히 띄운다. 본문 수치는 전부 기대값(해석해)이라
    독자가 화면에서 읽는 값과 어긋나지 않는다 — `content-audit.md` §1-1 의 교훈
  - 기대값: QoS 1 패킷 `(1+q)/q²`, QoS 2 는 그 두 배, QoS 1 중복 `p/q`
    (시도당 2패킷이 아닌 이유 — PUBLISH 가 유실되면 PUBACK 은 생기지 않는다)
  - 재전송 상한 12회. 실패율 40% 에서 QoS 2 의 0.8% 가 상한에 걸려 포기된다 —
    본문에 명시했다
  - 다룬 것: 홉 단위 QoS(가장 흔한 오해), TCP 가 가려주므로 실제 유실은
    연결이 끊길 때 몰린다는 점, MQTT 5 의 재전송 시점, DUP 플래그를 중복 판정에
    쓰면 안 되는 이유, 세션 유지(cleanSession / Session Expiry / client id)
- [x] 06. WebSocket 다중 서버와 Redis Pub/Sub — 서버를 늘렸더니 메시지가 안 간다 (`/websocket/`)
  - 전파 방식 3단(로컬만 → 전체 브로드캐스트 → 방별 채널)을 손잡이 하나로 오가게 했다.
    도달률과 팬아웃이 동시에 움직이는 걸 한 화면에서 본다
  - 기대값: 도달률 로컬만 `s`·Pub/Sub `1-d`, 팬아웃 브로드캐스트 `N`·방별 `N(1-(1-s)^k)`,
    헛일 `(1-s)^k` (`s = (1-d)/N`, `k` = 방 크기)
  - 발행 주체를 방 밖(서버로 들어온 이벤트)에 두었다. 구성원 중에서 뽑으면
    "발행자는 반드시 접속 중"이 조건으로 붙어 도달률이 `1-d` 보다 낮게 나온다 —
    작성 중 시뮬레이션으로 잡았다
  - 다룬 것: 대수에서 나오는 문제라 1대 환경에선 재현 불가, 스티키 세션이 답이 아닌 이유,
    발행 서버가 자기 소켓에 직접 쓰면 안 되는 이유, Redis Cluster 의 일반 PUBLISH 는
    전 노드로 퍼진다(샤드 Pub/Sub 필요), 구독 해지 누락, 배포 시 재연결 폭주
  - 공백 메우기는 `Pub/Sub + 저장소 + seq 재동기화` 로 정리했다
- [x] 07. Keep-alive 와 죽은 커넥션 + LWT — 서버는 두 시간 동안 살아있다고 믿는다 (`/keepalive/`)
  - **시간이 흐르지 않는 실험대.** 손잡이를 움직이면 그 조건의 사건 순서를 통째로
    다시 계산해 그린다 — 2시간 11분을 실시간으로 기다릴 수 없으니
  - 탐지 지연: TCP 기본 `7200 + 75×9 = 7875초`, TCP 튜닝 `KA + 10×6`, 앱 `1.5×KA`.
    `KA + 60 = 1.5KA` 는 KA=120 에서 만난다 — 주기를 2분보다 길게 잡으면
    앱 keep-alive 가 OS 튜닝보다 오히려 느려진다
  - 끊김 방식에 **앱 멈춤**을 넣은 게 핵심이다. 커널이 프로브에 대신 ACK 하므로
    TCP keepalive 로는 영원히 못 잡는다 — "회선이 살아있는지"와 "앱이 일할 수
    있는지"가 다른 질문이라는 걸 보여주는 자리
  - 다룬 것: SO_KEEPALIVE 가 기본 꺼짐, kill 과 전원 차단의 차이(개발 중 Ctrl+C
    테스트로는 재현 불가), tcp_retries2 로 약 15분, 브라우저가 ping 에 자동 pong
    한다는 함정, 브로커가 죽으면 Will 이 하나도 안 나감, MQTT 5 의 0x04 와
    Will Delay Interval, 경로상 유휴 타임아웃(NLB 350초 조정 불가)
  - 온라인 상태는 `접속 시 retained online + Will retained offline + 정상 종료 시
    직접 발행 + 타임스탬프 + 오래된 것 훑어 내리기` 로 정리했다

- [x] 09. **인스턴스를 2대로 늘리는 순간 같은 작업이 두 번 돈다** — 작업 선점 (`/jobclaim/`)
  - 출처: `blur` §3 · §5, `solution-review` §2-1 / 유형 D는 3/6 저장소
  - 선점 방식 4단이 `blur` 의 시도 궤적 그대로다
    (인메모리 `synchronized` → read-then-write → 조건부 UPDATE → `FOR UPDATE SKIP LOCKED`)
  - 기대값 (`T` = 폴링 주기 1초, `g` = 읽기–쓰기 간격 5ms)
    - 초과 실행률: 인메모리 `(N-1)·100%`, read-then-write `(1-(1-g/T)^(N-1))·100%`, 나머지 0
    - 헛돈 시도/건: 조건부 UPDATE `N-1`, 나머지 0
  - **N=1 이면 넷 다 0.** 이 페이지의 전부가 그 사실이다 — 부하가 아니라 대수에서 나오는 결함이라
    단위 테스트·로컬·스테이징이 전부 1대면 네 방식이 구별되지 않는다
  - read-then-write 를 가장 위험한 자리로 배치했다. 100% → 0.5% 라 고쳐진 것처럼 보이지만
    0 이 아니다. `solution-review` §2-1 이 지적한 그 갭
  - 조건부 UPDATE 와 SKIP LOCKED 를 나눈 이유: 둘 다 중복 0 이지만 조건부는 진 `N-1` 대가
    매번 헛돈다. SKIP LOCKED 가 왜 존재하는지가 여기서 나온다
  - 좀비 행 + 회수 타임아웃까지 넣었다 (`solution-review` §2-1 의 "회수 경로가 없다").
    회수 타임아웃이 최대 처리 시간보다 짧으면 선점이 도로 중복이 된다는 함정도 명시
  - 마지막 층은 멱등성 — 선점을 아무리 정확히 해도 at-least-once 라는 걸 못 박았다
