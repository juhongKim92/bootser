- [x] 05. MQTT QoS 0/1/2 — 한 번만 전달한다는 약속의 값 (`/mqtt/`)
  - 세 레인이 **같은 속도로 패킷을 하나씩** 소비한다. 같은 패킷 예산에서 끝낸

  - 기대값: QoS 1 패킷 `(1+q)/q²`, QoS 2 는 그 두 배, QoS 1 중복 `p/q`

- [x] 06. WebSocket 다중 서버와 Redis Pub/Sub — 서버를 늘렸더니 메시지가 안 간다 (`/websocket/`)
  - 전파 방식 3단(로컬만 → 전체 브로드캐스트 → 방별 채널)을 손잡이 하나로 오가게 했다.
    도달률과 팬아웃이 동시에 움직이는 걸 한 화면에서 본다
  - 기대값: 도달률 로컬만 `s`·Pub/Sub `1-d`, 팬아웃 브로드캐스트 `N`·방별 `N(1-(1-s)^k)`,
    헛일 `(1-s)^k` (`s = (1-d)/N`, `k` = 방 크기)
  - 발행 주체를 방 밖(서버로 들어온 이벤트)에 두었다. 구성원 중에서 뽑으면
    "발행자는 반드시 접속 중"이 조건으로 붙어 도달률이 `1-d` 보다 낮게 나온다 —
    작성 중 시뮬레이션으로 잡았다
  - 다룬 것: 대수에서 나오는 문제라 1대 환경에선 재현 불가, 스티키 세션이 답이 아닌 이유,
    발행 서버가 자기 소켓에 직접 쓰면 안 되는 이유, Redis Cluster 의 일반 PUBLISH 는
    전 노드로 퍼진다(샤드 Pub/Sub 필요), 구독 해지 누락, 배포 시 재연결 폭주
  - 공백 메우기는 `Pub/Sub + 저장소 + seq 재동기화` 로 정리했다
- [x] 07. Keep-alive 와 죽은 커넥션 + LWT — 서버는 두 시간 동안 살아있다고 믿는다 (`/keepalive/`)
  - **시간이 흐르지 않는 실험대.** 손잡이를 움직이면 그 조건의 사건 순서를 통째로
    다시 계산해 그린다 — 2시간 11분을 실시간으로 기다릴 수 없으니
  - 탐지 지연: TCP 기본 `7200 + 75×9 = 7875초`, TCP 튜닝 `KA + 10×6`, 앱 `1.5×KA`.
    `KA + 60 = 1.5KA` 는 KA=120 에서 만난다 — 주기를 2분보다 길게 잡으면
    앱 keep-alive 가 OS 튜닝보다 오히려 느려진다
  - 끊김 방식에 **앱 멈춤**을 넣은 게 핵심이다. 커널이 프로브에 대신 ACK 하므로
    TCP keepalive 로는 영원히 못 잡는다 — "회선이 살아있는지"와 "앱이 일할 수
    있는지"가 다른 질문이라는 걸 보여주는 자리
  - 다룬 것: SO_KEEPALIVE 가 기본 꺼짐, kill 과 전원 차단의 차이(개발 중 Ctrl+C
    테스트로는 재현 불가), tcp_retries2 로 약 15분, 브라우저가 ping 에 자동 pong
    한다는 함정, 브로커가 죽으면 Will 이 하나도 안 나감, MQTT 5 의 0x04 와
    Will Delay Interval, 경로상 유휴 타임아웃(NLB 350초 조정 불가)
  - 온라인 상태는 `접속 시 retained online + Will retained offline + 정상 종료 시
    직접 발행 + 타임스탬프 + 오래된 것 훑어 내리기` 로 정리했다

  - 선점 방식 4단이 `blur` 의 시도 궤적 그대로다

    - 초과 실행률: 인메모리 `(N-1)·100%`, read-then-write `(1-(1-g/T)^(N-1))·100%`, 나머지 0

  - **N=1 이면 넷 다 0.** 이 페이지의 전부가 그 사실이다 — 부하가 아니라 대수에서 나오는 결함이라

  - 조건부 UPDATE 와 SKIP LOCKED 를 나눈 이유: 둘 다 중복 0 이지만 조건부는 진 `N-1` 대가

  - 좀비 행 + 회수 타임아웃까지 넣었다 (`solution-review` §2-1 의 "회수 경로가 없다").

- [x] 12. **응답을 순서로 맞추면 언제 어긋나는가** — correlationId (`/correlation/`)
  - 출처: `vwc` §1.1, `solution-review` §1-1
  - 매칭 4단(단일 슬롯 → FIFO 큐 → 직렬화 → correlationId) × 교란 4종
    (없음 · 순서 뒤집힘 · 지각 응답 · 중복 응답) = 16칸 격자
  - **고정 배치가 아니라 끊기지 않는 스트림으로 모델링했다.** 지각·중복이 해를
    끼치려면 다른 요청이 아직 대기 중이어야 하는데, 배치 모델에서는 그게 안 생긴다
  - 동시 4건 · 교란 40% 실측
    - 교란 없음: 단일 슬롯 오매칭 100%, 나머지 0
    - 순서 뒤집힘: FIFO 51%, 직렬화·correlationId 0
    - 지각 응답: FIFO 80%, **직렬화 60%**, correlationId 0 (유실 40%만)
    - 중복 응답: FIFO·직렬화 100%, correlationId 0
  - **가장 중요한 발견 두 가지**
    1. 위치 매칭은 한 번 어긋나면 **스스로 복구하지 못한다** — 그래서 오매칭률이
       100% 에 붙는다. 정렬이 다시 맞을 이유가 없다
    2. **동시 요청이 1건이어도 지각·중복은 오매칭을 만든다** (위치 매칭 셋 다 ~55%).
       동시성 문제가 아니라 식별자 부재 문제라는 뜻이고, `solution-review` §1-1 의
       "직렬화" 대안이 부분적 해법인 이유다
  - 오매칭이 유실보다 나쁜 이유를 계기 3분할로 보여준다 — 유실은 예외로 시끄럽지만

### DB 정확성

- [ ] 15. **둘 다 확인했고 둘 다 통과했다** — 격리 수준과 write skew (`/writeskew/`)
  - 09 의 짝. 09 가 "누가 이 작업을 가져가나"라면 이쪽은 "각자 본 것이 다르다"
  - **lost update 가 아니라 write skew 로 잡는다.** lost update 는 09 와 4단 구조가
    똑같아져 반복으로 읽힌다. write skew 는 각자 자기 행만 건드리므로
    행 락으로 안 잡히고 `Repeatable Read` 로도 안 막힌다
  - 예시: 당직자가 최소 1명 있어야 하는데 둘이 동시에 "나 말고 한 명 더 있네"를
    확인하고 둘 다 빠진다
  - 손잡이: 격리 수준(RC / RR / Serializable) · 동시 트랜잭션 수 · 읽기–쓰기 간격
  - 반전
    - **RR 이 막아줄 것 같은데 안 막는다.** 여기가 핵심
    - Serializable 은 막지만 직렬화 실패를 던진다 — "켜면 끝"이 아니라
      **재시도 코드가 반드시 필요하다.** 안 쓰면 정합성 문제가 500 으로 형태만 바뀐 것
    - PostgreSQL 의 RR 은 스냅샷 격리라 표준 RR 과 다르다(팬텀을 막는다).
      "MySQL 에서 되던 게 안 된다"가 여기서 나온다
    - 충돌이 없으면 세 수준이 구별되지 않는다 — 09 · 11 의 수미상관과 같은 결
  - Spring: `@Transactional(isolation = ...)` · `SQLState 40001` ·
    `@Retryable` 을 **트랜잭션 밖에서** 걸어야 하는 프록시 순서 함정
  - 01(MVCC)과 이어져 DB 시리즈가 생긴다

### 캐시

- [ ] 16. **TTL 이 끝나는 순간** — 캐시 스탬피드 (`/stampede/`)
  - 03 과 묶여 캐시 축이 둘이 된다
  - 손잡이: 요청률 `λ` · 재계산 시간 `T` · TTL ·
    방식 4단(무방비 → 뮤텍스/싱글플라이트 → 확률적 조기 만료 → stale-while-revalidate)
  - 기대값
    - 무방비: 만료 한 번당 중복 재계산 `λ·T`.
      초당 500건 · 재계산 200ms → **한 번의 만료가 100개의 동시 재계산**
    - 확률적 조기 만료: `now - T·β·ln(rand()) ≥ expiry`.
      재계산이 오래 걸리는 키일수록 일찍 나선다
    - **뮤텍스는 중복을 없애지만 대기를 만든다** — 나머지 `λ·T - 1` 건이 기다린다.
      공짜가 없다는 05 의 결론과 같은 모양
  - 배포 직후 캐시를 한꺼번에 채우면 TTL 도 같이 끝난다 → 만료가 동기화된다.
    TTL 에 지터를 주는 이유이자 14 의 파도와 같은 현상
  - 반전: 히트율 99% 인데 장애가 난다. 1% 가 몰려서 오니까.
    **평균은 멀쩡한데 순간이 무너진다** — 13 의 젠센 부등식이 다른 옷을 입고 나온다
