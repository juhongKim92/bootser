### 1-1. 해시링 recipe 3 — 5노드 수치와 6노드 수치가 섞임

**위치**: `public/hashring/index.html`, `public/en/hashring/index.html`
— recipe 3 "가상 노드를 늘린다", 그리고 본문 "가상 노드가 필요한 이유" 표

recipe 3 은 "가상 노드를 1 → 20 → 160 → 200" 이라고만 적는다.
독자가 초기화 상태에서 슬라이더를 움직이면 **노드는 6개**다.

| vnode | 본문 주장 | 6노드 실측 | 5노드 실측 |
|---|---|---|---|
| 1 | 46.9% / 4.20× | **46.9% / 4.20×** | 41.4% / 4.21× |
| 20 | 17.0% / 1.54× | 20.4% / 1.85× | **17.0% / 1.54×** |
| 160 | 5.9% / 1.16× | 8.3% / 1.27× | **5.9% / 1.16×** |
| 200 | 5.5% / 1.16× | **5.5% / 1.16×** | 5.8% / 1.15× |

첫 값과 마지막 값은 6노드, 가운데 두 값은 5노드다.
"가상 노드가 필요한 이유" 표(1 → 47%, 20 → 17%, 160 → 6%)도 같은 혼합이다.

**재생 시나리오는 정확하다.** SCENE 2단계에서 노드를 하나 빼므로 3단계 시점에 5노드가
되고, scene 문안의 17% · 5.9% 는 맞다. 시나리오에서 뽑은 숫자를 recipe 로 옮기면서
전제(노드 수)가 빠진 것이다.

**고치는 법** — 둘 중 하나
- recipe 3 과 표에 "노드 5 기준" 을 명시한다
- 또는 6노드 실측값(46.9 → 20.4 → 8.3 → 5.5, 4.20 → 1.85 → 1.27 → 1.16)으로 바꾼다

> **채택**: 6노드 실측값. recipe 3 은 초기화 상태에서 슬라이더만 움직이라고 하므로
> 독자가 화면에서 보는 값과 본문이 일치해야 한다. 전제("초기화 상태(노드 6)에서")도 함께 명시했다.
> 표에는 "노드 6 기준" 을 헤더에 넣었다.

### 1-4. 해시링 recipe 6 — 결론은 맞고 이유가 틀림

**위치**: `public/hashring/index.html`, `public/en/hashring/index.html`
— recipe 6 "가상 노드 개수는 나중에 못 바꾼다"

> 가상 노드 개수를 바꾸면 **링 위 모든 지점의 위치가 달라지므로** 사실상 전체 재배치가 …

지점은 `hash('node-A#' + i)` 라서 **기존 지점은 그대로 있고 점이 추가·제거될 뿐**이다.
실측이 이를 드러낸다.

```
vnode   1 ->  20 :  84%  (1257/1500)
vnode   1 -> 160 :  85%  (1274/1500)
vnode   1 -> 200 :  86%  (1288/1500)
vnode  20 -> 160 :  75%  (1120/1500)
vnode 160 -> 200 :  16%  ( 235/1500)   <- 기존 160개 지점이 유지되어 이만큼만 이동
vnode 200 ->   1 :  86%  (1288/1500)
```

"70% 이상" 이라는 수치와 "운영 중엔 못 바꾼다" 는 결론은 성립한다.
설명만 **"지점이 추가·제거되며 구간 경계가 대부분 다시 그어진다"** 로 고치면 된다.

### 1-5. MVCC — 권장 진단 쿼리가 가이드와 어긋남

**위치**: `public/mvcc/index.html`, `public/en/mvcc/index.html`

가이드 recipe 1 은 이렇게 말한다.

> `pg_stat_activity` 에서 상태만 보지 말고 **`backend_xmin`** 이 잡혀 있는지를 함께 봐야 합니다.

그런데 "현장에서 확인할 것" 의 쿼리는 `age(backend_xid)` 만 뽑는다.
이 페이지의 주인공인 **읽기 전용 장기 트랜잭션은 `backend_xid` 가 NULL** 이라
그 쿼리에서 `xid_age` 가 비어 나온다.

```sql
-- 지금
SELECT pid, state, age(backend_xid) AS xid_age, ...

-- 이렇게
SELECT pid, state,
       age(backend_xid)  AS xid_age,
       age(backend_xmin) AS xmin_age,   -- 읽기 전용 장기 트랜잭션은 이쪽에 잡힌다
       now() - xact_start AS duration, query
FROM pg_stat_activity
WHERE state != 'idle' OR backend_xid IS NOT NULL
ORDER BY xact_start
LIMIT 10;
```

## 2. 방법론적 한계 — 거짓은 아니나 오해 소지

### 해시링의 CV 6%대는 키 표본 잡음 바닥에 닿아 있다

키 1500개 · 6노드면 링이 **완벽히 균등해도** 다항분포 잡음만으로 CV ≈ 5.8% 가 나온다.

```
Var = n·p·(1-p) = 1500 × (1/6) × (5/6) = 208.3
sd  = 14.4,  mean = 250  ->  CV ≈ 5.8%
```

그래서 측정값이 단조롭지 않다. 노드 수별 실측:

| 노드 | vnode 1 | vnode 20 | vnode 160 | vnode 200 |
|---|---|---|---|---|
| 3 | 29.0% / 1.88× | 6.1% / 1.14× | 5.9% / 1.14× | 4.0% / 1.09× |
| 4 | 19.5% / 1.74× | 12.0% / 1.35× | **2.4% / 1.07×** | **7.2% / 1.21×** |
| 5 | 41.4% / 4.21× | 17.0% / 1.54× | 5.9% / 1.16× | 5.8% / 1.15× |
| 6 | 46.9% / 4.20× | 20.4% / 1.85× | 8.3% / 1.27× | 5.5% / 1.16× |
| 7 | 64.2% / 19.27× | 20.5% / 1.84× | 8.3% / 1.27× | 5.7% / 1.23× |
| 8 | 75.9% / 26.50× | 10.2% / 1.36× | 6.3% / 1.18× | 3.9% / 1.13× |

4노드는 vnode 160 에서 2.4% 인데 200 에서 7.2% 로 **오히려 나빠진다.**
"160 → 6%" 는 링의 불균형보다 표본 잡음을 재고 있는 셈이다.

주장 방향(가상 노드가 분포를 고르게 만든다)은 맞다. 다만 절대값을 그대로 읽으면 안 된다.
본문 callout 에 한 줄 덧붙이는 것으로 충분하다.

## 3. 사소한 정밀도 문제

| # | 위치 | 내용 |
|---|---|---|
| 3-1 | 해시링 "실제로 어디에 쓰이나" | **DynamoDB** 항목. Dynamo 논문(2007)이 대중화시킨 건 맞지만 논문의 Dynamo 와 서비스 DynamoDB 는 다른 시스템. 항목명을 "Dynamo (논문)" 으로 두는 편이 정확 |
| 3-2 | Raft "현장에서 확인할 것" | 지표명 `wal_fsync_duration_seconds` → 실제는 `etcd_disk_wal_fsync_duration_seconds` |
| 3-3 | MVCC callout | "특정 테이블만이 아니라 **전역**입니다" — 정확히는 같은 데이터베이스 범위. 다른 DB 의 장기 트랜잭션은 일반 테이블 정리를 막지 않는다(공유 카탈로그는 별개) |
| 3-4 | GC "G1이 멈추는 지점" | "실험대에서 힙 16GB **까지 목표가 지켜지는**" vs 실측 208ms(목표 200ms). recipe 2 는 "거의 지킴" 으로 정직하게 씀 — 본문 쪽 표현만 살짝 과함 |
| 3-5 | 해시링 recipe 2 · UI | − 버튼이 항상 **마지막 노드**만 제거한다. 그래서 "어떤 노드가 죽느냐에 따라 3%가 될 수도, 30%가 될 수도" 를 독자가 실험으로 확인할 수 없다(실제 분포는 6.7%~28.3%) |

| 16GB / 500 | 208ms | 353ms | 11 | 95.7% | 0.28ms | — |

### 해시링 — recipe 1 · 2 · 4 · 5 전부 일치

```
[초기 6노드/vnode1]  CV 46.9%  최대/최소 4.20×  최대 424  최소 101
                     막대 257/424/106/345/267/101
[노드 제거]          링 101/1500 · 7%   나머지 연산 1263/1500 · 84%
                     막대 257/424/106/446/267        <- D 가 345 -> 446
[vnode160 5->4노드]  링 324/1500 · 22%  나머지 연산 1214/1500 · 81%
                     막대 387/371/379/363
[vnode160 4->5노드]  링 324/1500 · 22%  나머지 연산 1214/1500 · 81%
```

"이 값은 죽은 노드가 갖고 있던 몫과 정확히 같습니다" — F 가 갖던 101개, 이동 101개로 정확히 일치.
"이론 1/5 = 20%" 대비 실측 22% 도 타당. 나머지 연산 84% 는 `1 - 1/6 ≈ 83.3%` 와 부합.

### Raft

- 5노드 중 3개 정지 후 20.4초 관찰 → term **0 → 13**, 리더 0. 본문 "13 부근" 정확
- 3:2 분단 시 진영 2개(과반 확보 1 / 미달 1), 소수파 term 만 상승
- 분단 복구 시 `N4 리더 사임 — 더 높은 term 을 봄 (term 1 → 2)` — 페이지의 핵심 주장 그대로 재현
- 과반 겹침 논증, CheckQuorum, Pre-Vote, 로그 최신성 검사 설명 모두 타당

### MVCC — 시나리오 10단계 전부 일치

| 단계 | 크기 | live | dead | bloat | horizon |
|---|---|---|---|---|---|
| 00 초기 | 24KB | 16 | 0 | 0% | 101 |
| 01 B UPDATE×3 | 24KB | 16 | 3 | 16% | 102 |
| 02 VACUUM | 24KB | 16 | 0 | 0% | 102 |
| 03 A BEGIN+SELECT | 24KB | 16 | 0 | 0% | 102 |
| 04 B UPDATE×3 | 24KB | 16 | 3 | 16% | 102 |
| 05 VACUUM | 24KB | 16 | **3** | 16% | 102 |
| 06 B UPDATE×3 ×2 | **32KB** | 16 | 9 | 36% | 102 |
| 07 VACUUM | 32KB | 16 | **9** | 36% | 102 |
| 08 A COMMIT | 32KB | 16 | 9 | 36% | **105** |
| 09 VACUUM | **32KB** | 16 | 0 | 0% | 105 |
| 10 | 32KB | 16 | 0 | 0% | 105 |

05·07 에서 회수가 막히고, 06 에서 페이지가 늘고, 09 에서 전부 회수됐는데도 크기가
그대로인 것까지 본문 서술과 정확히 일치. 실제 PostgreSQL 동작과도 부합한다.

특히 **"BEGIN 만으로는 안 막히고 SELECT 부터 막힌다"** 는 이 페이지의 핵심 주장은
모델에서도(`horizon()` 이 `snap`/`xid` 가 null 이면 미래를 가리킴) 실제 PostgreSQL 에서도 참이다.

> API 가 몇 개뿐이라 `node:vm` + 최소 DOM 스텁으로 충분하다. 자세한 것은
> `tools/README.md` 를 본다. 아래 jsdom 메모는 이 감사(2026-08-11) 당시의 기록으로 남긴다.

당시 재현 방법 —

- 페이지를 jsdom 으로 로드 (`runScripts: 'dangerously'`, `resources: 'usable'`)
- jsdom 미구현 API 보강이 필요하다
  - `window.matchMedia` — jsdom 에 없다. 최소 스텁을 `beforeParse` 로 주입
  - `requestAnimationFrame` — `pretendToBeVisual: true` 필요
  - `<canvas>` — `npm i canvas` 필요 (해시링·Raft 페이지)
- 루트 절대경로(`/shared/...`)를 상대경로로 치환해야 `file://` 에서 로드된다
- 슬라이더는 `el.value = ...` 후 `dispatchEvent(new Event('input'))`
- 값은 DOM 에서 읽는다 — `#nG1` `#nZ` `#spread` `#moved` `#bars .val` `#readouts` `#events`
