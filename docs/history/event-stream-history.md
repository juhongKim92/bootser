# Vueroid Event Stream 개발 트러블슈팅 히스토리

> 분석 대상: `d303925`(2026-02-27, 최초 커밋) ~ `74e0ea5`(2026-06-12) / 총 115 커밋
> 분석 방법: 커밋 메시지 + 실제 diff 대조

블랙박스 단말이 TCP(FlatBuffers)로 밀어 넣는 H.264/AAC/GPS 프레임을 Netty로 받아
MP4로 먹싱하고, 썸네일·스프라이트를 만들어 S3에 올린 뒤 DB에 기록하는 서버다.
아래는 그 과정에서 실제로 터졌던 문제와 해결 내역을 계층별로 정리한 것이다.

## 1. 네트워크 / 세션 계층 (Netty)

### 1-1. Spring과 결합하니 Netty 서버가 그냥 죽어버림
- **커밋**: `68107d8` (03-05), `ebe9f96` (04-02)
- **증상**: 단독 실행에서는 멀쩡하던 Netty 서버가 Spring Boot에 붙이면 기동 직후 종료됨.
- **원인**: `@PostConstruct`에서 띄운 바인딩 스레드가 데몬 스레드로 남아 컨텍스트 기동 흐름과
  생명주기가 어긋났고, `@PreDestroy` 종료도 `shutdownGracefully()`를 던져만 놓고
  완료를 기다리지 않아 종료 타이밍이 비결정적이었음.
- **해결**:
  1. 1차 — 바인딩 전용 스레드를 `setDaemon(false)`로 명시해 JVM이 먼저 내려가지 않도록 함.
  2. 2차 — `@PostConstruct/@PreDestroy`를 버리고 `SmartLifecycle`로 전환.
     `serverChannel`을 필드로 들고, 종료 시 채널 → workerGroup → bossGroup 순으로
     `syncUninterruptibly()`로 **완료를 기다린 뒤** 스레드를 인터럽트하도록 정리.

### 1-2. 패킷 최대 길이 부족 (그리고 조용한 회귀)
- **커밋**: `1e088f6` (03-31), `ff18899` · `b9c31ac` · `3d5672b` (04-07)
- **증상**: 큰 I-프레임 수신 시 프레임 디코더에서 잘려나감.
- **경과**: `65536` → `655_360`으로 10배 확장. 그런데 며칠 뒤 값이 다시 `65536`으로
  되돌아가 있는 것을 발견(`ff18899` 커밋 메시지: *"655360 이였는데 언제 65536으로 롤백됬지.."*).
  이후 `1MB` → 최종 `4MB`로 확장하면서 **서버 디코더와 클라이언트 디코더, 그리고
  중간 파이프 버퍼(`PipedInputStream`)를 모두 같이 4MB로 맞춤**.
- **교훈**: 파이프라인상의 크기 제약이 서버/클라/버퍼 세 군데에 흩어져 있어 한 곳만 고치면
  회귀한다. 세 값은 항상 같이 움직여야 함.

### 1-3. TLS + AWS NLB 환경에서 마지막 패킷이 유실됨 ★
- **커밋**: `aafb260` (04-10), `b7ab1df` · `354e837` · `ef8a252` · `0ba4dd1` (04-13)
- **증상**: 단말이 데이터를 다 보냈는데 서버에 마지막 구간이 도착하지 않은 채 세션이 끊김.
- **원인**: 단말이 전송 완료 직후 소켓을 닫아버림. TLS 종단이 NLB에서 이루어지므로,
  NLB가 복호화한 데이터를 EC2로 다 넘기기 **전에** FIN이 먼저 도달해 뒷부분이 버려짐.
- **시행착오**: 처음엔 `channelInactive`에서 가상 스레드로 3초 재우고 finalize 하는
  우회책(`aafb260`)을 넣었으나, 버리는 주체가 Netty가 아니라 NLB라서 무의미했음 → 삭제.
- **해결(클라이언트와 합의)**: 서버가 **EOS를 수신하면 EOS를 그대로 에코**해 주고,
  단말은 그 응답을 받은 뒤에 소켓을 닫는다.
  - `354e837`: `writeAndFlush()`가 비동기 Future이므로 리스너 안에서 finalize → close 하도록 수정.
    (그 전엔 flush 완료 전에 닫아버림)
  - `ef8a252` → `0ba4dd1`: 에코 응답에도 1바이트 타입 프리픽스가 필요해 추가.
    처음엔 `Unpooled.wrappedBuffer(new byte[]{TYPE_EOS}, originalMessage.array())`로 짰는데
    다이렉트 버퍼는 `array()`로 접근할 수 없어 실패 → `ctx.alloc().buffer()`에
    타입 바이트와 페이로드를 직접 복사하고 `release()`까지 명시하는 방식으로 교정.

### 1-4. close 이벤트가 아예 오지 않는 단말 존재
- **커밋**: `2316ca2` (06-10)
- **증상**: 정상 종료도, `channelInactive`도 발생하지 않고 세션이 영원히 살아 있음
  → 먹싱이 마무리되지 않아 파일이 생성되지 않음.
- **해결**: 파이프라인에 `IdleStateHandler(readIdleTimeoutSeconds, 0, 0)`를 추가하고
  `userEventTriggered`에서 `READER_IDLE`을 잡아 `"reader-idle-timeout"` 사유로
  세션을 강제 종료. 기본 10초이며 `netty.read-idle-timeout-seconds`로 조정 가능.
  파이프라인 구성은 `configurePipeline()`으로 분리해 테스트 가능하게 만듦
  (`NettyServerPipelineTest`, `FlatBufferHandlerIdleTimeoutTest`).

### 1-5. 이벤트 루프에서 먹싱을 직접 수행
- **커밋**: `40e01a0` (04-10), `14fd975` (04-23)
- **증상**: 프레임 수신 핸들러가 `recordFrame()`으로 인코딩/IO를 직접 수행 → 이벤트 루프 블로킹.
- **해결**: `FlatBufferHandler`는 **타입 판별과 세션 라우팅만** 담당하고,
  `MuxingSession`이 `LinkedBlockingQueue`에 스냅샷을 적재 → 가상 스레드 워커가 소비.
  전체 동시 먹싱은 `Semaphore(MAX_CONCURRENT_MUX = 4)`로 제한.
- **후속 버그**: 큐가 비면 워커를 반납했다가 재제출하는 구조에서, 반납/재제출 경합 시
  `finishMuxing()`이 호출되지 않아 **inactive 시 먹싱이 되지 않는 현상** 발생.
  `14fd975`에서 워커 루프를 상태 머신으로 재작성하고 `terminal` 플래그를 도입해,
  실제로 종료된 경우에만 `isFinished`/`releaseResources()`를 타도록 수정.

## 2. 프로토콜 / 파싱

### 2-1. 불필요한 Message 래핑 제거
- **커밋**: `e7237c3` (04-02), `7bc8181` (04-02)
- 데이터 패킷을 `Message`로 한 번 더 감싸던 구조를 걷어내고 `FramePacket`을 직접 루트로 파싱.
  동시에 `TYPE_EOS = 3` 컨테이너 타입을 도입해 EOS를 별도 분기로 처리.
- 프레임 번호는 단말이 준 값을 검증하던 로직(누락 카운트, 기대값 추적)을 버리고
  **수신 순서 기반 자동 증가**로 단순화. 근거는 *"TCP라 프레임이 엇갈려서 올 일 없음"*.

### 2-2. MediaInfo(C 구조체) 파서가 실제 바이너리와 불일치 ★
- **커밋**: `84377bb` · `259c13f` · `2594e83` (04-07), `5db3757` (05-07)
- **증상**: 헤더 파일 기준으로 작성한 `FDLCloudMediaInfo` 파서가 실제 단말 데이터와 어긋나
  해상도/프레임레이트/비트레이트가 엉뚱하게 나옴.
- **접근**: 추측을 포기하고 **수신 바이트를 파일로 덤프 + 헥스 프리뷰 로깅**을 먼저 넣은 뒤,
  실측 데이터로부터 오프셋을 역산해 파서를 통째로 재작성.
  (`m_dwWidth`, `m_pConfig[512]`, `FDLVideoShape` 등 실제 정렬/패딩 반영)
- **후속 문제**: 펌웨어 버전에 따라 구조체 크기가 다른 단말이 발견됨.
- **최종 해결**: 크기 기반 레이아웃 자동 판별 도입.

  | 레이아웃 | VideoInfo | VideoShape | 전체 크기 |
  |---|---|---|---|
  | V1 (레거시) | 853 | 128 | 8499 |
  | V2 (현행) | 889 | 164 | 8823 |

  `resolveLayout(data.length)`로 분기하고, 최소 길이 검증도 `SIZE_MEDIA_INFO_V1` 기준으로 완화.

## 3. 먹싱(Muxing) — 가장 오래 헤맨 영역

### 3-1. 먹싱 구현 방식 3회 전환
| 단계 | 방식 | 커밋 | 전환 이유 |
|---|---|---|---|
| 1 | JavaCV `FFmpegFrameGrabber` + Piped 스트림 | 초기 | 디코딩까지 수행해 느리고, 파이프 버퍼 데드락 위험 |
| 2 | 외부 `ffmpeg` 프로세스 호출 (stdin 파이프) | `50dd01e` (04-09) | grabber 우회. stderr tail 20줄 로깅 추가 |
| 3 | **libav 직접 mux** (`AVFormatContext` / `AVPacket`) | `2edb771` (04-09) | 프로세스 오버헤드 제거, 타임스탬프 완전 제어 |

- 2단계에서 `-use_wallclock_as_timestamps 1`로 fps를 강제하던 옵션은
  오히려 타임스탬프를 망가뜨려 삭제하고, 대신 `pts<=0 && duration<=0` 패킷을
  버리는 예외 처리로 대체(`c1768d0`).

### 3-2. 단말이 보내는 타임스탬프를 믿을 수 없음 ★
- **커밋**: `44d9bd1` (04-23), `402e9d2` (05-28)
- **증상**: 프레임 간 타임스탬프가 갑자기 수 초씩 점프 → 재생 시 멈춤/길이 이상.
- **해결**: 수신 타임스탬프를 그대로 쓰지 않고 **`frameCount * 기본 프레임 duration`으로
  자체 생성**. 대신 진단을 위해 점프를 감지해 로그로 남김
  (임계값 `max(500ms, 기본 duration × 10)`, 최대 10회까지만 경고).

### 3-3. 타임스케일 1000 → 90000
- **커밋**: `05c6669` · `982b6b6` (04-24)
- 기본 타임베이스 1000으로는 정밀도가 부족했고 플레이어에 따라 길이가 어긋남.
  최종 remux 단계에 `-video_track_timescale <resolveVideoTimeScale()>`을 **강제로 지정**.

### 3-4. 회사(NCN) atom 규격 맞추기
- **커밋**: `2545b18` · `457a43b` · `b23a87a` · `3e3b213` · `a0dbc29` (04-15),
  `f41b4ae` (04-16), `dc402f2` (04-24)
- 미들웨어팀이 만든 실제 파일과 바이트 단위로 비교하기 위해 로깅 커밋만 4회
  (`e473d43`, `f28ea4a`, `2105f36`, `4d5f1e6`) 쌓아가며 규격을 역추적함.
- **작업 내용**
  - 비디오만 먹싱하던 것을 **비디오 + 오디오 + 텍스트(GPS/G센서)** 전부 처리하도록 확장.
    DATA 패킷에서 `GPSR`/`SENS` 엔트리를 수집해 별도 박스로 append.
  - `free` 박스 안에 `RECO` 시그니처로 회사 규격 메타데이터를 심음.
    `Recovery` 브랜드일 때만 `fvcr` 마킹, 빌드 정보가 있을 때만 user free atom 추가.
- **버그 1 — atom 버퍼 capacity 오산**(`3e3b213`): `8 + 4 + 4*7 + configLen`처럼
  필드 수를 손으로 세다 실제 기록 필드 수와 어긋나 `BufferOverflowException`.
  → 1차로 `8 + 4 + (8 * 4) + configLen`로 교정.
  → 2차(`a0dbc29`)로 **애초에 세지 않도록** `ByteArrayOutputStream + DataOutputStream`으로
  payload를 먼저 쓰고 길이를 나중에 채우는 `createRecoAtom(writer)` 헬퍼로 전면 리팩터링.
- **버그 2 — chunk offset 패치 오류**(`f41b4ae`): 삽입 atom 뒤에 `free`를 한 번 더 쓰면서
  `moov`의 `stco` 오프셋 보정값에 `free.size()`가 이중 반영됨.
  → `free` 재기록을 제거하고 보정값을 `insertedBytes - free.size()`로 정정.

### 3-5. SPS/PPS를 extradata로 넣으려던 시도 → 롤백
- **커밋**: `bf8f8d9` → `65b2264` → `346afcf` → `402e9d2` (전부 05-28, 하루)
- **가설**: SPS_PPS 패킷을 `frameCount`에 포함시키지 말고
  `AVCodecParameters.extradata`로 주입하면 더 규격에 맞는 파일이 나올 것.
- **결과**: `applyVideoExtradata()`(`BytePointer` + `AV_INPUT_BUFFER_PADDING_SIZE`)를
  넣었다 뺐다 반복한 끝에, ffprobe/썸네일 검증에서 개선이 확인되지 않아
  **"예전에 잘되던 상태로 롤백"**. 타임스탬프도 frameIndex 기반 추정 로직을 걷어내고
  단순 `frameCount * duration` 방식으로 되돌림.
- **교훈**: 같은 날 4커밋으로 왕복한 사례. 검증 기준(ffprobe 결과)을 먼저 고정하고
  들어갔다면 왕복 횟수를 줄일 수 있었을 것.

### 3-6. 프레임이 하나도 안 들어왔는데 remux를 시도함
- **커밋**: `26aa48c` (05-14)
- `hasMuxedVideoFrames()` 가드를 추가해 `frameCount == 0`이면 remux/후처리를 통째로 스킵하고,
  왜 0인지 알 수 있도록 패킷 종류별 카운터(I/P/B/SPS_PPS/audio/data/unknown)를 전부 로깅.

### 3-7. 실제 파일 길이와 파싱된 길이가 다름
- **커밋**: `59e8add` (05-14)
- **원인**: `grabber.getLengthInTime()`이 컨테이너 헤더 값을 그대로 반환해
  실제 비디오 스트림 길이와 어긋나는 케이스 존재.
- **해결**: 3단계 폴백 체인으로 교체.
  1. 비디오 스트림의 `duration × time_base` (가장 정확)
  2. `프레임 수 ÷ 프레임레이트`로 추정
  3. 기존 `getLengthInTime()`

## 4. 썸네일 / 스프라이트

### 4-1. 추출 성능 — 매번 seek → ffmpeg 원샷
- **커밋**: `f4eb4d0` (04-08, 최초 개발), `b4d6156` (webp 전환),
  `982b6b6` · `467cb4a` (04-24)
- 초기엔 `FFmpegFrameGrabber`로 캡처 지점마다 seek + `Java2DFrameConverter`로 이미지 변환 +
  Java2D로 스프라이트 합성 → 느림.
- **해결**: `filter_complex`로 개별 썸네일과 타일 스프라이트를 **ffmpeg 한 번에** 생성.
  ```
  fps=1/N, scale=160:90, split=2 [a][b]; [a]tile=10x10[sprite]; [b]fifo
  ```
  Java2D/ImageIO 의존을 전부 제거.

### 4-2. 고정 1초 간격 → 목표 프레임 수 기반 간격 계산
- **커밋**: `982b6b6` (04-24)

  (10×10 = 최대 100장 상한).

### 4-3. 스프라이트에 검은 줄이 남음
- **커밋**: `c7a283f` (05-11)
- **증상**: `tile=10x10`이 항상 10줄을 만들어, 30초 영상(3줄분)이면 나머지 7줄이 검게 남음.
- **해결**: 실제 생성된 썸네일 개수를 센 뒤 `spriteColumnCount`를 계산해 필요한 줄만
  타일링하도록 분리(`runFfmpegSpriteBuild`). DB의 `spriteColumnCount`도 상수 대신 실측값 저장.

### 4-4. 썸네일 개수 오차 / 출력 경로
- `5e47601` (04-22): 업로드 목록에 스프라이트 자체가 섞여 있어 `totalThumbnailCount`가 1 과다
  → `-1` 보정. 이후 `467cb4a`에서 아예 `thumbnailCount`를 명시적으로 들고 다니도록 정리.
- `b289c8e` (06-09): 썸네일을 영상 파일과 **같은 디렉토리**에 뿌리고 있었음(1 depth 부족).

  회귀 방지 테스트(`createThumbnailAssets_writesOutputsUnderFileBaseNameDirectory`) 추가.

### 4-5. 업로드 직렬화
- `05c6669` (04-24): 썸네일을 for 루프로 하나씩 S3에 올리던 것을

  스프라이트 `AwsInfo`는 파일명(`sprite.webp`)으로 필터링해 골라내도록 변경.

## 6. 반복해서 드러난 패턴

1. **바이너리 규격은 문서가 아니라 실측이 정답이었다.**
   MediaInfo 파서(2-2)와 회사 atom 규격(3-4) 모두, 헤더/문서 기준 구현이 실패하고
   *덤프 → 헥스 로깅 → 오프셋 역산* 사이클로만 해결됐다.
   `mediaInfo.bin` 덤프 로직이 계속 남아 있는 이유이기도 하다.

2. **먼저 관측 가능하게 만들고 고쳤다.**
   `[logging]` 태그 커밋이 10개 이상이고, `44d9bd1`·`26aa48c`처럼
   "방어 코드 + 로깅"이 한 커밋에 묶인 경우가 많다.
   `Session report` 한 줄에 15개 넘는 카운터를 실어 원격 단말 이슈를 로그만으로 좁혔다.

3. **단말 입력값은 신뢰하지 않는 방향으로 수렴했다.**
   프레임 번호(2-1), 타임스탬프(3-2), close 이벤트(1-4) 전부
   "단말이 준 값 검증" → "서버가 자체 생성/자체 판단"으로 바뀌었다.

4. **네트워크 경계(AWS NLB, TLS)가 애플리케이션 로직을 바꿨다.**
   3초 대기 같은 애플리케이션 레벨 우회는 통하지 않았고,
   결국 프로토콜에 EOS 에코라는 왕복을 추가하는 것으로만 해결됐다(1-3).

5. **왕복이 잦았던 구간은 검증 기준이 없던 구간이다.**
   패킷 크기(1-2), SPS/PPS extradata(3-5), atom capacity(3-4)가 대표적이다.
   반대로 후반부(`b289c8e`, `2316ca2`, `74e0ea5`)는 테스트 코드를 함께 넣으면서
   한 번에 마무리됐다.
