# 트러블슈팅 해결책 리뷰 — 그 선택은 정당했는가

> 대상: `docs/history/` 하위 6개 히스토리 문서
> (`blur-history` · `bsd-history` · `event-stream-history` · `sr-history` · `vwc-history` · `vwc-media-history`)
>
> 각 문서가 "무엇이 터졌고 어떻게 고쳤는가"를 기록했다면,
> 이 문서는 **그 해결이 원인을 제거했는지, 더 싼 방법은 없었는지**를 되짚는다.
> 결과를 아는 상태에서 보는 것이므로 당시 판단을 비난하려는 목적이 아니라,
> 다음 프로젝트에서 같은 지점에 다시 서지 않기 위한 재료로 쓴다.

## 1. 재검토가 필요한 해결 6건

### 1-1. 🔴 MQTT 응답을 FIFO로 매칭 — 오매칭이 남아 있다

**출처**: `vwc-history` §1.1 (`8b3482b`)

**채택한 해결**
`pendingMap`에 serial 키로 future를 `put` 하던 것을 키별 `ConcurrentLinkedQueue`로 바꿔,
응답이 오면 **가장 오래 기다린 요청부터 FIFO로** 완료시킨다.

**평가**
future 덮어쓰기(유실)는 확실히 제거됐다. 그러나 **오매칭은 제거되지 않았다.**
FIFO는 "먼저 보낸 요청의 응답이 먼저 온다"는 가정에 서 있는데, 이 가정은 보장되지 않는다.

- 요청 A가 10초 타임아웃으로 큐에서 제거된 직후 A의 응답이 도착하면 → **B의 future가 A의 응답으로 완료된다.**
- 단말이 응답 순서를 뒤집어 보내면 그대로 교차 매칭된다.
- 재전송(QoS 1의 중복 전달)이 발생하면 하나의 응답이 두 요청을 완료시킬 수 있다.

히스토리 문서는 *"단말 펌웨어 변경 없이 서버 코드만으로 해결했다는 점이 중요하다"* 고 서술했으나,
이는 장점이 아니라 **정확성을 포기하고 얻은 트레이드오프**로 기록되어야 한다.

**더 나은 방법**
1. **correlationId를 프로토콜에 넣는다.** 요청 payload에 UUID를 실어 보내고 응답이 그대로 되돌려주면,
   키를 `(serial, correlationId)`로 잡을 수 있어 매칭이 결정론적이 된다.
   MQTT 5를 쓴다면 `Correlation Data` / `Response Topic` 속성이 표준으로 있으므로 payload를 건드릴 필요도 없다.
2. 펌웨어 변경이 불가능하다면, 최소한 **serial+command 단위로 동시 요청을 1건으로 직렬화**(세마포어 또는 큐 depth 1)해야
   FIFO 가정이 성립한다. "동시에 두 번 들어올 수 있다"를 허용한 채 FIFO로 붙이는 것이 가장 나쁜 조합이다.
3. 지금 구조를 유지한다면 타임아웃으로 제거한 future의 키를 **tombstone으로 잠시 남겨**,
   지각 응답이 다음 요청에 붙지 않도록 버리는 방어가 필요하다.

> §8.2에서 *"응답이 안 온다"* 의 원인이 **구독 누락 → 타임아웃 상향 → future 유실** 세 겹이었다고 정리했다.
> correlationId가 있었다면 세 겹 중 두 겹은 로그 한 줄로 즉시 분리됐을 문제다.

### 1-2. 🔴 `limit(1000)` — 성능 문제를 정확성 문제로 바꿨다

**출처**: `vwc-history` §2.3 (`4e65eb5`)

**채택한 해결**
상한 없는 전체 조회를 막기 위해 `DeviceQueryDslRepository.findByCountry` /
`UaQueryDslRepository.findAll`에 `limit(1000)`을 추가.

**평가**
EAGER→LAZY 전환은 옳다. 그러나 `limit(1000)`은 **조용한 절단(silent truncation)** 이다.
단말이 1,001대가 되는 순간 1,001번째부터는 존재하지만 보이지 않는 데이터가 된다.
예외도 로그도 없이 결과가 틀려지는데, 이는 히스토리 문서가 §10-2에서 스스로
*"조용히 실패하는 코드가 가장 늦게 발견된다"* 고 지적한 바로 그 유형이다.
성능 방어를 위해 도입한 장치가 §4.3(확장자 검증 누락)과 같은 계열의 버그를 새로 만들었다.

**더 나은 방법**
- **페이징으로 전환.** `Pageable` 또는 keyset 페이징(`WHERE id > :lastId ORDER BY id LIMIT n`)으로
  전량을 나눠 가져오면 절단이 없다. 국가별 단말 목록은 본질적으로 페이징 대상이다.
- 페이징이 당장 어렵다면 **상한 도달을 관측 가능하게** 만들어야 한다.
  `limit(1001)`로 조회해 1001건이면 `log.warn` + 메트릭 증가 → 상한이 실제로 물리기 전에 알람이 뜬다.
- 진짜 상한이 필요한 방어 목적이라면 조용한 절단 대신 **예외**가 맞다.
  "너무 많으니 조건을 좁혀라"는 400 응답이 틀린 목록보다 낫다.

### 1-3. 🔴 스레드풀 큐를 무제한으로 — 거부를 OOM과 맞바꿨다

**출처**: `blur-history` §2 3단계 (`9ee4061`)

**채택한 해결**
```
CompletableFuture$AsyncSupply rejected from ThreadPoolExecutor
[pool size = 8, active threads = 8, queued tasks = 2000, completed tasks = 0]
```
`ThumbnailUploader`의 큐 상한 2000을 초과해 태스크가 거부되자, **큐를 무제한으로 변경.**

**평가**
`RejectedExecutionException`은 사라지지만, 거부는 **백프레셔가 작동했다는 신호**였다.
소비 속도(8스레드)보다 생산 속도가 빠르다는 사실 자체는 바뀌지 않았고,
큐를 열어두면 그 격차가 힙에 쌓인다. `completed tasks = 0`이 함께 찍힌 것은
소비가 아예 진행되지 않고 있었다는 뜻이라 더 위험하다 — 무제한 큐에서는 이 상태가
`OutOfMemoryError`로 나타나며, 그때는 어느 단계가 막혔는지 스택으로 알기 어렵다.

**더 나은 방법**
- 유계 큐를 유지하고 **`CallerRunsPolicy`** 로 거부를 처리한다. 생산자 스레드가 직접 업로드를 수행하게 되어
  자연스럽게 생산 속도가 떨어진다(가장 저렴한 백프레셔).
- 또는 `Semaphore`로 인플라이트 태스크 수를 제한하고, 획득 실패 시 생산자를 블로킹한다.
- 근본적으로는 **4단계에서 실제로 한 일**(FFmpeg 1회 호출 스트림 추출, `37a84b2`)이 정답이었다.
  생산량 자체를 1/N로 줄이자 큐 문제가 사라졌다. 3단계는 4단계에 도달하기까지의 시간 벌기였을 뿐이다.

### 1-4. 🟠 썸네일을 Virtual Thread로 병렬화 — 도구 선택이 틀렸다

**출처**: `blur-history` §2 2단계 (`ec3fc55`, `a0e6f6d` → `7c05bf7` 회귀)

**채택한 경과**
Virtual Thread 도입 → 스레드 과다 생성 → 개수 제한(30→10) → **일반 Thread로 회귀** → 2중 for문 step 처리.

**평가**
Virtual Thread의 이점은 "블로킹 I/O 대기 중 캐리어 스레드를 반납"하는 데 있다.
그런데 여기서 하는 일은 `ProcessBuilder`로 **OS 프로세스를 띄우는 것**이다.
프로세스 생성 비용과 FFmpeg의 CPU 점유는 스레드 모델로 줄어들지 않고,
오히려 값싸게 만들어지는 Virtual Thread 때문에 **동시 프로세스 수가 폭증**했다.
스레드 수 제한 → 회귀 → 2중 for문은 전부 이 오진에서 파생된 뒤처리다.

동시에 이 사례는 좋은 교훈이기도 하다. 히스토리 §11-5의 결론 —
*"병렬화는 2차 문제를 낳아, 호출 자체를 줄이는 편이 더 효과적이었다"* — 이 정확하다.

**더 나은 방법**
- **먼저 호출 횟수를 본다.** N초 영상에 FFmpeg N회는 병렬화 대상이 아니라 설계 오류다.
  `-vf fps=1/N` 원샷 추출(4단계, `37a84b2`)이 첫 수정이었어야 한다.
- 외부 프로세스 실행은 반드시 **고정 크기 풀 + 유계 큐**로 감싼다. 동시 프로세스 수는
  CPU 코어 수(또는 GPU 세션 수)에 묶이는 물리 자원이므로, 값싼 스레드로 늘릴 수 있는 대상이 아니다.
- Virtual Thread를 쓸 자리는 오히려 §4-5의 **S3 업로드 병렬화**(`event-stream` `05c6669`)다.
  거기서는 실제로 네트워크 블로킹이 지배적이고, 실제로 그렇게 적용됐다.

### 1-5. 🟠 ClamAV 연동을 3번 갈아엎었다 — 데몬 설정을 먼저 봤어야

**출처**: `blur-history` §8

**채택한 경과**
TCP INSTREAM(실패) → UNIX 도메인 소켓 `junixsocket`(불안정) → 검사 자체 주석 처리 → `clamdscan` CLI 호출.

**평가**
최종 선택(CLI 호출)은 실용적으로 옳다. 이미 FFmpeg·추론 앱을 `ProcessBuilder`로 호출하고 있었으므로
운영 일관성도 맞다. 문제는 **1단계 실패 원인의 진단**이다.

*"clamd가 TCP 리스닝을 하지 않아 실패"* — 이것은 애플리케이션 결함이 아니라 **데몬 설정 문제**다.
`clamd.conf`에 `TCPSocket 3310` 한 줄을 추가하고 재시작하면 해결되는 사안이었다.
그런데 연동 방식을 바꾸는 쪽으로 진행해 2·3단계를 소모했다.
3단계에서 결국 OS 권한(`sudo usermod -aG datagrp clamav`)을 부여한 것을 보면,
서버 설정을 만질 수 없는 상황도 아니었다.

**더 나은 방법**
- 외부 데몬 연동이 "연결 거부"로 실패하면, **애플리케이션 코드보다 데몬 설정과 `ss -lntp` / `netstat` 을 먼저** 본다.
  연결 자체가 성립하지 않는 실패는 대체로 우리 쪽 코드 문제가 아니다.
- 소켓 프로토콜을 직접 구현하기 전에 **검증된 클라이언트 라이브러리**를 찾는다.
  ClamAV INSTREAM 프로토콜은 자바 구현체가 여럿 있고, 이는 "직접 구현"과 "CLI 호출"의 중간 비용이다.
- 현재의 CLI 방식에도 남은 비용이 있다: **파일당 프로세스 생성**. 업로드 트래픽이 늘면
  §1-4와 같은 프로세스 폭증에 그대로 노출되므로, 스캔 호출도 유계 풀 뒤에 두어야 한다.

### 1-6. 🟠 무한 재시도를 "미검출 가드"로 막았다 — 다음 원인에는 무력하다

**출처**: `sr-history` §5 (`156a34b`)

**채택한 해결**
LPR 응답 직후 `isPlateNotFound()`로 판정해 `LprRestoreException(404)`를 던진다.
이 예외가 기존 catch절에 걸려 즉시 FAILED 확정 + 실패 알림 발송.

**평가**
해당 케이스는 정확히 막혔고, 조기 실패 판정 자체는 옳다.
그러나 **무한 재시도라는 구조적 결함은 그대로 남아 있다.**
문제의 구조는 이렇다.

```
runMultiPlateExtract 실패
  → 좁은 catch(IllegalStateException|IOException|InterruptedException)를 벗어나면
  → 상위 lambda catch(Exception)
  → addWaitList 재큐잉
  → 시도 횟수 제한 없음 → 영원히 반복
```

`isPlateNotFound`는 이 루프로 새어나가던 **원인 하나**를 막았을 뿐이다.
디스크 가득 참, S3 권한 만료, LPR 서버 다운 등 다른 원인이 생기면 같은 루프가 다시 돈다.
히스토리 §7 "남은 작업 #3"이 제시한 대응(`NoSuchElementException`을 catch 대상에 추가) 역시
**예외 타입을 하나씩 늘려가는 대증요법**이라 같은 한계를 갖는다.

**더 나은 방법**
`bsd-history` §2에서 이미 답이 나와 있다 — **재시도 배치에는 영구 실패 상태값과 시도 횟수가 필수다.**

1. `dv_file`에 `attempt_count` 컬럼을 두고 재큐잉할 때마다 증가시킨다.
   `attempt_count >= MAX_ATTEMPTS`면 재큐잉하지 않고 FAILED 확정 + 알림.
2. 재큐잉 조건을 **화이트리스트**로 뒤집는다. 지금은 "이 예외들만 실패 처리, 나머지는 재시도"인데,
   **"일시적 오류로 알려진 것만 재시도, 나머지는 실패"** 가 안전한 기본값이다.
   (네트워크 타임아웃·5xx는 재시도, 그 외 전부 실패)
3. 재시도 간 **지수 백오프**를 넣는다. 매분 재시도는 실패 케이스에서 외부 서버를 함께 두들긴다.

> 같은 조직의 다른 저장소(`bsd-taxi-api`)가 두 달 전 21억 시퀀스를 태우며 얻은 교훈이
> 이 저장소로 전파되지 않았다. §4-2 참고.

## 2. 방향은 맞으나 구멍이 남은 해결

### 2-1. 🟡 추론 중복 실행 — DB 상태값은 맞지만 "조건부 UPDATE"여야 완전하다

**출처**: `blur-history` §3

**경과**: `synchronized` 위치 교정 → 프로세스 분리 → `InferenceState.RESERVE_INFERENCE` 상태 도입.

**평가**
인메모리 컬렉션에서 DB 상태값으로 옮긴 방향은 정확하다(§11-3의 결론도 같다).
다만 "다운로드 완료 즉시 상태를 갱신한다"만으로는 **여전히 read-then-write 갭**이 남는다.
두 인스턴스가 동시에 `state = DOWNLOADED`인 행을 읽으면 둘 다 `RESERVE_INFERENCE`로 쓰고 둘 다 진행한다.
단일 인스턴스에서는 드러나지 않지만, 스케일아웃하는 순간 원래 증상이 그대로 돌아온다.

**더 나은 방법**
```sql
-- 조건부 원자적 UPDATE로 "선점"하고, 영향 행 수가 1일 때만 진행
UPDATE ai_file
   SET state = 'RESERVE_INFERENCE', reserved_at = now(), reserved_by = :instanceId
 WHERE id = :id AND state = 'DOWNLOADED';
-- rowCount == 1 인 경우에만 추론 실행
```
또는 PostgreSQL이라면 작업 큐 표준 패턴인 **`SELECT ... FOR UPDATE SKIP LOCKED`** 로
픽업 자체를 경합 없이 만든다. 어느 쪽이든 인메모리 컬렉션도, 별도 락도 필요 없다.

추가로 `reserved_at`이 있으면 **선점 후 죽은 작업**(프로세스 강제 종료)을 타임아웃으로 회수할 수 있다.
현재 구조에는 이 회수 경로가 없어, `RESERVE_INFERENCE` 상태로 영원히 멈춘 행이 생길 수 있다.

### 2-2. 🟡 크레딧 동시성 — 원자적 UPDATE는 맞고, 멱등성이 빠졌다

**출처**: `blur-history` §5

**채택한 해결**
낙관적 락(`@Version`)을 걷어내고 비관적 락 / 원자적 UPDATE로 통일.
소비·환불은 `UPDATE` + `SELECT … FOR UPDATE`, 충전은 `PESSIMISTIC_WRITE`.

**평가**
잔액 차감처럼 **충돌률이 높고 재시도가 UX를 해치는** 도메인에서 낙관적 락을 버린 것은 옳다.
낙관적 락은 충돌이 드물 때만 이득인데, 인기 있는 결제 경로는 정확히 그 반대다.

두 가지가 남는다.

**(1) `SELECT FOR UPDATE`와 원자적 UPDATE의 중복**
잔액 검증을 SQL 조건에 넣었다면 선행 잠금은 불필요하다.
```sql
UPDATE credit SET balance = balance - :amount
 WHERE user_id = :uid AND balance >= :amount;
-- rowCount == 0  →  잔액 부족 (락 없이 판정)
```
이 한 문장이 원자성과 검증을 동시에 처리한다. 락을 먼저 잡으면 동일 사용자 요청이 직렬화되어
처리량만 떨어진다.

**(2) 멱등성 키가 없다**
문서에 "프로세스 실패 시 포인트 환불"(`ae31b49`)이 나오는데, **환불/차감이 중복 실행되는 경로**에 대한
언급이 없다. 클라이언트 재시도, 게이트웨이 타임아웃 후 재요청, 배치 재실행이 모두 이중 차감/이중 환불을 만든다.
락은 동시성을 막지 성능 재실행을 막지 못한다.

**더 나은 방법**
- 요청마다 `idempotency_key`(UUID)를 받아 `credit_history`에 **unique 제약**으로 걸고,
  중복 삽입 시 기존 결과를 그대로 반환한다.
- 더 나아가면 잔액 컬럼 대신 **append-only 원장(ledger)** 구조가 정석이다.
  모든 증감을 행으로 남기고 잔액은 합계(또는 스냅샷 캐시)로 유도하면,
  이중 차감이 unique 제약으로 원천 차단되고 감사 추적도 공짜로 얻는다.
  §5의 "크레딧 히스토리에 소모 사유 추가"(`5541cd2`)는 이미 그 방향으로 가고 있었다.

### 2-3. 🟡 self-proxy로 트랜잭션 분리 — 스프링이 제공하는 표준 도구가 있다

**출처**: `vwc-history` §2.2 (`13c6cb1`)

**채택한 해결**
`UaService.updateLoginDtm`에서 로그인시각 갱신과 MQTT 발행을 **self-proxy로 분리**해
커밋·커넥션 반납 후 발행하도록 변경.

**평가**
"트랜잭션 경계와 외부 I/O 경계를 겹치지 않는다"는 원칙(§10-5)은 정확하고 중요하다.
`getEndPoint`에 `@Transactional(NOT_SUPPORTED)`를 준 것, 롤백이 필요한
`sendRemoveKVSChannel`을 동기 + 예외 전파로 바꾼 것 모두 옳다.

다만 **self-proxy(자기 자신을 프록시로 주입해 호출)** 는 스프링에서 안티패턴으로 취급된다.
순환 참조를 만들고, AOP를 이해해야만 읽히며, 프로젝트의 `CLAUDE.md`가 경계하는
self-invocation 문제와 정확히 같은 뿌리(프록시 우회)에서 나온 우회책이다.

**더 나은 방법**
```java
// 커밋 이후 발행 — 스프링 표준
@Transactional
public void updateLoginDtm(...) {
    ua.updateLoginDtm(now);
    eventPublisher.publishEvent(new LoginRecordedEvent(serial));
}

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onLoginRecorded(LoginRecordedEvent e) {
    mqttService.publish(...);   // 커밋·커넥션 반납 후 실행
}
```
`@TransactionalEventListener(AFTER_COMMIT)`는 정확히 이 목적의 도구다.
프록시 트릭이 없고, 발행 로직이 트랜잭션 코드에서 분리되며, 테스트도 이벤트 단위로 쪼갤 수 있다.
발행 실패를 흘려보내면 안 되는 경우라면 **Outbox 패턴**(booster 프로젝트가 이미 채택한)으로 올라가면 된다.

### 2-4. 🟡 단말 타임스탬프를 전부 버림 — A/V 드리프트가 남는다

**출처**: `event-stream-history` §3-2 (`44d9bd1`, `402e9d2`)

**채택한 해결**
수신 타임스탬프를 쓰지 않고 `frameCount * 기본 프레임 duration`으로 PTS를 자체 생성.
점프는 로그로만 남긴다.

**평가**
"단말 입력값을 신뢰하지 않는다"(§6-3)는 방향은 이 도메인에서 대체로 옳다.
다만 이 방식은 **모든 프레임이 정확히 등간격으로 도착한다**고 가정한다. 실제로는

- 단말이 부하로 프레임을 드롭하면 → 영상이 실제보다 **짧게** 만들어지고 그만큼 느리게 재생된다
- 가변 프레임레이트(저조도에서 fps를 떨어뜨리는 펌웨어)면 → 전 구간이 어긋난다
- **오디오는 별도 타임라인**이므로 긴 세션에서 A/V 싱크가 점진적으로 벌어진다(드리프트)

§3-3에서 타임스케일을 90000으로 올린 것도 정밀도 문제였는데, 정밀도를 올려도
**기준 자체가 추정값**이면 오차는 남는다.

**더 나은 방법**
전부 버리는 대신 **단조 증가 보정(monotonic clamp)** 을 쓴다.
```
if (ts <= lastTs || ts - lastTs > JUMP_THRESHOLD) {
    ts = lastTs + defaultDuration;   // 이상값만 대체
}
```
정상 구간에서는 단말 타임스탬프의 실제 간격을 살리고, 역행·과도 점프만 보정한다.
이미 점프 감지 로직(`max(500ms, duration×10)`)을 넣어두었으므로 **감지 결과를 로그가 아니라 보정에 쓰면 된다.**

검증은 ffprobe로 고정한다 — 산출 MP4의 `duration`과 세션 수신 시간(wallclock)의 차이가
임계치를 넘으면 경고. 히스토리 §6-5가 지적한 *"왕복이 잦았던 구간은 검증 기준이 없던 구간"* 에 대한 대응이기도 하다.

### 2-5. 🟡 가짜 엔티티를 음수 id로 구분 — 규약이 코드에만 있다

**출처**: `vwc-history` §4.1 (`042ca2a`)

**채택한 해결**
설정 행이 없을 때 음수 id의 가짜 엔티티를 합성해 반환하고,
저장 시 `UserAlarmSettingFacade`에서 **id 부호로 분기**해 음수면 INSERT.

**평가**
`Batch update returned unexpected row count`는 사라진다. 그러나 "음수 id = 미영속"이라는 규약이
**타입이 아니라 관례로만 존재**한다. 이 엔티티를 다루는 새 코드가 생길 때마다 분기를 다시 써야 하고,
빠뜨리면 같은 예외가 다른 경로에서 재발한다. 히스토리 스스로도
*"합성 엔티티를 만들 때는 표식을 두고 반드시 분기해야 한다"* 고 적었는데, "반드시"에 강제력이 없는 게 문제다.

**더 나은 방법**
1. **조회 응답을 엔티티가 아니라 DTO로.** 기본값 채우기는 표현 계층의 일이지 영속 계층의 일이 아니다.
   `AlarmSettingView(값들…, boolean persisted)` 로 내려주면 부호 관례가 필요 없다.
2. 또는 쓰기 경로를 **upsert로 통일**한다.
   ```sql
   INSERT INTO uc_service_set (ua_id, ...) VALUES (...)
   ON CONFLICT (ua_id) DO UPDATE SET ...
   ```
   존재 여부를 분기할 필요 자체가 사라진다. (`ua_id` unique 제약이 전제)
3. 최소한 지금 구조를 유지한다면 `isSynthetic()` 메서드를 엔티티에 두어
   부호 검사가 한 곳에만 존재하게 하고, 회귀 테스트로 고정한다.

### 2-6. 🟡 `IncorrectResultSizeDataAccessException` — 조회는 고쳤고 원인은 남았다

**출처**: `vwc-media-history` §6-3 (`77175a9`)

**채택한 해결**
`updateFileViewDtm(serial, fileName)`의 (serial, fileName) 단건 조회를
**파일 id 기준 `findById`** 로 변경(자연키 → PK).

**평가**
호출부가 이미 `DvFile`을 갖고 있었으므로 PK 조회로 바꾼 것은 명백히 옳다.
그러나 **"같은 단말에 동일 파일명 행이 왜 중복 존재하는가"** 는 다뤄지지 않았다.

**더 나은 방법**

- 중복이 **버그**라면 → `UNIQUE (serial, file_name)` 제약을 걸어 유입을 차단하고 기존 중복을 정리한다.
  제약이 있어야 다음 사람이 자연키로 조회해도 안전하다.
- 어느 쪽인지 결정하지 않고 넘어간 것이 이 항목의 실제 미해결 부분이다.

### 2-7. 🟡 회전(rotation)을 파이프라인 진입점마다 정규화

**출처**: `blur-history` §1-1

**채택한 해결**
썸네일 / HLS / 렌더링 / 좌표 CSV 네 경로에서 각각 rotation을 소비하도록 처리.
최종적으로 *"메타데이터가 살아있으면 영상만 재인코딩"* 방식으로 정리.

**평가**
1년 넘게 6번 재발한 항목이다. 히스토리의 교훈 — *"rotation은 한 곳에서 처리할 수 없다"* — 은
경험적으로는 사실이지만, **구조적으로는 그렇지 않다.**
문제는 rotation을 파이프라인 **전 구간에 흘려보낸 것**이다.
회전 메타데이터가 살아있는 한 모든 소비자가 각자 해석해야 하고, 소비자가 늘 때마다 재발한다.

주목할 점은 **마지막 해결(`e4e789c`)이 사실상 정답에 가까웠다**는 것이다.
"재인코딩해서 FFmpeg이 알아서 회전을 반영하게 한다"를 **렌더링 시점이 아니라 업로드 직후에** 했다면,
그 아래 모든 단계는 rotation을 몰라도 됐다.

**더 나은 방법 — 진입점 1회 정규화(bake)**
```
업로드 → [정규화 단계] 회전을 픽셀에 굽고 rotate 메타 제거 → 이후 전 파이프라인은 rotation-free
```
- 썸네일·HLS·렌더링이 각각 회전을 처리할 필요가 없어진다
- **좌표계 역변환(`edcf891`)과 `AI_FILE.rotation` 컬럼(`e7cc354`) 자체가 불필요해진다** — 이 둘이 가장 비쌌다
- CUDA transpose 순서 문제(`8b578fa`)도 정규화 단계 한 곳에만 존재하게 된다

비용은 업로드당 1회 재인코딩이다. 이 프로젝트는 어차피 추론·HLS·렌더링에서 여러 번 인코딩하고 있으므로
추가 비용이 크지 않고, 6회의 재발 비용보다 훨씬 싸다.

> 정규화가 불가능한 제약(원본 무손실 보존 의무 등)이 있었다면,
> 최소한 `rotation`을 `int`가 아니라 **값 객체**로 감싸고 좌표 변환을 그 타입에서만 수행하게 해야 했다.
> §11-2의 *"단위를 타입으로 감싸지 않은 대가"* 가 여기에도 그대로 적용된다.

### 2-8. 🟡 배치 건별 `REQUIRES_NEW` — 방향은 맞고 입도가 과하다

**출처**: `bsd-history` §3-3 (`6f78ad2`)

**채택한 해결**
거대 `@Transactional`을 제거하고 레코드 1건당 `REQUIRES_NEW` 독립 트랜잭션 + 건별 `try/catch`.

**평가**
"거대 트랜잭션 = 커넥션 장기 점유 + 전량 롤백"이라는 진단은 정확하고, 분리는 옳다.
호출부를 non-transactional로 만들어 `REQUIRES_NEW`가 커넥션을 2개 잡지 않도록 한 것도 정확하다.

다만 **건당 트랜잭션은 커넥션 획득/커밋 왕복이 건수만큼 발생**한다.
수십만 건 배치라면 이 오버헤드가 지배적이 될 수 있다.

**더 나은 방법**
- **청크 단위 트랜잭션**(예: 100~1000건)이 일반적인 절충안이다.
  실패 시 해당 청크만 롤백하고, 재시도에서 건별로 좁혀 들어가는 2단계 전략이면
  진행분 보존과 처리량을 모두 얻는다.
- 이미 §3-3 1단계에서 Slice 페이징(1000건)을 도입했으므로, **페이지 = 트랜잭션 단위**로 맞추면
  구조 변경 없이 적용된다.
- 처리량 요구가 크지 않다면 현행 유지도 무방하다. 다만 배치 소요 시간을 메트릭으로 걸어두고
  건수 증가에 따라 재검토할 지점을 정해두는 편이 좋다.

### 2-9. 🟡 웹소켓 진행률 1초 스로틀 — conflation이 더 정확하다

**출처**: `blur-history` §9 (`b42ddde`)

**채택한 해결**
이전 전송 시점 기준 1초 경과분만 전송.

**평가**
단순 고정 주기가 아니라 경과 기준으로 구현한 것은 잘 한 것이다.
다만 스로틀은 **버려지는 값 중에 마지막 값이 포함될 수 있다**.
진행률이 98%에서 멈추고 100%가 스로틀에 걸려 사라지면 클라이언트는 완료를 못 본다.
(§9의 *"`ready` 전송 시 퍼센트 100 대신 0 전송"*, *"배치 완료 후 READY 전송 순서 조정"* 같은
후속 커밋들이 이 계열의 증상으로 보인다.)

**더 나은 방법**
진행률은 **최신값만 의미 있는 값**이므로 스로틀이 아니라 **conflation**이 맞다.
- 최신 값을 `AtomicReference`에 덮어쓰고 1초 타이머가 그 값을 읽어 보낸다 → 값이 버려지지 않고 **뒤로 미뤄질 뿐**
- 종료 상태(100%, FAILED)는 **스로틀을 우회해 즉시 전송**한다. 상태 전이는 중간값이 아니다

## 3. 모범 사례로 남길 해결

되짚어도 더 나은 대안이 떠오르지 않는, 그대로 재사용할 만한 해결들이다.

| 해결 | 출처 | 왜 좋았나 |
|---|---|---|
| **MyBatis resultMap 로드 테스트** (`d426a19`) | `vwc` §6.1 | XML 매핑 오류는 컴파일에 안 걸리고 해당 API 호출 시에만 터진다. 이걸 CI로 끌어온 것이 대규모 리네임 작업의 안전망이 됐다. **6개 문서 전체를 통틀어 가장 파급력 큰 대응** |
| **검증을 부수효과보다 먼저 + 영구 실패 상태 `'E'`** (`3bbc9eb`) | `bsd` §2 | 21억 시퀀스 소모의 원인을 정확히 짚었다. "시퀀스는 롤백되지 않는다"는 통찰과 재시도 배치의 종료 조건을 함께 잡은 드문 사례 |
| **atom 길이를 세지 않고 스트림으로** (`a0dbc29`) | `event-stream` §3-4 | `BufferOverflowException`을 "계산식 교정"이 아니라 "계산 자체를 없애기"로 푼 것. 필드가 늘어도 재발하지 않는다 |
| **격자를 실측 개수로 산정** (`c7a283f`, `468215e`) | `event-stream` §4-3, `vwc-media` §5-1 | 외부 도구의 산출을 추정하지 않고 확인 후 할당. 두 프로젝트에서 독립적으로 같은 결론에 도달했다 |
| **OSIV 누수의 오독을 밝혀낸 진단** (`5d2f090`) | `bsd` §1-2 | 스택 최상단(17ms 쿼리)이 범인이 아님을 밝힌 과정. `ProxyLeakTask`가 "빌린 시점"의 스택을 찍는다는 사실까지 파고든 것이 핵심 |
| **폴백 제거** (`d4e2886`) | `vwc-media` §5-2 | null을 기본값으로 채우던 편의를 걷어냈다. "조용한 데이터 오염 < 명시적 실패"라는 올바른 우선순위 |
| **광범위 catch 제거** (`b81bfef`, `d63edb4`) | `vwc-media` §2-3, §4-1 | 예외를 뭉개던 코드를 없애자 실제 원인이 즉시 드러났다. 고치는 대신 지우는 것이 답인 사례 |
| **EOS 에코 프로토콜** (`b7ab1df`) | `event-stream` §1-3 | 3초 대기 같은 애플리케이션 우회가 통하지 않음을 확인하고, TLS/NLB 경계 문제는 프로토콜 왕복으로만 풀린다는 결론에 도달. 진단이 정확했다 |
| **stage 변수로 실패 단계 분리** (`cc76c9f`) | `sr` §4 | `download failed` 하드코딩이 오진을 유발한다는 발견 자체가 좋다. (개선안은 아래 참고) |

> `cc76c9f` 보완 제안: `stage` 문자열 대신 **단계별 예외 타입**(`DownloadFailedException` 등)으로 구분하면
> 로그 포맷이 아니라 타입으로 분기할 수 있고, `stage`를 **MDC에 넣으면** 그 구간의 모든 로그에 자동 부착된다.
> catch절 한 곳이 아니라 구간 전체가 관측 가능해진다.

## 4. 여러 프로젝트를 관통한 반복 패턴

개별 문서의 회고는 각자 잘 정리되어 있다. 여기서는 **문서를 가로질러야 보이는 것**만 다룬다.

### 4-1. 같은 버그가 두 프로젝트에서 독립적으로 발생했다

| 버그 | A | B |
|---|---|---|
| 스프라이트 격자를 **예상 프레임 수**로 먼저 할당 → 빈 칸이 검게 남음 | `event-stream` §4-3 (`c7a283f`, 05-11) | `vwc-media` §5-1 (`468215e`, 07월) |
| **OSIV** 기본값 true로 커넥션 핀닝 | `bsd` §1-2 (`5d2f090`, 06-30) | `vwc-media` §6-4 (`e0a58a6`) |
| S3 키 조립 시 **선행 슬래시로 `//` 발생** | `event-stream` §5 (`eaece48`, 03-06) | `vwc-media` §2-2 (`dbb15ad`) / `blur` §7 |
| 대규모 **컬럼 리네이밍 후 XML 매퍼 누락** | `vwc` §6.1 / `vwc-media` §6-1 (3회 보정) | `blur` §6-2 |

앞의 두 건은 **A가 B보다 앞서 해결됐는데도 B에서 다시 발생**했다.
같은 조직·같은 스택인데 교훈이 저장소 경계를 넘지 못했다는 뜻이다.

**대응**
- 저장소별 히스토리와 별개로, **조직 공통 체크리스트**를 한 곳에 둔다(§6이 그 초안이다).
- 특히 OSIV·S3 키 조립·JPA 기본 설정처럼 **신규 프로젝트 초기 설정에서 한 번에 끝나는 항목**은
  프로젝트 템플릿(또는 `libs/storage-db` 같은 공통 모듈의 기본값)에 박아두는 편이 문서보다 확실하다.
  이 저장소의 `booster`가 `libs/*` 구조를 갖고 있는 것은 그 자리를 이미 마련해 둔 셈이다.

### 4-2. "무한 재시도"는 두 저장소에서 각각 대형 장애를 만들었다

| | `bsd` §2 | `sr` §5 |
|---|---|---|
| 증상 | 매분 재시도 → 시퀀스 21억 소진 → COPY 전면 실패 | 동일 uuid 무한 재큐잉, 상태가 FAILED로 확정 안 됨 |
| 직접 원인 | 검증이 부수효과 뒤에 있었음 | 예외가 좁은 catch를 빠져나가 상위 재큐잉 경로로 |
| **공통 근본 원인** | **재시도 루프에 종료 조건이 없었다** | 동일 |
| 채택한 해결 | 영구 실패 상태 `migrate_flag='E'` ✅ | 특정 케이스 가드 🟠 |

`bsd`는 근본(종료 조건)을 잡았고 `sr`은 케이스 하나를 막았다.
**두 사건이 같은 문제라는 인식이 없었기 때문**으로 보인다.

> **재시도 루프를 만들 때의 최소 요건 3가지**
> 1. **시도 횟수 상한** (`attempt_count` + `MAX_ATTEMPTS`)
> 2. **영구 실패 상태** — 재시도 대상에서 제외되는 종료 상태가 반드시 있어야 한다
> 3. **재시도 대상은 화이트리스트로** — "이것만 실패 처리"가 아니라 "이것만 재시도"

### 4-3. 타임아웃 상향은 세 번 등장했고 전부 유예였다

| 조치 | 실제 원인 | 규명까지 |
|---|---|---|
| `vwc` MQTT future 3s → 10s (`3a8e9cb`) | future 덮어쓰기 + 구독 누락 | 8일 |
| `sr` LPR timeout 70s → 300s (`4f2cf12`) | (추론 시간 자체가 김 — 이 건은 타당) | — |
| `blur` `ProcessBuilder` 60s → 120s (`b40b3ad`) | 대용량 처리 시간 (타당하나 상한 없음) | — |

`vwc` §10-1의 회고 — *"타임아웃 상향은 진단이 아니라 유예"* — 는 정확하다.
다만 나머지 둘은 실제로 작업 시간이 긴 경우라 상향 자체가 틀리지 않았다.
**구분 기준**은 이렇다.

- 정상 케이스의 소요 시간 분포를 알고 있고 그 p99보다 타임아웃이 짧았다 → **상향이 정답**
- 왜 오래 걸리는지 모른 채 늘렸다 → **유예**. 원인 티켓을 반드시 남긴다

`blur`의 120초는 "최소 대기 시간"이라 상한이 없는 것으로 보이는데,
**대용량 파일에서 무한 대기가 되지 않는지** 확인이 필요하다.

### 4-4. 평문 크리덴셜이 두 저장소에서 미해결로 남아 있다

`vwc` §5.2와 `vwc-media` §9에 동일한 항목이 있다.
Firebase 키, AWS IAM 키, DB 접속정보, Google OAuth secret, **JWT 서명 secret**, Apple `.p8`.

두 문서 모두 *"git 이력에 남아 있어 파일 삭제만으로는 부족하고 rotate가 필요하다"* 고
정확히 진단했는데, 진단이 같은 채로 양쪽 다 미해결이다.
특히 **JWT 서명 secret은 임의 사용자 토큰 위조가 가능**하므로 다른 모든 항목과 심각도가 다르다.
§5에서 우선순위를 다시 잡는다.

### 4-5. 컴파일러가 지켜주지 않는 영역에서 반복해서 터졌다

6개 문서 전부에 등장한다.

- MyBatis XML 컬럼명 (`vwc` §6.1, `vwc-media` §6-1, `blur` §6-2)
- yml boolean 오타 — `order_updates: ture` (`vwc-media` §6-4)
- FFmpeg 커맨드 문자열 — 단위 `k` 누락, 옵션 순서 (`blur` §1-2, §11-1)
- 로그 문자열 하드코딩 — `download failed` (`sr` §4)
- 파이프라인 3곳에 흩어진 버퍼 크기 상수 (`event-stream` §1-2)

**대응은 전부 같은 형태다 — 런타임 검증을 빌드/기동 시점으로 당긴다.**

| 영역 | 당기는 방법 |
|---|---|
| MyBatis XML | 매퍼 전체 로드 테스트 (`d426a19` — 이미 검증됨) |
| 설정 오타 | `@ConfigurationProperties` + `@Validated`, 기동 시 **실제 적용값 로깅** |
| 외부 커맨드 | 타입 세이프 빌더(`Bitrate.ofKbps(2000)`) + 샘플 입력에 대한 **골든 산출물 테스트** |
| 흩어진 상수 | 단일 상수를 세 곳이 **참조**하게 하고, 세 값이 같은지 검증하는 테스트 |
| SQL 인젝션 `${}` | CI grep 룰 — `${` 사용을 화이트리스트 밖에서 금지 |

## 6. 다음 프로젝트용 체크리스트

6개 문서에서 **실제로 대가를 치르고 얻은 것만** 추렸다. 일반론은 뺐다.

### 프로젝트 초기 설정 (한 번에 끝나는 것들)

- [ ] `spring.jpa.open-in-view: false` — 두 저장소에서 뒤늦게 발견됐다
- [ ] Hikari `leak-detection-threshold` + 커넥션 풀 메트릭을 **처음부터**
- [ ] 모든 HTTP 클라이언트(RestTemplate/RestClient/WebClient)에 connect·read 타임아웃
- [ ] PK는 `bigint`. int4 시퀀스 상한(21억)은 실제로 도달한다
- [ ] 시퀀스 사용률 알람 (`last_value / max_value`) — 도달 전에 알 수 있는 유일한 방법
- [ ] 크리덴셜은 첫 커밋부터 외부화. 나중에 빼면 **이력에 남아 rotate가 강제된다**
- [ ] 소스 인코딩 UTF-8 통일 (설정 파일·XML 포함)

### 설계 시점 결정

- [ ] **경로/키 조립은 한 곳에.** 문자열 연결이 두 클래스에 있으면 반드시 어긋난다 (4개 문서에서 반복)
- [ ] **단위는 타입으로.** ms/sec, byte/MB, kbps/bps, 회전 각도 — 원시 타입으로 흘리면 변환 지점마다 터진다
- [ ] **외부 도구의 산출은 추정하지 말고 확인 후 할당.** 스프라이트 격자가 두 번 같은 이유로 깨졌다
- [ ] **재시도 루프에는 상한 + 영구 실패 상태 + 재시도 화이트리스트** (§4-2)
- [ ] **검증(precondition)은 부수효과보다 먼저.** 시퀀스·파일 생성·외부 호출은 롤백되지 않는다
- [ ] **동시성 제어는 DB 레벨 원자적 연산으로.** 인메모리 컬렉션 + `synchronized`는 두 저장소에서 모두 실패했다
- [ ] **트랜잭션 경계 안에 네트워크 I/O를 넣지 않는다.** 커밋 후 발행은 `@TransactionalEventListener(AFTER_COMMIT)`
- [ ] **요청-응답 매칭에는 correlationId.** 순서 가정(FIFO)은 매칭 근거가 될 수 없다
- [ ] **외부 서버의 `success:true`를 성공으로 믿지 않는다.** 도메인 결과 필드까지 확인 (`sr` §8-5)

### 코드 작성 시

- [ ] **광범위 `catch`를 만들지 않는다.** `catch (RuntimeException) → 401`, `catch (Exception) → InvalidRequestException` 모두 진단 능력을 없앴다
- [ ] **NPE를 인증 실패와 같은 분기에 묶지 않는다.** 예외→상태코드 매핑은 장애 분석의 출발점이다
- [ ] **`InterruptedException`에서 `RuntimeException` 재던지기 금지.** `Thread.currentThread().interrupt()`
- [ ] **로그 메시지에 단계를 하드코딩하지 않는다.** stage는 MDC로, 구분은 예외 타입으로
- [ ] **null 폴백으로 기본값을 채우지 않는다.** 조용한 데이터 오염보다 명시적 실패가 낫다
- [ ] 래퍼 타입 비교는 `equals` — `Integer status == 3`은 언박싱 NPE
- [ ] MyBatis `${}` 금지 (CI 룰로 강제)
- [ ] 조회 편의로 **가짜 엔티티를 합성하지 않는다.** 필요하면 DTO로, 쓰기는 upsert로

### 성능 문제를 만났을 때 (순서대로)

1. [ ] **호출 횟수부터 본다.** N회 → 1회가 가능한지. 병렬화는 그다음이다 (`blur` §11-5)
2. [ ] **행 단위 후처리를 DB로 내린다.** "전부 로딩 → Java 루프 합산"이 두 저장소에서 문제를 만들었다
3. [ ] **범위 조회에 선두 인덱스 컬럼이 포함됐는지.** `time` 단독 조건은 풀스캔이자 **정확성 버그**였다
4. [ ] 외부 프로세스 실행은 **고정 크기 풀 + 유계 큐**. Virtual Thread로 늘릴 수 있는 자원이 아니다
5. [ ] 큐가 넘치면 **무제한으로 열지 말고 백프레셔**(`CallerRunsPolicy` / 세마포어)
6. [ ] 상한(`limit`)은 **조용한 절단**을 만든다. 페이징이거나, 최소한 상한 도달을 관측 가능하게
7. [ ] 타임아웃을 늘릴 때는 **p99를 알고 늘린다.** 모르면 그건 유예이므로 원인 티켓을 남긴다

### 리팩터링 / 마이그레이션 전

- [ ] **매퍼 XML 로드 테스트를 먼저 넣는다** (`d426a19`). 이 6개 문서에서 가장 효과가 컸던 단일 대응
- [ ] 컬럼/식별자 리네임은 `Grep` 전수 검색 후 일괄. 세 번 나눠 하면 세 번 다 누락된다
- [ ] 스키마 변경 파급은 **컴파일러가 절반만 잡는다.** XML·SQL 문자열·로그 인코딩은 통과한다
- [ ] 왕복이 예상되는 작업(포맷·규격·인코딩)은 **검증 기준을 먼저 고정**한다.
      SPS/PPS extradata는 ffprobe 기준 없이 들어가 하루에 4커밋을 왕복했다

### 외부 시스템 연동

- [ ] 연결 자체가 거부되면 **데몬 설정을 먼저 본다.** ClamAV 3회 전환은 `clamd.conf` 한 줄로 끝날 수 있었다
- [ ] 소켓 프로토콜을 직접 구현하기 전에 검증된 클라이언트 라이브러리를 찾는다
- [ ] 외부 응답 DTO는 **실제 응답을 덤프해서** 검증한다. 매핑 실패는 조용히 null이 된다
- [ ] 바이너리 규격은 문서가 아니라 실측이다. **덤프 → 헥스 로깅 → 오프셋 역산** (`event-stream` §6-1)
- [ ] 네트워크 경계(NLB/ALB/TLS 종단)가 걸린 문제는 **애플리케이션 레벨 우회로 풀리지 않는다.**
      프로토콜에 왕복(ACK)을 추가하는 것이 정답이었다
