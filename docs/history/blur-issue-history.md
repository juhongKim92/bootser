## 1. 미디어 처리 (FFmpeg)

이 프로젝트에서 가장 오래, 가장 많이 손본 영역이다. FFmpeg 커맨드를 문자열로 조립해
`ProcessBuilder`로 실행하는 구조여서, 옵션 하나·단위 하나가 곧바로 산출물 품질 문제로 이어졌다.

### 1-1. 영상 rotation(회전 메타데이터) 처리 — 가장 길게 끌었던 이슈

스마트폰으로 촬영한 영상은 실제 픽셀은 가로인데 `rotate` 메타데이터로 세로 표시되는 경우가 많다.
FFmpeg 파이프라인 단계마다 이 메타데이터가 서로 다르게 취급되어, 같은 문제가 여러 번 다른 얼굴로 재발했다.

| 시점 | 증상 | 해결 |
|---|---|---|
| 2025-09-18 · 2025-09-26 | 추출한 썸네일이 눕거나 뒤집힘 | 원본 rotation 값을 읽어 썸네일에도 동일 회전 적용 (`152c79b`, `18ac960`). 원본 덮어쓰기 대신 tmp 파일 생성 후 move (`9ca5a31`) |
| 2025-09-30 | 추론 결과 object 이미지 방향이 반대 | 회전 방향 역전 (`51000b7`) |
| 2025-10-31 | 렌더링용 CSV의 블러 좌표가 어긋남 | 회전된 프레임 기준 좌표를 **원본 좌표계로 역변환**하는 로직을 `AiFileDetect`에 추가 (`edcf891`). `AI_FILE` 테이블에 `rotation` 컬럼 신설 (`e7cc354`) |
| 2025-12-01 | HLS 변환 시 CUDA를 쓰면 회전 영상이 깨짐 | GPU 필터가 `transpose`를 제대로 처리하지 못하는 문제. **CPU에서 transpose → `hwupload`로 GPU 업로드 → 이후 CUDA 사용** 순서로 파이프라인 재구성 (`8b578fa`) |
| 2025-12-09 | -90도 케이스 미처리 | 회전 각도 분기에 -90도 추가 (`23d38fe`) |
| 2025-12-16 | 렌더링 결과물 회전 미적용 | 여러 차례 시도/롤백 후, **메타데이터가 살아있으면 영상만 재인코딩**하는 방식으로 정리 — FFmpeg이 알아서 회전 반영 (`a37d617` → `67db330` 롤백 → `78e0be6` 재적용 → `e4e789c` 최종) |

> **교훈**: rotation은 "한 곳"에서 처리할 수 없다. 썸네일 / HLS / 렌더링 / 좌표 CSV 네 경로가
> 각자 회전을 다르게 소비하므로, 파이프라인 진입점마다 명시적으로 정규화해야 했다.

### 1-2. 렌더링 화질 문제

- **화질이 심하게 나쁨** → `-b:v` 비트레이트 값에 단위 `k`가 빠져 bps로 해석되고 있었다. 문자열에 `"k"` 부착으로 해결 (`d31ca50`)
- **무손실 인코딩으로 용량 폭증** → 무손실 대신 `cq 18` 적용, 원본 유사 화질 유지 + 용량 축소 (`b5328da`)
- **회전 재인코딩 시 화질 저하** → rotation 처리 경로의 인코딩 품질 옵션 보정 (`a5c0407`)

### 1-3. fps 처리

- **영상 split 시 30.0f로 하드코딩**되어 프로젝트 설정 fps가 무시됨 (`923662f`)
- fps를 `int` → `double`로 변경, 커맨드 포맷도 함께 수정 (`b5e25b7`, `6d7e0cd`, `dc989c6`)
- `-r` 옵션은 타임스탬프만 조정할 뿐이라 **실제 프레임을 버리거나 늘리도록 `-vf`로 전환** (`9b4793f`)
- HLS 생성 시 fps가 60을 초과하면 30으로 고정 (`8fd3e4b`)

### 1-4. 영상 split / 시점 불일치

렌더링 시 시간(time) 기준으로 잘랐으나 FFmpeg이 가장 가까운 I-Frame을 참조해
**프리뷰에서 본 시점과 결과물 시점이 달라지는 버그**가 있었다.
→ I-Frame을 참조하지 않고 정확히 자르도록 split 로직 수정 (`3964b9e`)

### 1-5. frame → time(ms) 단위 전환

초기 설계는 프레임 번호 기준이었으나, fps가 가변이면 프레임 번호가 시점을 특정하지 못한다.
2025-10-22 전후로 전 구간을 **밀리초 단위 시간 기준으로 전환**했다.

- DTO / 응답 명세 `frame` → `time` (`3be5b3e`, `5a88ba3`, `8df12b6`, `1d21a1a`)
- `totalFrame` → `totalTime(ms)` 및 렌더링 로직 수정 (`733e4d3`)
- `AI_FILE.duration` `double` → `integer` (`24ecfe8`, `a82f520`)
- 전환 과정에서 **duration 단위(sec→ms) 변경으로 썸네일 개수가 1000배로 뛰는** 사고 발생 → 즉시 수정 (`4b9d22b`, `a9c7341`)

### 1-6. 기타 FFmpeg 이슈

| 문제 | 해결 |
|---|---|
| 파일명에 공백·특수문자가 있으면 FFmpeg 구동 실패 | 커맨드 인자 처리 방식 수정 (`4d0c600`) |
| 한글 파일명이 정상 처리되지 않음 | 최종 파일 생성 로직을 우회 방식으로 변경 (`bdcd0f6`), 서버 환경에 UTF-8 강제 (`13a35c7`, `873e846`) |
| mp4 변환 시 오류 | **FFmpeg 4 → 7 업그레이드로 근본 해결** (옵션 조정은 임시방편이었음, `9675de1`) |
| 오디오 트랙이 없는 영상에서 HLS/렌더링 실패 | 무음 케이스 예외 처리 분기 추가 (`4b89642`, `d9e5693`, `8fd3e4b`) |
| m3u8 종횡비 깨짐 | 스케일 옵션 수정 (`0fe8ea5`) |
| 다중 텍스트 오버레이 불가 | text add 방식 변경 (`553fed9`) |
| 렌더링 시 audio가 지정 시간에 노출되지 않음 | 오디오 타임라인 계산 수정 (`30e8cba`) |
| 오디오 파일 개수 미스매치로 렌더링 실패 | 유형별 aiFile 추출 로직 수정 (`8672140`, `b8f44ce`) |
| 이미지 반복(loop)이 동작하지 않음 | text·image 유형의 시간 계산 로직 오류 수정 (`d862d26`) |
| `ProcessBuilder` 타임아웃으로 대용량 처리 실패 | 최소 대기 시간 60초 → 120초 (`b40b3ad`) |
| 블러 강도가 약함 | `blurbox` → `gBlur` 필터 교체 + 가중치 40 → 50 조정. CUDA 환경에서 실측 후 재보정 (`876e9e3`, `063e0d4`, `21d9578`) |
| 폰트 파일 참조 실패 | fontforge 대신 **OS(Ubuntu)에 폰트 설치 후 `fontfile` → `font` 지정**, 폰트 패밀리 생성 (`b6cc59a`, `91e16b2`) |

### 1-7. GPU(CUDA) 도입

성능 개선을 위해 단계적으로 CUDA를 적용했으나, 서버가 인식하지 못해 한 번 롤백했다가 재적용했다.

- 초기 도입 (`1e63a3a`) → 서버 인식 실패로 주석 처리 (`736e8f0`) → 복원 (`07be9cf`)
- 썸네일 추출에 GPU 디코더 적용 (`8df24be`, `87b8171`, `78fc950`)
- HLS(m3u8) 생성에 CUDA 적용 (`e98697d`, `3359bb7`)
- CUDA 사용으로 블러 체감 강도가 달라져 가중치 재조정 필요 (위 1-6 참고)

## 2. 썸네일 추출 성능

썸네일 추출은 "동작은 하지만 너무 느린" 대표적 병목이었고, 네 번에 걸쳐 구조가 바뀌었다.

**1단계 — 단일 스레드 순차 처리 (초기)**
영상 길이 N초면 FFmpeg을 N번 호출. 수십 초짜리 영상에도 수십 번 프로세스를 띄웠다.

**2단계 — 병렬화 (2025-10-01)**
Virtual Thread 도입 (`ec3fc55`, `a0e6f6d`).
→ 부작용: 스레드가 과도하게 생성되어 개수 제한 필요 (30개 → 10개, `7c7ee77`, `3dc4b51`),
Virtual Thread → 일반 Thread로 회귀 (`7c05bf7`), 2중 for문으로 step을 두어 실행 (`d57165f`)

**3단계 — 업로드 백로그 초과 (2025-10-01)**
```
CompletableFuture$AsyncSupply rejected from ThreadPoolExecutor
[Running, pool size = 8, active threads = 8, queued tasks = 2000, completed tasks = 0]
```
`ThumbnailUploader`의 큐 상한(2000)을 초과해 태스크가 거부됨 → 큐 무제한으로 변경 (`9ee4061`)

**4단계 — 근본 재설계 (2025-10-24)**
`FFMPEGStreamExtractor` 신설. **FFmpeg을 1회만 호출하고 1초 간격 프레임을 스트림으로 받아 저장**하는 방식으로 전환 (`37a84b2`). 프로세스 생성 비용 자체를 제거했다.

**부수 이슈**

- 정확히 `7.00`초로 끝나는 영상은 마지막 프레임이 존재하지 않아 추출 실패 (`d81197f`)
- 마지막 순번 썸네일 누락 (`b758b99`, `2134845`)
- 썸네일 height가 0으로 저장됨 (`e6c4354`)
- 추출 포맷을 원본 포맷 따라가지 않고 JPG/PNG로 고정 (`8cf5ac5`, `542bbb8`)
- 스케일 조정 반복: 640 → 160 → 320 (`efc4166`, `fbef787`, `f21c1a1`) / 화질 3으로 하향해 속도 확보 (`30c1116`)
- 10초 초과 시 강제 종료 (`346f180`), 추출 후 원본 삭제하지 않도록 수정 (`6cd4529`, `d0c53a0`)

## 3. 추론(Inference) 배치 동시성

**문제**: 추론 배치가 간헐적으로 **같은 파일을 여러 번 실행**했다. GPU 자원을 중복 점유하고
결과 파일이 서로 덮어써지는 심각한 이슈였다. 세 차례에 걸쳐 해결했다.

**시도 #1 — synchronized 블록 위치 오류 (2025-10-02)**

```java
// asis: 검사(contains)가 락 밖에서 수행 → 검사와 추가 사이에 다른 스레드 진입 가능
if (!waitList.contains(dvFile) && !downList.contains(dvFile)) {
    synchronized (waitList) { waitList.add(dvFile); }
}

// tobe: 검사와 추가를 하나의 임계 영역으로 묶음
synchronized (waitList) {
    if (!waitList.contains(dvFile) && !downList.contains(dvFile)) { waitList.add(dvFile); }
}
```
전형적인 **check-then-act 경쟁 조건**이었다 (`8db4f77`).

**시도 #2 — 프로세스 분리 리팩토링 (2025-10-02)**
`InferenceBatchFacade`를 재개발해 **다운로드 처리 프로세스와 작업(work) 프로세스를 분리** (`67e1291`).
대기열 조회 시 `waitList`만 보지 않고 `downList`까지 함께 확인하도록 조건 보강 (`8ddc07c`).
"download 큐에 있는데 wait에 다시 등록되는" 스레드 오류도 함께 수정 (`81d44d0`).

**시도 #3 — 상태값으로 예약 표시 (2025-11-06)**
인메모리 컬렉션만으로는 완전히 막지 못해, `InferenceState`에 **`RESERVE_INFERENCE`** 상태를 추가하고
다운로드 완료 즉시 DB 상태를 갱신하도록 변경 (`dd8ed35`). 중복 픽업을 DB 레벨에서 차단했다.

**관련 개선**

- 추론 진행률(%)을 읽는 로직을 별도 스레드로 분리, 60초 초과 시 강제 종료 (`6362168`)
- 추론/HLS를 독립 태스크로 분리해 상태 관리 (`108b136`, `e315335`)
- 추론 실패 시 상태 업데이트를 `FileNotFoundException` 외 케이스에도 수행 (`41640ae`)
- 추론 실패 시 웹소켓 실패 메시지 누락 수정 (`069daa1`, `d97c7b1`)
- 다운로드 실패 시 상태값 갱신 추가 (`7c5687b`)

## 4. 파일 업로드

### 4-1. 파일명 → UUID 체계 전환

**문제**: 실제 파일명을 S3 키로 사용하면서 한글·특수문자 깨짐, 동일 파일명 충돌이 반복됐다.

**해결** (2025-10-15): S3 업/다운로드 전 구간에서 **UUID + 확장자를 저장 파일명으로 사용**하고,
원본 파일명은 별도 컬럼(`STORE_FILE_NAME`)에 보관 (`778d62a`, `8768a8d`).
렌더링·다운로드 로직도 `storeFileName` 기준으로 정정 (`2505acf`, `fb4a53f`).
구파일 호환을 위해 `storeFileName`이 없을 때의 예외 처리 추가 (`e563dee`).

이후 저장 경로에 `userId`를 추가해 사용자별로 분리 (`d50e0ec`, `8e3712a`, `7836ae2`).

### 4-2. Multipart(Chunk) 업로드

- **Presigned Part URL에 UUID를 키로 잘못 전달** → 실제 S3 키(`s3StorePath`)로 교체 (`f82d697`)
- **5MB 미만 파일**은 S3 멀티파트 최소 파트 크기 제약으로 실패 → 소용량 단일 업로드 경로 분기 (`77b1b71`, `6903f21`)
- **통파일 여부 판정 오류**: `MultipartFile.getSize()`와 실제 파일 length가 다를 수 있어 체크 로직 변경 (`9611866`)
- 업로드 중인 파일이 파일 리스트에 노출됨 → `fileType == NULL`인 항목 제외 (`43a2379`, `77b1b71`)
- 단일 업로드도 `aiFileUpload`에 row를 남기고 complete 시 삭제하는 방식으로 구조 통일 (`4133c51`)
- Content-Type 검증 추가 (`7c02913`)
- Presigned URL 지연 개선을 위해 Global Accelerator 적용 (`30797b0`, `fb0c692`)

### 4-3. 기타

- 업로드 최대 크기 2GB로 확대, 200MB 초과 시 디스크 저장 방식 (`d712e74`)
- `readMimeType` 검사가 오류를 유발해 임시 제외 (`e621809`, `52477c7`)
- CORS 설정 수정 (`0f05bd0`), UTF-8 파일명 다운로드 지원 (`cb022e8`, `88dc459`)
- 업로드 취소 시 삭제 순서 변경 — `aiFileUpload` 선삭제 후 `aiFile` (`82f306d`, `fde62f0`)
- 파일 업로드 정책(용량·개수·확장자) 적용 (`f496743`, `37f72ff`)

**문제**: 잔액 차감·충전·환불이 모두 read-modify-write 패턴이라
동시 요청 시 **lost update**가 발생했다. 잔액 100에 60짜리 요청 2건이 동시에 들어오면
두 요청 모두 "100"을 읽고 각자 40을 저장 → 120을 소비했는데 40이 남는다.

**해결 경과 (2025-11-05, 하루에 집중 처리)**

1. `@Version` 기반 낙관적 락 시도 (`23dfb61`)
2. 번호판 복원 결제 경로의 동시성 이슈 수정 — `PlateResolutionFacade` 재구성 (`16b70fc`)
3. 환불 동시성 수정 (`882b5e5`)
4. 최종적으로 **낙관적 락을 걷어내고 비관적 락 / 원자적 UPDATE 전략으로 통일**
   - 소비·환불: DB 단일 원자적 `UPDATE` + `SELECT … FOR UPDATE`(잔액 검증을 SQL 조건에 포함)
   - 충전: JPA `PESSIMISTIC_WRITE`로 행 잠금 후 수정

**관련 이슈**

- 프로세스 실패 시 포인트 환불 기능 추가 (`ae31b49`) — 번호판 복원 (`305ab97`), 렌더링 (`e236da0`)

## 6. DB / 쿼리 성능·정합성

### 6-1. N+1 문제

`available` API 개선 중 N+1이 발생했고(`2dd58ec`), `byPlate` API에서도 동일 문제가 확인됐다.

**해결** (`85a945c`): 목록을 먼저 조회한 뒤
① 비디오 파일 ID만 추출 → ② 프리뷰를 `findAllByFileIds`로 **한 번에 조회** → ③ Map으로 매핑.

## 8. 바이러스 검사 (ClamAV)

업로드 파일 백신 검사 기능을 붙이는 과정에서 **연동 방식만 세 번 바꿨다.**

1. **TCP 소켓 (INSTREAM)** — clamd가 TCP 리스닝을 하지 않아 실패 (`7543c64`, `c3b782a`)
2. **UNIX 도메인 소켓** — `junixsocket`으로 `/run/clamav/clamd.ctl` 접속. 통신이 계속 불안정 (`725cf65`)
3. → 연동 실패로 검사 자체를 임시 주석 처리 (`eec6b32`)
4. **최종: `clamdscan` 프로세스 실행 방식** (`907fae3`)
   ```java
   ProcessBuilder pb = new ProcessBuilder(
       "clamdscan", "--fdpass", "--no-summary", target.toAbsolutePath().toString());
   ```
   데몬은 그대로 두고 CLI를 `ProcessBuilder`로 호출. 파일 디스크립터 전달(`--fdpass`)을 사용하며,
   `workDir` 접근을 위해 OS 권한 부여가 필요했다 (`sudo usermod -aG datagrp clamav`).
   결과 파싱용 `ClamScanResult` DTO를 함께 도입.

> **교훈**: 소켓 프로토콜 직접 구현은 디버깅 비용이 컸다. 이미 검증된 CLI를 호출하는 쪽이
> 이 프로젝트의 다른 외부 도구 연동(FFmpeg, 추론 앱)과도 일관성이 있었다.

## 11. 회고: 반복된 패턴

이력을 관통하는 실패 유형은 크게 다섯 가지다.

**1. 외부 프로세스(FFmpeg·추론 앱·ClamAV) 연동의 불투명성**
문자열 커맨드는 컴파일 타임 검증이 없어, 오타(`5fa9c5e`, `60b2276`)·단위 누락(`d31ca50`)·
옵션 순서(`8b578fa`)가 런타임에야 드러났다. 로깅 커밋이 유독 많은 것도 이 때문이다.

**2. 단위/좌표계 변환 지점의 누락**
frame↔ms, sec↔ms, 회전 좌표계, bitrate 단위 — 변환 지점이 코드 여러 곳에 흩어져 있어
한 곳을 고치면 다른 곳이 터졌다. 단위를 타입으로 감싸지 않은 대가였다.

**3. 인메모리 큐 기반 동시성 제어의 한계**
`waitList`/`downList` 컬렉션에 `synchronized`를 거는 방식으로는 중복 실행을 끝까지 막지 못해,
결국 **DB 상태값(`RESERVE_INFERENCE`)** 을 도입해야 했다. 크레딧도 동일하게
애플리케이션 레벨 락에서 **DB 레벨 원자적 UPDATE**로 수렴했다.

**4. ID 체계 변경의 파급**
`set` → `project`, `frame` → `time`, 파일명 → UUID 등 핵심 식별자를 여러 번 바꿨고,
그때마다 누락된 매핑이 버그로 나타났다.

**5. 성능 개선은 대체로 "호출 횟수 줄이기"로 귀결**
썸네일(N회 → 1회 호출), N+1 쿼리(N회 → 1회 조회), Bulk Insert 모두 같은 구조의 해결이었다.
병렬화(Virtual Thread)는 스레드 수 제한·큐 상한 같은 2차 문제를 낳아,
호출 자체를 줄이는 편이 더 효과적이었다.
